Major API review — same rules as the resolve-hook notes
========================================================

Rules used (not ADRs):

1. Name the job, not the pipeline.
2. Do not invent a type for a one-field box, a future key, or a second name for the same write.
3. App authors and plugin authors are different callers. Hide the second surface from the first.
4. Core does the merge, the tree walk, the from-value, the zone math. Callers do not.
5. The call site must read as a true English sentence.
6. One word, one meaning. Two knobs for one job is dirt.
7. A deep module: small interface, lots of behaviour behind it.

Shipped vs planned: I mark each. A planned API that fails these rules will hurt more than the hook, because more people will write it.

--------------------------------------------------------------------------------
What already meets the bar
--------------------------------------------------------------------------------

Dataset vs Gantt (shipped)
  new Dataset({ entries, timeZone })
  new Gantt({ container: '#gantt', dataset })
  Two objects, two jobs. Many views of one dataset falls out. Single-Gantt users never meet
  TimeScaleModel. That is the right depth.

Loose dates in, strict dates stored (shipped)
  start: '2026-09-01' on EntryInput. Callers never call instant() or entryId().
  EntryInput / Entry is two types for a real job (write vs store), not ceremony.

entries.add / update / remove (planned S2.3, spec is good)
  dataset.entries.update('t2', { name: 'Framing — north wing' })
  That sentence is true. Better than dataset.update. Keep this. Drop the flow-doc sample
  that called dataset.update.

Auto-wrap + transaction() (planned)
  One edit is one transaction. Fifty edits in transaction(() => { ... }) is one commit.
  Callers do not pass a "batch" flag. Core decides. Same rule as "core merges the patch."

Live assignment (shipped for theme, gridWidth, preset, range, zoom)
  gantt.preset = 'weekAndMonth'
  Reconfiguration is not a remount. Good.

Shared axis by handing over the object (shipped)
  new Gantt({ ..., scale, scroll })
  No link manager. The person who does not share never constructs a model.
  That is two callers, two surfaces, done right.

beforeX / X event pairs (partially shipped)
  gantt.on('beforeEntryMove', ({ entry, start, end }) => false)
  Grep works. Veto is return false. Persistence is dataset.on('change', ...).
  View events on Gantt, data events on Dataset. Split is correct.

formatEndInclusive (shipped)
  Names the job. Callers do not subtract one millisecond.

reveal(entryId) (shipped)
  "Reveal this entry." Core pans. Caller does not compute x/y.

dateOnlyEnd: 'inclusive' (shipped)
  One constructor key instead of every caller doing end+1day. Deep.

Cascading remove (planned)
  remove(parent) removes descendants. Core walks the tree. Do not make the caller do it.

CSS then renderers then events then plugins (planned ladder)
  Stop at the shallowest level. That is the same "don't expose the hook" idea.

Typed errors with codes (shipped)
  catch (e) { if (e.code === 'entry-not-found') }
  Actionable. Keep.

--------------------------------------------------------------------------------
Fails — ranked by how many callers will feel it
--------------------------------------------------------------------------------

1. TimeScaleModel / Intent / Zoom / TimeScale / Viewport  (shipped — worst sibling of the hook)

   The app call is fine: omit scale, set gantt.preset.
   The moment someone shares an axis, they meet:

     TimeScaleIntent, TimeScaleZoom, TimeScaleModel, TimeScale, ScaleBinding,
     ScaleBindingHandle, Viewport (internal, good), bind()

   TimeScaleIntent is the constructor argument with a pipeline name ("stated vs resolved").
   Callers write new TimeScaleModel({ preset, range, zoom }). They do not need the word Intent.
   Stop exporting it, or name it TimeScaleModelOptions.

   ScrollIntent is { position?: Partial<Point> }. Same { patch } smell: a box around one field.
   new ScrollModel({ x, y }) or panTo after construct. Delete ScrollIntent.

   bind() is public on TimeScaleModel. ScrollModel.bind is marked @internal in a comment and
   still public on the class. App authors can bind a model nothing will unbind. Hide bind
   from the published types. View calls it; consumers pass the instance on GanttOptions.

   Verdict: the *behaviour* is deep. The *names around it* are the pipeline. Same disease as
   EditRequest / EditAdjustment.

2. "zoom" means three things  (shipped)

   gantt.zoom = 'fitViewport' | 'preset' | { pxPerMs }   // a mode
   gantt.zoomTo(pxPerMs, anchorX)                         // a density
   gantt.zoomBy(factor, anchorX)                          // a multiplier

   Check 4 fails. One word, three jobs.
   App authors think in "show weeks", not px per millisecond.
   The simple path is already preset = 'weekAndMonth'. Keep that as the name people search.
   zoomBy(1.2) is a real gesture name. Keep it.
   zoom as a mode should not share the word. Density mode is "fit": 'pane' | 'preset' | number.
   zoomTo(pxPerMs) is an expert knob; it can stay if it is clearly the expert path.

3. Two ways to set the same axis  (shipped)

   new Gantt({ preset, range, zoom, scale })
   If scale is passed, the other three are ignored and warn in dev.

   Two knobs, one job. Types should make the illegal combination unrepresentable:

     { dataset, container, preset?, range?, zoom? }           // private scale
     { dataset, container, scale: TimeScaleModel, scroll? }   // shared scale; no preset/range/zoom here

   Then nobody reads a warning to learn the API.

4. snapshot() vs get()  (shipped S2.1)

   dataset.entries.snapshot()   // committed array, stable identity
   dataset.entries.get(id)      // sees in-transaction writes
   get(id: EntryId)             // branded
   update(id: string | EntryId) // loose

   Two read methods for "the entries", and they disagree inside a transaction.
   That is "do the merge in your head" again.

   App author: I want the list, and I want one by id. They should agree.
   Layout needs the committed snapshot — that is an internal caller.

   Simpler public surface:
     dataset.entries.all        // or [...dataset.entries], committed
     dataset.entries.get(id)    // same world as all, outside a transaction
   Inside transaction(), get/has/size seeing writes is a feature for helpers.
   snapshot() as a verb makes people copy. If identity-stability is the point, a getter
   named entries.list or .committed that *is* the cached array is clearer than a method
   that sounds like it allocates.

   And get() must accept string, same as update(). Loose in, strict stored. One rule.

5. Stored Entry.kind is optional  (shipped)

   After ingest, every entry has a kind (default 'span'). The stored type still says kind?:
   Every reader writes entry.kind ?? 'span'. Core already knows the default. Put it on
   the stored type. Input may omit it.

6. TimeUnit 'M' vs 'm'  (shipped)

   Month vs minute. Classic trap. Callers will get it wrong.
   Use 'min' | 'month' (or 'minute' | 'month'). One extra character, one meaning.

7. Preset export pile  (shipped)

   gantt.preset = 'weekAndMonth' is the call site.
   api also exports hourPreset, dayPreset, weekPreset, monthPreset, yearPreset,
   dayAndWeekPreset, weekAndMonthPreset, monthAndYearPreset, presets, resolvePreset,
   PresetRef, ShippedPresetId, ViewPreset.

   Custom-preset authors need ViewPreset and maybe presets.foo.
   They do not need both the named constants and the string ids and resolvePreset.

   Keep: string ids on Gantt, ViewPreset for custom objects, maybe presets record.
   Hide: resolvePreset (core's job), duplicate named exports if the record exists.

8. Field declaration vs grid column  (planned — good split, heavy write)

   The sentence is right: a field is what a value is; a column is where this Gantt shows it.
   gridColumns: ['name', 'start', 'cost'] is the call site you want.

   The declaration is not:

     { key: 'cost', type: 'money', source: { from: 'meta', key: 'cost' } }

   key twice. source is a pipeline (where it is stored). For the common case the job is
   "this meta key is a field."

   Shorthand I would ship:

     fields: ['cost']                                  // meta, same key, no rollup
     fields: [{ key: 'cost', type: 'money', rollUp: 'sum' }]
     fields: [{ key: 'duration', compute: e => ... }]  // no stored home

   Keep the long source form as the expert escape. Default source is meta when the key
   is not a core field. Core fields need no declaration.

   fieldTypes + aggregators by name: keep. That is serialization, not ceremony.

9. interactions vs features  (planned — two slots for "can I make a link")

   interactions: { linkCreate: true }
   features:     { links: { allowCreate: true } }

   Same job, two trees. Pick one.
   Gestures (move, resize, select, edit, link) are one config.
   Chrome (tooltips, contextMenu) is another, if you must split.
   Do not put link creation in both.

10. Three shapes for "writes to fields"  (planned)

    EntryEdit          { start?, name?, cost? }     // what update() takes
    FieldUpdated       { id, field, from, to }      // what a ChangeSet records
    FieldPatch         { id, field, from, to }      // what the hook returns

    Persistence callers need from/to. That is a real second shape.
    Plugin callers should return EntryEdit maps, as in the hook notes.
    FieldPatch should not exist. ChangeSet.updated is enough for history.

11. ChangeSet.origin  (planned)

    'user' | 'undo' | 'redo' | later 'engine' | 'load'
    Persistence may need it. App authors saving on 'change' mostly do not.
    Fine as a field on the event payload. Do not make them switch on it to know
    whether to save — if undo emitted a change, say so in the docs: save it or don't,
    one rule.

12. dataset.apply(changeSet)  (planned, already hedged as "inverse-ish")

    If it is not actually the inverse of on('change'), do not ship it until it is.
    Callers will treat it as sync. A method that "validates and reports rejections
    rather than throwing" is a second error style next to typed throws on update().
    Pick throw vs result object. One policy.

13. overscan on Gantt  (shipped)

    Virtualization padding. Default exists. App authors do not think in
    { verticalRows, horizontalPx }. Hide until someone asks. Same as not putting
    editResolver on Dataset.

14. Plugin / hook / Dataset.dependencies  (planned)

    plans/02 puts dependencies: [] on Dataset. That is the simple call site.
    A plugin-only dependencies API is "correct" internally and worse for callers.
    If the library is a Gantt of dated entries that can link, dataset.dependencies.add
    is the sentence people will say.
    Do not make them install a plugin to pass two ids and 'FS'.
    The engine can still be optional; the data can still live in a store.
    The *call site* should look like entries.

15. barRenderer element descriptions  (planned)

    Returning { tag, class, text } instead of a DOM node is a real constraint, but
    the call site is one function and a kind map. Depth is good.
    Do not add a second renderer style (vnode vs DOM vs HTML string) later.

16. Duration { value, unit }  (shipped type)

    Needed for lag and widthForDuration. Fine.
    Public widthForDuration on TimeScale is a plugin/draw call. Not on Gantt. Good
    if TimeScale stays off the main export that harness uses. api re-exports
    TimeScaleModel.scale which returns TimeScale — expert path, acceptable.

--------------------------------------------------------------------------------
Smaller nits that will compound
--------------------------------------------------------------------------------

- dataset.transaction vs dataset.transact. Spec says transaction. The flow doc said
  transact. Pick the verb that reads: dataset.transact(() => ...) is better English.
  transaction() sounds like it returns a Transaction object.

- Gantt is a pass-through to GanttShell. Fine. Do not put GanttShell in api/.

- Point as ScrollPosition: a type alias is ok for search. Do not also export a third
  name for {x,y}.

- meta generic on Dataset: new Dataset<{ team: string }> is the right depth if it
  actually flows to events and renderers. If it only types constructor input, it is
  a lie. Ship it when it flows, not as a decorative parameter.

- hierarchy.autoGroup on Dataset: data behaviour on the data object. Good.
  derivedSpanKinds: ['group'] is the expert opt-out. Default ['group'] is correct.
  Do not put autoGroup on Gantt.

--------------------------------------------------------------------------------
If I were cutting this for callers only
--------------------------------------------------------------------------------

App author writes:

  const dataset = new Dataset({
    timeZone: 'America/Chicago',
    entries: [ { id: 't1', name: 'Groundwork', start: '2026-09-01', end: '2026-09-11' } ],
    dependencies: [ { id: 'd1', from: 't1', to: 't2', type: 'FS' } ],  // if links exist
    fields: [{ key: 'cost', type: 'money' }],
  })

  const gantt = new Gantt({
    container: '#gantt',
    dataset,
    preset: 'weekAndMonth',
    columns: ['name', 'start', 'cost'],   // or gridColumns — one name
  })

  dataset.entries.update('t1', { start: '2026-09-03', cost: 12000 })
  gantt.on('beforeEntryMove', ({ entry, start }) => start >= mobilization)
  dataset.on('change', ({ changeSet }) => save(changeSet))
  dataset.undo()

Expert / multi-Gantt adds:

  const scale = new TimeScaleModel({ preset: 'weekAndMonth' })
  const scroll = new ScrollModel()
  new Gantt({ container: '#a', dataset: deliveries, scale, scroll })
  new Gantt({ container: '#b', dataset: workforce,  scale, scroll })

Never in the app surface:

  EditRequest, EditAdjustment, FieldPatch, identityResolver, editResolver
  TimeScaleIntent, ScrollIntent, ScaleBinding, bind()
  resolvePreset, snapshot() as a required verb
  interactions.linkCreate AND features.links.allowCreate
  overscan, pxPerMs (except zoomTo as expert)
  Field source { from, key } on the happy path

--------------------------------------------------------------------------------
Bottom line
--------------------------------------------------------------------------------

The resolve hook is not a one-off mess. It is the same pattern as TimeScaleIntent /
ScrollIntent / FieldPatch: pipeline types leaking into the published vocabulary.

The parts that already follow the rule are the ones you use in the harness:
new Dataset, new Gantt, preset assignment, loose dates.

Protect those. When S2/S3/S5 land, make the new call sites look like entries.update,
not like EditAdjustment.

Highest-leverage cleanups if you only do a few:
  1. Discriminated GanttOptions so scale and preset cannot both appear.
  2. Hide bind / Intent types; keep TimeScaleModel as { preset, range, zoom }.
  3. entries.get accepts string; rename or demote snapshot().
  4. One write shape for plugins (EntryEdit map); ChangeSet keeps from/to.
  5. Field shorthand; one place for "can create a link."
  6. TimeUnit 'min' / 'month'.
  7. Stored Entry.kind required.
