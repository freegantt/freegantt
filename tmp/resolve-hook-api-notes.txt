The mutation call site is already clean. The dirt is the hook: three named types, a one-field wrapper, and a patch format that leaks how commit works.

dataset.update(...) inside transact is the API that most people will write. That part is fine. Do not put editResolver on new Dataset({...}) in a sample. That teaches the wrong caller.

================================================================================
What makes it feel dirty
================================================================================

You named the pipeline, not the job.

A caller who writes a cascade must learn EditRequest, EditResolver, EditAdjustment, FieldPatch, identityResolver, and patch. The job is: given this user edit, write extra fields. That is one function.

EditAdjustment is a box around an array. { patch } exists so you can add keys later. Until those keys exist, it is noise. return { patch } is not simpler than return patch.

The hook does not return the edit. It returns leftovers. The transaction then merges user edits + leftovers + rollup. The resolver author must keep three rules in their head:

1. Do not repeat the user’s fields.
2. Fill from yourself.
3. Apply proposed onto entries in your own head, because entries is still the old world.

The sample already has that bug-shaped smell: it reads dependent.start from the old snapshot and takes to from edit.start. That works for this toy. It fails the first time a cascade needs “the world after the user edit.”

FieldPatch is FieldUpdated with a different name. identityResolver is () => [] promoted to a glossary term. App code should never see it.

editResolver on construction is a raw function slot. App authors do not think that way. They think “turn scheduling on,” not “occupy the hook.”

================================================================================
How I would make it for callers
================================================================================

Two callers. Two surfaces. Hide the rest.

1. App author (almost everyone)

They never see a hook.

    dataset.transact(() => {
      dataset.update('pour-foundation', { start })
    })

If they want a cascade, they install a plugin, not a function:

    new Dataset({ entries, timeZone, plugins: [cascadeStartDate] })

Or, if you have no plugin system yet, do not expose the slot. Keep it internal. Tests inject it. The harness does not.

2. Plugin author (the real user of this seam)

One function. Same edit shape as update(). Core fills from, merges, rolls up, and builds the changeset.

    type EntryEdits = ReadonlyMap<EntryId, EntryEdit>

    type ResolveEdit = (args: {
      entries: ReadonlyMap<EntryId, Entry>  // already includes the user's proposed writes
      proposed: EntryEdits                  // what this transaction asked for — the worklist seed
    }) => EntryEdits                        // extra writes only; empty map = do nothing

Call site:

    const cascadeStartDate: ResolveEdit = ({ entries, proposed }) => {
      const extra: Map<EntryId, EntryEdit> = new Map()

      for (const [id, edit] of proposed) {
        if (edit.start === undefined) continue
        const dependent = findDependent(entries, id)
        if (dependent === undefined) continue
        extra.set(dependent.id, { start: edit.start })
      }

      return extra
    }

What this removes:

    Now                                              After
    -----------------------------------------------  -----------------------------------------------
    EditRequest + EditAdjustment + FieldPatch        EntryEdit / EntryEdits (you already have this)
    return { patch: [{ id, field, from, to }] }      return extra — same shape as update
    author computes from                             core reads it from the store
    author merges proposed onto entries              core passes entries as the post-edit view
    named identityResolver                           default is “no function”; internally () => new Map()

Give them entries after the user write. Give them proposed as the delta. Do not make them do that merge.

Do not let them overwrite a field the user wrote in this transaction. Enforce that in core. If they return a colliding key, drop it or throw in dev. Do not make “I4” part of the plugin author’s type.

================================================================================
What I would not do
================================================================================

I would not make the hook return the full committed map (return proposed plus extras). Then every plugin must copy the user’s edits through or the user’s write vanishes. That is a worse footgun than “return extras.”

I would not put rollup in this function. Rollup is yours. Always run it after. The plugin author should not know it exists.

I would not call this “resolve.” That word says “here is the answer.” The function only adds writes. A name like afterEdit or extendEdit matches the call:

    extendEdit({ entries, proposed })

That sentence is true. resolve(request) is not — nothing is resolved; you appended a patch.

If a later plugin must change the user’s value (snap to a calendar, clamp), that is a different seam: normalize before commit, not “add extras after.” One function that both rewrites and appends is how this gets messy again.

================================================================================
Bottom line
================================================================================

Keep update / transact as they are.

Delete the Request / Adjustment / Patch / identity vocabulary from anything a caller reads.

The seam is: after the user edit, return more update-shaped writes. Core does the rest.
