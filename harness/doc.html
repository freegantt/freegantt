FreeGantt — Code Flow Walkthrough

How harness/main.ts reaches the DOM: every module in the path, what it owns, and how it connects to its neighbors.

This is a walkthrough, not a review. It exists to build a shared mental model of the current call graph, drawn straight from the code on review-2026-08-25-deepenings as of 2026-08-25. A few things looked odd while tracing the flow — those are called out inline as smell boxes and indexed at the end. None of them are fixed here.

2Boot sequence: what new Gantt(...) actually does

Reading harness/main.ts top to bottom, then following each call one layer deeper. 

import { Gantt, Dataset } from '../src/api/index.js';
import { sampleEntries } from '../fixtures/sample-project.js';

const dataset = new Dataset({ entries: sampleEntries, timeZone: 'UTC' });
new Gantt({ host: '#gantt', dataset });
  1. new Dataset(...) — api/dataset.ts wraps entries + IANA timeZone in a read-only class. It satisfies model/'s structural Dataset contract; no computation happens here.
  2. new Gantt(...) — api/gantt.ts resolves nothing itself. It constructs exactly one GanttShell and forwards host/dataset/optional scale/scroll. This is the entire public surface: one class, one constructor, one destroy().
  3. GanttShell constructor — view/gantt-shell.ts — runs, in this order:
    1. resolves host (element or selector) — throws if a selector matches nothing
    2. builds a Viewport (layout/viewport/viewport.ts), the fan-in over TimeScaleModel + ScrollModel
    3. creates the DOM render backend and mounts it before binding — so the backend's render target exists before the viewport's first onChange fires
    4. attaches native scroll (attachScroll) to the host, which is the single native scroller
    5. viewport.bind(dataset, onChange) — binds TimeScaleModel and ScrollModel together; each fires its own binding callback synchronously, but a local ready flag swallows those premature calls
    6. takes one synchronous pane-size measurement (a real ResizeObserver's first callback is queued, so the first paint can't wait for it), then hands off to attachPaneSize for every measurement after
    7. flips ready = true and calls render() once, deliberately, now that scale, scroll, and pane size are all wired
  4. render() — see §3.

3One render pass

GanttShell.render() is the one place all the pure modules meet the DOM-touching ones.

GanttShell.render()

→

computeFrame()
layout/frame.ts — pure geometry
→
backend.sync(frame)
render/dom/index.ts

Inputs to computeFrame: dataset.entries, the viewport's resolved TimeScale, its preset, the locally-clamped visible rect, overscan, and the current row height. It returns a GeometryFrame — rows, bars, header ticks, links, decorations, content extents — and holds no state of its own; FrameLayout is the one place that remembers the row-height index between passes, so no caller upstream has to.

After backend.sync(), the shell pushes the frame's contentWidth/contentHeight back into the Viewport (so ScrollModel knows its extents) and calls scrollAttachment.writePosition() — deliberately last, because the content layer must already be the new size before a scroll-position write means anything.

4The two reactive loops

Nothing polls. Two browser-driven signals feed back into the same Viewport, which coalesces both into one render() call per tick.

Both TimeScaleModel and ScrollModel already dedupe within themselves — a setter only notifies if the resolved value actually changed (a documented contract, D-S1.5-4). Viewport layers a second dedupe on top so a single setPaneSize call, which touches both models, still reaches the shell as one reaction, not two.

smell

GanttShell's constructor uses a closure-scoped ready boolean to discard the premature onChange calls that Viewport.bind() fires synchronously before the shell has finished wiring pane size. It's commented and intentional, but it means the "first render" invariant lives as a side-effect of construction order rather than something the type system or the binding contract enforces — a future refactor that reorders those constructor steps would fail silently (extra empty renders, not a crash). Worth a named guard or an explicit two-phase construction if this class gets touched again.

5Module by module

Same order as the layer map in §1, top to bottom. Interface = what a caller has to know to use it correctly, not just its method list.

api/ public

src/api/gantt.ts · src/api/dataset.ts

The entire consumer-facing surface. Gantt is a thin, deliberately shallow adapter: its whole job is constructing one GanttShell and forwarding options. Dataset is a read-only wrapper satisfying model/'s structural contract.

Interface

new Gantt({ host, dataset, scale?, scroll? }), .destroy(). That's the whole thing — no partial-mutation methods yet because data/ (§6) isn't wired in.

view/ DOM

src/view/gantt-shell.ts · scroll-attachment.ts · pane-size-attachment.ts

Owns the one GanttShell per Gantt instance: host resolution, mount ordering, the render loop, and the two DOM attachments. This is the deepest module in the current codebase — GanttShell's constructor alone encodes the mount-before-bind ordering, the synchronous-first-measurement workaround, and the render-after-sync-before-scroll-write ordering, none of which a caller of Gantt ever has to think about.

scroll-attachment.ts is the only file allowed to touch element scroll (I12, lint-enforced) — a real, narrow seam with exactly one adapter today.

Interface

new GanttShell(options), .render(), .destroy().

render/ DOM

src/render/backend.ts · render/dom/index.ts · render/null/index.ts

RenderBackend<THost> is the seam (backend.ts): mount, sync(frame), applyState, hitTest, destroy, rowLabelWidth. Two adapters exist — createDomBackend() (keyed reconciler, absolutely-positioned rows/bars/header) and createNullBackend() (headless, records the last frame for tests/SSR/export). Reconciler scope is hard-bounded to attr/class/style/text + keyed children by design (plans/01 §8).

Interface

RenderBackend<THost> — five methods, one property.

smell

GanttShell hardcodes createDomBackend() (gantt-shell.ts:6,80) with no injection point. Two adapters exist for RenderBackend — a real seam by the "two adapters" test — but only one is reachable from the public constructor path; createNullBackend() is presumably exercised directly by tests, not through Gantt/GanttShell. That may be fine for S1 scope (the null backend's own comment calls it "future export seam"), but it means the seam's flexibility isn't actually wired up yet — worth flagging before an SSR or export feature tries to use it and discovers there's no constructor option for it.

layout/ pure

src/layout/viewport/* · frame-layout.ts · frame.ts · row-height-index.ts

Two deep modules live here. Viewport fans TimeScaleModel and ScrollModel into one bind/one handle/one reaction — explicitly built so view/ never holds more than one live subscription, after an earlier version (S1.5) held both models separately and paid for it with two reactions. FrameLayout exists purely to keep a PrefixSumHeightIndex alive across renders so "top of row i" stays O(log n) across passes instead of being rebuilt each time; computeFrame() itself (frame.ts) is pure and stateless — same inputs, same GeometryFrame, every time.

TimeScaleModel and ScrollModel are the two shareable, bindable objects (D9) — passing the same instance to two Gantts syncs their x-axis or scroll position by construction, no event plumbing.

Interface

Viewport.bind(dataset, onChange) → handle with setPaneSize/setContentSize/unbind; .timeScale, .visible, .overscan getters; FrameLayout.computeFrame(input).

time/ pure

src/time/instant.ts · zone.ts · scale.ts

The only place in src/ allowed to construct new Date()/use time constants/do arithmetic on an Instant (I10, lint-enforced outside this directory). Provides TimeScale (time↔pixel conversion) and view presets (day/week/etc. header bands) that layout/ consumes but never computes itself.

Interface

createTimeScale(), Instant/TimeSpan helpers, TimeScale.xForInstant()/.ticks(), view presets.

model/ pure

src/model/entry.ts · dataset.ts · ids.ts · geometry.ts · errors.ts

Types only, by rule: zero runtime beyond id/brand helpers and FreeGanttError. Every other layer imports from here but nothing here imports anything. model/Dataset is the structural contract; api/Dataset (above) is the concrete class that satisfies it — the same concept at two altitudes, not a duplicate.

Interface

Entry, EntryKind, EntryId/RowId/ItemId + their brand constructors, Point/Size/Rect, FreeGanttError.

data/, scheduling/, interaction/, extensions/ not yet wired

src/data/index.ts · scheduling/index.ts · interaction/index.ts · extensions/index.ts — each currently export {};

Reserved seams, not missing pieces: data/ is where every mutation will route through a transaction → resolve hook → changeset (S2); scheduling/ is the first-party propagation engine that will occupy that resolve hook when installed (S3); interaction/ is gesture controllers (S4); extensions/ is the plugin host (S6). None of the current boot/render/scroll flow touches them because nothing upstream calls into them yet — this walkthrough only traces what actually runs today.
