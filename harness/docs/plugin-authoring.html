Writing a plugin

How a plugin author writes one plugin, installs it once, and fills the public seams. The worked example is a milestone variant: a diamond core does not ship. It takes four lines and no id list.

Four things change from the page it replaces. One plugin has a data half and a view half, and installs once. An Entry answers questions about itself, so a rule reads entry.hasChildren. A variant is one object, matched by a rule, and nothing stores one. A plugin may say what the tree is. Plugin lifecycle is the install machinery, not this page.

1One plugin, one install site

A feature is usually one thought — this value is true, and the row draws as a milestone. It was two plugins, two contracts and two install sites. It is now one plugin with two halves.

derived from ADR 0019, ADR 0017, plans/01 §10

import { definePlugin } from 'freegantt';

export const phases = definePlugin({
  id: 'demo.phases',
  requires: ['demo.calendar'],

  // What is the data? Runs once, as the Dataset constructs. Never touches the DOM.
  data(ctx) {
    ctx.fields.register({ key: 'demo:phaseId' });
  },

  // What does it variant like? Runs once per bound Gantt, with that Gantt's own context.
  view(ctx) {
    ctx.addVariant({ name: 'phase', when: { 'demo:phaseId': true }, paint: phaseBar });
  },
});
question data(ctx) view(ctx)
runs once, while the Dataset constructs once per bound Gantt, each with its own ctx
may touch the DOM no — it is core-layer code yes
what it fills Fields, field types, aggregators, the hierarchy, the edit extender, its own store variants, renderers, decorations, columns, commands, keybindings
can you add it later? no — a Field must exist before the first Rollup, so a different plugin set is a new Dataset yes, when the plugin has no data half — chrome installs live on the Gantt
order requires — [a, b] and [b, a] install the same way the order the data halves resolved to

Where it installs is where its state lives. A plugin with a data half installs on the Dataset, because a Field and a store belong to the data, not to one view of it. Every Gantt bound to that Dataset then runs its view half once. Two Gantts on one Dataset get two contexts and two sets of registrations, which is what keeps them independent (I2). A plugin with no data half still installs on the Gantt.

requires now covers the whole plugin, not half of it. That is the pair the old split could not even state.

2The Entry answers questions about itself

Every seam that receives an Entry receives one that answers. You write entry.hasChildren, not dataset.entries.childrenOf(entry.id).length > 0.

derived from ADR 0017

interface Entry<TProps> {
  readonly id: EntryId;
  readonly name: string;
  readonly start?: Instant;
  readonly end?: Instant;
  readonly segments: readonly Segment[];

  read<K extends FieldKey>(field: K): FieldValue<TProps, K> | undefined;
  duration(): Duration | undefined;  // computes through time/, so it costs

  readonly hasChildren: boolean;     // a cached index read, so it is free
  readonly depth: number;
  children(): readonly Entry<TProps>[];
  parent(): Entry<TProps> | undefined;
  descendants(): readonly Entry<TProps>[];

  toInput(): EntryInput<TProps>;
}

A member that does no work is a property. A member that computes, walks or allocates carries parentheses. That is the whole rule, and it is about cost, never about how many values come back: hasChildren is one index lookup on the hover path, descendants() is a walk, and parent() answers one value and still costs. The shape tells you which you are paying for.

It reads. It never writes. There is no entry.update(). Writes go through dataset.entries.update(), the one write door, so every change is still one transaction and one ChangeSet.

Two types, one row

A seam that asks a question about now receives an Entry. A seam that describes a change carries the stored values, and those never move on their own.

seam gets why
when, items, paint, can Entry a variant rule asks about the row as it is right now
command when Entry it asks a live question and it writes nothing
Aggregator, FieldDistributor, compute Field StoredEntry the Rollup hands each one a child it has already given this pass's value to. That row is not in the store, so a live one would read the value the pass just replaced. Ask the tree through ctx.children() — the pass's children, not the store's.
EditRequest.entries StoredEntry the pre-transaction state, on purpose — a cascade reads it to compute a delta (D-S5-45)
entryAfterEdits(id) StoredEntry the post-body state — a different answer from the line above, which one live object could not hold
ChangeSet { from, to } StoredEntry a recorded change must not move after it is recorded
The two names — ruled 2026-09-11. Entry names the live one, and StoredEntry names the values. The bare word goes to the live one because that is the surface most people read.

4Write a variant

A variant is one object, and it answers from a rule. Nothing stores a variant. Core ships no diamond, so a milestone is the smallest real example — and it needs no plugin at all.

derived from ADR 0018, ADR 0017

An app author, with no plugin

const dataset = new Dataset({ fields: [{ key: 'milestone' }] });

const gantt = new Gantt({
  container: '#gantt',
  dataset,
  variants: [
    {
      name: 'milestone',
      when: { milestone: true },
      paint: () => ({ class: { 'demo-milestone': true } }),
      can: { resize: false },
    },
  ],
});

dataset.entries.update('launch', { milestone: true });

That is the whole feature. The row wears the variant because of a value the app owns, in the app's own word. The write is an ordinary Field write, so it is in a ChangeSet, it undoes, the write door gates it, and gridColumns: ['milestone'] shows it. No id set, and no list that freezes at install.

Core never learns what a milestone is. A shift roster writes { handover: true } and a factory writes { changeover: true }, and core reads none of those words.

A plugin that does not know the ids

export const milestones = definePlugin({
  id: 'demo.milestones',
  view(ctx) {
    // Which entries wear it? A rule, not a list — a row added tomorrow gets it too.
    ctx.addVariant({
      name: 'milestone',
      when: (entry) => !entry.hasChildren && entry.duration()?.value === 0,
      paint: () => ({ class: { 'demo-milestone': true } }),
      can: { resize: false },
    });
  },
});

when takes the §2 Entry, which is the only reason that predicate compiles. It also takes the shorthand the app author used above — a Field match core can index, which never runs a function per row.

The one object

interface EntryVariant {
  name: string;          // this variant's identity: the `data-variant` you style, and the registry key
  when?: VariantRule;       // a predicate or a field match; omit it on a last-resort variant
  items?: ItemProducer;  // default: one Item over the Entry's whole span
  paint?: BarRenderer;
  can?: Interactions;    // per variant, one level under the consumer's own
}

Every key is optional except the name. items defaults to the line both old examples hand-wrote, so a variant that draws an ordinary bar in a new colour is a name and a paint. There is no half to forget: a claim with no producer is not a shape you can write any more.

The name is an identity, not a value you store. It is the data-variant on the painted element, so a stylesheet can select on it, and it is the key the registry and the double-claim report use.

How an Entry gets its variant

Core's two variants are ordinary variants. They are registered last, and they carry no privilege. 'parent' and 'leaf' are not reserved words, because nothing can store a variant name in the first place. Delete the stored value and the whole reservation goes with it.

A variant never decides what a row derives. Children do, and only children. A parent that wears your 'milestone' variant still rolls up like a parent. That is ADR 0013, and this design does not spend it.

You have two honest ways to make a childless row paint as a summary. Register a variant that paints that way — it changes the paint and claims nothing about the data. Or give the row children with the hierarchy source in §6, in which case it really is a parent and it rolls up like one.

Two variants can both answer yes. The first registered wins, and the library raises a 'variant-claimed-twice' report naming both plugins. Core does not pick a winner on merit — it picks the one you installed first, and it tells you.

5Gantt seams

What the view half can fill. The variant is one row of this table now, not four.

derived from ADR 0018, view/plugin-ports.ts, plans/02 §4.4

seam call two registrations on the same key
variant ctx.addVariant(variant) first rule to answer wins and the second is reported; a stored value beats every rule
decoration ctx.view.registerDecoration(layer, provider) additive — every provider paints, in registration order
grid column ctx.view.registerGridColumn(column) additive; a duplicate field the consumer already named is dropped — config beats a plugin
command ctx.commands.register(command) newest wins on command.id; dispose restores the one before
keybinding ctx.interaction.registerKeybinding(binding) newest-first on binding.chord; falls back on dispose

Four calls retire. registerLookClaim, registerItemProducer, registerLookDefaults and the barRenderer: RendererByLook option are all keys on the one EntryVariant object now. KindDefaults retires with them: it was boolean-only because a registering plugin never saw an Entry, and §2 hands it one, so can takes the same predicates interactions takes.

The view half declares no Field. It shows one with registerGridColumn; the data half declares it. A consumer's own barRenderer or cellRenderer always beats a plugin's paint: if the page wants the plugin's, it omits its own.

6Dataset seams

What the data half can fill: Fields, a store, extra writes on an edit, and the tree itself. It stays DOM-free.

derived from ADR 0020, ADR 0011, ADR 0015, ADR 0016, api/dataset-plugin.ts

A Field the plugin owns

Plugin Field values share props with the consumer, so a plugin key should name its plugin. Core does not enforce that — ctx.fields.register takes the key you give it. The convention is a prefix, exported as a const, and the app names that const. 

export const DEMO_NOTE = 'demo:note';

export const noteField = definePlugin({
  id: 'demo.note',
  data(ctx) {
    ctx.fields.register({ key: DEMO_NOTE });
  },
});
const dataset = new Dataset({ entries, plugins: [noteField] });
dataset.entries.update('t1', { [DEMO_NOTE]: 'cutover' });

dataset.entries.get('t1')?.read(DEMO_NOTE);   // through the Entry
gantt.gridColumns = ['name', DEMO_NOTE];

One question, one call site. A Field read is entry.read(key), and that is the same call an app author writes and a plugin writes. entries.fieldValue(id, key) and ctx.read(entry, key) both retire — they were the same question with two doors. entry.props.k is storage, not a resolver: it misses a compute Field and it does not know the Field's type. Duration is a core Field, so it has both doors: entry.duration() is the typed one, and entry.read('duration') answers the same value by key. It carries parentheses because it computes.

A store that is not a Field

Dependencies, lock flags, baselines and caches are not per-Entry Fields. They live in a PluginStore the plugin reserves. Another plugin may read that store, and may not write it. 

data(ctx) {
  const store = ctx.store.reserve<{ locked: true }>();
  store.set('t2', { locked: true });
  const other = ctx.store.read<{ locked: true }>('demo.lockEntries');
}

The consumer reads the same rows with dataset.pluginStore('demo.lockEntries'). A plugin that owns data a consumer must keep publishes its own reader. It does not get a hook into a library save format — there is none.

Extra writes on an edit

The extender composes: you receive the current occupant and return the one that replaces it. Call next when you want its writes, and skip it when you do not. The runtime owns merging and branding. Non-overlapping keys on one Entry combine. The same Field on the same Entry is a collision: neither value applies, and one warning names both plugins and the Field. Do not throw. Do not call mergeEntryEdits. 

data(ctx) {
  // What else does this edit write?
  ctx.edits.setExtender((next) => (request) => {
    const moved = request.proposed.get('t1');
    if (moved === undefined) return next(request);
    return new Map([['t2', { start: moved.start }]]);
  });
}

Returned extras are the same object entries.update() takes — flat Field keys, no props: wrapper. They are not a ProposedEdit. Spreading request.proposed into a returned edit is a type error.

request.entries is the pre-transaction state and request.entryAfterEdits(id) is the post-body state. They are deliberately different answers, which is why both carry StoredEntry and not the live Entry of §2.

The hierarchy — expert

An app can have a tree core cannot see: a WBS in another system, a parent named by a props key, a level it wants skipped. A data half may say what the parent of an Entry is. It composes the same way the extender does. 

data(ctx) {
  // Which Entry is the parent of this one?
  ctx.setHierarchySource((next) => (entry) => entry.props.phaseId ?? next(entry));
}

One Entry in, one parent id out. Core's own source is (entry) => entry.parentId, with no special claim on the seam. An Entry a source gives children to is a parent: it derives, it rolls up, and core's own parent variant in §4 paints it as a summary.

You change the tree, and the Rollup follows. There is no second knob. Which values a parent takes from its children is the Aggregator, and how one spreads back down is the FieldDistributor — both already pluggable, both by registered name. The only part with no seam was which Entries roll into which, and that is the tree. One seam means the two can never disagree.

The source takes a StoredEntry, never the live Entry. The live one answers children(), parent() and depth — every one of those answers is built from this source, so a source that received one would ask the question it exists to answer.

Core keeps four things. It inverts the answer, so nothing can produce two parents for one Entry. It refuses a cycle with ParentCycleError and reads that Entry as a root. It treats an unknown parent id as a root and reports it once per revision. And parentId is still stored and update() still writes it — a source that ignores the field is a plugin taking the tree over on purpose.

Grouping does not come here. { source: 'group', groupBy } is a row source, and it stays one: a group header holds no values and rolls nothing up. A hierarchy source answers with an EntryId, so it can only ever name an Entry that exists. It cannot invent a row.

requires

A plugin may name plugin ids that must install first. Order follows requires, not array position. A missing id throws MissingPluginError. A cycle throws PluginRequirementCycleError. It now covers the whole plugin, both halves.

7Gate, dispose, install

Every register* is legal only while that half is on the stack. After data(ctx) or view(ctx) returns, the same call throws RegistrationClosedError.

derived from extensions/plugin-runtime.ts, view/plugin-ports.ts, plans/02 §4.4

ctx.disposables already retracts every gated registration. A plugin that owns no timer, socket or outside subscription returns nothing. The milestone plugin in §4 is that case. A returned Disposer runs after the registrations have already come off. The two halves dispose independently: unbinding one Gantt retracts that Gantt's view registrations and leaves the data half running for every other Gantt on that Dataset.

Two calls stay open after the gate closes, on purpose. ctx.interaction.registerKeyHandler is how a popup binds Escape for as long as it is open, not once at install. ctx.view.onDomEvent is the same lifetime. Reads such as ctx.interaction.canWrite are not registrations and stay available.

The install diff, the rollback on a throw, and the requires walk are on Plugin lifecycle. This page stops at the call a plugin author writes.
