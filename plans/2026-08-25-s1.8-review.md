Three parallel analyses of the `s1.8-pane-layout` branch (`176966e...origin/s1.8-pane-layout`, 50 files, ~2000 lines).

## 1. Code Review — Standards

**Hard violations: None found.** Layer boundaries, transaction→resolve→changeset flow, TS strictness, time/ isolation, no module-level singletons, and invariant-scoped lint rules all hold.

### Judgement calls

**Mysterious Name — `toInstant` (time/input.ts:93)**
The exported `toInstant(zone, input)` validates, coerces, resolves Plain strings through a zone, and handles date-only edge cases — it is a multi-responsibility parser, not a type cast. The old private `toInstant` in zone.ts was renamed to `fromZoned` to disambiguate, confirming the name is overloaded. A name like `parseInstant` or `readInstantInput` would better signal "may throw" vs. `instant()` (a branded passthrough).

**Duplicated Code — readEntry field copying (api/entry-input.ts:43–49)**
Five nearly-identical `if (input.X !== undefined) entry.X = input.X` guards. Idiomatic for `exactOptionalPropertyTypes`, but the shape repeats. A helper like `copyDefined(target, input, key)` would collapse it. Low severity — the fields are heterogeneous so a generic has limited payoff.

**Speculative Generality — EventBus (view/event-bus.ts)**
`EventBus<TEvents>` is generic and ships with exactly two events. The generic costs nothing now but adds a layer of abstraction the codebase doesn't yet need. If no second instantiation appears by S4, this should be de-genericized.

**Cross-layer import — pane-layout.ts → render/dom (view/pane-layout.ts:10)**
`PaneLayout` imports `readPixelProperty` from `render/dom/pixel-property.ts`. The plans list view→render as an allowed edge, so this is legal. However, `readPixelProperty` lives inside `render/dom/` (not a shared utility), coupling view/ to a specific render backend's internal. Consider moving it up to `render/` or a shared location if more view/ files need it.

**Data Clump — GanttShell construction (view/gantt-shell.ts:102–127)**
The constructor orchestrates six collaborating objects (`PaneLayout`, `EventBus`, `SplitterAttachment`, `PaneSizeAttachment`, `ScrollModel`, `RenderBackend`). Each is one delegation hop, so no single chain is long, but the `Panes` record (`grid`, `splitter`, `timeline`) immediately gets unpacked and handed to separate attachments. Acceptable for a composition root, but worth watching as more panes land (S6).

### Clean areas

- `time/zone.ts` rename (`toInstant` → `fromZoned`): clarity win, zero behavioral change.
- `src/render/backend.ts` `RenderSurfaces<THost>`: clean seam replacing `rowLabelWidth` and single-host `mount()`.
- `no-flow-layout-rows` lint rule: scoped, exempted correctly, matches invariant I9.
- `splitter.ts`: well-factored pointer-drag attachment; Escape cancel (U5) and `endDrag` encapsulation are clean.
- `entry-input.ts` and `time/input.ts`: proper separation of field mapping (api/) from date reading (time/).

### (b) Scope creep

**`InvalidInstantError` not in S1.8 spec.**
Spec D-S1.8-9 names only `HostNotFoundError` as the first catchable error. `InvalidInstantError` is new, not listed in the spec's error table, yet exported from `api/index.ts`.

**PR #66 content contaminates the diff.**
The entire `EntryInput`/`InstantInput`/`DateOnlyEndRule`/`entry-input.ts`/`time/input.ts` system is PR #66 content, not in the S1.8 spec. The merge base appears to include PR #66 commits, creating ambiguity about what belongs to which step.

### (c) Implemented but potentially wrong

**Header spacer fallback rationale is stale (D-S1.8-11).**
The spec says `--fg-header-height` falls back to `20`, "matching today's harness". The code implements `fallback: 20` correctly, but the harness previously set a different value (removed in this diff). The "matching today's harness" rationale is slightly misleading.

**EventBus veto path — technically correct but subtle.**
The `previewGridWidth` path writes directly to `paneLayout.gridWidth` during an Escape. The spec says "no event, no commit" but not "no DOM effect" — technically correct.

### Summary
The core S1.8 implementation (pane layout, splitter, event bus, GanttShell wiring, render backend surfaces) is faithful to the spec. The main concerns are PR #66 content contaminating the diff and `InvalidInstantError` being added without spec coverage.

## 4. Architecture — Deepening Opportunities

| # | Candidate | Strength | Key insight |
|---|-----------|----------|-------------|
| 1 | Move `readPixelProperty` to `view/` | **Strong** | Conceptual seam is backwards; S1.10 multiplies the cost |
| 2 | Explicit setter return from `PaneLayout.gridWidth` | Worth exploring | Implicit identity check should be an explicit contract |
| 3 | `EventBus` lifecycle context | Worth exploring | Interface will shallow as events multiply |
| 4 | Split `PaneLayout` constructor | Speculative | Adequate today; revisit for S6 grid columns |

### 1. Move `readPixelProperty` to `view/` (Strong)

**Files:** `src/view/pane-layout.ts:10`, `src/view/gantt-shell.ts:8`, `src/render/dom/pixel-property.ts`

**Problem:** `readPixelProperty` lives in `render/dom/` but is consumed by `view/` files. The dependency is backwards conceptually: `view/` owns DOM construction and CSS; `render/` owns painting. S1.10's theming pass will multiply CSS reads, dragging more `view/ → render/dom` imports.

**Solution:** Extract `readPixelProperty` and `PixelPropertyPolicy` into `view/css-property.ts`. `render/dom/pixel-property.ts` re-exports from it or disappears.

**Benefits:** Locality — CSS reading lives with CSS writing. Leverage — S1.10 theming reads multiply without multiplying layer crossings. The deletion test strengthens.

### 2. Explicit setter return from `PaneLayout.gridWidth` (Worth exploring)

**Files:** `src/view/gantt-shell.ts:155–164`, `src/view/pane-layout.ts:116–121`

**Problem:** `GanttShell.#commitGridWidth` writes `this.#paneLayout.gridWidth = to`, which clamps inside PaneLayout's setter. The veto path writes `from` back — but PaneLayout's setter already returns early if `clamped === this.#gridWidth`, so the undo is sometimes a no-op. The invariant is implicit.

**Solution:** Make `PaneLayout.gridWidth` setter return `{ changed: boolean }`. `GanttShell` emits `gridWidthChange` only when changed, and the veto-undo is unnecessary when `!changed`.

**Benefits:** Locality — veto identity check lives at the write boundary. Leverage — S4's async veto needs to know whether a write actually landed.

### 3. `EventBus` lifecycle context (Worth exploring)

**Files:** `src/view/event-bus.ts`, `src/view/gantt-shell.ts`

**Problem:** `EventBus` is generic but instantiated once. Dataset events will need a bus too (S2), and the step that shares them "makes that call." If the bus stays in `view/`, Dataset events cannot reach it without a layer violation.

**Solution:** Leave `EventBus` in `view/` but deepen its interface before S4: add `EventBusContext` — a disposable-scoped factory that creates per-Gantt bus instances tied to `GanttShell.destroy()`, so handlers are bulk-removed without each caller tracking its own `off()`.

**Benefits:** Locality — handler lifecycle lives next to bus construction. Leverage — S4's gesture controllers need `before*Move`/`afterMove` pairs; a context-scoped bus avoids handler leaks.

### 4. Split `PaneLayout` constructor (Speculative)

**Files:** `src/view/pane-layout.ts:47–110`

**Problem:** The constructor does four things: reads 3 CSS properties, builds the flex skeleton (7 DOM elements), sets grid width, and exposes `panes` + `measureTimelinePane()`. Interface ≈ implementation — barely more than "the constructor ran."

**Solution:** Split into `createPaneSkeleton(host, options)` factory (DOM construction) + `PaneLayout` (stateful width holder). Mirrors the `attachSplitter` pattern.

**Benefits:** Locality — DOM construction is pure, testable without state. Leverage — factory can be called independently for test harnesses. Worth revisiting when S6 adds grid columns.

---

## 5. Top Recommendation

**Move `readPixelProperty` to `view/`** is the strongest action item. It is a small, safe change that corrects a conceptual seam inversion before S1.10's theming pass multiplies the cost. The other candidates are worth tracking but not urgent.

The S1.8 implementation is solid: faithful to spec, well-tested, clean seams, appropriate module sizes. The PR #66 contamination is a branch hygiene issue, not a code quality one.
