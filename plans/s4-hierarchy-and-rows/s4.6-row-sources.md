# S4.6 — Row sources and the layout pipeline

**Slice:** S4 · **Step:** 6 of 11 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S4-19 – D-S4-23 · **Closes:** issue #91 §9-B
**Prerequisite:** S4.3 · **Ends with:** a tree in the grid pane with working twisties, and `gantt.rows` switching between three sources live.

This is the step that decides whether S4 stays clean. Everything else adds a module; this one changes the shape of the layout pass.

## 1. Decisions

### D-S4-19 — `computeFrame` becomes composition over four named stages

`computeFrame` is 293 lines and already carries culling, header bands and decorations. Row sources, trees, per-Kind emission and lane packing are four more concerns. Put inside the current loop they produce exactly the ball of mud this slice is most likely to leave behind.

The pipeline `plans/01` §2.3 already names becomes four modules, each pure, each separately testable, each with one reason to change:

```ts
// layout/rows/resolve-rows.ts    — what the rows ARE
export function resolveRows(input: RowResolutionInput): RowPlan;

// layout/items/emit-items.ts     — what each row CARRIES
export function emitItems(rows: readonly PlannedRow[], ctx: ItemEmissionContext): readonly Item[];

// layout/lanes/pack-lanes.ts     — how overlapping items STACK
export function packLanes(items: readonly Item[]): LanePacking;

// layout/frame.ts                — where it all SITS, in pixels
export function computeFrame(input: LayoutInput, memory?: FrameMemory): GeometryFrame;
```

`computeFrame` keeps the header, decoration and culling work it already owns, and calls the three stages instead of growing branches. `PlannedRow` is the internal row before pixels:

```ts
export interface PlannedRow {
  id: RowId;
  kind: 'entry' | 'group' | 'custom';
  index: number;
  depth: number;                       // tree indent level; 0 for a flat source
  entryIds: readonly EntryId[];        // may be empty (a grouping header carries none)
  expandable: boolean;
  expanded: boolean;
  heightMode: 'fixed' | 'pack';
  headerLabel?: string;              // grouping headers only; column 0 of cells
}
```

`FrameRow` gains `depth`, `expandable` and `expanded` from it, so the grid pane can draw indentation and a twisty from the frame alone.

Rejected: branch inside the existing loop. Rejected: one `RowResolver` class per source with inheritance — a source is a function of data plus config, and a class hierarchy adds a lifecycle none of them has.

### D-S4-20 — Row resolution walks the whole dataset; the three later stages are windowed

Virtualization must survive this refactor. The order that keeps it:

1. **Resolve rows** for the whole dataset. Cheap — ids, depth, entry ids. No dates, no pixels.
2. **Cull** with the height index, exactly as today (`indexAtY`, plus the overscan buffer in index space).
3. **Emit, pack and place** for the windowed rows only.

Collapse is applied in stage 1, so a collapsed subtree's rows do not exist at all — they are not hidden rows, they are absent ones. That keeps `rowCount`, `aria-setsize` and the scrollbar honest.

Pack mode needs a lane count per row before the height index can answer `topAt`. S4.8 resolves that with a per-row memo the index pulls; nothing in this step's ordering changes because of it.

### D-S4-21 — One `RowSource` interface, three shipped occupants

```ts
export type RowSource = EntriesRowSource | GroupRowSource | CustomRowSource;

export interface EntriesRowSource {
  source: 'entries';
  tree?: boolean;                       // default false — S1's flat list
  heightMode?: 'fixed' | 'pack';        // default 'fixed'  (S4.8)
  filter?: RowFilter;                   // S4.9
  sort?: RowSort;                       // S4.9
}
export interface GroupRowSource {
  source: 'group';
  groupBy(entry: Entry): string;
  heightMode?: 'fixed' | 'pack';
  filter?: RowFilter;
  sort?: RowSort;
}
export interface CustomRowSource {
  source: 'custom';
  resolve(input: RowResolveInput): readonly PlannedRowInput[];
  heightMode?: 'fixed' | 'pack';
}
```

All three ship in this step. A seam with one occupant is not a proven seam, and `plans/01` §2.3 promises that a workload or resource view is "simply another row source" — a promise this step either keeps or quietly breaks.

`gantt.rows` defaults to `{ source: 'entries', tree: false }`, which is exactly what S1 draws today.

**Live reconfiguration.** Assigning `gantt.rows` re-resolves rows, invalidates the height index from 0, and requests one frame. No remount: bar node identity is `ItemId`, which does not depend on the row source (I8). Scroll survives because it is a pixel position, clamped against the new content height (D-S4-27).

### D-S4-22 — Collapse is Gantt state

```ts
gantt.collapsed = ['p1', 'p2'];        // live; ids, loose on the way in
gantt.collapse('p1');
gantt.expand('p1');
gantt.toggleCollapse('p1');
gantt.on('beforeCollapseChange', ({ from, to }) => …);   // return false to veto
gantt.on('collapseChange', ({ from, to }) => …);
```

Collapse is per Gantt, never in the Dataset — `plans/03` §S4 says so, and it is the same rule selection already follows (D-S3-10). Two Gantts on one Dataset collapse independently, and a collapse writes no transaction and no changeset.

The event pair follows `beforeGridWidthChange`/`gridWidthChange`: `{ from, to }`, cancelable, fired by both a twisty click and a direct assignment, from one commit sequence in `GanttShell`.

`view/collapse-state.ts` holds the set. It survives data edits — an id whose entry was removed stays in the set and simply matches nothing, exactly as a stale selection id does (`[S4-A6]`).

Naming: `collapsed` and not `collapsedEntries`, because `selectionEntries` already means "the Entry records", and reusing the `*Entries` suffix for a list of ids would give one suffix two meanings. The ids are **`RowId`s**. For `{ source: 'entries' }` a `RowId` equals the `EntryId`, so `collapse('p1')` stays the call above. A grouping header uses a derived `RowId` from the `groupBy` value, so those headers can collapse too.

### D-S4-23 — `Row.kind: 'group'` names a row that stands for no Entry

Two different things are called "group" in this codebase, and CONTEXT.md already warns about it. This step is where they meet, so the rule is stated once:

| | Authored or derived | What it is |
|---|---|---|
| `Entry.kind === 'group'` | authored | an Entry whose values the Rollup derives from its children. Produces a row of `Row.kind: 'entry'`. |
| `Row.kind === 'group'` | derived | a grouping header row produced by `{ source: 'group', groupBy }`. Stands for no Entry; `entryIds` is empty. |

A tree of `'group'` Entries under `{ source: 'entries', tree: true }` therefore produces **no** `Row.kind: 'group'` rows at all. CONTEXT.md gains this table.

A grouping-header row has no Entry, so `ResolvedColumn.format(entry)` does not run. `PlannedRow.headerLabel` holds the `groupBy` value. Column 0 of `cells` is that label; the rest are empty strings. No view-side aggregate — Rollup is data, and this row is not data.

### Issue #91 §9-B — `GanttShell`'s `#wiring` boolean

Construction now wires row sources, columns and collapse state as well as everything it already did, so the "true until pane-size wiring completes" flag guards more. Resolve it in this step: either the flag becomes an explicit construction phase with a name, or the premature-render path it guards goes away. Do not leave a boolean that more code has learned to check.
