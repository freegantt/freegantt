# S4.7 — Item emission per Kind

**Slice:** S4 · **Step:** 7 of 11 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S4-24, D-S4-25
**Prerequisite:** S4.6 · **Ends with:** groups draw as brackets, milestones as diamonds, and an entry with three segments draws three bars on one row.

## 1. Decisions

### D-S4-24 — `ItemProducer` is the per-Kind seam; S4 ships three occupants and no public registration

`plans/01` §2.5 promises that a Kind selects item emission through a registry, never through an `if (kind === …)` chain. This step builds the registry and fills it:

```ts
// layout/items/produce-items.ts
export type ItemProducer = (entry: Entry) => readonly Item[];

export interface ItemProducerRegistry {
  /** The producer for `kind`, or the `'span'` producer when nothing is registered (§2.5's graceful
   *  degradation rule). Never throws on an unknown Kind. */
  producerFor(kind: EntryKind): ItemProducer;
}
```

| Kind | Producer | Emits |
|---|---|---|
| `span` | `produceSpanItems` | one Item per Segment, or one for the whole span |
| `group` | `produceGroupItems` | one Item, flagged for the bracket renderer |
| `milestone` | `produceMilestoneItems` | one zero-width Item at `start` |
| anything else | `produceSpanItems` | the fallback §2.5 requires |

The bracket and the diamond are **shape**, not geometry: `produceGroupItems` and `produceMilestoneItems` produce ordinary Items, and `render/dom` draws them differently off `data-kind`, which S1 already stamps. `layout/` stays pure numbers.

**No public registration in S4.** A consumer-defined Kind reaching all four seams is an S5 acceptance box, and registration needs `PluginContext`. The registry is built per Gantt (never module-level, I2), seeded with the three, and reachable only through an internal `GanttShellOptions` key that tests use — the same posture S2 took for the extender slot (D-S2-6). Publishing `registerItemProducer` now would be a public key with no consumer, which I11 exists to catch.

Rejected: a `switch (kind)` in `produceItemsForRow` with a `TODO` for S5. The seam is the design; a switch that a later slice must dismantle is not a cheaper first version of it.

### D-S4-25 — One Item per Segment, and one id builder

`Item.id = ${entryId}:${segmentIndex}` is `plans/01` §2.4's rule and `model/ids.ts`'s `itemId(entry, segmentIndex = 0)` already builds it. Until this step every Item used index `0`, so the rule was true but untested against a second segment.

Two things follow:

- **`produceSpanItems` emits `entry.segments.length` Items** when segments are present, indexed in array order, each with its own `start`/`end`. An entry without segments emits one Item at index `0` — unchanged, so every existing `ItemId` keeps its value and I8's determinism test keeps passing.
- **Reading an `ItemId` gets its own helper.** `model/ids.ts` gains `entryIdOfItem(id)` and `segmentIndexOfItem(id)`. S3's `entryFor(itemId)` and the shell's `#itemEntryIds` map both go through them. Splitting an `ItemId` inline anywhere else is a review finding — the format is the builder's business, and a segment index is now load-bearing (S4.10 drags one).

**Lane assignment is not this step's.** `produceItemsForRow` leaves lane assignment to `packRow`; S4.8's `packRow` overwrites it. Keeping emission and packing apart is what lets a custom row source carry Items from several entries and still pack correctly. A header row (`PlannedRow.kind: 'header'`) produces no Items. **Retired by #298:** there is no lane assignment and no `packRow` — `produceItemsForRow` emits every Item onto the row's one band. This paragraph records the split S4 shipped, not current code.

**`a11yLabel` gains the segment.** A bar that is one of several says so: `${name}, part ${i + 1} of ${n}, ${start} – ${end}`. Library-derived text on the existing precedent; the single-segment wording is unchanged.
