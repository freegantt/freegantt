# S4.4 — Serialization: `schema: 2`

**Slice:** S4 · **Step:** 4 of 11 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S4-15, D-S4-16
**Prerequisite:** S4.1, S4.2 · **Ends with:** `fromJSON(toJSON(dataset), { aggregators })` gives back a Dataset whose parents still sum.

## 1. Decisions

### D-S4-15 — The Document carries the data half of each Field; `fromJSON` takes the code half

Without declarations in the Document, a round-trip returns a Dataset that still **holds** rolled-up values but no longer **maintains** them: the next child edit leaves every ancestor stale, and nothing says so. That is a corruption, not a limitation.

So the Document carries what is data, and the reading application supplies what is code:

```ts
interface DatasetDocument {
  schema: 2;
  timeZone: string;
  dateOnlyEnd: DateOnlyEndRule;
  rollUpKinds: readonly EntryKind[];
  /** Declaration order. Core Fields are never written — the reader seeds them itself. */
  fields?: readonly SerializedField[];
  entries: readonly SerializedEntry[];
  meta?: unknown;
}

/** A `Field` minus its function-valued keys. `type` and `rollUp` travel as names. */
type SerializedField = Pick<Field, 'key' | 'type' | 'source' | 'rollUp' | 'column'>
  & { source: { from: 'entry'; field: CoreFieldKey } | { from: 'meta'; key: string } };

Dataset.fromJSON(doc, options?: { fieldTypes?; aggregators?; fields? }): Dataset;
```

Rules, each stated because a reader will otherwise assume the other answer:

- **A `compute`-sourced Field is not written.** Its `read` is code, and a source with no `read` is meaningless. A round-trip that needs one takes it from `options.fields`.
- **Omitted `source` is written resolved.** `{ key: 'cost', type: 'money' }` serializes as `source: { from: 'meta', key: 'cost' }`. The Document does not depend on the construction default.
- **`equals`, `compare` and `formatValue` are not written.** They travel with the application, through `options.fieldTypes` or `options.fields`.
- **A key present in both** takes the Document's **data** keys and the option's **functions**. Table:

  | Key | Winner |
  |---|---|
  | `source` | Document (slot identity) |
  | `rollUp` | Document |
  | `type` | Document |
  | `column` | Document |
  | `equals`, `compare`, `formatValue` | `options.fields` |

  A Field only in `options.fields` is added whole. A Field only in the Document keeps its data keys; functions come from `options.fieldTypes` by the Document's `type` name, the same as at construction. Reloading with a richer Field type does **not** replace a Document `rollUp: 'sum'` — edit the Document, or omit that Field from the Document and pass it only in `options.fields`.
- **The Rollup function is not an option.** The leaf always runs (D-S4-7). `fromJSON(doc, { aggregators })` still maintains parents. Document `rollUpKinds: []` is none: parents keep stored values and the next child edit does not overwrite them.
- **An Aggregator named in the Document but absent from `options.aggregators`** throws `UnknownAggregatorError`, exactly as it would at construction. A silent `'none'` fallback would return wrong numbers.
- **Byte stability is unchanged** (D-S2-12): declared key order, optional keys omitted, entries in insertion order, instants as `Z`-suffixed ISO. `fields` is written in declaration order, and each Field's keys in declared order.

Rejected: declarations are construction config only, never serialized, and `fromJSON` takes the whole registry. The second parameter exists either way, and a Document that cannot describe its own aggregates is a worse artefact — it stops diffing in review, which ADR 0005 names as a reason levels 1–3 are plain data.

### D-S4-16 — `schema` goes to 2, and a `schema: 1` Document still reads

Two changes land together with a third that ADR 0008 already made in source: the `derivedSpanKinds` → `rollUpKinds` key (D-S4-6), `fields`, and `progress` gone from `EntryDocument`.

`readDocument` accepts both versions:

| Read | `schema: 1` | `schema: 2` |
|---|---|---|
| Kind gate | `derivedSpanKinds` | `rollUpKinds` |
| Fields | none in the Document — `options.fields` only | `fields`, merged with `options` |
| Anything else | unchanged | unchanged |

`toJSON` always writes `schema: 2`. An unknown or higher `schema` still throws `UnsupportedSchemaError`, unchanged.

A `schema: 1` Document read under S4 is upgraded in meaning: its `derivedSpanKinds` list becomes `rollUpKinds`, which now gates every rolling-up Field rather than only the span. With no declared Fields there are no other rolling-up Fields, so nothing about the round-trip changes.
