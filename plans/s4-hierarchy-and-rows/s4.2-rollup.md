# S4.2 — Rollup over the registry

**Slice:** S4 · **Step:** 2 of 11 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S4-6 – D-S4-11 · **Closes:** issue #80, ADR 0005's two open questions
**Prerequisite:** S4.1 · **Ends with:** a parent's `cost` equals the sum of its children's, it undoes in one step, and it survives a bulk edit.

## 1. Decisions

### D-S4-6 — `derivedSpanKinds` becomes `rollUpKinds`, and the gate widens

The gate answers "which parents derive their values from their children". Before S4 the only such value was the span, so the name said `Span`. From S4 it governs `cost` too, and a name that says "span" over a value that is not a span is the drift #7 records.

**The rule:** a parent whose Kind is in `rollUpKinds` derives **every** rolling-up Field. A parent of any other Kind keeps its authored values, for every Field.

That keeps the two axes orthogonal exactly as `plans/01` §2.6 states them: `rollUpKinds` says **which parents** derive; each Field's `rollUp` says **how** that Field derives.

**Rollup none** is the named opt-out on that first axis: `rollUpKinds: 'none'`. It means no Kind derives. The pass emits no rows. Every parent keeps the values the caller wrote — `start`, `end`, `cost`, or any other Field. `'none'` is constructor and setter sugar for the empty list. The getter and `toJSON` always expose `rollUpKinds: []`. A live assignment of `'none'` or of `[]` is one job.

The second axis already has the same word, read **after** Field-type merge (D-S4-3): a resolved Field with `rollUp: 'none'`, or with no `rollUp`, does not participate even when its parent’s Kind is in the list. That parent keeps the caller’s value for **that** Field only. A Field that omitted `rollUp` but named a type whose bundle carries one still participates — the type supplied the name.

Rejected: a second Dataset option (`rollUp: false`, `rollUp: 'none'` beside `rollUpKinds`). Two knobs for one job.

Rejected: keep the name and scope it to `start`/`end`, letting every other Field roll up onto any parent. A plain `'span'` entry that happens to have children would then have its **authored** `cost` overwritten by a pass the consumer never opted into. Silently destroying authored data is worse than a rename.

Rejected: keep the name and widen the meaning. That is the failure CLAUDE.md names by example.

**Renames, no aliases** (pre-1.0, ADR 0003's precedent):

| Before | After |
|---|---|
| `DatasetOptions.derivedSpanKinds` | `DatasetOptions.rollUpKinds` |
| `Dataset.derivedSpanKinds` | `Dataset.rollUpKinds` |
| `Dataset.isDerivedSpanKind(kind)` | `Dataset.isRollUpKind(kind)` |
| `DatasetDocument.derivedSpanKinds` | `DatasetDocument.rollUpKinds` (S4.4 reads the old key at `schema: 1`) |
| `warnIfDerivedSpansWereCorrected` | `warnIfRollUpsWereCorrected` |

`view/capability.ts` reads the renamed predicate. Its default table is unchanged in meaning: a parent whose values the Rollup owns refuses `move` and `resize`, because the identity extender has nothing to write its children with. With `rollUpKinds: 'none'`, `isRollUpKind` is false for every Kind, so a `'group'` may move and resize — the caller owns those values.

### D-S4-7 — `data/span-rollup.ts` becomes `data/rollup.ts`, and its removability rule follows

`rollUpDerivedSpans` becomes `rollUpFields(entries, proposed, registry, rollUpKinds, ctx)`. The function stays a leaf with exactly one importer (`data/transaction.ts`), and `.dependency-cruiser.cjs`'s `span-rollup-is-removable` becomes `rollup-is-removable`.

The Dataset constructor does not take a rollup function. The common call site is `new Dataset({ timeZone, entries })`. Construction and `fromJSON` call the same leaf the commit path calls. `Gantt` does not import it.

The degradation the rule proves is still honest: delete `rollup.ts` and every entry keeps its authored values — the same stored result a consumer gets from `rollUpKinds: 'none'`.

The pass is not an extender occupant (D-S2-22 still holds): nothing installable can displace it with scheduling.

Rejected: default `identityRollUp` with a public `rollUp: rollUpFields`. That is two knobs, a `fromJSON` trap, and an extra import for the common case. Tree-shaking the leaf is a later headless entry if a measurement asks for it — not an app-author option.

### D-S4-8 — The pass walks the ancestor chains of touched entries, and every Aggregator takes that path

Today `rollUpDerivedSpans` sorts and walks **every** deriving entry on every commit. With N Fields that becomes N times too much work on a 500-entry bulk edit (`[S2-A3]`).

S4's pass:

1. Collect the touched ids — the transaction's added, removed and edited entries, plus the former parent of any reparented entry.
2. Walk each id's ancestor chain, deduplicated, deepest first. Those are the parents to recompute.
3. For each such parent and each rolling-up Field, read **all** its children through the Field and run the Aggregator.
4. Emit a `FieldUpdated` row only where the value moved, under that Field's `equals`.

Construction and `fromJSON` still walk the whole tree once (`applyConstructionRollUp`), because there is no "touched" set to narrow by.

**One path for shipped and consumer Aggregators.** ADR 0005 asked whether shipped ones could be maintained incrementally while consumer ones force a full recomputation. They cannot have different commit semantics without giving a consumer Field second-class behaviour — the thing ADR 0005 exists to remove. Step 3 reads every child either way.

**Precedence is unchanged** (D-S2-22): the Rollup yields to a Field the body proposed in the same transaction, and wins over one the extension hook proposed. Bottom-up, one pass, so nested parents settle together.

### D-S4-9 — An Aggregator that throws fails the transaction

`AggregatorFailedError` carries the Field key, the Aggregator name and the parent's id. The write set is discarded. Nothing commits, no `change` fires, and no history entry is pushed — the same shape a `beforeChange` veto already has, with a different error.

Rejected: keep the stored value and carry on. The Document then holds a parent whose value no longer follows its children, and nothing says so. Principle 6 forbids the silent fix, and the diagnostics channel that would carry the alternative is S7's.

A gesture commit sees this as a failed commit: `api/gantt.ts`'s `commitEntryEdits` restores the pre-gesture paint, then rethrows. `MutationCancelledError` stays the only error it swallows.

### D-S4-10 — A computed Field is memoized on `(entryId, fieldKey, dataset revision)`

A `compute`-sourced Field has no stored home, so its value — a parent's included — is read on demand and never written. The cache is per Dataset, cleared on every commit.

ADR 0005 named the **subtree** revision as the key. A dataset-wide revision is the same answer, coarser: it never returns a stale value, it only recomputes more often than it must. Subtree revisions need a per-entry counter maintained up the tree on every commit, which is bookkeeping this slice does not need to buy. It returns at S6 if the spike says so.

**A computed Field reads the Dataset only** — no zoom, no visible range, no selection. That is what makes the cache key correct, and it is the rule that would quietly break a shared Dataset, so it is asserted, not assumed.

### D-S4-11 — View state never changes a stored value

Collapse, filter and sort are `view/` and `layout/` concerns. None of them reaches `data/`:

- A **collapsed** parent still rolls up. Collapsing hides rows; it does not change data.
- A **filtered-out** child still counts toward its parent's aggregate.
- **Sort** never touches the Store's order, so `entries.all` and `toJSON` keep insertion order (D-S2-12).

Three assertions, one rule. Without them the Document would depend on what a view is currently showing, which is the AG Grid `aggFunc` design ADR 0005 deliberately did not copy.

## 3. Tests

- `src/data/rollup.test.ts` — `sum` up two levels; `min`/`max` keep the shipped span behaviour; a non-`rollUpKinds` parent keeps its authored value; `undefined` from an Aggregator leaves the stored value alone
- `src/data/rollup.test.ts` — `rollUpKinds: 'none'` (and `[]`) leaves the caller’s parent `start`/`end`/`cost` after a child edit; `isRollUpKind` is false for `'group'`
- `src/data/rollup.property.test.ts` — random trees and random edits: every rolling-up parent equals its Aggregator over its children after commit
- `src/data/rollup.test.ts` — `[S4-A8]`: an empty `'group'` keeps its zero-length span, then gains a real one when a child arrives
- `src/data/rollup.test.ts` — D-S4-9: a throwing Aggregator raises `AggregatorFailedError`, commits nothing, pushes no history
- `src/data/computed-cache.test.ts` — a computed Field recomputes after a commit and not before
- `src/data/history.property.test.ts` — `[S4-A1]`'s undo half: a declared Field's rolled-up parent value inverts with the child edit, in one step
- `src/api/dataset.test.ts` — D-S4-11: collapsing, filtering and sorting a Gantt leave every stored value and `entries.all`'s order untouched
- `src/data/transaction.test.ts` — a 500-entry bulk edit still produces one changeset, and touches only the ancestors it must
