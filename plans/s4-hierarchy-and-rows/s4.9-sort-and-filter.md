# S4.9 — Sort and filter

**Slice:** S4 · **Step:** 10 of 12 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S4-28, D-S4-29
**Prerequisite:** S4.6 · **Ends with:** filtering to one team still shows a matching deep child under its chain of parents.

## 1. Decisions

### D-S4-28 — Sort and filter belong to the row source, not to the Store

`plans/03` §S4 called them "store-level view specs". They are not, and this step edits that line.

Sorting the Store would reorder `entries.all`. That order is insertion order, it is what `toJSON` writes, and it is half of what makes the Document byte-stable (D-S2-12). A view knob that rewrites the Document is the same mistake ADR 0005 refused when it kept aggregation off a Grid column.

So both live on the row source, beside the other question about what the rows are:

```ts
rows: {
  source: 'entries', tree: true,
  filter: (entry) => entry.meta.team === 'A',
  sort: { field: 'start', direction: 'asc' },
}

export type RowFilter = (entry: Entry) => boolean;
export interface RowSort {
  field: FieldKey;                                  // a declared Field, core or consumer
  direction?: 'asc' | 'desc';                       // default 'asc'
  compare?(a: unknown, b: unknown): number;         // default: the Field's own ordering
}
```

`sort.field` names a **declared Field**, so a consumer sorts by `cost` the same way they sort by `start` — one code path, ADR 0005's whole point. An unregistered key is `UnknownFieldError`. Sorting reads the **stored** value through the Field, never `formatValue`. Money stays a number in the store; the cell shows currency text; sort still orders 500 before 12000. A computed Field sorts too, with no stored column to sort on.

**Default order** is ascending, then `desc` reverses it. The comparer is, in order: `RowSort.compare` if the view set one; else the matching `FieldCompare.compareStored` (built at the same Gantt locale bind as columns, D-S4-13); else a shipped compare on the stored value — numbers by numeric order, Instants by time, strings by `localeCompare`, `undefined` last. `formatValue` is display only. A status Field whose order is not alphabetical puts `compare` on the Field type; that flows into `FieldCompare` at resolve time.

`RowResolutionInput` carries `fieldCompares: readonly FieldCompare[]` — one entry per declared Field, not the visible `LayoutInput.columns`. `layout/rows/sort.ts` never imports `data/` or `view/`, and it never looks up `sort.field` on the Grid. A Field that is not in `gridColumns` still sorts.

Both are live: assigning `gantt.rows` with a new `filter` or `sort` re-resolves rows and requests one frame.

**Neither reaches `data/`.** D-S4-11's three assertions cover it: a filtered-out child still counts toward its parent's aggregate, and sort never touches the Store's order.

Rejected: `gantt.filter` and `gantt.sort` as their own top-level properties. They only mean anything relative to a row source — a `{ source: 'custom', resolve }` source answers both questions itself — so hanging them off the Gantt puts two knobs on one job.

### D-S4-29 — Filter keeps ancestors; sort stays within a parent

Two tree-aware policies, each with one default and one escape.

**Filter — keep ancestors (default).** A row survives when its own entry matches, **or** when any descendant's does. A matching deep child therefore appears under its full chain of parents rather than orphaned at the root (`[S4-A7]`). An ancestor kept only for its descendants is marked so the grid can style it — `PlannedRow.matched: boolean` — but it is a real, selectable row, not a placeholder.

`filterPolicy: 'keepAncestors' | 'matchOnly'` on the row source, defaulting to `'keepAncestors'`. `'matchOnly'` flattens to just the matches; a consumer building a search result list wants that and would otherwise re-implement it.

**Sort — within a parent.** Sorting reorders siblings under each parent and never lifts a child past its parent. A tree whose sort could reparent rows is not a tree. Under `{ source: 'entries', tree: false }` the whole flat list sorts, because there is no parent to stay inside.

Under `{ source: 'group', groupBy }`, sort orders the entries inside each header row's block, and the header rows themselves keep first-seen order. Sorting the headers is a second question with a second answer (`groupSort`), and nothing needs it yet — deferred until a caller does.

**Order of operations:** filter, then sort, then collapse. Filtering first means sort never orders rows that are about to disappear; collapsing last means a collapsed subtree's rows are removed from a list that is already correct.

## 3. Tests

- `src/layout/rows/filter.test.ts` — `[S4-A7]`: a deep match keeps its whole ancestor chain, each ancestor marked unmatched; a filter matching nothing yields no rows and no crash
- `src/layout/rows/filter.test.ts` — `[S4-A10]`: `filterPolicy: 'matchOnly'` returns the matches alone, with no ancestor rows
- `src/layout/rows/sort.test.ts` — siblings reorder, a child never passes its parent; `desc` reverses; a computed Field sorts; money sorts by the number, not the formatted string; `RowSort.compare` beats `FieldCompare.compareStored`; a Field-type `compare` flows into `FieldCompare`; `sort: { field: 'cost' }` with `gridColumns: ['name']` still uses the cost comparer (D-S4-13); an unregistered key throws `UnknownFieldError`
- `src/layout/rows/resolve-rows.test.ts` — the filter → sort → collapse order; a collapsed parent that survives the filter still hides its descendants
- `src/api/gantt.test.ts` — assigning `rows` with a new `filter` re-resolves live, with no remount
- `src/data/rollup.test.ts` — D-S4-11: a filtered-out child still counts toward its parent's aggregate
