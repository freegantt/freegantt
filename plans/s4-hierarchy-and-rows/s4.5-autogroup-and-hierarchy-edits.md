# S4.5 — `autoGroup` and hierarchy edits

**Slice:** S4 · **Step:** 5 of 11 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S4-17, D-S4-18 · **Closes:** S2's Q3
**Prerequisite:** S4.2 · **Ends with:** reparenting an entry under a plain entry promotes that parent to `'group'` in the same undo step.

## 1. Decisions

### D-S4-17 — `hierarchy: { autoGroup: true }` is the default, and promotion runs in the triggering transaction

```ts
const dataset = new Dataset({ entries }); // autoGroup on
const authored = new Dataset({ hierarchy: { autoGroup: false }, entries });
```

Nesting is the common case, so the convention "a parent is a `'group'`" is the default. Pass `{ autoGroup: false }` when a `'span'` must keep children and keep its authored Kind.

**When it fires.** An entry gains its first child, through `entries.add({ parentId })` or through `entries.update(id, { parentId })`. The promotion is staged inside the same transaction, so it is one changeset, one `change` event and one undo step. Construction promotes too, on the same rule, and emits nothing — construction is silent (D-S2-22's precedent).

**What it writes.** One `FieldUpdated` row, `field: 'kind'`, `from: 'span'`, `to: 'group'`. Nothing else. The parent must already be `'span'`. An already-`'group'` parent is a no-op. Any other Kind stays as authored — no throw, no promotion. When a `'span'` is promoted, the span then follows from the Rollup on the same commit, because `'group'` is in `rollUpKinds` by default — so the parent's `start`/`end` rows appear in the same changeset, from the pass that already runs.

**Where it lives.** `data/hierarchy.ts`, a leaf with one importer (`data/transaction.ts`), on the same removability rule as `data/rollup.ts`: delete it and promotion never runs — the consumer sets Kind themselves. `.dependency-cruiser.cjs` gains `autogroup-is-removable`.

**Order within the commit.** Promotion runs **before** the Rollup, because promoting a parent is what puts it inside `rollUpKinds` and therefore inside the Rollup's own reach on that same commit. A parent promoted after the Rollup would keep its authored span until some later edit touched a child.

Rejected: promote from a `change` subscriber. It would be a second transaction, a second undo step, and a moment where the Document holds a parent with children and no group Kind.

Rejected: derive `'group'` from "has children" at read time. `01` §2.5 forbids it by name — a Kind that flickers with current structure is the identity problem the authored rule exists to prevent.

### D-S4-18 — Promote only, never demote

Removing the last child leaves the parent a `'group'`. Demotion is always an explicit edit.

The reason is the same one that makes Kind authored: demoting on the last removal makes a parent's identity flicker as children come and go, and "add a phase, then fill it" — the empty group — stops being expressible. An empty `'group'` is legal, renders as one, and keeps whatever span the Rollup last gave it (`[S4-A8]`).

**Reparenting has a second edge.** Moving an entry out from under a parent leaves that former parent childless. Two things follow, and both are already decided elsewhere: no demotion (this decision), and the former parent's ancestors are in the Rollup's touched set (D-S4-8), so its aggregates settle in the same commit.
