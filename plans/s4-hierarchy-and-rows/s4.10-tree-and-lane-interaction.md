# S4.10 — Tree and lane interaction

**Lane packing retired by #298.** Every row now draws its items on one shared band; every mention
below of a lane, or of dragging/resizing within one, records what S4 shipped, not current behavior.

**Slice:** S4 · **Step:** 10 of 11 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S4-30 – D-S4-33 · **Closes:** issue #91 §9-G
**Prerequisite:** S4.7, S4.8 · **Ends with:** a drag on a picked bar of a multi-bar entry moves that bar alone, and a drag with no pick moves all of them; the keyboard collapses and expands a row.

## 1. Decisions

### D-S4-30 — A drag writes every Segment, or the picked one; the Selection decides

> **Superseded (#212, `docs/adr/0010-the-selection-holds-segments-not-entries.md`).** The rule this
> decision states — the Selection owns the drag, and what paints as selected is what moves — stands
> unchanged. Only the pick clause below is gone: the Selection now holds Segments directly, so no
> separate `pickedItemIdByEntryId` state is needed to say how much of a drag reaches. The rule holds
> **by construction**, because paint and gesture now read the one Segment set. The mechanism below
> (`ItemId`, the pick, `pickedItemIdByEntryId`) is kept as the record of how S4.10 shipped; read it
> for history, not for current behaviour.

**Amended by #200, and #200's amendment withdrawn by #211** (`plans/s5-extensibility-and-editing/spec-211-gesture-units.md`). The section below records #200's own reasoning as it was written; read it for history, not for current behaviour. The first version of this decision gave the drag to the grabbed `ItemId`: one of N Segments wrote `segments`, "with that index's span stepped and the rest untouched". #185 then made every bar of a selected Entry paint `selected`, and the two decisions disagreed in public — the paint said "this Entry", the drag said "this bar". #200 resolved that disagreement by widening the drag to the whole Entry, always. #211 found the fix over-corrected: `render/dom` still narrows paint to the Picked Item (`pickedItemIdByEntryId`, #185's own state, never removed), so a bar click already paints one bar alone — #200's "always the whole Entry" drag then moved three bars under a paint that showed one. #211 restores the original per-Segment gesture, gated on that same pick: a picked bar moves alone, and a selection with no pick (a grid-row click, or several Entries at once) still moves every Segment, exactly as #200 intended for that case.

**A gesture acts on exactly what paints selected.** Not behind a modifier, not behind a capability — behind the pick alone. A consumer moves one Segment through `dataset.entries.update(id, { segments })`; only the gesture reads the pick.

| Entry's own pick (#211) | What the draft writes |
|---|---|
| no Segments | `start` and `end` — S3's behaviour, unchanged |
| a picked Segment | `segments`, that Segment alone stepped, plus the envelope |
| no pick, has Segments | `segments`, every Segment stepped by the same delta, plus the envelope |

A **resize** follows the same pick: a picked Segment's own edge moves; with no pick it acts on the Entry's envelope instead — the `start` handle moves the earliest Segment's start, the `end` handle moves the latest Segment's end, and every other Segment stays where it is. The earliest and the latest Segment are a comparison, never index 0 — a consumer authors Segments in any order.

The handle pair follows the same rule: a picked bar gets both handles; with no pick, for a segmented Entry the two handles sit on two different bars — `InteractionState.resizableEntryId` names the Entry, and a backend resolves the leftmost and rightmost bar from the frame it synced (#185's shape for the Selection, applied to the handles), or the one picked bar when `pickedItemIdByEntryId` names one.

Both cases go through the same `draftForMove` / `draftForResize` in `layout/gesture-draft.ts`, the same calendar-delta stepping (D-S3-3), the same snap rule (D-S3-12) and the same one-transaction-per-gesture commit (D-S3-16). `interaction/` still performs no arithmetic; `GesturePipeline.session()` resolves each gestured Entry's own pick from `pickedItemIdByEntryId` — the same state paint already narrows to (#211) — into the Segment index `layout/gesture-draft.ts` needs.

The comparator for `segments` already exists — `data/change-set.ts`'s `segmentsEqual` was written for exactly this, so a gesture that ends where it started still records nothing.

**Multi-selection** (D-S3-19) moves every selected entry by the same rigid delta: an Entry with its own pick contributes that Segment alone, an Entry with no pick contributes its whole span, the grabbed one included (#211).

**Capabilities** are per entry, not per Item (`02` §4.1). A `move: false` entry refuses a drag on any of its bars, and shows no handles on any of them (I14).

**Envelope invariant.** A write to `segments` also writes `start`/`end` to the min/max of those Segments, in the same transaction. Parent Rollup of `start`/`end` reads each child's envelope, never walks Segments. A `start`/`end` write on an entry that has Segments throws a named invariant error (`SegmentsOutOfSyncError`); the consumer writes `segments` instead. A single-Item entry still writes `start`/`end` only, as today.

### D-S4-31 — Row reorder and reparent **by drag** are not S4's

S3's deferred table pointed both at S4. They do not land here, and that table is edited (S4.11).

Reordering rows by drag needs an **authored order Field** — today's row order is insertion order for a flat source and `parentId` order for a tree, and neither is a value a consumer can write. Adding one is a Document change with its own rollup and undo questions, and no acceptance box in `plans/03` §S4 asks for it. Reparenting by drag needs the same drop-target vocabulary as reordering, so the two ship together or not at all.

What S4 does ship is the **data** half: `entries.update(id, { parentId })` reparents, `autoGroup` promotes, and the Rollup settles both ends (S4.5). A consumer can build the gesture on the public API today.

### D-S4-32 — `EntryGestureContext.rowOrder()` retires

`rowOrder()` returns `readonly EntryId[]` and its own comment says "S4's row sources replace this once they exist". They do, and the replacement matters: a shift-click range must walk the **rows the user sees** — filtered, sorted, collapsed — not the Store's insertion order.

It becomes `selectableEntriesInRowOrder(): readonly EntryId[]`, answered from the resolved rows: each row's `entryIds` in row order, skipping rows the `select` capability refuses. A collapsed subtree contributes nothing, because its rows do not exist (D-S4-20). One grouping header row contributes nothing either — it stands for no Entry.

Call site: `const range = context.selectableEntriesInRowOrder()` — "the selectable entries, in row order". That says both things the caller needs and neither thing it does not.

### D-S4-33 — Keyboard collapse and expand on the focused row

`plans/03` §S4 asks for "collapse/expand by keyboard". The bindings follow the tree-grid convention, so nothing here is novel:

| Key | Action |
|---|---|
| `ArrowRight` | expand the focused row; if already expanded, move focus to its first child |
| `ArrowLeft` | collapse the focused row; if already collapsed or a leaf, move focus to its parent |
| `*` (numpad or shifted) | expand every row |

These are view gestures. They write no transaction, so the arm-threshold and one-transaction rules do not apply — the same exemption S3's viewport gestures took (D-S3-14). They do run through `beforeCollapseChange`, so a consumer vetoes a keyboard collapse and a twisty click identically.

`ArrowLeft`/`ArrowRight` currently pan the viewport (D-S3-13). The tree bindings win **only when the focused element is a grid row of an expandable tree**; everywhere else the pan bindings are unchanged. That resolution lives in one place with the rest of the key map, not as a second listener.

Full grid a11y — roving tabindex, `role="treegrid"`, axe in CI — is S5's. S4 ships `aria-level`, `aria-expanded` and the bindings above, because D11 says accessibility lands as slices land.

### Issue #91 §9-G — `hitTest` names its coordinate space

`RenderBackend.hitTest(x, y)` does not say which space `x, y` are in: the DOM backend takes client coordinates, `GeometryFrame` is in content coordinates. S3's controllers were its first callers; lane hit-testing is its second, and a lane is picked by a `y` offset **inside** a row, which is a third space again. Give it a named type now:

```ts
hitTest(at: ClientPoint): HitResult | null;
```

`ClientPoint` is a `model/geometry.ts` type. Do this before wiring lane hits, not after.
