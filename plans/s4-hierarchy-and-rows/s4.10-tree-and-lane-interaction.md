# S4.10 — Tree and lane interaction

**Slice:** S4 · **Step:** 10 of 11 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S4-30 – D-S4-33 · **Closes:** issue #91 §9-G
**Prerequisite:** S4.7, S4.8 · **Ends with:** one segment of a multi-bar entry drags on its own, and the keyboard collapses and expands a row.

## 1. Decisions

### D-S4-30 — A Segment drag writes `segments`; the grabbed `ItemId` decides

S3's `draftForMove` moves an entry's whole span. From S4 the grabbed Item may be one Segment of several, and the two cases are told apart by the id the pointer hit:

| Grabbed Item | What the draft writes |
|---|---|
| the only Item of its entry | `start` and `end` — S3's behaviour, unchanged |
| one of N Segments | `segments`, with that index's span stepped and the rest untouched |

`segmentIndexOfItem(id)` (S4.7) is how the gesture knows. Both cases go through the same `draftForMove` / `draftForResize` in `layout/gesture-draft.ts`, the same calendar-delta stepping (D-S3-3), the same snap rule (D-S3-12) and the same one-transaction-per-gesture commit (D-S3-16). `interaction/` still performs no arithmetic.

The comparator for `segments` already exists — `data/change-set.ts`'s `segmentsEqual` was written for exactly this, so a gesture that ends where it started still records nothing.

**Multi-selection** (D-S3-19) is unchanged: a Segment drag inside a multi-entry selection moves the grabbed Segment and the whole span of every other selected entry. Moving "the same Segment index" across entries is meaningless — the entries have different Segment counts — so the grabbed entry is the only one whose Segment moves.

**Capabilities** are per entry, not per Item (`02` §4.1). A `move: false` entry refuses a Segment drag the same way it refuses a whole-span drag, and shows no handles on any of its bars (I14).

**Envelope invariant.** A write to `segments` also writes `start`/`end` to the min/max of those Segments, in the same transaction. Parent Rollup of `start`/`end` reads each child's envelope, never walks Segments. A `start`/`end` write on an entry that has Segments throws a named invariant error (`SegmentsOutOfSyncError`); the consumer writes `segments` instead. A single-Item entry still writes `start`/`end` only, as today.

### D-S4-31 — Row reorder and reparent **by drag** are not S4's

S3's deferred table pointed both at S4. They do not land here, and that table is edited (S4.11).

Reordering rows by drag needs an **authored order Field** — today's row order is insertion order for a flat source and `parentId` order for a tree, and neither is a value a consumer can write. Adding one is a Document change with its own rollup and undo questions, and no acceptance box in `plans/03` §S4 asks for it. Reparenting by drag needs the same drop-target vocabulary as reordering, so the two ship together or not at all.

What S4 does ship is the **data** half: `entries.update(id, { parentId })` reparents, `autoGroup` promotes, and the Rollup settles both ends (S4.5). A consumer can build the gesture on the public API today.

### D-S4-32 — `EntryGestureContext.rowOrder()` retires

`rowOrder()` returns `readonly EntryId[]` and its own comment says "S4's row sources replace this once they exist". They do, and the replacement matters: a shift-click range must walk the **rows the user sees** — filtered, sorted, collapsed — not the Store's insertion order.

It becomes `selectableEntriesInRowOrder(): readonly EntryId[]`, answered from the resolved rows: each row's `entryIds` in row order, skipping rows the `select` capability refuses. A collapsed subtree contributes nothing, because its rows do not exist (D-S4-20). One grouping header row contributes nothing either — it stands for no Entry.

Call site: `const range = context.selectableEntriesInRowOrder()` — "the selectable entries, in row order". That says both things the caller needs and neither thing it does not.

### D-S4-33 — Keyboard collapse and expand on the focused row

`plans/03` §S4 asks for "collapse/expand by keyboard". The bindings follow the tree-grid convention, so nothing here is novel:

| Key | Action |
|---|---|
| `ArrowRight` | expand the focused row; if already expanded, move focus to its first child |
| `ArrowLeft` | collapse the focused row; if already collapsed or a leaf, move focus to its parent |
| `*` (numpad or shifted) | expand every row |

These are view gestures. They write no transaction, so the arm-threshold and one-transaction rules do not apply — the same exemption S3's viewport gestures took (D-S3-14). They do run through `beforeCollapseChange`, so a consumer vetoes a keyboard collapse and a twisty click identically.

`ArrowLeft`/`ArrowRight` currently pan the viewport (D-S3-13). The tree bindings win **only when the focused element is a grid row of an expandable tree**; everywhere else the pan bindings are unchanged. That resolution lives in one place with the rest of the key map, not as a second listener.

Full grid a11y — roving tabindex, `role="treegrid"`, axe in CI — is S5's. S4 ships `aria-level`, `aria-expanded` and the bindings above, because D11 says accessibility lands as slices land.

### Issue #91 §9-G — `hitTest` names its coordinate space

`RenderBackend.hitTest(x, y)` does not say which space `x, y` are in: the DOM backend takes client coordinates, `GeometryFrame` is in content coordinates. S3's controllers were its first callers; lane hit-testing is its second, and a lane is picked by a `y` offset **inside** a row, which is a third space again. Give it a named type now:

```ts
hitTest(at: ClientPoint): HitResult | null;
```

`ClientPoint` is a `model/geometry.ts` type. Do this before wiring lane hits, not after.
