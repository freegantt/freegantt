# S4.8 — Lane packing and pack-mode row heights

**Slice:** S4 · **Step:** 8 of 11 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S4-26, D-S4-27 · **Closes:** issue #91 §9-E
**Prerequisite:** S4.7 · **Ends with:** overlapping Items stack into lanes, the row grows to fit them, and the scroll position stays where the user left it.

## 1. Decisions

### D-S4-26 — Lane packing is per row and memoized; the height index is its only forcing caller

Packing is a per-row question — "how many lanes do this row's Items need, and which lane is each in?" — so it is a per-row function:

```ts
// layout/lanes/pack-lanes.ts
export interface LanePacking {
  laneOf: ReadonlyMap<ItemId, number>;
  laneCount: number;
}
/** Greedy first-fit over Items sorted by `start`. Deterministic: equal starts break by `Item.id`. */
export function packRow(items: readonly Item[]): LanePacking;
```

The hard part is not packing; it is **ordering**. A pack-mode row's height depends on its lane count, the height index needs every row's height to answer `topAt` and `totalHeight`, and item emission is supposed to be windowed (D-S4-20). Emitting every row's Items to measure them would defeat virtualization.

`PrefixSumHeightIndex` already takes `getHeight(index)` as a callback, which is the seam that resolves it:

- `FrameLayout` builds the index with a `getHeight` that, for a pack row, emits and packs **that row** and reads `laneCount`.
- The result is memoized per `(rowId, dataset revision, row-source revision)` in `FrameMemory`, so a row is packed at most once per revision.
- `computeFrame`'s windowed stages read the same memo, so a visible row is packed once, not twice.

Cost: one emit-and-pack per row per revision, forced by `totalHeight`. That is what a prefix-sum index already costs, and S6's spike is where a cheaper structure is chosen if the numbers say so (D2). A `'fixed'` row's `getHeight` never packs anything, so the whole cost is opt-in with `heightMode`.

`computeFrame`'s second parameter becomes `FrameMemory` — what the pass remembers between renders — holding the height index and this memo. `FrameLayout` owns one; a caller with nothing to remember still omits it and gets one built and discarded inside the call.

**Issue #91 §9-E.** `RowHeightIndex.heightAt` and `invalidateFrom` finally get production callers here: `heightAt` is what a pack row's height flows through, and `invalidateFrom` is what a changed row calls instead of rebuilding the whole index. If either still has no caller when this step lands, remove it rather than leave decoration.

**Invalidation.** A changeset that only updates fields invalidates from the lowest changed row index; one that adds or removes entries invalidates from 0 (D-S2-16's existing rule, now also clearing the pack memo for the affected rows).

### D-S4-27 — `heightMode` belongs to the row source, and scroll is a pixel position

`heightMode: 'pack'` sits on the row source (`rows: { source: 'entries', tree: true, heightMode: 'pack' }`), not on the `Gantt`. It answers "how tall are the rows this source produces", which is the same question the source already answers for what the rows are — one config tree per job (`plans/02` §1). Default `'fixed'`.

A row height in `'fixed'` mode is `--fg-row-height`, unchanged. In `'pack'` mode it is `laneCount × (--fg-row-height)` plus `laneCount - 1` gaps of `--fg-lane-gap`, and an empty row still gets one lane's worth so it does not collapse to nothing.

**Scroll stability** is structural rather than maintained: `ScrollModel` holds a pixel offset, and a height change re-clamps it against the new `contentHeight`. So the content under the viewport shifts when a row above it grows — which is correct, and is what "stays stable" in `[S4-A5]` means. It does not mean the same row stays under the cursor; anchoring to a row is a feature nobody has asked for, and inventing it here would be scope the acceptance box does not ask for.
