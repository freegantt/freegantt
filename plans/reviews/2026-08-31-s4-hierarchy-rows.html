C1 — Give the commit pipeline a module

STRONG DONE in-process

Files. data/transaction.ts:230–305 · data/change-set.ts · data/rollup.ts · data/hierarchy.ts

Before — one 75-line script

pendingEdits → diffEdit loop
editExtender → diffEdit loop + I4 dev check
promoteNewParents → diffEdit loop
re-overlay added rows
rollUpFields → rows
foldChangeSet(...4 arrays)
endTransaction / commitChangeSet

Three identical for … diffEdit(byId, id, edit, data.fields, data.fieldContext) loops. Order, yielding rules and merge sequence are all implicit in statement order.

After — one interface, four stages inside

buildCommitChangeSet(data, origin)

→ ChangeSet | undefined

body edits
extension hook (I4 guard)
autoGroup promotion
rollup
fold

runTransaction shrinks to: open, run body, build, commit.

Problem

The five-stage commit order is the load-bearing rule of data/ and it exists only as statement order inside a 107-line function that also owns nesting, token minting and error unwinding.

Solution

Move stages 1–5 behind one interface that takes committed state and pending edits and returns a folded ChangeSet. Extract diffEdits(byId, edits, …) so the three copies become one call.

  • locality: stage order and yielding rules live in one module
  • leverage: S7's scheduler joins the pipeline, not the script
  • the interface is the test surface — commit order gets tested without a store
  • three loops collapse to one call

BUG · CONFIRMED FIXED

P1 — Removing a child never recomputes its parent

The Rollup collects touched ids from the committed map but walks ancestors through the effective map, from which the removed rows have already been deleted. A removed child therefore contributes zero ancestors, and its parent is never queued for recomputation.

sequenceDiagram
  participant T as runTransaction
  participant R as rollUpFields
  participant C as collectTouchedIds
  participant A as ancestorsOf
  T->>R: pending { removed: [b] }
  R->>R: entries = buildEffectiveEntries(...)
DELETE b
  R->>C: collectTouchedIds(committed, …)
  C-->>R: touched = { b }
  R->>A: ancestorsOf(b, entries)
  Note right of A: entries.get(b) === undefined
→ parentId undefined
  A-->>R: []
  R-->>T: no rows — p keeps stale aggregate

Spec

s4.2-rollup.md, D-S4-8 — "Collect the touched ids — the transaction's added, removed and edited entries, plus the former parent of any reparented entry."
D-S4-18 — "the former parent's ancestors are in the Rollup's touched set (D-S4-8), so its aggregates settle in the same commit."

Code

data/rollup.ts:157–161 — entries is the effective map (removed deleted at line 34); parentsToRecompute calls ancestorsOf(id, entries) at line 107.

collectTouchedIds does handle the reparent case (line 84–89, reading the former parent off committed). Removal has no equivalent.

// probe run against HEAD — parent p, children a (cost 10) and b (cost 5)

dataset.entries.remove('b')

AssertionError: expected 15 to be 10

// p.end also stays at b's end

This is a regression. span-rollup.ts on main walked every deriving parent on every commit, so removal corrected the parent's span. S4.2's touched-set optimisation (D-S4-8) is what narrowed the walk — and dropped this case with it.

Fix. In collectTouchedIds, add each removed entry's parentId (read off committed, as the reparent branch already does). Add the case to data/rollup.test.ts: it is not covered today.

Top recommendation

Fix P1, then deepen the tree it lives in

P1 first, and on its own: a parent that keeps a stale aggregate after a child is removed is wrong data, silently, on the commit path. It needs the one-line touched-set fix and the regression test that was missing.

Then C2 — one module owns the Entry tree. It is the right deepening to take next, and P1 is the argument for it: the bug is exactly a disagreement between two maps of the same tree, written in a file that carries a byte-identical copy of its neighbour's overlay function. C2 deletes that duplicate, kills both quadratic walks on the commit path, and gives S4.9's filter/sort and S7's cascade the walk they will both need.

Alongside those sit two honesty fixes that cost a line each: S2 (export AggregatorFailedError) and S1 (withdraw filter / sort / filterPolicy until S4.9 makes them real). A knob that silently ignores its argument for two slices is the kind of thing that gets written into a consumer's app and never gets un-written.

Order: P1 → S2 → S1 → C2 → S4/P5 (harness) → C3 → P2–P4 (docs) → C1 → C4. C4's registry fallback (frame.ts:233) rides along with C2 for free.
