Consumer API surface — the priority

Goal: easy for callers and agents; call site first; small app-author surface; loose-in; one place per knob.

A4 RowHeightMode ships on the public surface but is not exported

HARD

EntriesRowSource, GroupRowSource, CustomRowSource all declare heightMode?: RowHeightMode, so the type ships in the d.ts — but it is never re-exported from layout/index.ts or api/index.ts. api-extractor flags it ae-forgotten-export (api report lines 75, 161). An agent who reads heightMode?: RowHeightMode cannot resolve the name; the 'fixed' | 'pack' members stay invisible.

Fix: re-export RowHeightMode from both layout/index.ts and api/index.ts, and doc-comment 'pack'. Packaging break, not style.

A5 gantt.rows returns RowSource, not rows

HARD

Call: const list = gantt.rows; — a reader expects the derived rows and gets the source config instead. rows collides with the core glossary Row (a derived track — CONTEXT.md: “a Row is not an Entry”). This is the #7 “chart” failure again: one word, two concepts.

gantt.rows = { source: 'entries', tree: true } // “rows” names the config, but the word claims the derived rows

Fix: name the config rowSource, matching its type RowSource. gantt.rowSource reads as the source; gantt.rows is freed for an actual row getter.

A6 heightMode: 'pack' is not discoverable

JUDGEMENT

It lives only inside each row-source variant, absent from Gantt’s surface, and its type can’t be named (A4). An app author who wants packed lanes must already know to open the row-source config and find a string literal. Export the type and doc-comment the value (A4); consider a top-level heightMode on Gantt.

A7 sort/filter/filterPolicy/heightMode duplicated across two row sources

JUDGEMENT

Both EntriesRowSource and GroupRowSource carry all four. Defensible (they are genuinely per-source options), but it spreads one knob across two trees. Extract a shared RowSourceCommon block without renaming members.

Confirmed clean. gridColumns, fields, rollUpKinds, hierarchy.autoGroup, collapsed/collapse() all read true, live on one obvious place each, loose-in with branded-out, shorthand default present. No data//layout/ internals (overscan, itemEmitterRegistry, editExtender, PlannedRow, RowResolutionInput, DEFAULT_ROW_SOURCE) leak onto Gantt. Two-surfaces separation holds.

Data-core hook & the S7 OCP gap

Verified holds. One transaction → one hook call is structural, not convention: the extender fires exactly once under the outermost guard (transaction.ts:215,228,242). rollUpFields is imported from exactly one file (transaction.ts:23) and dependency-cruiser enforces it. FieldSource switches in field-access.ts:108–172 (runtime) and field-document.ts:95 (serialization) are two different concerns. No-silent-rewrite holds (rollup.ts:182).

A8 — the extender→rollup sequence is hardcoded; S7 slides in before rollup only

HARD / S7 FLAG

The hook (transaction.ts:242) runs before the rollup (:277), and both are two fixed steps. Today that is correct (D-S2-22: rollup is a core step, not an extender occupant). But S7’s schedule() occupies the extender slot, so it can only add writes before the rollup — it cannot reorder it or run after it. If scheduling must propagate dependency-caused date shifts onto already-rolled-up parents, transaction.ts becomes the place that changes — a violation of OCP this slice promised.

Recommendation: record this as an S7 pre-requisite ADR/note now: introduce a postRollup hook (or make the commit sequence explicit/pluggable) so S7 slots in behind the rollup without editing the transaction. Not S4 scope to fix — S4 scope to flag in writing so it is not re-derived at S7.

A9 — the commit block of runTransaction is growing but still named-step clean

JUDGEMENT

runTransaction (transaction.ts:203–309) is ~100 lines: body → extender → hierarchy → rollup → fold → commit. Each step is already a named function, so it is not a ball of mud today. The risk is linear growth at S7. The structure is ready; just keep the S7 hook from being inlined into this function (see A8).

Row dispatch & the three kind colliders

A10 — PlannedRow.kind is redundant and collides with two other kind fields

HARD

The layout path carries three different kind fields in one flow: Entry.kind, Item.kind, and PlannedRow.kind ('entry' | 'header'). PlannedRow.kind is the weak one: a header is already derivable from entryIds.length === 0 (frame.ts:191, emit-items.ts:17, custom-source.ts:16). Three kinds in one path is exactly the word-collision the naming rules forbid.

Fix: drop PlannedRow.kind; derive header-ness. Keep Entry.kind (authored) and Item.kind (which the renderer reads off data-kind).

Row-source dispatch is not a repeated switch — OCP holds

HOLD

resolveSource (resolve-rows.ts:30–34) is the only place that switches on source.source; gantt-shell forwards RowSource opaquely and heightModeOf needs no switch. Adding a 4th row source touches two files (type + dispatch), so the branch stays closed for modification. Good. The typed-union plus one dispatcher is the idiomatic TS OCP.

Minor: stampIndex overwrites a placeholder index: 0 (see loop 1 St6 — remove the authored placeholder); ?? 'fixed' appears in three places (heightModeOf plus per-source defaults) — low risk since height mode is baked per row.
