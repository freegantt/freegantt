What landed

The base sheet ships inside @layer freegantt, so an unlayered consumer rule wins at any specificity. Core exports three EntryVariant factories — bar(), summary(), diamond(). An Item may state a painted box the time scale does not size (Item.box), and FrameBar.minimumSpan: boolean becomes FrameBar.span: 'exact' | 'minimum' | 'fixed'. A variant carries its own css, written to one <style data-freegantt-variant-styles> node per Gantt. variantOf(entry): string retires for gantt.variantFor(entry): ResolvedVariant. Core's parent variant becomes summary.

The build did the hard part. harness/planner.ts lost checkpointDiamond and ~40 lines of page CSS and gained one line of config; harness/main.ts reviewed clean; the boundary seal from build 1 puts harness/, e2e/ and fixtures/ behind the published specifier. Findings below are about the shape of what shipped, not about whether it works.

High

F1

ResolvedVariant does not carry css, and three published places say it does

API

src/layout/items/variants.ts:29–34 · src/api/gantt.ts:517 · src/view/gantt-shell.ts:1152 · docs/adr/0022…md §3 · etc/freegantt.api.md:1890–1896

Problem. ResolvedVariant extends DrawnVariant and adds paint and can. DrawnVariant is { name, items }. There is no css member anywhere on the type.

What the docs promise. ADR 0022 §3 writes the call site as // { name, items, paint, can, css }. Gantt.variantFor's own doc comment says "read .paint/.can/.css off the same answer". GanttShell.variantFor says "One door answers items/paint/can/css together."

Why it matters. ADR 0022's whole argument for retiring variantOf is that one door answers the whole question. A consumer who follows the published call site gets a type error on the fifth answer. Either add readonly css: string | undefined to ResolvedVariant (the registry already holds it on registration.variant), or correct all three doc sites.

F2

The per-Gantt style node does not buy the isolation its I2 justification claims

Architecture

src/view/variant-styles.ts:5–12 · src/api/gantt.test.ts:2313–2334 · docs/adr/0022…md §5 "One node per Gantt"

Problem. variant-styles.ts:7 says: "Two Gantts must be fully independent: a summary rule on one page must not un-paint a diamond on another." The fragments are written verbatim into doc.head with no container scoping, so two Gantts in one document do see each other's rules. Gantt A installing diamond({ css: … }) restyles Gantt B's .fg-bar-diamond too, and at equal specificity the later node in head wins for both.

What the test proves. gantt.test.ts:2313 ("two Gantts … each carry their own node … (I2)") asserts node identity and node text, then asserts that A's destroy() leaves B's node connected. That is lifecycle independence, which the design does deliver. It is not cascade independence, which the comment claims.

Options. Say what the node actually buys (lifecycle ownership, not cascade isolation), or scope each fragment to the Gantt's own container — the shell already stamps data-fg-theme on it, so a per-instance attribute is one line away.

F3

bar() is an opt-in workaround for a default that could simply be correct

API

src/layout/items/variants.ts:440 · variants.ts:398–410 (produceLeafItems) · docs/adr/0022…md §1

Problem. ADR 0022 §1 states the defect plainly: "An author who hand-writes { name: 'x', when: myRule } silently gets wholeEntryItem instead, and their Segments disappear. bar() is what prevents that." The fix shipped as an export the author must know to reach for. The registry's default is unchanged at variants.ts:440: items: variant.items ?? ((entry, name) => [wholeEntryItem(entry, name)]).

The smaller fix. produceLeafItems is a strict superset of wholeEntryItem — it falls back to exactly one whole-entry Item when the row has no Segments. Making it the registry default closes the trap for every author, including the one who never finds bar().

The cost, stated. summary() also relies on the whole-entry default, and a parent with Segments would then draw several rails instead of one. So the move is: default becomes produceLeafItems, and summary() states its own single-Item producer. bar() survives as a convenience rather than as a trapdoor. Worth deciding explicitly, because the current shape leaves a silent data-loss default in the library.

F4

@layer blinds every happy-dom computed-style read, and one test was rewritten for it

Testing

src/view/styles.ts:161 · src/view/styles.test.ts:243–259 · src/render/dom/pixel-property.ts:26 · src/view/column-chrome.ts:243

Probed, not assumed. A throwaway dom test (written, run, deleted) read getComputedStyle(fgContainer).getPropertyValue('--fg-row-height') after ensureBaseStyles: ''. The same property from an identical unlayered <style>: 28px. happy-dom's CSSOM drops the whole layered sheet.

Consequence. pixel-property.ts and column-chrome.ts now take their library-default fallback path in every dom test, unconditionally. The token→layout wiring the base sheet provides is no longer exercised by the unit suite at all. The branch noticed the effect on one test (styles.test.ts:249, "dark theme paints bar labels…", where a real getComputedStyle(bar).color === '#16181D' assertion became two text regexes) and logged it as J14, but nothing records the wider blind spot.

What would settle the scope. A list of dom tests that read a sheet-provided value, and a decision per test: move to e2e, or assert the sheet text. The two tests above pass today only because the default equals the shipped token value.

F5

diamond()'s shipped default when allocates on a path the file declares zero-allocation

src/layout/items/variants.ts:317 · variants.ts:36–37 · src/data/fields/field-access.ts:179–190

when: (entry) => entry.duration()?.value === 0. measureEntryDuration returns a fresh { value, unit } object on every call. variants.ts:36 says of a VariantPredicate: "It runs on the hover path, so keep it cheap." I5 budgets zero allocation there. One object per row per resolve is the shipped default for core's own look. F6

A fixed box is never clamped, so fixedWidthItem(0) reopens the #212 unclickable-bar defect

src/layout/frame.ts:77–78 · src/layout/items/item.ts:121–126

barSpan returns width: entry.box.widthPx unmodified. The two neighbouring paths both guard: the plain path is Math.max(0, end - x), the narrow path floors at minBarWidthPx. fixedWidthItem(px) validates nothing, so fixedWidthItem(0) paints an invisible, ungrabbable bar and fixedWidthItem(-4) puts a negative width on the element. DEFAULT_MIN_BAR_WIDTH_PX's own doc says why 12px exists — "too thin to grab back by its resize handle". A fixed box skipping the floor is the ADR's decision; skipping Math.max(0, …) looks like an omission.

F7

The new boundary guard cannot tell the published specifier from a relative path, and the branch's own new e2e takes the relative one

.dependency-cruiser.cjs:105–119 · e2e/variant-styles.spec.ts:16 · docs/03-boundaries-and-config.md:42 · docs/04-hooks-and-ci.md §4.1

The rule is from ^(harness|e2e|fixtures)/ to ^src/ pathNot ^src/api/index\.ts$. dependency-cruiser sees resolved paths, and the freegantt alias resolves to src/api/index.ts — so the exception exists to let the alias through, and it lets a hand-written '../src/api/index.js' through with it. e2e/variant-styles.spec.ts:16 writes exactly that. Both docs state the rule as "never a relative path", which is stronger than what it enforces. Either an ESLint no-restricted-imports rule on the literal specifier closes it, or the docs should say what the guard actually catches.

harness/planner.ts (deleted checkpointDiamond, :186–:205 at the fixed point) · harness/planner.html (deleted .demo-checkpoint-label) · plans/shipped-variants/build/build-3…md unit G

F11

Public ResolvedVariant extends unexported DrawnVariant

etc/freegantt.api.md:1890 · src/layout/index.ts:19–29 · src/api/index.ts:364

The committed API report carries // Warning: (ae-forgotten-export) The symbol "DrawnVariant" needs to be exported. ResolvedVariant's two most-read members — name and items — therefore do not appear in the report at all, on the headline new public type of this ADR. Four such warnings already sit in the report, so this follows precedent rather than breaking it; the question is whether a type a consumer is told to call gantt.variantFor for should be the fifth. Exporting DrawnVariant, or inlining its two members into ResolvedVariant, both close it.
