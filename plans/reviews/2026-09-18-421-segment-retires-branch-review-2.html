New findings

bpF1naming · major · Confirmed

claim gains a row-packing sense in core — the exact word the user dislikes.

Sites (packing sense, all src/): layout/rows/row-source.ts:40-46 ("Claims a parent Entry") and :151-156 (PlannedRow.claimed?: boolean); layout/rows/entries-source.ts:2-3, :44 (compileClaim), :59/:62/:71 (claimedChildren, claimed: true), :88-111, :124-130, :149-165 (claimedChildrenOf); layout/bars/bar.ts:67-69, :168-174; layout/bars/produce-bars.ts:23, :52-54. Contrast sense 1 (variant selection, pre-existing): layout/bars/variants.ts:110,153-155,354-364; report code 'variant-claimed-twice' (model/error-report.ts:97); layout/entry-rule.ts:1-2,17,22.

One word, two meanings, one module. The variant sense read "a row's when has nothing else claiming it"; the packing sense read "this parent's children draw on its own row". A reader of entries-source.ts must hold both.

bpF2naming · major · Confirmed

unclaimedSpan ships a two-meaning identifier: its name is sense 1 ("nothing else claimed this row", see variants.ts:279-280), its doc and parameter are sense 2.

The doc at layout/bars/bar.ts:168-174 has to flag the collision in words: "'Claimed' here means childrenAsSegments (#421 C2)". That banner comment is the smell — a symbol whose doc must disambiguate its own name reads two ways in one call.

Two public types also share the word with different jobs: VariantRegistration.claim (variants.ts:155) and PlannedRow.claimed (row-source.ts:151). The Q26/Q27/Q33 design is fine; the vocabulary it chose is not.

bpF3naming · major-ish · Confirmed

The public BarProducer's third parameter childrenAsSegments?: boolean (layout/bars/bar.ts:71) is named for the feature, not for the fact the producer receives.

The boolean is computed row.claimed === true && id === row.entryIds[0] (produce-bars.ts:54) — the fact is "I am this row's claimed subject". So the very child the feature draws receives false (produce-bars.test.ts:176-180), and a differently-ordered custom row source silently flips the truth for every Entry (entries-source.ts:57-58, subject is positional). The name is plan-ruled (README C2) and is not wrong for the subject; it is wrong for the child, which is most of the call sites the feature creates.

bpF4coverage · hard spec · Confirmed

Branch exists at data/fields/field-access.ts:222-227 (children.length === 0 → own span). The only two 'children' tests (live-entry.test.ts:184, :196) both use parents with children. The gate line it proves would currently pass with the fallback deleted. ~5 minutes to add.
