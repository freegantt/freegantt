What landed well

Findings

High

F1 — data-reason now carries two vocabularies, and the documented consumer-styling selector silently changed meaning

Where. src/extensions/features/inline-editing.ts:367 (invalid editor stamps data-reason), :444 (refusal notice stamps it), :143-148 (CellEditorCommitRefusal), :127-133 (REFUSAL_TEXT), :430 (stale doc); src/view/styles.ts:298; src/extensions/features/inline-editing.test.ts:145-149.

What. Before this branch, data-reason meant one thing: a key of REFUSAL_TEXT, which is also the kebab-case code of the Error report the plugin raises, and which always has user-visible words. #160 stamps the same attribute with CellEditorCommitRefusal — 'unreadable-value' and 'refused-write' — which have no REFUSAL_TEXT entry, raise no report, and carry no words. One attribute, two disjoint vocabularies. CLAUDE.md's first hard rule is one meaning per word.

Concrete failure. inline-editing.ts:429-430 still tells a consumer that view/styles.ts styles .fg-cell-editor[data-state='invalid'][data-reason] "so a consumer stylesheet can still win". It no longer does — styles.ts:298 is now …[data-reason]:not(:has(.fg-cell-editor-control)). A consumer who followed that documented advice and wrote the old selector now paints the live editor with the notice's pointer-events: none, and the invalid editor becomes unclickable — including its new discard button. The stale sentence is the one that invited the mistake.

Smell. The test helper at inline-editing.test.ts:145-149 had to learn the identical :not(:has(…)) trick. When a stylesheet and a test both need the same structural workaround to tell two things apart, the two things want different names, not a cleverer selector.

Fix I would apply (not applied): give the notice its own class — fg-cell-notice — and keep .fg-cell-editor for things that hold a control. Both :not(:has(…)) sites and the stale doc sentence then delete themselves. If the shared class must stay, stamp the commit refusal on a second attribute (data-commit-refusal) so data-reason keeps answering exactly one question.

High

F2 — Escape and the discard button take two different roads to one job, and the comment claims otherwise

Where. src/extensions/features/inline-editing.ts:274 (Escape), :386-387 (button), :212-221 (the two ports), :597-603 (Escape's registration).

What. Escape binds bindEscape(() => this.#ports.requestDiscard()), which calls editing.discard() directly. The discard button binds runDiscardCommand(), which calls ctx.commands.run('freegantt.discardCellEdit'). Two ports (requestDiscard, runDiscardCommand) for one job — the second rule where one would do.

Concrete failure. :386-387 states "The command, not the method (D-S5-26): a consumer who overrides freegantt.discardCellEdit changes what this button does too." That is true of the button and false of Escape. A consumer who overrides the command to also clear their own side-panel form gets the override on click and not on Escape — two behaviours from one gesture pair, with nothing in the API saying so. :213-216 compounds it by calling requestDiscard "the same 'one implementation, two entry points' shape" — the shapes are not the same.

Fix I would apply (not applied): bind Escape through the command too, and delete requestDiscard. One port, runDiscardCommand, becomes the only road, D-S5-26's principle becomes true rather than claimed, and the comment stops needing a caveat. The one thing to check first is whether Escape must still close a valid editor when the command's when declines — it should not, since when is editing.editor !== undefined, which covers both.

Medium

F3 — the placeholder command's run is unreachable, and it costs a port, an implementation and a test

Where. src/view/core-commands.ts:150-156 (the registration), :45-49 (the port), src/view/gantt-shell.ts:1281-1283 (the implementation), src/view/core-commands.test.ts:162-169 (the test), src/extensions/commands.ts:63 (why it cannot fire).

What. The placeholder registers when: () => false and run: () => ports.discardCellEdit(). CommandRegistry.run returns before command.run(ctx) whenever when declines, and this when is a constant. So ports.discardCellEdit can never be called. The test at core-commands.test.ts:162-169 asserts exactly that — it proves the port is dead rather than proving behaviour.

Why it matters. Four artifacts across three files exist to service a call site that cannot be reached, and CoreCommandPorts grows a member every future reader must trace before learning it does nothing. The placeholder's real purpose is sound — without it, gantt.commands.run('freegantt.discardCellEdit') throws UnknownCommandError on a Gantt with no inlineEditing(). Only the plumbing is surplus.

Fix I would apply (not applied): run: () => {} inline at core-commands.ts:155, and delete the port, the shell implementation and the port half of the test. Keep the registration and the "the plugin overrides this" comment — those carry the design. The test's first assertion (the id never appears in available()) is worth keeping; the second (the port was not called) goes with the port.

Medium

F4 — InvertedSpanError names the wrong caller, names an id its author never wrote, and carries nothing a program can read

Where. src/model/errors.ts:186-191 (the class); src/data/entry-reader.ts:61, :129, :218 (the three throw sites); src/data/entry-reader.test.ts:479-493 (proof of the wrong caller).

Four separate faults, one error:

  1. Wrong caller. entry-reader.ts:218 says entries.update: "t1" would end before it starts. It is thrown from reconcileEnvelope, which reconcileExtenderEdits also calls — the branch's own test "refuses an inverted cascade against a sole-Segment Entry" proves it. A plugin author whose EditExtender cascade is wrong is told entries.update failed, a call they never made, and will look in the wrong place.
  2. Wrong subject. The same line sits inside for (const segment of next.segments) yet names the entry. Its sibling at :61 names the segment. One fault, two spellings, and neither names both halves.
  3. An id the author has never seen. :61 reports segment.id, which for a segment written without an id is whatever context.mintSegmentId() just minted. Feed it { id: 't1', segments: [{ start: '2026-09-05', end: '2026-09-01' }] } and the message names a synthetic id and omits t1 — the one identifier the consumer wrote and can search for.
  4. No values, and no members. The owner's rule (#237, plus the addition this session) is that an error says what distinguishes, not just that something is wrong. No InvertedSpanError message states the two instants. InvalidSnapIncrementError, landed in this same branch at errors.ts:35-48, does the opposite and does it well: it prints the offending value and exposes .unit/.increment as members. InvertedSpanError takes a bare message: string and carries nothing, so catch (e) { if (e instanceof InvertedSpanError) highlight(e.entryId) } is impossible. Two errors born in one branch, two shapes.

Concrete failure. A consumer bulk-loading 500 rows whose date parsing shifted a timezone gets entries: "t1" would end before it starts — no start, no end, no way to see that the two are one hour apart in the wrong direction, and no .entryId to drive a row highlight.

Fix I would apply (not applied): make the constructor structural, on the pattern InvalidSnapIncrementError already sets in the same file — constructor(entryId, span, segmentId?) — build the message from those (naming both the entry and, when it applies, the segment, and printing both instants), and expose them as readonly members. Then drop the caller name from the text, or pass it, so a cascade is not told it was an entries.update.

Medium

F5 — snap has two doors, only one is validated, and the harness picker #201 rewrote uses the other

Where. src/view/gantt-shell.ts:1188-1197 (the guard); src/api/gantt.ts:445-448 (the doc that calls the other door obsolete); harness/editing.ts:141-147; harness/gantt-toolbar.ts:217-220, 245.

What. #201's promise, in its own words at errors.ts:29-32, is that "the mistake names the assignment rather than the drag two gestures later". That holds for gantt.snap = … and not for gantt.preset = { …gantt.preset, snap }, which reaches #viewport.preset.snap unchecked. The time/ guard (snap.ts:15-19) still stops the hang, so this is not a freeze — it is the deferred-error experience #201 set out to delete, surviving on the second door.

Concrete failure, in this repo. harness/editing.ts:141-147 — the function #201 rewrote — sets snap through gantt.preset. src/api/gantt.ts:447-448 documents that exact spelling as "the old spelling" which "built a one-off copy of a shipped preset, and the next zoomIn() threw the snap away with it." So in harness/editing.html: pick Snap = day, zoom, and the choice is gone. The other harness picker, harness/gantt-toolbar.ts:245, uses gantt.snap. Two harness pickers, two doors, one of them the door the library documents as wrong — and CLAUDE.md makes reviewing the harness a standing duty precisely to catch this.

Second-order. The two pickers also disagree on what an unrecognised value does: editing.ts:145 returns and silently changes nothing; gantt-toolbar.ts:218 silently substitutes 'tick'. Both are guards over a <select> whose options the harness itself writes, so neither can fire — but they are two policies for one job in code the library holds up as its worked example.

Fix I would apply (not applied): move harness/editing.ts's applySnapChoice to gantt.snap = …, matching gantt-toolbar.ts. Separately, decide whether set preset should validate a concrete snap the same way set snap does — I lean yes, since a ViewPreset is public input and CLAUDE.md says input is loose on every way in, with the library doing the validating.

Low — transitional

F6 — the published API now has two names for one type, and the newer one has no doc

Where. src/model/entry.ts:105-110; etc/freegantt.api.md (the EntryEdits, StoredEdits, Dataset.extraEditsFor and EditRequest.proposed entries).

What. The report exports StoredEdits as @public with a doc comment, and EntryEdits as @public (undocumented). Both resolve to ReadonlyMap<EntryId, StoredEdit>. They meet in one signature pair — extraEditsFor(request: EditRequest): EntryEdits beside EditRequest.proposed: StoredEdits — where an app author has no way to learn that they are the same thing, or which one to write.

Why it is still worth saying. This is C1 scaffolding and C3 flips EntryEdits to the loose write shape, per the #209 handoff. It is reported only because it is on the published report today: if this branch merged as-is, the surface ships a silent alias. Nothing to do beyond landing C3 — but C3 must land before this reaches a consumer.

Low — unsure

F7 — available(ctx?) writes a contract only one implementation can honour

Where. src/api/command.ts:115-118; src/extensions/commands.ts:78-83.

What. The interface doc says omitting ctx makes "the registry build the same live context run(id) already builds internally." That is true of CommandRegistry, which holds a #buildContext the constructor was given. CommandRegistryOf is public, so anyone else implementing it must invent a context builder to satisfy a clause written from one implementation's internals.

Marked unsure. The app-author win is real and I would not trade it away. Whether CommandRegistryOf is meant as an implementable contract or only as the shape of the thing core hands out decides whether this matters at all, and I could not settle that from the code. Owner's call.

Naming verdicts

Each name read aloud at its real call site, per CLAUDE.md.

Name Read aloud Verdict
isTimeUnit "is value a time unit" Keep. Narrows, so it deletes casts instead of hiding them.
extraEditsFor "dataset, extra edits for this request" Keep. Names the job, not the pipeline, and consistent with commands.available()'s noun-phrase precedent. Reads slightly worse as an options field (new GanttShell({ extraEditsFor: … })) but not badly.
discard "editing, discard" Keep, and better than revert: nothing is restored, the edit is dropped.
InvalidSnapIncrementError — Keep. Specific, and the message prints the value that distinguishes.
InvertedSpanError — Name is right; the constructor is not (F4).
runDiscardCommand "ports, run discard command" Reject. Names the pipe — the command registry — not the job. CLAUDE.md: name the job, not the pipeline. The name disappears with the fix in F2; if the two ports must stay, discardEdit is the job's name.
CellEditorCommitRefusal — Reads fine on its own. The problem is that it and CellEditorRefusal share one DOM attribute (F1) — two types over one word.
StoredEdits — Keep. Plural of StoredEdit, and it says which side of the write shape it is.
