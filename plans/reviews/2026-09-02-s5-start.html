Deepening candidates

Make install() atomic

Strong in-process

src/extensions/plugin-runtime.ts, src/extensions/plugin-runtime.test.ts

Problem. D-S5-3's promise — a failed assignment leaves the previous plugin list alive — is broken by ordering: removals are disposed before additions are set up, so a setup() throw strands disposed-but-listed plugins whose disposers will fire twice.

Solution. Set additions up first (unwinding only the batch on failure leaves the old set untouched), dispose removals only after every setup() succeeded, commit the merged list last.

Before — dispose runs first

  participant R as PluginRuntime
  participant Old as removed plugin
  participant New as added plugin
  C->>R: install(next)
  R->>Old: dispose()
  Note over Old: gone
  R->>New: setup(ctx)
  New--xR: throws
  R->>C: PluginSetupError
  Note over R: #installed still lists Old — disposed, never re-alive

After — setup runs first

sequenceDiagram
  participant C as caller
  participant R as PluginRuntime
  participant Old as removed plugin
  participant New as added plugin
  C->>R: install(next)
  R->>New: setup(ctx)
  New--xR: throws
  R->>C: PluginSetupError
  Note over Old: untouched — previous list fully alive
  • locality: one ordering rule, one module
  • interface unchanged; implementation absorbs the fix
  • spec promise D-S5-3 becomes testable
  • disposers run at most once

One gate for every register*

Strong local-substitutable

src/extensions/plugin-runtime.ts, src/api/plugin.ts, src/view/gantt-shell.ts

Problem. D-S5-4 ("registration is legal during setup only") is enforced seam by seam by hand — and the commands seam already leaked: ctx.commands is the raw registry, so its register outlives setup. Every future register* (S5.4 renderers, S5.6 decorations, S5.7 columns) re-derives the same check or repeats the leak.

Solution. Deepen the registration seam inside the runtime: hand each plugin registration views whose register asserts the plugin's own gate, and stop exporting raw registrables on the context. The gate closes once, in install(), for every seam at once.

Fold popup Escape into the keymap

Worth exploring in-process

src/extensions/popup.ts, src/extensions/keymap.ts, src/view/gantt-shell.ts

Problem. Two keyboard-resolution mechanisms now coexist: the keymap (newest-first, editable-target aware) and popup's own capture-phase Escape stack on a module WeakMap — a second resolver that bypasses the editable-target rule and gives two Gantts registration-order-dependent Escape handling. The spec asked for the keymap path; newest-first already is innermost-wins.

Solution. On open, the popup registers { chord: 'Escape', command }/run-close through the keymap and unregisters on close; the LIFO stack, the WeakMap and the document listener disappear.

Top recommendation

One gate for every register* — with install() atomicity in the same pass.

Both live in plugin-runtime.ts, both are spec promises already broken once each, and the plugin seam is the foundation S5.4–S5.12 build on — every later register* either inherits the gate for free or copies the leak. The popup Escape and command-catalog moves are follow-ups, not prerequisites.

Second pass — ball of mud, API friendliness, self-documentation, extensibility

Re-read after the first review landed, with four questions: where could the mud pool, what reads awkwardly at the call site, what doesn't document itself, and what will S5.4–S5.12 hit first.

Ball-of-mud verdict, per area

  • plugin-runtime — healthy and deep. One interface, diff/unwind/gate semantics inside. Only fix: C1's ordering. The gate extension (C2) is what keeps it deep as S5.4–S5.9 add seams — without it, per-seam gate bookkeeping spreads back across gantt-shell.ts, and that is how this layer starts to mud.
  • popup — the main mud risk. Two keyboard-resolution mechanisms (keymap + escape stack), a document-wide scroll listener broader than its spec line, and a module-level WeakMap — three mechanisms where C3 needs one. The placement/flip/clamp math itself is clean and well-factored.
  • gantt-shell — divergent-change pressure. 19 commands + 8 default bindings + the S5 context builders now live inline; the shell is still the composition root, but every future command and every S5.5 menu hook edits it. C4 is the release valve.
  • api ↔ view ↔ extensions type binding — accepted knot, verified not emergent. The *Of<TGantt> generics, the ShellPlugin seam, and the two casts are one seam in each direction, and all four file headers (api/plugin.ts, api/command.ts, extensions/plugin-runtime.ts, extensions/commands.ts) explain the same cycle story. No action beyond C5 (publish the generics so the report can name them).
  • overlay / pane-layout — healthy. Structure-only pane layout holding; overlay is a thin adapter over it. Two naming unifications below.

API that could read friendlier at the call site

  • Overlay.present(HTMLElement) + Overlay.render(ElementDescription) is a two-step mount: a plugin with described content writes overlay.present(overlay.render(desc)). When S5.4 makes ElementDescription the renderer output, consider present(content: ElementDescription | HTMLElement) — one call, the reconciler seam stays hidden. Not a pre-S5.4 change.
  • plugins' id-diff semantics are correct but subtle: a same-id new instance is a silent no-op in production and a console warning in dev. That is the spec's chosen posture (D-S5-3) — keep it, but the GanttOptions.plugins doc should say "same id, new object → ignored (dev: warns)" in one sentence where the consumer reads it.
  • commands.run(id) silently no-ops when the command's when declines — spec posture ("a disabled menu item"), and the doc comment on the registry says so. The public Gantt.commands doc should carry the same sentence, since consumers read the alias, not the class.
  • Gantt.commands' public doc lists the eleven D-S5-6 commands; the shell registers nineteen (the eight navigation commands included). Either list all nineteen or state the rule ("freegantt.* is the core namespace; register order is overridden newest-first").

Self-documentation gaps (small, each one line)

  • createPopup hand-rolls an unsubscribers array while DisposableStore sits in the same layer — one disposal mechanism per layer reads better and deletes six lines. src/extensions/popup.ts:149–156
  • Keymap.resolve(event, commands, buildContext) carries the same two arguments on every call from the only caller — constructor injection turns it into resolve(event) and removes the clump. src/extensions/keymap.ts:107–111
  • Related: resolve evaluates command.when, then run() rebuilds the context and evaluates it again. Resolving to a command and running once removes the double work and the duplicated guard.
  • The Popup interface doesn't state that open() while open replaces the open popup (it calls close() first) — one sentence on open documents the contract.
  • buildElement(desc) — spell the parameter description; the abbreviation saves nothing in a 40-line file. src/render/dom/element-description.ts:13
  • attachKeyboardNavigation has zero production callers (verified by search) — still exported and tested. Fine to keep per the S5.2 TODO's own rule, but mark it in its header as superseded by the command bindings, or the next reader wires it back in.
  • The flip test's fixture cannot distinguish pane-clamping from container-clamping (pane.right === bounds.right, popup.test.ts:91–114) — give the timeline pane a right edge inside the container's so the test proves D-S5-8's pane rect, not the outer clamp.

Extensibility forward-check — what S5.4–S5.12 hits first

  • registerRenderer (S5.4), registerDecoration (S5.6), registerGridColumn (S5.7) all need the gate — C2 is load-bearing for the whole slice. Shipping each seam ungated, then gating later, is the path that turns PluginContext into an audit.
  • S5.8's cell editor needs Escape while an editable target has focus — today's document-capture Escape path ignores the editable-target rule, so the editor's Escape and the popup's will race. C3 fixes it by construction.
  • S5.5's context menu is available(ctx)'s first real consumer — the registry shape is ready; the double-evaluation note above is the only friction.
  • ElementDescription is positioned as the reconciler's one shape with buildElement as S5.4's diffing sibling's building block — correct placement in model/render.ts, no change needed.
  • DisposableStore after-dispose semantics (add → immediate dispose) make plugin teardown races safe — keep that guarantee when S5.10's DatasetPlugin reuses the store.
