Simplicity — SOLID, DDD, no ball of mud

S1 · “The three later stages are windowed” is over-stated for pack rows — D-S4-20 vs D-S4-26

Strong

Problem

D-S4-20 says resolve whole-dataset, then “Emit, pack and place for the windowed rows only.” D-S4-26 makes the height index's getHeight callback, for a pack row, emit and pack that row to read its lane count. The prefix-sum index must answer topAt for every row above the viewport, so pack rows are emitted from index 0 up, not just in the window. The two decisions are reconciled by the memo (“one emit-and-pack per row per revision”), but the literal wording of D-S4-20 is true only for 'fixed' rows. An implementer who takes D-S4-20 literally will window emission and stall the height index.

Fix (one sentence). Reword D-S4-20: “rows resolve whole-dataset; geometry placement is windowed; emission and packing are on-demand per row, forced by the height index for pack rows and memoized.” Say which passes are really windowed and which are forced.

Ordering truth

resolve (whole)
// height index needs every pack row above viewport:
getHeight(packRow) ──> emit + pack ──> laneCount
// then, in the window only:
emit + pack + place (visible rows)
topAt(index) = prefix-sum(getHeight 0..index)

Emission is forced twice for visible pack rows unless the memo guarantees once — it does, but the two decisions should say so together.

S2 · 'none' is a triple-loaded word

Worth exploring

Problem

'none' means three different things in this slice: (1) dataset rollUpKinds: 'none' — no Kind derives; (2) field rollUp: 'none' — this Field does not participate; (3) the shipped 'none' Aggregator — always returns undefined. D-S4-3, D-S4-6 and the foot-guns table disambiguate each, and each reading is locally correct. But a caller holding one word across three axes must hold all three distinctions, and an agent reading the spec must too.

Consider. It is defensible — verboten is a heavier hammer and these are genuinely the same “derive nothing from this” idea at three scopes. Keep it, but add one line to D-S4-3 stating the three are conscious homonyms with the same intent at different scopes, so a future editor does not “fix” one into a different word.

Three scopes, one word

rollUpKinds:'none'  // no Kind derives
rollUp:'none'       // this Field opts out
Aggregator:'none'   // always → undefined

Three readings, one intent (“derive nothing here”). Document the homonym instead of renaming any one of them.

S3 · 'matchOnly' filter policy and the three-occupant “proven seam” are the slice's mild speculative-generality

Worth exploring

Problem

D-S4-29 ships filterPolicy: 'keepAncestors' | 'matchOnly'; only the default has a box ([S4-A7]). G6 (parked) already asks whether S4.9 is over-specified. Separately, D-S4-21 ships a CustomRowSource with no acceptance box, justified as “a seam with one occupant is not a proven seam.” Both are cheap and each has a named consumer, but both are exactly the no-box surface the slice's own YAGNI discipline (I11: nothing unimplemented publicly; “no speculative generality”) exists to keep out.

Recommendation. Either keep them and add one acceptance line each in plans/03 §S4 (cheapest — makes them first-class), or cut 'matchOnly' and the custom source to S5. Do not leave a shipped knob with no box: an agent implementing the slice has no gate to prove it.

Shipped-but-unboxed in S4

filterPolicy:'matchOnly'  // no [S4-A*] box
source:'custom' resolve  // no [S4-A*] box
groupSort (deferred)     // correctly parked

Contrast with groupSort, which the spec rightly defers with a reason. These two lack the same treatment.

Caller ergonomics — easy to use, unambiguous

E1 · gridColumns object-form merge semantics are unspecified — the slice's most likely caller confusion

Strong

Problem

S4.3/ADR 0005 say a GridColumn object “overrides this Gantt's presentation.” A  { field: 'cost', header: 'Budget' }  object carries four presentation keys (header, width, flex, align). The spec never states the merge level: does an omitted width inherit the Field's declared column.width (per-key merge), or does the object replace the Field's column defaults wholesale? A caller who expects “keep the Field's currency alignment, just rename the header” and gets a bare cell is going to file a bug.

Fix (one sentence). Add to D-S4-12: “the object form merges per-key over the Field's column defaults; an omitted key inherits the Field's value.” Then cover it with one grid-columns.test.ts case (src/view/grid-columns.test.ts).

Merge level is the question

field.column = { width: 90, align:'end', header:'Cost' }
gantt: { field:'cost', header:'Budget' }
── ── ── merge? ── ── ──
A) { header:'Budget', width:90, align:'end' }  (per-key)
B) { header:'Budget' }             (replace)

A is the intuition ADR 0005's “overrides … presentation only” whispers; B is what “overrides” can be misread as. State it.

E2 · Locale binding (G3) is load-bearing for S4.9 but parked — sort and format disagree on whose locale

Strong

Problem

D-S4-13 as written binds formatValue to the Dataset's FieldContext. G3's recommended answer is to bind at column-resolve time with the Gantt's locale. S4.9 then says the default string sort uses localeCompare “with the Gantt's locale” — but the comparator runs in layout/rows/sort.ts, resolved from gantt.rows before/inside the Gantt-agnostic row pipeline. The spec never says how the locale reaches that code path (RowResolutionInput? on ResolvedColumn?).

Recommendation. Settle G3's recommended answer before S4.9 lands — not during implementation. Decide one place (ResolvedColumn is the natural carrier: it already holds the bound format closure, so put the bound default compare beside it) and write it into D-S4-13 and S4.9.

Who owns the locale today?

Dataset.FieldContext   timeZone, locale?
Gantt.locale         (S5-era)
◆ format (D-S4-13) → Dataset
◆ default sort (S4.9) → “Gantt's”

Two halves, two homes, one unresolved path into a headless row pass. Close it in the doc, not in code.

E3 · A grouping header shows blank cells in every column but the label (D-S4-23) is a silent product surprise

Worth exploring

Problem

D-S4-23: a Row.kind:'group' header fills column 0 with the groupBy label and “the rest are empty strings.” This is deliberate and architecturally right — D-S4-11 forbids view-side aggregates — but a caller who turns on { source:'group' } beside a cost column sees a header row with a team name and empty cells, expecting a per-team sum. Not a bug; a stated consequence that would read as a bug.

Recommendation. One foot-gun row (the table already has the right shape) and one line in the public surface: “group headers render the group label in column 0 and blank cells elsewhere; per-team aggregates are the caller's data (declare a computed Field or write through a group, D-S4-11).”

What the caller sees

Team A  │        │       │      
── framing │ 2026-10-01 │ 2026-10-10 │ $12,000
── roof    │ 2026-10-08 │ 2026-10-20 │ $9,400

Header “Block” cell is empty. Correct per D-S4-11; should be a documented, deliberate surprise.

E4 · Public constructor surface is large but each group is one concept — a strength, not a finding

Positive

The S4 call site adds rollUpKinds, hierarchy, fieldTypes, aggregators, fields to Dataset and gridColumns, rows (+ sub-keys), collapse to Gantt. That is twelve options, but every one maps to one concept and every one is optional with a sensible default (['name'], tree:false, 'fixed', autoGroup:false, rollUpKinds:['group']). The “one write shape, one knob” rule (plans/02 §1) is honored — 'none' is rollUpKinds, not a second option; sort/filter live on the row source, not on the Gantt (D-S4-28's rejection is a model example of the rule). This is the difference between surface area and complexity: the spec adds area, not coupling.

Extensibility & naming

X1 · Registered-name seams are cleanly extensible — the model to follow

Positive

Why it extends well

Three seams in this slice take the “registered name, never inline” shape: aggregators (name → function, so rollUp:'sum' serializes), fieldTypes (name → bundle), and ItemEmitter (kind → emitter with the span fallback). Each is open/closed: adding a value is registration, not a branch. The kind → emitter fallback (§2.5's graceful degradation) is the piece that keeps a consumer Kind working before S5 lands the four-seam story. D-S4-24's “no public registration, tests inject through an internal option” correctly clones S2's D-S2-6 posture and keeps I11 honest — no public key with no consumer.

The seam table (what a new thing does)

new Aggregator   → aggregators[name]
new Field type    → fieldTypes[name]
new Entry kind   → ItemEmitter (S5 registers)
new Grid column  → names a declared Field only
new row view     → a RowSource (S6+)

X2 · The Row.kind / Entry.kind collision is contained by a stated rule — but two names for the same glyph will keep asking for one

Worth exploring

Problem

D-S4-23 names two different things 'group' — an authored Entry.kind and a derived Row.kind. The spec handles it head-on with a two-row table, which is the right minimal response (CONTEXT.md already had a warning). But this is a genuine homonym that will keep confusing readers and agents forever after, and it is the exact failure mode CLAUDE.md's #7 example (#54, pane size) warns about — except this one was consciously chosen.

Consider. A PlannedRow.kind literal of 'group' is internal-only (README §5: PlannedRow is “not public”), so renaming the row-side literal to e.g. 'header' costs nothing public and removes the collision at the one place it bites (a grouping header “stands for no Entry”). Worth debating; if kept, the D-S4-23 table plus a CONTEXT.md cross-reference is enough.

Two 'group's, one glyph

Entry.kind === 'group'  → Row.kind 'entry'
Row.kind === 'group'   (by groupBy) → no Entry

The dart is D-S4-23's own table. If the row literal is internal, a rename is free and kills the homonym at source.

X3 · S5 handoff is precise — nothing this slice builds is orphaned by the next

Positive

The “what this slice is not” line (README) and the Deferred table route every seam to its future owner: registries open to PluginContext at S5, cellRenderer and column chrome at S5, drag-reparent waits on an authored order Field. The registries are built per-Gantt in S4 and registration moves to the plugin context at S5 — the spec says so explicitly, so S5 does not have to relitigate who owns them. weightedMeanByDuration ships as an Aggregator “because S7's Progress Field needs it,” a just-in-time justification that keeps it honest. This is the property that keeps the slice sequence from compounding into a ball of mud across slices, not just within one.

Top recommendations — in the order to do them

  1. E1 · State the gridColumns merge rule (one sentence in D-S4-12 + one test). The most likely real-caller confusion; cheapest to fix; zero architectural risk.
  2. E2 · Settle G3's recommended answer into D-S4-13 and S4.9 before S4.9 lands. It is load-bearing — a headless row pass has no obvious locale carrier today. Decide the carrier in the doc, not in code.
  3. S1 · Sharpen D-S4-20's “windowed” wording for pack rows. One sentence; prevents an implementer from stalling the height index. Pairs with E2 as “close the doc gaps” before implementation.
  4. S3 / X2 · Either give the two no-box shipped kinks (and the Row.kind 'group' literal) acceptance lines or trim them. Both are cheap; the point is nothing ships a knob with no gate.
  5. E3 · One foot-gun row for blank group-header cells + one public-surface line (S2's homonym note). Documentation polish; low effort, high reader/agent value.

Summary. 10 findings across three axes: 3 simplicity/SOLID/DDD, 4 caller ergonomics, 3 extensibility/naming — of which 2 are strong (E1, E2), 5 worth-exploring, 3 positive notes. The worst issue within each axis: simplicity — D-S4-20's over-stated “windowed” (an implementer trap); ergonomics — the undefined gridColumns merge (a caller bug waiting to happen); extensibility — the Row.kind 'group' homonym (a durable reader/agent confusion). No finding threatens the architecture; the two-context split and registered-name seams are the right spine. All three strong issues close with documentation sentences before any code ships.
