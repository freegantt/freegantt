F1

A hierarchy source that loops hangs the library inside an open transaction

BlockerADR 0020Reproduced

Files. src/data/live-entry.ts:125–135 (descendants()) · src/data/entry-store.ts:695–702 (#subtreeOf) · src/data/entry-store.ts:362–382 (#childrenOfWriteSet) · src/data/entry-store.ts:273–275 (#askSource) · src/data/entry-store.ts:250–261 (#depthOf, which does guard) · src/data/hierarchy-source.ts:41–70 · src/data/entry-tree.ts:57–59, 75–105 

flowchart LR
  subgraph C["committed read — checked"]
    A1["#byParent()"] --> A2["#parentById()"] --> A3["checkHierarchySource
breaks the cycle"]
  end
  subgraph T["open transaction — UNCHECKED"]
    B1["storedChildrenOf"] --> B2["#childrenOfWriteSet"] --> B3["#askSource
raw source, no check"]
  end
  B3 -.loops.-> B4["descendants() / #subtreeOf
no visited set"]
  classDef bad stroke:#dc2626,stroke-width:3px,fill:#fee2e2;
  class B3,B4 bad

The defect. The committed tree is checked once per revision: #parentById (entry-store.ts:216–219) runs checkHierarchySource, which drops the link that closes a loop. Inside an open transaction the store bypasses that index and asks the raw source through #askSource. Neither LiveEntry.descendants() nor EntryStore#subtreeOf carries a visited set, so a cyclic answer makes both walk forever.

Concrete failure. With harness/plugins/phase-hierarchy.ts's exact source — (next) => (entry) => entry.props.phaseId ?? next(entry) — this body never returns:

dataset.transaction(() => {
  dataset.entries.update('a', { phaseId: 'b' });
  dataset.entries.update('b', { phaseId: 'a' });
  dataset.entries.remove('a');          // #subtreeOf recurses forever
});

A throwaway test (written, run, deleted) proved it two ways. A bounded stand-in for descendants() — 50 steps of children() from 'a' inside that transaction — returned b,a,b,a,b,a,b,a… and would not have stopped. The unbounded form killed a 60-second vitest run at the timeout. The same two updates committed resolve fine (a.parent=b, b.parent=undefined, one hierarchy-cycle Fault), which pins the failure to the transaction path alone.

Reachability. Any data plugin that owns the tree, plus one consumer transaction that writes two rows into a loop. The library states this is a supported plugin shape (docs/adr/0020, harness/plugins/phase-hierarchy.ts), and CONTEXT.md's Hierarchy source entry promises "a chain that loops is broken at the link that closes it … neither throws". Inside a transaction neither half of that promise holds.

Fix. Give the two unbounded walks the seen: Set<EntryId> guard #depthOf (entry-store.ts:254–259) already has — it is the same file, three methods apart, and it already states the reasoning. LiveEntry.descendants() pushes only ids it has not seen; #subtreeOf takes a seen set through its recursion or becomes a worklist. Do not fix this by checking the source on every transaction read — entry-store.ts:263–265 already argues (correctly) that the in-transaction walk must stay O(chain).

Also, unguarded but not currently reachable. src/data/entry-tree.ts:75–105's depthOf and ancestorsOf are bare while loops. The file header at lines 57–59 states the contract ("Hand these a checked source … a chain that loops never terminates otherwise"), and the only caller (rollup.ts:106, 114) obeys it. Nothing in the signature does. A CheckedHierarchySource brand, or taking the ParentIndex directly instead of a function, would make the contract the type rather than a comment.

F2

A when field match on an undeclared key throws from the layout pass

BlockerADR 0018Reproduced

Files. src/layout/items/variants.ts:201–211 (valueMatches) · src/layout/items/variants.ts:38–40 (FieldMatch) · src/layout/items/variants.ts:31–33 (the doc that says an undeclared key is legal) · src/data/entry-store.ts:199–203 (the throw) · src/data/live-entry.ts:93–103, 190–192

The defect. FieldMatch carries { [key: string]: unknown }, so any key typechecks — deliberately, so a plugin may match on 'scheduling:progress'. valueMatches then calls entry.read(key) with no guard, and entry.read throws UnknownFieldError for a key no Field declares. A rule that should simply not match takes the frame down instead.

Concrete failure. Reproduced in a throwaway test (deleted):

registry.addConsumerVariant({ name: 'typo', when: { notAField: true }, paint: … });
registry.variantFor(entry);
// THREW UnknownFieldError: entry.read: there is no field called "notAField".

registry.addPluginVariant({ name: 'p', when: { 'scheduling:progress': 1 }, paint: … });
registry.variantFor(entry);
// THREW UnknownFieldError: entry.read: there is no field called "scheduling:progress".

Why this is a blocker, not a nit. Three reasons. First, variantFor runs on every row on every layout pass and on the hover path (variants.ts:25–26 says so), so the throw is a mount failure or a render failure, not a one-off. Second, the second case is the documented one: variants.ts:31–33 tells a plugin author to write exactly { 'demo:phaseId': true }, and BUILD-LOG.md J41 records "An undeclared key is accepted, and that is the ADR's own FieldKey arm, not a hole" — accepted by tsc, refused at runtime. Third, it is the one shape where a plugin cannot help itself: a chrome plugin installs after the Dataset's registration gate closes (harness/plugins.ts:36–38 states this), so it cannot declare the key it matches on.

Fix. Make a field match on an undeclared key answer false. valueMatches already looks the Field up (variants.ts:208): read that lookup first and return false when it is undefined, before touching entry.read. That is one reordered line and it costs nothing — the lookup already happens. Raising a one-per-Gantt Fault beside it ("a variant rule names x, and no Field declares it") keeps the typo visible without taking the frame down, and matches the posture ADR 0020 already took for a refused hierarchy answer.

F3

A variant's paint, items and can resolve by name, not by the rule that won

MajorADR 0018Reproduced

Files. src/layout/items/variants.ts:277–285 (registrationFor) · src/layout/items/variants.ts:290–314 · src/layout/items/variants.ts:247–255 (register, where items is defaulted) · src/layout/items/produce-items.ts:18–20 (resolveItems) · src/view/gantt-shell.ts #paintFor and #resolveCapabilities

The defect. variantFor(entry) returns a string. itemsFor, paintFor and interactionsFor then look that string up through registrationFor, which answers with the newest registration carrying that name — which need not be the registration whose rule actually answered yes. The file documents the round trip as intentional (variants.ts:274–276: "Two variants may share a name … the winner is the one that would also have claimed the row"). That sentence is not true: the winner is the one that ranks highest by name, regardless of its when.

Concrete failure. Reproduced in a throwaway test (deleted). Two consumer variants share the name 'x' and split the rows between them:

addConsumerVariant({ name: 'x', when: { a: 1 }, paint: () => ({ class: { P1: true } }) });
addConsumerVariant({ name: 'x', when: { a: 2 }, paint: () => ({ class: { P2: true } }) });
// row with a === 1
variantFor(entry)           // 'x'   — matched by the FIRST registration
paintFor('x')               // {"class":{"P2":true}}   — the SECOND registration's paint

The worse half is items. paint and can can answer undefined and fall through. items cannot: variants.ts:250 bakes wholeEntryItem in at registration when items is omitted. So a plugin that re-skins core's leaf — ctx.variants.add({ name: 'leaf', paint }), which the file's own comment at line 275 names as the expected case — silently replaces core's per-Segment produceLeafItems with one whole-span bar on every leaf row in the Gantt. A multi-Segment Entry loses every bar but one, and nothing reports it.

Related. gantt-shell.ts's #reportDoubleClaim dedupes on `${painted.variant}|${ignored.variant}` — a pair keyed by name — so two distinct registrations sharing one name collapse into one reported pair.

Fix. Stop the string round trip. Have the frame pass resolve a row to the registration, and read items/paint/can off that object; keep the name on it for data-variant and the command context. VariantItems (item.ts:31–34) becomes one member — resolveVariant(entry): ResolvedVariant — instead of two that must be composed in the right order at produce-items.ts:19. That also removes the two-call composition #resolveCapabilities writes today (interactionsFor(variantOf(entry))), which re-runs the whole rule walk once per canWrite call. If a full change is too large for this branch, the minimum honest fix is to refuse a duplicate name at registration inside one rank, the way RendererAlreadyRegisteredError already refuses a second claim on one renderer point — and to correct the comment at variants.ts:274–276, which currently states a guarantee the code does not keep.

F4

A consumer's own bad parentId is reported as by: 'plugin' with no plugin installed

MajorADR 0020Reproduced

Files. src/data/hierarchy-source.ts:51–63 (unknown-parent, by: 'plugin') · src/data/hierarchy-source.ts:94–103 (hierarchy-cycle, same) · plans/row-redesign/BUILD-LOG.md J54.

The defect. Both Faults hard-code by: 'plugin'. J54 justifies it: "core's own source reads a parentId that entries.update already checked, so a refused answer can only have come from a plugin." That reasoning misses the construction door. Nothing validates an authored parentId at ingest.

Concrete failure. Reproduced in a throwaway test (deleted). A Dataset with zero plugins:

new Dataset({ timeZone: 'UTC', entries: [{ id: 'a', name: 'A', parentId: 'nope' }] });
// Fault raised:
// { code: 'unknown-parent', by: 'plugin', entryId: 'a',
//   message: 'hierarchy: the source named "nope" as the parent of "a" …' }

A consumer who typed a parent id wrong in their own data is told a plugin did it, and the message says "the source" — a word an app author never meets, because api/dataset-plugin.ts:70–75 correctly calls setSource "an expert door. An app author never meets it." The Fault that a non-expert is most likely to hit is written entirely in the expert's vocabulary, and it names the wrong culprit. dataset.replay(changeSet) is a second door with the same shape: it applies with no validation by design (D-S2-14, CONTEXT.md Replay).

Fix. Two choices, and either closes it. (a) Track whether any plugin ever composed the seam — entry-store.ts:296–298's setHierarchySource is the one writer, so one boolean beside #hierarchySource answers it — and report by: 'consumer' when core's own source is still the only occupant. (b) Validate an authored parentId at ingest the way entries.add does (entry-store.ts:521–523), so the construction door stops producing an unknown parent at all. (a) is smaller and also fixes the replay door. Either way the message needs a second wording for the core case: name parentId, not "the source".

F5

The tree check runs inside an alien-signals computed, so a Fault reports only when something reads

MajorADR 0020

Files. src/data/entry-store.ts:216–219 · src/data/entry-store.ts:143–149, 174–176 · src/data/hierarchy-source.ts:41–45.

this.#parentById = computed(() => {
  this.#revision.get();
  return checkHierarchySource(this.#byId, this.#hierarchySource.get(), this.#raiseError);
});

The defect. A computed body is a pure derivation. This one performs a side effect: it fans a Fault out to the Dataset's error bus and, by default (entry-store.ts:184), to console.warn. That posture is new on this branch — no other computed in data/ reports anything — and it buys a guarantee the comment claims but the mechanism does not give.

Concrete consequence. The comment at lines 147–149 says "an unknown parent id and a cycle are each reported once per revision". A computed is lazy, so the true rule is once per evaluation, and only if somebody evaluates it. A Dataset with no Gantt bound — the headless case the layering exists to support, and the case a plugin's own tests run in — never reads #parentById unless the Rollup or a live row asks for the tree. So a plugin that answers with a parent id nothing holds can report nothing at all, for arbitrarily many commits, and then report every accumulated revision's worth at once the first time a row is read. The Rollup's own pass makes this worse rather than better: it calls checkHierarchySource with report omitted (rollup.ts:268–273), deliberately, so the commit path sees the broken tree and says nothing about it.

Second-order risk, not proven. The evaluation point is whatever the signal graph decides, which can be inside a change fan-out. data/ forbids mutation there (MutationDuringNotificationError), so a consumer handler that writes in response to a Fault would see an error whose origin is invisible from the stack. I did not construct this case; I am naming it as a hazard the posture creates, not as a reproduced failure.

Fix. Split the two jobs. Keep the computed a pure inversion — checkHierarchySource(entries, source) with no report, exactly the call the Rollup already makes. Raise the Faults from the commit path, where the revision actually moves and where ChangeSet notification order is already defined. That also answers the Rollup's one-revision-late problem the same way, in one place, instead of leaving one caller silent and one caller lazy.

F6

The Rollup now walks the whole dataset five times per commit

MediumD-S4-8

Files. src/data/rollup.ts:266–279 · src/data/entry-store.ts:216–219 (#parentById, already memoized).

The defect. Every commit now runs, before it reaches the touched set: buildEffectiveEntries (a whole-dataset Map copy, line 267), checkHierarchySource(committed, …) (line 271), checkHierarchySource(entries, …) (line 273), childIdsByParent(entries, …) (line 277) and childIdsByParent(committed, …) (line 278). Two of those five are new on this branch. D-S4-8 states the Rollup "walks the ancestor chains of touched entries only, deepest first" — it does, but only after five O(dataset) passes.

Why it matters here and not before. This is the drag-commit path. A parent-bar drag stages every dated descendant in one transaction, and this pass runs once over the whole Dataset regardless of how few rows moved. On a 5,000-row fixture (the size plans/01 §7 already fixtures for) a one-row nudge pays five full sweeps.

Fix. parentOfPrior (line 271) is the checked parent index over the committed map — which is exactly what the store's #parentById() already holds, memoized per revision. Pass that index in instead of recomputing it. That removes one of the two new passes for free and makes the store and the Rollup provably read one index rather than two computations that happen to agree. The second (parentOfEffective) is genuinely about a tree no revision holds, and has to stay.

F7

#assertParentValid still walks entry.parentId, not the hierarchy source

MediumADR 0020Body unchanged on this branch

Files. src/data/entry-store.ts:707–714 (body, unchanged by this branch) · call sites entry-store.ts:521–523, 544–546 · BUILD-LOG.md J54.

Every other tree read in the store moved onto the source. This one did not: the loop walks this.storedEntry(current)?.parentId. J54 defends it — "It guards a parentId write … and parentId is still stored and still written" — and as a write-shape guard that is coherent. Two things are still wrong at the seam. (a) An app author writing update(id, { parentId }) against a Dataset whose plugin ignores parentId gets ParentCycleError for a cycle in a tree the library never reads; and a parentId write that does make a cycle in the real tree passes. CONTEXT.md's Hierarchy entry lists "the tree is parentId" under Avoid; this guard still believes it. (b) The while (current !== undefined) loop carries no visited guard, so a stored parentId cycle — reachable through dataset.replay, which applies with no validation by design — hangs it. That is F1's family, in a method the branch did not touch.

Fix. Add the seen guard for (b) — same one-line shape as F1. For (a), either state in the ADR that ParentCycleError guards the stored field and not the tree (and say so in the error message, which currently says nothing about which tree), or move the guard onto the source. Do not do both halves silently.

V2 — stageUpdate's allocation on the drag-commit path

Verdict: not an I5 breach. It is the price of ADR 0020, and it should be recorded as accepted, not "fixed".

src/data/entry-store.ts:792–794 · entry-store.ts:756–759 (#recordStagedParent) · entry-store.ts:325–335 (storedEntry → entryAfterEdit) · entry-store.ts:101–111.

Why it is not I5. I5's hot path is hover, selection and drag preview. The preview reads entries.storedValues and entryAfterEdits (entry-tree.ts:42–55, written for exactly this) and stages nothing. One transaction per gesture, at commit, is the rule — so stageUpdate runs once per gesture, not once per rAF frame. The branch also removed a much larger per-frame cost on the same path: GanttShell#committedEntriesById, a whole-Dataset Map rebuild, is gone in favour of the store's own index (J20). Net, the drag path allocates less than it did on main.

What the cost really is. One entryAfterEdit copy per staged update, at pointerup. A parent-bar drag stages every dated descendant, so a 5,000-row subtree allocates 5,000 throwaway StoredEntry copies in one commit. That is real, and it is unavoidable under ADR 0020: the source reads a whole StoredEntry, because it may read any props key, so there is no way to ask it about a staged row without materialising that row. The alternative — asking only when the edit named parentId — is precisely V1's hole.

What I would change. Nothing in the code. One sentence in WriteSet.stagedParents' comment (entry-store.ts:101–111), which today explains why the filter exists and why it reads the source, but leaves a reader believing the source call is free. It costs one row copy per staged update. Say so, so the next person measuring the commit path starts from the truth.
