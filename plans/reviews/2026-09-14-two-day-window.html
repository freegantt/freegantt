F1 · resolvedTheme goes stale under the one case it was built for

Pass 2 · Confirmed Strong
in-process #330 · #271

src/view/gantt-shell.ts:546, 989–994, 1798, 1808–1822 · src/view/theme.ts:13, 26 · src/view/styles.ts:33–42 · CONTEXT.md:527 

flowchart LR
  subgraph triggers["What re-resolves the answer"]
    A["theme setter"] --> S["#syncResolvedTheme()"]
    B["OS matchMedia 'change'"] --> S
    C["ancestor writes data-fg-theme"]:::leak -.-> X["nothing"]:::leak
  end
  S --> F["#resolvedTheme (cached field)"]
  F --> G["get resolvedTheme()"]
  F --> E["emit themeChange"]
  classDef leak stroke:#dc2626,stroke-width:2px,color:#dc2626;

Problem. get resolvedTheme() returns the cached #resolvedTheme field (gantt-shell.ts:1808–1809). Only two things write it: the theme setter (1798) and the OS matchMedia listener (993–994). But resolveTheme resolves through container.closest('[data-fg-theme]') (theme.ts:13), and styles.ts:33–42 documents an ancestor pin as the supported consumer move — it is exactly what #271 fixed. A consumer who flips data-fg-theme on a wrapper gets new paint, a stale gantt.resolvedTheme, and no themeChange. The answer stays wrong until an unrelated theme write or OS flip happens to correct it.

Why it matters more than a missing event. A getter that is sometimes right is harder to use than one that is always computed. harness/planner.ts:246 already reads it as authoritative, and CONTEXT.md:527 promises "what theme resolved to right now, through the walk theme's own entry describes" — the walk includes ancestors, the cache does not.

Solution. Resolve in the getter (it is one closest() plus one matchMedia read, not a hot path), and keep the cached field only as the from value themeChange compares against. Or observe the ancestor pin with a MutationObserver and keep the cache honest. The first is smaller and cannot drift.

  • Getter stops lying under the documented case
  • One resolution path, no second copy to age
  • Locality: the walk lives in theme.ts alone

Pass 2 · Confirmed

Proved with a throwaway test, since deleted: with theme: 'auto', after wrapper.setAttribute('data-fg-theme','dark'), container.closest(…) answers dark, gantt.resolvedTheme still answers light, and zero themeChange events fired.

The proposed fix is incomplete. Resolving in the getter stops the getter lying, but themeChange still needs the cached field as its from, so an ancestor flip still fires no event. Closing the event half needs a MutationObserver — or a decision, recorded in CONTEXT.md, that themeChange deliberately does not cover the ancestor path.

F9 · lastWritten is never cleared, so one class of real user scroll is swallowed

Pass 2 · Wrong — struck

src/view/scroll-attachment.ts:25–65

Problem. writePosition sets lastWritten; nothing ever clears it. The new early return in onNativeScroll (lines 51–58) fires whenever the element is within 1px of that stored value, however old it is. So: the library writes position B; later the model target moves to C by some path that does not call writePosition; the user then drags the scrollbar to B. The genuine user scroll is read as the echo of a write that happened long ago, and the model never learns.

Why it may be harmless. If writePosition runs on every model change, lastWritten and the live target never diverge for long, and the pre-existing second check would have skipped the same event anyway. The fix for #131 is correct in its own frame; this is about the state it leaves behind.

What would settle it. A test that pans the model without a writePosition (if such a path exists), then dispatches a scroll at the stale lastWritten coordinates and asserts the model followed. If no such path exists, the finding is Wrong and the answer is one sentence in the comment saying writePosition runs on every model change.

Pass 2 · Wrong — struck by the verifier

No such path exists, so the premise fails. GanttShell.render() calls this.#scrollAttachment.writePosition() unconditionally (gantt-shell.ts:2219). Every viewport change reaches it: viewport.bind's onChange (771–778) calls #frames.request() for any scale, scroll, pane or content change, and FrameScheduler.request() coalesces to the next rAF and always runs render() (frame-scheduler.ts:20–27). The one suppressed path is #phase === 'constructing', which ends in a synchronous #frames.flush() (985) and during which lastWritten is still undefined, so the guard cannot fire.

So lastWritten is stale only within one animation frame — and during that frame the element still displays lastWritten, which means a scroll event reporting it there carries no information by construction. The scenario the finding describes needs the element to already sit elsewhere, and if it does, the first check passes and the model follows.

What is left. The finding's own stated criterion applies: one added sentence in the comment at scroll-attachment.ts:25–33 saying render() calls writePosition unconditionally. Not a queue item.
