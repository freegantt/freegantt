F1 · resolvedTheme goes stale under the one case it was built for

Strong
in-process #330 · #271

src/view/gantt-shell.ts:546, 989–994, 1798, 1808–1822 · src/view/theme.ts:13, 26 · src/view/styles.ts:33–42 · CONTEXT.md:527 

flowchart LR
  subgraph triggers["What re-resolves the answer"]
    A["theme setter"] --> S["#syncResolvedTheme()"]
    B["OS matchMedia 'change'"] --> S
    C["ancestor writes data-fg-theme"]:::leak -.-> X["nothing"]:::leak
  end
  S --> F["#resolvedTheme (cached field)"]
  F --> G["get resolvedTheme()"]
  F --> E["emit themeChange"]
  classDef leak stroke:#dc2626,stroke-width:2px,color:#dc2626;

Problem. get resolvedTheme() returns the cached #resolvedTheme field (gantt-shell.ts:1808–1809). Only two things write it: the theme setter (1798) and the OS matchMedia listener (993–994). But resolveTheme resolves through container.closest('[data-fg-theme]') (theme.ts:13), and styles.ts:33–42 documents an ancestor pin as the supported consumer move — it is exactly what #271 fixed. A consumer who flips data-fg-theme on a wrapper gets new paint, a stale gantt.resolvedTheme, and no themeChange. The answer stays wrong until an unrelated theme write or OS flip happens to correct it.

Why it matters more than a missing event. A getter that is sometimes right is harder to use than one that is always computed. harness/planner.ts:246 already reads it as authoritative, and CONTEXT.md:527 promises "what theme resolved to right now, through the walk theme's own entry describes" — the walk includes ancestors, the cache does not.

Solution. Resolve in the getter (it is one closest() plus one matchMedia read, not a hot path), and keep the cached field only as the from value themeChange compares against. Or observe the ancestor pin with a MutationObserver and keep the cache honest. The first is smaller and cannot drift.

  • Getter stops lying under the documented case
  • One resolution path, no second copy to age
  • Locality: the walk lives in theme.ts alone

F2 · A gesture core dropped reports 'entry-move-cancelled', and nobody cancelled it

Strong
in-process #272 · #273 · #341

src/view/gesture-pipeline.ts:410–411, 532–539 · src/data/error-reporting.ts:546–597 · src/model/error-report.ts:38–47

What a consumer reads now

code:     'entry-move-cancelled'
by:       'core'
severity: 'warning'
message:  "…was dropped: the rows it was
           measured from changed…"

The code says cancelled. The message says dropped. Only by separates them.

What the sibling case already does 

code:     'gesture-commit-failed'
by:       'plugin'
severity: 'error'
message:  "…broke while it saved…"

#reportCommitFault minted its own code for the same shape of problem.

Problem. #reportGestureDropped (gesture-pipeline.ts:532–539) passes refusal.code straight through, and refusal.code is fixed at 'entry-resize-cancelled' / 'entry-move-cancelled' when the gesture is built (410–411). All five GestureDroppedReason values land under that code — including 'data-changed', 'entry-gone' and 'write-refused', where no before* handler was involved at all. model/error-report.ts:38–40 files those two codes under the comment "A refusal core observed", which is now only true for some of their occurrences.

Why the by field is not the answer. The branch's own reasoning says so: buildCommitFaultReport could equally have reused the cancel code and leaned on by: 'plugin', and it did not — it took a code of its own, and error-report.ts:41–47 explains why. The same argument applies one line up. A switch (report.code) is the shape the union exists to support; asking it to also read by to know what happened is what #7 calls a generic word covering two concepts.

Solution. One code for the core-dropped family — 'gesture-dropped' — with GestureDroppedReason already carried on the report for the detail. refusal.code then stays what its name says: the code for an actual refusal.

  • Code names the event again
  • switch on .code stays sufficient
  • Matches the choice gesture-commit-failed already made

F3 · 'overlayOnTimeLine' / 'overlayOnGanttBody' name no glossary term

Strong
app-author surface #318 · #225

src/layout/date-line.ts:28–37 · src/api/gantt.ts:53–60, 171–178 · CONTEXT.md:448 · etc/freegantt.api.md (DateLineLabelPlacement)

The five checks

1 · Glossary term Fails. Gantt body appears nowhere in CONTEXT.md or plans/00–04. Time line as two words appears nowhere either. The region both values talk about has a glossary name already: the Header (.fg-header, Header bands).
2 · Read the call site Fails. gantt.dateLineLabelPlacement = 'overlayOnTimeLine' reads "place the label overlaying the time line". It means "inside the header bands". The sentence is false.
3 · Search test Weak. Searching timeline gives .fg-timeline-pane, timelineHost, the S1 spec — a lot of other things.
4 · One word, one meaning Fails, and CONTEXT.md says so out loud: the Date line entry (line 445) lists _Avoid_: Timeline (the pane, not the marker). This value spells it TimeLine and means neither.
5 · Category word last N/A — but note overlay carries no information here. Every placement of this label overlays something.

Solution. Name the two anchors in the words the glossary already has: 'inHeader' and 'belowHeader'. Read the call site — gantt.dateLineLabelPlacement = 'belowHeader' — and the sentence is true, the default is obvious, and the number arm reads as what it is, "px from the header's own top edge", which is what the docblock already says.

This is a public enum on the app-author surface and it has shipped to nobody. Changing it costs one rename; leaving it costs a glossary term with two meanings, forever.

F5 · Two internal-only codes autocomplete on the public surface

Worth exploring

src/model/errors.ts:22–34, 84–86 · src/data/fields/field-registry.ts:104–120 · src/layout/viewport/viewport.ts:96–100 · etc/freegantt.api.md (BuiltInThrownCode)

Problem. BuiltInThrownCode is published (@public in the API report) and is what an app author's switch (error.code) autocompletes against. Two of its 44 members have no class, and the union's own docblock says why: "Both report an internal invariant a consumer cannot reach, let alone act on, so neither earns a public class to catch." The same sentence is the argument for them not earning a place in the published union either — a code you cannot reach is a code you cannot handle, and it sits in the reader's autocomplete beside 42 they can.

The tension is real, and the branch chose deliberately. Leaving them out means satisfies BuiltInThrownCode stops covering those two new FreeGanttError(...) sites, which is the typo guard the whole change exists for. So the fix is not "delete them".

Solution. Split the union: InternalThrownCode (unpublished, what the two invariant sites satisfies) and BuiltInThrownCode (published, the 42 a consumer can catch), with the constructor taking ThrownCode | InternalThrownCode. The guard survives; the app-author surface loses two entries it cannot use.

  • Interface shrinks; the check stays
  • Published union means "you can catch this"

F7 · 'Parent (checked)' ships internal jargon to an end user

Worth exploring

src/data/fields/core-fields.ts:111–118 · docs/adr/0024-…md:29

Problem. A column.header is the string an end user reads at the top of a Grid column — not a comment, not a type name. An app author who puts 'hierarchyParentId' in gridColumns gets a column headed Parent (checked). Checked is this repo's word for checkHierarchyAnswers, the internal pass that validates a plugin-owned hierarchy source. It is not in CONTEXT.md as a user-facing word, and the parenthetical reads as a note-to-self that escaped into the product.

Solution. The header states what the column shows, not how core got it: 'Parent', with the stored-vs-tree distinction where it already lives — the Field docblock and ADR 0024. If both columns are on screen at once the pair is 'Parent' (tree) and 'Parent id' (stored), which is the distinction a user can act on.

ADR 0024 records this literal too (line 29), so the ADR follows the fix.

F8 · The harness still restates a library default "under protest" — and this window edited the protest

Worth exploring

harness/planner.html:58–68

/* NOT a page choice — 4px is the library's own default, restated here under protest.
   `.demo-bar-progress` below reads `var(--fg-bar-radius)` so its leading corners match the
   bar it sits in. A metric token is only declared on `.fg-container` for `--fg-indent-width`;
   the rest live as `var(--fg-x, default)` fallbacks inside library rules, so consumer CSS
   cannot read one back. Delete this line and the progress shading
   goes square in Light and Dark. The library should close this, not this page. */
--fg-bar-radius: 4px;

Problem. This is the stop rule's exact shape: harness code compensating for something src/ does not give it, and the comment says so. It is not new — but the branch touched these lines (removing --fg-lane-gap from the same sentence) and left the gap open, so it now sits unrecorded against this slice. CLAUDE.md asks that a gap found in harness/ be recorded against the current slice and closed in src/, not tidied in place.

The gap. A consumer's CSS cannot read back a metric token the library only publishes as a var(--fg-x, default) fallback inside its own rules. Any consumer styling a Part that must match a library metric hits this, not just the planner's progress shading.

Solution. Declare the metric tokens on .fg-container the way --fg-indent-width and --fg-bar-label-gap already are — they are px metrics, not colour, so #294's rule (a theme pin must never change a layout metric) is satisfied by keeping them out of the light/dark blocks, which is where they already sit. Then delete the protest.

Record as an API gap against the current slice, per the stop rule. Not a harness fix.

F9 · lastWritten is never cleared, so one class of real user scroll is swallowed

Speculative

src/view/scroll-attachment.ts:25–65

Problem. writePosition sets lastWritten; nothing ever clears it. The new early return in onNativeScroll (lines 51–58) fires whenever the element is within 1px of that stored value, however old it is. So: the library writes position B; later the model target moves to C by some path that does not call writePosition; the user then drags the scrollbar to B. The genuine user scroll is read as the echo of a write that happened long ago, and the model never learns.

Why it may be harmless. If writePosition runs on every model change, lastWritten and the live target never diverge for long, and the pre-existing second check would have skipped the same event anyway. The fix for #131 is correct in its own frame; this is about the state it leaves behind.

What would settle it. A test that pans the model without a writePosition (if such a path exists), then dispatches a scroll at the stale lastWritten coordinates and asserts the model followed. If no such path exists, the finding is Wrong and the answer is one sentence in the comment saying writePosition runs on every model change.

F10 · Three new definite-assignment assertions on GanttShell

Speculative

src/view/gantt-shell.ts:546, 550, 551, 989–994

Problem. #resolvedTheme!, #darkSchemeQuery! and #darkSchemeQueryListener! each tell the compiler to stop checking. All three are assigned at 989–994, the very last statements of the constructor before a11yLabel. #syncResolvedTheme() reads #resolvedTheme and is reachable from the theme setter (1798), which the constructor calls at 986 — before 991. On that path #resolvedTheme is undefined and the comparison at 1818 is against undefined, so themeChange fires from inside the constructor. The comment at 989–990 says the plain read at 991 exists precisely to avoid firing one there.

Why Speculative, not Strong. Nothing can have subscribed at construction time, so the emit reaches no handler and is invisible. It is the assertion hiding an ordering the comment believes is the other way round, not a user-visible bug. Moving the three assignments above line 986 removes both the ! and the question.

What would settle it. A throwaway test that constructs a Gantt with theme: 'dark' and asserts no themeChange emit occurred during construction. Delete it after.
