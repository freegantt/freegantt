API surface — six questions

Does an app author read the call site as the job it does? Yes: scroll: { x: sharedX } on two Gantts reads "these two share their horizontal scroll". The both-axes case the old API did implicitly is one object per direction. No new verb needed.

Does the branch add a knob or a hook an author must set for the default? No. Omitting scroll builds private axes; single-Gantt users never see the concept, just as with scale.

Same concept, one name? Almost — but the doc comment for scroll still says "its time axis" where the branch's own new public noun is "axis" (F3).

Loose on the way in, typed inside? Yes: plain ScrollAxis instances, one per direction; a Gantt built without them mints its own. ScrollAxisState is frozen (freeze(), so the D-S1.5-4 guarantee survives the rename).

One write shape? Yes — scroll is not a data write, so it stays outside EntryEdit; panTo/batch is the entire mutation surface, unchanged in spirit.

Illegal combinations unrepresentable? Sharing a direction by passing the same instance is the only link mechanism; the consumer owns the pairing. Nothing on this surface can half-share a direction.

F3 · "its time axis" next to the new public noun "axis"

Low · Naming

src/api/gantt.ts:95-98 · src/view/gantt-shell.ts:271-273

Problem. The rewritten scroll doc says: "pass the same ScrollAxis as x (or y) ... a Gantt may share its scroll position, its time axis, both, or neither." Three lines apart the word "axis" means a ScrollAxis, then means the shared TimeScaleModel. Two senses of one word in one comment, and the branch just made one of them a public class name. The invariant already owns the right term for the scale: "All pixels-from-time via TimeScale".

Why it is new. The phrase "time axis" predates the branch, but the branch rewrote the sentence that carries it and loaded "axis" as a scroll-direction term in the very same paragraph. Fix: "its scale, both, or neither". (Cited gantt-shell.ts:271-273 is the parallel doc, which says only "sync that direction ... omit a direction to keep it private" — the collision is gantt.ts's alone.)

Pass 2 — Confirmed.

Line 95 says "the same ScrollAxis as x (or y)" and line 97 says "its time axis, both, or neither" — the collision is real and lives entirely in gantt.ts:95-98. The gantt-shell.ts:271-273 parallel doc does not contain "time axis", so the finding's citation was clipped to gantt.ts.

F4 · Viewport.scroll wears the public config type for a live bound pair

Low · Simplicity / type design

src/layout/viewport/viewport.ts:66

readonly scroll: ScrollAxes & { readonly x: ScrollAxis; readonly y: ScrollAxis }. The runtime object is not the config record — it is the two bound axes, always both present — but its type is the public options shape plus an intersection promise. A reader decrypts ScrollAxes (optional record) to learn where this Gantt's live axes live. This is a Viewport-internal field; give it a shape that says "a bound pair", e.g. a BoundScrollPair = { x: ScrollAxis; y: ScrollAxis }, and keep ScrollAxes as the config entry, or make the two requirements part of one named type.

Pass 2 — Confirmed.

viewport.ts:66 is exactly readonly scroll: ScrollAxes & { readonly x: ScrollAxis; readonly y: ScrollAxis }. ScrollAxes (scroll-axis.ts:46-49) is the optional config record { x?: ScrollAxis; y?: ScrollAxis }; the runtime value is always-both (viewport.ts:89-92 freezes the pair). The internal field wears the public options type for a live bound pair, as described.
