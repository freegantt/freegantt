What this branch does

Landed clean

  • #264 part 1 — SHIPPED_FIELD_TYPES now seeds text, number, percent, date, duration. A Field naming one of those strings needs no local fieldTypes entry.
  • #264 part 2 — core name / start / end / duration name those types. end keeps its inclusive formatValue. parentId, segments, hierarchyParentId stay untyped.

API surface — six questions

Does an app author read the call site as the job it does? Yes for the type names and for the meter: { key: 'permitExpiry', type: 'date' }, { key: 'cost', type: currency({ code: 'EUR' }), rollUp: 'sum' }, { field: 'progress', cellRenderer: meterCell() }. No for a column of different images — F1.

Does the branch add a knob, a hook, or a handle an app author must set to get the default behaviour? No. Seeded types apply by name. meterCell() defaults text: true. imageCell is opt-in; requiring alt is the a11y answer, not a hidden default knob. Core Fields pick up types with no consumer declaration.

Can the code say what a comment says, and delete the comment? The long notes on no default rollUp, percent's divide-by-100, and currency as a factory are design history a signature cannot carry. Keep them. fieldWithoutInlineType's comment is the one the code almost says already — the function name is the job.

Does a new kind, field, or plugin extend through a seam, or does it need an if chain? Seam. New types join SHIPPED_FIELD_TYPES. Currency is a factory because a code is per-Field data. Cell renderers are factories on the column (D-S5-17). isDateField dropped its key special-case. writesSegmentEnvelope still names start/end by key — that door is the segment envelope, not the type table, and the comment says so.

Does the change move this code toward a ball of mud? Away. Core eats the type layer. The date editor routes on the type name. The planner stops re-implementing a meter. Two leftover leaks: the type-table override still rewrites core Fields (F2), and cell-renderer look lives in the always-on sheet (F6).

Is each new type and module SOLID, extensible, and easy to use? field-types.ts is one deep module behind a name table plus one factory. layout/cells.ts is one module for the two shipped paints. The Field.type union FieldTypeName | FieldType<TValue> is the price of inline currency; after merge a string stays and an object does not, which the glossary now states.

F1 · imageCell({ alt }) stamps one alt on every row

Strong · Spec / naming

src/layout/cells.ts:79–94 · src/model/field.ts:36–42 · issue #265 a11y section

Call site. imageCell({ alt: 'Owner' })({ fieldValue: url, value: 'Ada' }) Read aloud: "the image cell's alt is Owner." That sentence is false for a column of different people. Every row announces the same name. The renderer already receives value (the Field's formatted text) and does not use it:

export function imageCell(options: { alt: string }): ColumnCellRenderer {
  const { alt } = options;
  return ({ fieldValue }) => {
    if (typeof fieldValue !== 'string' || fieldValue === '') return undefined;
    return { tag: 'img', class: { 'fg-image-cell': true }, attrs: { src: fieldValue, alt } };
  };
}

Spec. #265: "alt carries the formatted value when [the cell] does not [also show text]." The "What to ship" line also wrote imageCell({ alt }), so the factory signature and the a11y rule disagree. The implementation kept the signature and dropped the rule. There is also no text-beside option, so the alt="" half of that same sentence has nothing to apply to.

Search test. A search for alt on this renderer finds the factory option, not the per-cell name a reader hears.

Fix shape (not verified). Default alt to value. Keep an optional static string for a column that really is one picture. The issue's own call site then reads cellRenderer: imageCell() — "the photo column's cell renderer is an image cell" — and the formatted caption is the alt.

F2 · Type-table override rewrites core Fields the Field door refuses

Worth exploring · API / architecture

src/data/fields/field-registry.ts:146, 167–175 · src/data/fields/core-fields.ts:52–70 · src/data/fields/field-registry.test.ts:298–307

Problem. After this branch, core start and end name type: 'date'. A consumer declaration { key: 'start', type: 'text' } throws IllegalCoreFieldOverrideError — type is not in CORE_FIELD_OVERRIDABLE_KEYS (['editable'] only). The same consumer can still write new FieldRegistry({ fieldTypes: { date: myBundle } }) and the constructor spread { ...SHIPPED_FIELD_TYPES, ...options.fieldTypes } silently replaces the bundle those core Fields merge. Format and compare of start/end change. The date editor still routes, because isDateField reads the string 'date' on the Field, not the bundle body.

Why it is new. The silent option-vs- registerType asymmetry already existed (the test at field-registry.test.ts:298 pins it for percent). It did not rewrite core Fields until core started naming the seeded keys. #264 said a consumer must not redeclare start/end/duration, and also said the table is "seeded before the consumer's option so a consumer can still override by name." Those two sentences now meet, and only one door is locked.

Deletion test. Deleting the silent override would concentrate the rule in one place: a shipped name is not replaceable at construction, same as registerType. Keeping it means core's "cannot redeclare" rule is a Field-key check only.

F5 · First consumer still hand-writes money instead of currency()

Worth exploring · Spec / stop rule

fixtures/demo-dataset.ts:131–163 · fixtures/hierarchy-dataset.ts:78–107 · src/data/fields/field-types.ts:132–149

#264's evidence was consumer code compensating for a missing type. After currency({ code: 'USD' }) ships, both gallery fixtures still declare:

fieldTypes: { money: { rollUp: 'sum', formatValue: (value, ctx) =>
  new Intl.NumberFormat(ctx.locale, { style: 'currency', currency: 'USD', maximumFractionDigits: 0 }).format(value), … } }

What the factory does not give them. maximumFractionDigits: 0, and a parseValue that strips currency signs. rollUp, editable, and column.header can sit on the Field. If the number input shows the stored number, the strip-signs parser is leftover from a text-shaped editor. If the 0-fraction format is the real gap, the factory has no parameter for it.

This is not a new workaround in harness/main.ts. It is the library's first consumer not eating the new factory. Same shape the stop rule exists to catch.

F6 · Cell-renderer look leaks into the always-on sheet

Worth exploring · Architecture

src/layout/cells.ts:1–7, 26–36 · src/view/styles.ts:376–384 · src/layout/items/variants.ts:100–110 · harness/planner.html:197–213

Before — variant (deep)

diamond() carries css. view/ wraps it in @layer freegantt. Look travels with the factory. A Gantt that never installs the variant never pays for its rules.

After — cell renderer (shallow)

ColumnCellRenderer has no css key. meterCell hard-codes .fg-meter* class names in layout/. The rules live in the always-on sheet. Every Gantt ships them. Planner then overrides those core classes to shrink the track.

The comments already name the constraint. It is not a functional bug: meterCell() needs no extra consumer CSS to look like a meter, which is the right default. The cost is locality: look is split across layout/cells.ts and view/styles.ts, and a consumer themes by fighting core class names (planner.html:197–213) instead of passing a fragment the way a variant does.
