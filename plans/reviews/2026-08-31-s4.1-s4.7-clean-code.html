Naming

N1 — “emit” has two meanings in the codebase

HARD

emitRow/emitSpan… and the file emit-items.ts use “emit” to mean produce layout Items. bus.emit() (data/event-bus.ts:52) and this.#events.emit() (view/gantt-shell.ts) use “emit” to mean fire a Gantt event. One word, two unrelated operations.

emitRow(planned, { entryById }, registry) // “emit row” ≠ fire an event

Call site read aloud: “emit the row” reads false against every other “emit” = “send an event”. A search for emit returns layout producers, the event bus, and its test doubles together.

Fix: rename the layout side to produceItemsForRow / produceSpanItems / ItemProducer and the file to produce-items.ts — or rename the event-bus method to fire. Either split works; do not keep both senses of “emit”. (CLAUDE.md naming rule #7 / #54 precedent.)

N2 — emit-items.ts exports emitRow while item-emitter.ts holds the registry

JUDGEMENT

Two files cover one concept — the item-production seam. A caller imports emitRow from emit-items and createItemEmitterRegistry from item-emitter. The split has no semantic reason today (the working tree already extracts Item/ItemEmitter into item.ts, which is the right shape — finish it: fold emitRow into the same seam).

N3 — partCountByEntry calls completed segments “parts”

JUDGEMENT

CONTEXT.md defines Segment. The emitter and a11y label are consistent with it, but partCountByEntry (frame.ts) and the a11y string “part N of M” introduce “part” as an undocumented synonym. segmentCountByEntry would keep one word. Minor.

N4 — segmentIndexOfItem doc example names the wrong type

JUDGEMENT

JSDoc reads “segmentIndexOfItem(bar.id)” but the call site passes an Item.id, not a FrameBar.id. The example points a reader at the wrong type.

Names that pass. PlannedRow vs public Row; RowResolutionInput/rowResolutionInput/resolveRows pair; RowHeightMode ('fixed'|'pack'); heightModeOf; DEFAULT_ROW_SOURCE; RowFilter/RowSort/FilterPolicy; CollapseState/CollapseChange (propose/commit); render-side barA11yLabel/barClassName/BAR_SHAPE_CLASS. Item vs Entry stay glossary-separate. These pass the five calls.

Standards (simplicity + SOLID)

St1 — ItemEmissionContext is speculative generality: no emitter reads it

HARD

All three shipped emitters declare ctx: ItemEmissionContext and ignore it (_ctx). emitRow already resolved the entry (emit-items.ts:18), so entryById on the context is dead through the whole public seam — it threads into the exported ItemEmitter type, the registry, and every signature.

Speculative Generality (Fowler ch.3) carried into a public contract. The deletion test: delete the parameter and nothing changes anywhere.

Fix: drop ctx (and the interface) now; re-add it only when an emitter genuinely needs a sibling lookup. A public seam that takes an always-empty argument is a lever every caller and agent must learn for no behaviour.

St2 — computeFrame’s “four stages” are prose, not seams

HARD

The spec (D-S4-19) and the code comment present resolve → emit → pack → place as named stages. In the code they are inline statements inside one coordinative loop (frame.ts): resolve (:231), emit (:273), pack (:274), then a single loop that interlocks bar and row construction (:288–305). Only leaf helpers are extracted.

Fix: extract placeRow(planned, items, …): { row, bars } so emit → pack → place become real functions with one reason to change. Small and low-risk; it is the difference between “reads as stages” and “is stages”, and the measured contract a test can hang on.

St3 — emitterFor silently falls back to span for an unknown Kind

JUDGEMENT

emitterFor(kind) returns emitSpan when nothing is registered (item-emitter.ts:28); the test asserts it never throws. This is OCP-correct and quiet, but it masks an authored unknown kind — a typo or a forgotten registration silently renders as a span bar with no diagnostic. That sits in tension with AGENTS.md §7 “conflicts become diagnostics; never silently rewrite”.

Fix (when S7’s diagnostics channel lands): throw for unregistered kinds, keep the span default only for the three shipped kinds; or expose has(kind). Flag for S7, not now.

St4 — emitRow’s optional registry default is a hidden per-call registry

JUDGEMENT

emitRow(row, ctx, registry = createItemEmitterRegistry()) (emit-items.ts:14): a caller who forgets the registry silently builds a per-call one — contradicting “one registry per Gantt, never module-level”. The shell always passes one. Make the registry required; let tests construct theirs explicitly. The default hides a real invariant.

St5 — three near-copy emitters (Duplicated Code)

JUDGEMENT

group-emitter and milestone-emitter (18 lines each) are near-copies of emitSpan’s no-segment branch, differing by one expression (end: entry.start vs end: entry.end). The per-kind split is spec-mandated (D-S4-24, replacable seams) so it stays; but the bodies could collapse to one parameterized producer plus a small kind→producer table, keeping the registry as the real OCP seam. Defer until St1 lands so the shape is proven.

St6 — PlannedRow.index is a dead placeholder

JUDGEMENT

All three sources write index: 0; stampIndex unconditionally overwrites it (resolve-rows.ts:26–28). The authored index: 0 is mystifying — drop it from construction and let stampIndex own the field. Also do a quick check of group-source.ts:29 (rowId('group:'+key)) and custom-source.ts:18 for RowId collision with consumer ids (Primitive Obsession) — a namespaced row-id constructor is cleaner.

Architecture — deepening candidates

Vocabulary: module / interface / implementation / depth / seam / adapter / leverage / locality. Candidates are for the final consolidated report; each shows what deepens and why.

A1 — Make the item seam the single Item producer module

STRONG

Files: layout/items/ (item.ts, item-emitter.ts, emit-items.ts, 3 emitters)

Problem: 6 files form one interface (a Kind → Items producer) with the type scattered from the registry and the row walk, and a `ctx` no consumer uses. Understand one concept → bounce across modules.

Solution: one seam ItemProducer (or produceItemsForRow) that owns type + registry + fallback, with the per-kind producers private; drop ItemEmissionContext.

Benefit: deeper seam (a caller learns one name), locality for the fallback rule, and one test surface. Deleting the split concentrates, not spreads.

A2 — Restore the four computeFrame stages as real functions

STRONG

Files: layout/frame.ts

Problem: resolve → emit → pack → place is prose over one interlocked loop; the row and its bars are placed together, so lane/height and geometry are not independently testable.

Solution: placeRow(planned, items, scale, …): { row, bars }; keep computeFrame as thin orchestration.

Benefit: locality (S4.8 packs lanes inside placeRow, not a growing loop), leverage (each stage’s test is one call), and a clear seam where S4.8 inserts packed height.

A3 — Commit-delimited transaction seam: one rollup importer today, growth guarded

WORTH EXPLORING

Files: data/transaction.ts (sole rollup importer, Q15), data/rollup.ts

Problem: the “transaction → extension hook → one changeset” invariant (AGENTS.md §6) is the deepest rule in the data core, but its enforcement point today is a single static import. As schedule() (S7) lands behind the same hook, keep the one-importer discipline explicit to avoid the hook becoming a second rollup path.

Solution: a named extension-hook adapter in data/ (identity when no plugin) so the hook is a real seam with one owner, not scattered call sites.

Benefit: locality for the single-write contract; a seam S7 fills. Worth exploring, not urgent.

Top recommendation for loop 2: A1 + St1 — collapse the 6 item files into one deep producer seam and drop the unused context. It is the newest code, still in the working tree, and the cheapest place to set the shape before S5 starts registering emitters from outside.
