What this branch got right

Recorded so a later reviewer does not re-open settled ground.

#158 is a root-cause fix, not a patch

The first attempt repositioned from a scroll listener and chased a paint that had already happened. The second mounts in the element the scroll already moves, and needs no listener at all. It is covered by a real browser e2e (e2e/editing.spec.ts:73) and two dom tests.

No dead code from the superseded attempt

cellInRow, findCell and the scroll-reposition path are gone; onScroll is back to a pure anchorage check.

R2's premise holds

registerWhileOpen and listenWhileInstalled factor twelve register/listen sites down to two shapes with no repetition. #158 added a seam through exactly that path, which is the working proof S5.10 needs.

The .fg-* read side is closed

No plugin and no harness page reads a .fg-* selector or a data-* key of the rendered Gantt. dom-contract.ts is the single owner, and gantt-dom.test.ts paints a real frame to assert the two still agree.

A6's column index is exact

#adoptColumns is the only writer of both the array and the map, and every mutation path routes through #bindColumns. The map cannot go stale on its own.

Lazy where it counts

DomOverlay.onResize observes lazily and disconnects at zero listeners. targetUnder's one-slot memo stamps item/entry/field, so a recycled row invalidates it and a scroll target returns before touching it.

S1

gantt.gridColumns changes meaning after the user's first column drag

API trap
src/view/column-chrome.ts:94–105, 111–130, 280–294 · src/view/gantt-shell.ts:836

The behaviour is deliberate and the comment at column-chrome.ts:70 states it exactly: plugin columns are appended by effectiveInput(), never stored, and "a plugin column reaches the getter only once a resize/reorder/plain assignment commits it". But follow what that means for the consumer:

t0
gantt.gridColumns → the 3 columns the consumer authored
t1
a plugin installs and registers 'risk' — getter unchanged, correctly
t2
the user drags any column edge → commit bakes effectiveInput() in
t3
gantt.gridColumns → 4 columns. One the consumer never authored.
t4
gantt.on('gridColumnsChange', ({ to }) => save(to.map((c) => c.field))) persists it

On the next load, without that plugin, the saved config authors a column for a field with nothing behind it. The round-trip in that last line is the documented pattern (plans/s5-extensibility-and-editing/handoff-s5.7-in-progress.md:58), and it is the natural thing an app author writes.

This was predicted. The S5.9 review wrote: "The unfriendly part is silent: gantt.gridColumns can grow a field the consumer never assigned, with no event that says 'a plugin column was adopted'. If adoption stays, raise gridColumnsChange with a from that the consumer actually authored, and say so on registerGridColumn." It is still open at HEAD: registerPluginColumn calls rebindFields() and requestFrame() and raises no event pair at all.

Fix, cheapest first. Mark a baked plugin column so the getter and the event payload can tell the two apart — the consumer then saves what they authored and the library re-adopts the rest. Failing that, do what the S5.9 review asked: say it on registerGridColumn's own doc, and give the event a from the consumer recognises. Either way this is a src/ fix, and CLAUDE.md's rule applies — the gap is real whether or not a lint fires.

S2

A registerKind() shorthand — checked, and correctly rejected

recorded, not raised

Defining one Kind takes four calls on four different groups, and the kind string is repeated four times. CLAUDE.md says "Common case is a shorthand; the long form is expert", so this pass tested whether ctx.registerKind(kind, { items, bar, defaults, commands }) is owed. It is not. The S5.9 review already ruled on it: "Do not add registerKind({ producer, renderer, defaults, commands }). D-S5-22 wants four seams so a plugin can fill one. The call sites already read as English."

Confirmed against the real call sites. harness/plugins/buffer-kind.ts and risk-kind.ts are four lines of registration, each answering the question written above it. A plugin that only wants a renderer writes one of the four and nothing else — which a bundled shorthand would tax.

Recorded here so a third review does not re-raise it a third time.

S3

The demo plugins are the branch's best self-documentation — make it the house style

pattern to copy

harness/plugins/buffer-kind.ts and risk-kind.ts label each registration with the question it answers — "What shape does it draw?", "How does it look?", "What can you do to it?", "What actions does it offer?" — so the four seams read as one story rather than four API calls. It is the clearest code on the branch and it cost four comments.

The contrast is src/view/gantt-shell.ts, where the same information is spread across ~50 fields and ~35 setter pairs and every comment explains a mechanism rather than a question. Candidate 2 is what closes that gap structurally; this pattern is what closes it in prose meanwhile.

Two caveats already filed against these files: Q8 (the module-level demoView stash in popup-demo.ts) and H1's comment-length rule, which the demo files themselves pass.
