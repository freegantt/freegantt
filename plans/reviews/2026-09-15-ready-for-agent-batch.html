F1 · ErrorReport.because fails its own naming test

Extra scrutiny — ungrilled API (#377)

src/model/error-report.ts:182 · src/data/error-reporting.ts:108,113,115,141–152 · src/view/gesture-pipeline.ts:149,537–540,614,617

Call site. dataset.on('error', (report) => { if (report.because === 'superseded') return; }); Read aloud: "if the report's because is superseded" — grammatically odd for a property read, because because is a conjunction, not a noun. Every other ErrorReport field name is a noun (reason, severity, code, entryId); this one is the sole exception.

Search test. because is one of the most common words in this codebase's own prose comments — a repo-wide grep for the bare word returns well over 150 hits, almost all of them the ordinary English conjunction, not this field. A reviewer or an IDE search for "every use of the gesture-dropped-reason field" gets buried in noise a scoped name would not produce.

One meaning per word. CLAUDE.md's ASD-STE100 rule ("every approved word has only one definition") is aimed at terminology, and because as ordinary prose glue is exempt from it — but promoting it to a field name on the most-subscribed public type in the library gives the word a second, code-level job it did not have before, right beside its first one.

Recommendation. droppedReason. It pairs directly with the already-chosen type name GestureDroppedReason (the field and its type read as one phrase, the same way rowSource: RowSource or theme: Theme do elsewhere in this API), it is unambiguous under grep, and the call site reads cleanly: if (report.droppedReason === 'superseded') return;. It also can't be confused with the existing reason?: string field (the free-text one), which was the documented reason a bare reason was rejected in the first place — that argument supports a distinct name, just not necessarily this one.

This is the exact API surface the issue flagged for a human call before code was written (#377's "two forks a human should call"), but the naming of the field itself was not one of the two forks listed — it was decided implicitly when the design was implemented. Worth a second look precisely because nobody looked yet.

F3 · The ancestor-pin MutationObserver watches the whole root, not just this Gantt's ancestors

Low severity · noted, not blocking

src/view/gantt-shell.ts:1004–1010 (constructor), :556 (field), :2268 (disconnect)

What it does. this.#themePinObserver.observe(this.#container.getRootNode(), { attributes: true, subtree: true, attributeFilter: ['data-fg-theme'] }) — subtree: true on the root node means this observer wakes on every data-fg-theme write anywhere in the document, including a second, unrelated Gantt's own container writing its own pin, not only a real ancestor of this container.

Cost. Each wake runs #syncResolvedTheme, which recomputes via container.closest('[data-fg-theme]') and correctly finds no change for an unrelated write — so this is wasted work, not a correctness bug. With N Gantt instances on one page, one instance's own theme write wakes all N observers. Given data-fg-theme writes are rare (a theme flip, not a per-frame event), the actual cost is negligible in realistic page sizes — this is a note for the record, not a fix request.

Why it is probably the right tradeoff anyway. MutationObserver has no native "observe only my ancestor chain" mode; scoping tighter would mean observing each ancestor element individually and re-subscribing on every re-parent, which is more moving parts for a write that happens on the order of once per theme toggle. Worth recording so a future reviewer does not rediscover this from scratch, not worth reopening #375 for.

M1 · A Gantt built detached and mounted afterwards never fires themeChange for an ancestor pin

New in pass 2 · real bug, fixed

src/view/gantt-shell.ts:1005 (constructor)

Found by pass 2, not pass 1. observe() binds to the node object getRootNode() returns at construction time. When a container is built inside a detached tree and the app appends that tree to the document afterwards — an ordinary mount pattern — the observer stays bound to the old detached root. A data-fg-theme write on any ancestor added later (document.body, a wrapper, html) sits outside the observed subtree, and no event fires — even though resolvedTheme (#375's own uncached getter) answers the new value correctly on read. Verified with a throwaway probe test (written, run, deleted): resolvedTheme = 'dark', themeChange events fired = 0, for a flip that genuinely moved the answer.

Why #375's own CONTEXT.md note doesn't cover this. That note excuses re-parenting the container ("no data-fg-theme attribute changed"). Here an attribute did change, on a real ancestor of the (now-attached) container — a different case than the one written down.

Fix, applied. Watch the container's document instead of the node captured at construction, when that node is a plain Element (an Node.ELEMENT_NODE) rather than a ShadowRoot (DOCUMENT_FRAGMENT_NODE) — a document-rooted observer already covers the common case and correctly still stops at a shadow boundary, matching closest()'s own behaviour. Pinned with a new test built from the pass-2 probe.

M2 · The #383 drift guard checks a dead fallback, not the value that ships

New in pass 2 · real gap, fixed

src/view/styles.ts:186–213 (METRIC_TOKENS) · test/guards/theming-contract.test.ts:166–174

Found by pass 2, not pass 1. Eight tokens (--fg-band-height, --fg-bar-radius, --fg-column-resizer-hit, --fg-cell-padding-inline, --fg-cell-padding-block, --fg-indent-width, --fg-ghost-opacity, --fg-pending-opacity) now carry two independent copies of the same number: the new :root declaration in METRIC_TOKENS, and the pre-existing var(--fg-x, literal) fallback inline in each library rule. Since :root now sets each property, the inline fallback is unreachable — the :root copy is the one that ships. But resolvePixelTokenDefault resolves a literal token as baseVarFallback.get(token) ?? baseDeclared.get(token), and baseDeclared can't contain these (the stylesheet source holds the METRIC_TOKENS placeholder, not the expanded declaration) — so the guard checks the dead fallback, not the live value. Changing METRIC_TOKENS's --fg-bar-radius to 6px and leaving the unreachable var(--fg-bar-radius, 4px) alone would ship 6px while the doc says 4px, and the guard would still pass — the exact drift class this guard exists to catch, opened by the PR that closed #157/#383.

Fix, applied. In resolvePixelTokenDefault, prefer metricDeclared.get(token) ahead of baseVarFallback, and add one assertion that for every token present in both maps, the two values agree — so a future drift between the :root declaration and an inline fallback fails loudly instead of shipping silently.
