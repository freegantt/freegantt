Standards

  • Contradicts precedent D-S3-7 · D-S1.10-2

    data-state tokens are claimed to be "generated from the carrier type's own keys, so a new key needs no render/dom edit". The cited precedent D-S1.10-2 grows tokens from BarFlags (via Object.keys, render/dom/index.ts:36). The proposed tokens are hovered selected dragging ghost pending — but D-S3-6's InteractionState keys are hoveredItemId, selectedItemIds, preview, cursorX, cursorLabel, pending. dragging and ghost are not among them, so the "own keys" derivation does not hold as written. State that the token set is a fixed projection of InteractionState, or add the missing keys.

  • Feature-envy seam D-S3-8 · D-S3-9 · I14

    D-S3-9 resolves capabilities in view/ so both interaction/ and the affordance side share one answer (I14). But D-S3-8 makes applyState (in render/dom, which may reach layout/ only) park handles on canResize and write cursor: grab on canMove. InteractionState has no per-item capability field — so the one-resolution promise either splits across two layers or the shell must push capabilities into the paint state. Name this seam explicitly: capability-bearing ItemPreview-style entries, or a resolved capability map the shell hands applyState.

  • Judgement call D-S3-2 · CONTEXT.md · CLAUDE.md #7

    Draft is proposed as a glossary term. CONTEXT.md's Write set entry lists _Avoid: Draft (implies a persisted intermediate state this isn't). Both are transient, so "one word, one meaning" (CLAUDE.md #7) is strained. The new entry must explicitly distinguish the gesture Draft from the transaction Write set — or the implementer conflates them.

  • Judgement call D-S3-15 · CONTEXT.md

    Cursor line is proposed as a glossary term. Both Date line and Today line carry _Avoid: cursor (the pane, not the marker). D-S3-15 already disambiguates ("never in a frame"); record that in the glossary entry so a reader does not mis-map it onto the Date line seam.

  • Scope widening D-S3-4 · plans/01 §1

    model/ is itself a public entry (src/model/index.ts already exports EntryEdit). Moving EntryEdits/StoredEdit in (D-S3-4) widens the published type surface. §4 says they "stay unexported from api/index.ts" — that is not sufficient. State the sealing rationale or accept the widening under I11.

  • Minor D-S3-4

    xForInstant/widthForDuration are TimeScale methods (src/time/scale.ts); only barSpan (src/layout/frame.ts:18) literally lives in layout/. D-S3-4's "an X-for-Y naming tradition already in layout/" is partly misattributed — tighten the wording so the implementer looks in the right home.

Spec

Originating source: plans/03-slices.md §S3 + D1–D12 + prior specs (s2-data-core, s1.13). Every [S3-A#] exists once in §6 with a host file; the six untagged acceptance items map 1:1 to A1–A6.

  • Layer-map violation D-S3-6 · I1

    ItemPreview is placed in src/render/backend.ts (D-S3-6), yet layout/gesture-draft.ts's previewOffsets returns it (D-S3-4). layout/ may not import render/ (plans/01 §1). ItemPreview must move to model/ the way EntryEdits does — same step, D-S3-4.

  • Layer-map violation D-S3-15 · plans/01 §1

    The cursor-label string is "composed in view/" via time/'s formatDate. But the layer map gives view/ only REN/LAY/DATA arrows — no time/. The a11yLabel precedent (S1.10) composes date text in layout/. Compose the cursor label in layout/, which can reach time/.

  • Acceptance gap plans/03 §S3 · D-S3-13

    §S3 asks "Keyboard parity begins" and "Enter/Escape semantics". D-S3-13 reduces Enter to "no-op in S3", and there is no [S3-A#] accepting arrow-nudge (U9) — only A5 covers the refusal half. Keyboard parity has no acceptance box.

  • Reconcile plans/03 §S3 A1 · D-S3-10

    A1's "exactly one transaction" includes selection, but D-S3-10 makes selection Gantt state with no Dataset write. The spec never reconciles these — A1's test bullet just logs selection. Say explicitly: selection is a Gantt write, not a transaction(), and A1 covers only move/resize.

  • Status inconsistency plans/03 · spec header

    plans/03:142 still lists "the EditExtender install seam" as an open prerequisite of §S3, while the spec header says "P1 closed on 2026-08-29" and §0 counts "two prerequisites remain". Align: the editExtender internal seam is settled; only P2 (S1.13) and P3 (the INT → MODEL arrow) remain.

  • Wrong precedent cited §6 · S3.6 · [S2-A1]

    S3.6 and [S3-A6] cite [S2-A1] as the "injected-extender" precedent ("as [S2-A1] already does"). But plans/03:82 says [S2-A1] runs with the identity extender. D-S2-6 sanctions the internal-option route — cite that, not [S2-A1].

Simplify

  • Overbuilt D-S3-5 · EntryGestureContext

    Twelve methods is a wide surface and the move/resize pair repeats: draftMove/commitMove/draftResize/commitResize differ only by an edge and an event name. entryFor/entriesForGesture/selection overlap, and previewDraft/hover/cursorAt are three sibling paint-writes. Consider a narrower seam: { entryFor, can(gesture, entry), draftFor(kind, entries, byPx, edge?), preview(draft), commit(draft, edge?), paint({hover, cursorX, cursorLabel}), selection } — roughly 8 instead of 12, killing the duplicated pair.

  • Concept clash D-S3-6 · InteractionState

    One struct mixes three lifecycles: hover/selection paint (recomputed per pointer move, I5), gesture preview (preview/cursorX/cursorLabel, only during a drag), and pending — an async-veto mode gate, not a per-pixel value. Split pending into the gesture machinery (a value the shell owns beside the draft), leaving InteractionState pure paint. The shared handle pair (D-S3-8) and single draft shape (D-S3-2/18) are the deep calls to keep.

  • Repeated switch D-S3-9/13/22

    The move/resize/select triplet recurs four times: events (D-S3-22), capabilities (D-S3-9), context methods (D-S3-5), keyboard map (D-S3-13). D-S3-9's capability table already drives handles+cursor — drive the keyboard rows from it too (a capability → keybinding map) so the third and fourth restatements read off the first instead of re-encoding it.

  • Slice-bloat to watch D-S3-14/15/17

    22 decisions is heavy for a slice. Wheel/keyboard pan (D-S3-14) and the cursor line (D-S3-15) are S1-viewport / S1.13 concerns pulled in — the cursor line is not "direct manipulation of entries". Not obesity, but be ready to split the viewport family into its own step if S3 front-loads.

Top recommendation

Candidate 1 first — deepen EntryGestureContext before S3.3 writes code

It is the earliest decision (D-S3-5), the widest seam, and the one that forces the most follow-on names (context methods, event pairs, keyboard rows, capabilities). Collapsing the move/resize pair onto one parameterized Gesture and folding the paint-writes together shrinks the surface before any of the other candidates — #2's pending split and #3's capability carrier are natural to land in the same pass, and #4 is a two-line home fix. Fix the plan's data-state token story (Standards 1) and the ItemPreview/cursor-label layer breaches (Spec 1–2) as you go. The originating acceptance list and P1/P3 shape are sound.
