D1 · fixed

rowSource is not live for the tree keyboard

src/view/gantt-shell.ts:450–455 spreads tryTreeArrow / expandAllRows into gestureContext only when #treeKeyboardEnabled() is true — evaluated once, in the constructor. The rowSource setter (:519) invalidates rows and requests a frame; it never rebuilds the context.

constructed with tree:false → tryTreeArrow present? false
after rowSource = tree:true → tryTreeArrow present? false

Breaks plans/02: “Every config key is live-reconfigurable.” Also the mirror case — constructing with tree: true then switching to { source: 'group' } leaves the arrows live on rows that are not a tree.

Fix: always install both handlers. TreeCollapse.handleArrow already returns false when the focused row is not expandable — that is the real question, and it is asked of the resolved rows rather than of the config discriminant.

D2 · reproduced

filterPolicy: 'matchOnly' + collapse paints a twisty that hides nothing

src/layout/rows/filter.ts:53 flattens depth to 0 under matchOnly but leaves expandable: true. src/layout/rows/collapse.ts:18–28 hides descendants purely by depth. With every row at depth 0, nothing is a descendant.

resolveRows({ tree: true, filterPolicy: 'matchOnly', filter: () => true }, collapsed: ['a'])
→ a: expandable:true, expanded:false, depth 0
→ b: expandable:true, depth 0    // still visible
→ c: expandable:false, depth 0    // still visible

Fix: decide matchOnly's contract once — a flattened row is not a tree row, so clearing depth must also clear expandable. Candidate A1 is where that contract should live.

D3 · reproduced

A one-segment entry cannot be dragged — the commit throws

Two guards disagree on what “has segments” means. src/layout/gesture-draft.ts:112 — usesSegmentEdit requires segments.length > 1, so a one-segment entry drafts { start, end }. src/data/entry-reader.ts:106 refuses that write for segments.length > 0.

1 segment → SegmentsOutOfSyncError: entries.update: "t1" has segments — write segments, not start/end alone
2 segments → SegmentsOutOfSyncError   // correct: draft writes segments

Spec s4.10 D-S4-30 states the store rule in terms of “an entry that has Segments”, so the drafting side is the half that is wrong. The store's guard also fires for every other selected segmented entry in a multi-selection drag, which D-S4-30 says must move as a whole span. attemptMutation only catches MutationCancelledError, so this escapes a pointer handler.

Fix: usesSegmentEdit fires on segments !== undefined && length > 0, with index defaulting to 0 for a non-grabbed entry.

src/view/tree-collapse.ts:142 asks String(current.parentId) === candidateRowId. Four shallow modules whose composition nobody owns and no test covers.

  • a fourth source stops needing five conditionals
  • fixes D2; retires C3, C6, C7

Deletion test: deleting filter.ts/sort.ts/collapse.ts as files concentrates complexity in resolve-rows.ts, where it belongs. Concentrates.

Worth exploring API gap

Hand the row-source callbacks a field reader

src/layout/rows/row-source.ts · harness/main.ts · harness/hierarchy.ts

Today — the consumer writes this, twice

function teamOf(entry: Entry) {
  const meta = entry.meta;
  if (typeof meta !== 'object' || meta === null)
    return undefined;
  const team = (meta as { team?: unknown }).team;
  return typeof team === 'string' ? team : undefined;
}

rowSource = { source: 'group',
  groupBy: (e) => teamOf(e) ?? 'unassigned' };

Published call site

rowSource = { source: 'group',
  groupBy: (e, fields) =>
    fields.read<string>(e, 'team') ?? 'unassigned' };

rowSource = { source: 'entries', tree: true,
  filter: (e, fields) =>
    fields.read(e, 'team') === 'core' };

FieldContext already exists, is already bound per Gantt, and already routes entry, meta and compute Fields through one call.

Problem

RowFilter, groupBy and RowSort.compare hand out a bare Entry. Every consumer that declared a meta Field must then unpack meta by hand — which is what CONTEXT.md says a Field exists to prevent, and what the harness proves twice.

Solution

Pass the bound reader as a second argument. Existing one-argument callbacks keep working — JS ignores an argument a callback never declares, the same precedent runTransaction's TxToken already sets.

Wins

  • closes the S4 harness gap in src/, not in the harness
  • consumer Fields and core Fields take one code path at the call site too
  • compute Fields become filterable and groupable
  • no breaking change; the long form stays available

Second pass · added after the first report was committed

Ball of mud, friendlier API, self-documentation, extensibility

A fresh look, not a re-run: where does this codebase turn into a ball of mud, which parts of the API are less friendly than they could be, which names still need a comment to be understood, and what does it actually cost to extend each seam.

1 · Ball-of-mud pressure — the six-edit ritual

The layering holds. Dependency-cruiser enforces it and nothing crosses a line it should not. The pressure is not on the layers; it is on the ritual for publishing one concept, which no compiler checks.

Proof the ritual gets missed: the API report carries four ae-forgotten-export warnings — RollUpKinds, TimeScale, GanttOptionsBase, GanttScaleOptions. Each is a type a consumer meets in a signature and cannot name. They are warnings, so pnpm verify stays green.

What would relieve it

  • Fail the build on ae-forgotten-export. One line of api-extractor config turns the silent half of the ritual into a red test. Cheapest fix in this report, and it closes SP2 permanently rather than once.
  • Keep extracting stateful clusters from the shell — A3 and A6 above. The shell should be wiring; every job that has a rule of its own belongs in a module, the way TreeCollapse and GesturePipeline already are. C4 already established the pattern and closed itself out; the discipline is what stops S5's plugin attach points landing back in the same file.
  • Curate the barrels rather than growing them. See §3 — several exports are internals that arrived by forwarding rather than by decision.

Self-documentation — the comments are load-bearing

Comment density runs 17–30% in the S4 files, and the comments are good: they carry decision ids and the reason a thing is the way it is. That is the right use of a comment. But two patterns show a name doing too little work:

  • row-source.ts:67 — a six-line comment explains that PLANNED_ROW_KIND exists to satisfy a lint rule. When the comment's subject is the linter rather than the domain, delete the construct (C12).
  • gantt-shell.ts:216 — setOptional needs eight lines to explain exactOptionalPropertyTypes. The rule is real; the name says nothing. clearOrSet(target, key, value) states the two branches.
  • transaction.ts:43 — writeCommittedFieldRows introduces “Field row”, a noun the glossary does not define. The thing is a FieldUpdated[], the changeset's own updated shape. Either glossary the term or name it for what it is.

3 · A friendlier public surface

127 exported names. The consumer-facing shape is genuinely good — loose input everywhere (string ids, InstantInput dates), branded output, live setters, a cancelable before* for every mutation, and MS / addMs so a consumer does day maths without magic constants. Three things would make it friendlier.

Needed, not nameable

RollUpKinds · TimeScale · GanttOptionsBase · GanttScaleOptions

All four appear in public signatures. A consumer writing function setKinds(k: ???) has no type to write. Fix with SP2 plus the build-fails-on-warning change in §1.

Public by forwarding, not by decision

ClientPoint · AsyncCancelableEvent · EntityAdded · EntityRemoved · StoreName

None appears in docs/05-consumer-api.md or the harness. ClientPoint is structurally identical to Point, so it teaches a distinction the type system does not make (C14). Each is a name a consumer must read past.

Holding well

“Two callers, two surfaces” holds: overscan, backend, editExtender and itemProducerRegistry are on GanttShellOptions and deliberately not on GanttOptions. Illegal combinations are unrepresentable — scale vs preset/range/fit is a discriminated union, not a runtime warning.

The one call site that still reads badly

A5 above is the biggest friendliness win — a consumer who declared a Field should not unpack entry.meta to filter on it. Behind it, the same asymmetry runs through the whole S4 surface: the Gantt takes Field keys everywhere except in the three callbacks where it hands back a raw Entry. Closing that closes the harness gap, the duplication in two demo pages, and the “compute Fields cannot be filtered or grouped” hole in one change.

4 · Extensibility scorecard

CLAUDE.md names four seams for per-kind behaviour: policy, item emitter, renderer registry, capability resolver. Two are open. Two hardcode. That is the crisp statement of where this design is closed to extension today.

Second-pass verdict

This is not a ball of mud and it is not trending into one. The layers are enforced, the vocabulary is deliberate, decisions are recorded next to the code that implements them, and C4 shows the team already extracting from the shell rather than letting it grow — the parked items in that plan were parked with reasons, not forgotten.

The real risk is narrower and worth naming plainly: S4 added several tagged unions (RowSource, FieldSource, EntryKind) and dispatched on their tags with if-chains instead of tables. Each chain is small and readable today. S5 adds a plugin runtime on top of all three at once. That is when six small chains across five files become the thing nobody wants to touch — and A1, A4 and the two closed seams in §4 are all the same fix applied in different places. Do them while each is still three conditionals.
