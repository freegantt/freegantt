Findings

F1message quality · minor · Confirmed

The new fault reads “null is null.” NULL_VALUE begins “is null.”, and invalid() prefixes the printed value — for null that value is String(null) === "null". The tautology is the first thing the reader sees, on a branch whose whole purpose is message quality.

src/time/input.ts:50-51 (reason), 62-64 (prefix) · src/api/dataset.test.ts:147

probe: toInstant('America/Chicago', null, 'construction')
  -> "construction: null is null. An Entry with no span of its own omits the property instead — …"

Fix: make the reason read as a predicate over the value, e.g. 'names no instant. An Entry … omits the property instead …', so the sentence becomes “null names no instant…”.

F2comment accuracy · nit · Confirmed

The doc comment above the reason constants still says “Three of the four faults below end with this sentence.” The change left five reason constants below it — UNREADABLE, NO_SUCH_DATE, NOT_FINITE, NULL_VALUE, NOT_A_DATE_VALUE — three of which append WRITE_A_DATE. The count is stale.

src/time/input.ts:41

Fix: “Three of the five faults below…”.

F3naming · simplicity · minor · Confirmed

NOT_A_DATE_VALUE (“is not a date value. Write an ISO date…”) is a second name for the job UNREADABLE already does (“is not a date this library reads. Write an ISO date…”). Both live in the same file, are read in the same function, and differ only in five words of preamble. A boolean or an object is covered by UNREADABLE just as well.

src/time/input.ts:43, 54, 143

Fix: reuse UNREADABLE in the final throw and delete NOT_A_DATE_VALUE; F2’s count also settles to “three of four”.

F4API · message scope · judgement · Confirmed

NULL_VALUE tells the reader “An Entry with no span of its own omits the property instead.” But time/toInstant is not an Entry-only seam. Its internal callers include gantt.todayLine, gantt.dateLines, zoomToSpan and panToDate (which hands to the shell's panToInstant). A null there now receives Entry advice that names a concept the caller never touched.

src/time/input.ts:50-51 · src/api/gantt.ts:392, 399, 406, 865, 871

Options: keep the Entry wording and accept that toInstant is Entry-facing in practice; or split the reason so the generic layer says only “names no instant — pass a date or omit the property”, leaving Entry-specific guidance in entry-reader.

F5types · minor · Confirmed

invalid(input: InstantInput, …) declares an InstantInput, but the new fall-through hands it a boolean or a plain object at runtime, and null is outside InstantInput too. The function’s job is to format any rejected value — the error it builds already stores value?: unknown (InvalidInstantError).

src/time/input.ts:61 · src/model/errors.ts:160-167

Fix: widen the parameter to unknown, which is the truth at the untyped door.

F6spec location · low · judgement · Confirmed

The issue proposed catching null in the public instant() helper — the function that actually throws the zoneless message. The branch catches it one caller up, in toInstant. The Dataset path is fixed, but instant(null as unknown as string) remains public (api/index.ts:417) and still throws the old misleading RangeError.

src/time/instant.ts:16-22 · src/time/input.ts:129 · src/api/index.ts:417

Judgement: instant’s type already rejects null, and no library path reaches it with null now. Fixing at toInstant is the smaller change; decide whether the public helper deserves the same guard.

F7test quality · minor · Confirmed

Both new null assertions pass a message that opens with the F1 tautology. input.test.ts:77 matches the substring null. An Entry… — matching the second null — and dataset.test.ts:148 matches /is null\. An Entry/, inside null is null.. Neither pins the sentence, so the defect ships green.

src/time/input.test.ts:76-78 · src/api/dataset.test.ts:147-157

Fix: assert the whole message (or toMatchInlineSnapshot), so the wording itself is pinned.
