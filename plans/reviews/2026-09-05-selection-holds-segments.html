What the branch got right

One resolution, no declaration

Carrying segmentIds and entryIds on ActedOn and refusing a per-command actsOn removes a state, a default and a way for two commands to disagree. resolveActedOn is one function, read by the pointer path and the keyboard path alike.

The Picked Item is gone, not renamed

pickedItemIdByEntryId, samePicks, #resolvePicks, #writePicks, paintedPicks and #pickedSegmentIndexByEntryId all deleted. The deletion test passes: the complexity did not move, it vanished, because paint and gesture now read one set.

The frame stamp on the pointer memo

ContainerDom's memo keying on FrameLayout.frameRevision is exactly right, and the comment says why in one sentence: a bar keeps its data-item-id while the Segment under it changes, so no node stamp can report the staleness. Moving data-segment-id from create to patch follows from the same fact.

Ingest fills a Segment

"Every Entry stores at least one Segment" removes a branch from every downstream reader instead of adding one. That is the right kind of invariant: it makes callers simpler, not more careful.

1 · A duplicate SegmentId is representable

Strong Blocking in-process

src/data/entry-reader.ts:44 · src/model/ids.ts:29 · src/data/dataset-state.ts:210 · src/data/entry-store.ts:264

Reproduced against the source

new DatasetState({ timeZone: 'UTC', entries: [
  { id: 'a', name: 'a', start: 0, end: 10, segments: [{ id: 'sg1', start: 0, end: 10 }] },
  { id: 'b', name: 'b', start: 0, end: 10 },                     // authors none
]});

A segments  [{"id":"sg1", ...}]      // the consumer's own id
B segments  [{"id":"sg1", ...}]      // minted from the counter — the same id

entries.removeSegments(['sg1']) →  entries remaining: [ 'a' ]   // 'b' is gone, 'a' is untouched

Problem. mintedSegmentId(counter) returns sg<counter> from a counter that only advances when it mints, so it walks straight into the namespace SegmentInput.id invites a consumer to author. Nothing checks uniqueness — unlike entries.add, which throws DuplicateEntryIdError.

Failure. EntryStore.#groupSegmentsByOwner builds Map<SegmentId, EntryId>; the second owner found overwrites the first. So a user who selects a's bar and presses Delete watches b disappear. On the paint side itemIdsBySegmentId files both bars under the one id, so selecting either lights both.

Solution. Uniqueness is a store rule, so put it in the store. Mint from a namespace a consumer cannot author, and reject a duplicate at ingest and at update with a DuplicateSegmentIdError that mirrors DuplicateEntryIdError. The SegmentId → EntryId index of finding 6 makes the check a Map.has that costs nothing.

  • locality: identity rules concentrate in data/
  • illegal combinations become unrepresentable
  • ADR 0010's "a Segment carries a stable id" becomes true

2 · The documented "move one Segment" call mints a fresh id

Strong Blocking

src/data/entry-reader.ts:42–48, 137–139

Reproduced against the source

// stored: [{ id: 'keep', start: 0, end: 10 }]
entries.update('t1', { segments: [{ start: 5, end: 15 }], start: 5, end: 15 });
// stored: [{ id: 'sg1', start: 5, end: 15 }]   ← 'keep' is gone

Problem. readSegment mints whenever input.id === undefined. That is right for readEntry — a brand-new Entry has no prior identity. It is wrong for readEdit, where the Segment at that position already has one.

Failure. CONTEXT.md's Segment entry names this exact call as how a consumer moves one Segment. Run it and the Segment's identity changes, so the bar drops out of the Selection mid-interaction and any SegmentId the consumer was holding is dead. That is the same class of failure ADR 0010 exists to close — a Selection pointing at a stretch that renumbered — arriving through a different door.

Solution. In readEdit, an omitted id carries over the id of the Segment at that position. The file already does exactly this one branch below, where the sole-Segment envelope carry-over keeps sole.id with the comment "this is the same stretch, moved". Apply the same rule to the general case.

3 · An id-only segments write is silently dropped

Strong Blocking

src/data/fields/core-fields.ts:9–15

const segmentsEqual = (from, to) =>
  a.every((span, index) => span.start === b[index]?.start && span.end === b[index]?.end);
//                        ^ id is never compared

entries.update('t1', { segments: [{ id: 'brandNew', start: 0, end: 10 }] });
// stored id is still 'old'

Problem. Before #212 a Segment was its span, so span equality was identity equality. Since #212 the id is the identity the Selection, undo and removeSegments all point at, and the equals function never learned that.

Failure. A consumer re-keying Segments from their own backend — update(id, { segments: stored.map((s, i) => ({ ...s, id: backendIds[i] })) }) — sees a successful call, no changeset row, no undo entry, and a later removeSegments(backendIds) that throws SegmentNotFoundError.

Solution. One clause: span.id === b[index]?.id.

4 · The envelope invariant has no owner

Strong Blocking

src/data/entry-reader.ts:52,137 · src/data/entry-store.ts:47–58 · src/layout/gesture-draft.ts:167–176

Reproduced against the source — two ways in

// (a) a plain segments write
entries.update('t1', { segments: [{id:'s1',start:100,end:110},{id:'s2',start:110,end:120}] });
stored → start 0, end 20        // the bars moved; the envelope did not

// (b) ingest
entries: [{ id:'t1', start:0, end:10, segments:[ {0..10}, {50..60} ] }]
stored → start 0, end 10        // the Segments reach 60; toJSON writes both facts out

Before — three bodies, one rule

entry-store.envelopeOf() → {start:number,end:number}
gesture-draft.envelopeOfSegments() → {start:Instant,end:Instant}
gesture-draft.envelopeOfIndexes()
readEntry()  — no envelope
readEdit({segments}) — no envelope

The two paths the invariant most needs are the two that do not have it.

After — one interface

envelopeOf(segments): TimeSpan

called by readEntry · readEdit · removeSegments · every draft

Depth: the invariant becomes a fact about a stored Entry, not a thing each writer remembers.

Problem. CONTEXT.md and model/entry.ts both state that start/end are the envelope over the Segments. removeSegments and the three draft builders honour it by hand. Ingest and a plain update({ segments }) do not, and a stale envelope reaches reveal, the Rollup, zoomToSpan and the Document.

Solution. One envelopeOf(segments): TimeSpan. Apply it in readEntry and in every readEdit branch that writes segments. Delete entry-store.envelopeOf (which also widens Instant back to number on the way through) and let layout/gesture-draft.ts import the same helper. Note the sole-Segment carry-over at entry-reader.ts:142 is already the degenerate case of this rule, written out longhand.

  • leverage: one interface, five call sites
  • locality: an envelope bug is one function away
  • the brand survives — Instant stops decaying to number

5 · removeSegments deletes the subtree, undocumented and untested

Strong Blocking

src/data/entry-store.ts:288–300 · src/view/core-commands.ts:120–142 · src/view/gantt-shell.ts:1403

entries: [{ id:'p', segments:[{id:'ps'}] }, { id:'c', parentId:'p', segments:[{id:'cs'}] }]
entries.removeSegments(['ps'])
→ entries remaining: []          // #removeSegmentsFrom → this.remove('p') → #subtreeOf

Problem. ADR 0010's consequence list says "removing an Entry's last Segment removes the Entry, in the same transaction". It does not say "and every descendant". CONTEXT.md does not say it. No test covers it. This branch also binds Delete as a default keybinding and puts freegantt.deleteSelection in the right-click menu, so one keystroke on a parent's grid row now removes a subtree the user never selected.

Solution. Decide, then write it down. Either it is the intent — record it in ADR 0010's consequences and CONTEXT.md's Segment entry, and add the test — or #removeSegmentsFrom stops going through remove for a parent and refuses (or re-parents) instead. Do not ship it implicit behind a default Delete binding.

This is the one place where a behaviour the ADR does not describe reaches the user through a key the ADR added.

Problem. The Selection changed unit, and every layer that had to follow it wrote its own Segment↔Entry walk. GanttShell grew 1,774 → 1,882 lines and six of its eight new members are that lookup. Six of the nine bodies are full-dataset scans. The store that owns the Segments publishes no index for them, so the shell re-derives what the library already holds — the shape CLAUDE.md's stop rule names for harness/, here inside src/.

Solution. EntryStore keeps a SegmentId → EntryId map beside #byId, maintained by the same staging path, and publishes two questions: entryIdOfSegment(id) and entryIdsOfSegments(ids) (deduped, in Dataset order). #groupSegmentsByOwner, #findSegmentOwner, #forgetSegmentsTheDatasetDropped and selectedEntryIds's scan each become one call. Row ordering stays in view/, because row order is a Gantt fact, not a Dataset fact.

Deletion test. Delete the index and the complexity reappears in six callers, each with its own scan — which is where it is today. That is a "yes, concentrates".

  • leverage: one interface, six call sites
  • locality: findings 1, 8 and 15 all land on it
  • O(dataset) becomes O(ids) on the pointer path
  • the shell stops accreting a store responsibility

7 · selectedEntryIds runs a sorted O(dataset) projection on every hover step

Strong Blocking

src/view/gantt-shell.ts:1033–1053, 1069–1075, 1419–1441 · src/view/affordance-projection.ts:59–86

Before this branch — one hover step

read #selection (array)

After this branch — the same hover step

Problem. #setHovered calls #refreshAffordances on every hover change, and #refreshAffordances reads this.selectedEntryIds — a getter, not a field. projectAffordances then uses only selectedEntryIds.length !== 1 and selectedEntryIds[0], so the row-rank map, the sort and the full projection are pure waste on that path. Why CI is silent. I5's row in plans/01 §11 names "perf test on applyState" as its enforcement, and perf is still in FUTURE_PLANNED_JOBS (test/guards/matrix-coverage.test.ts:80). I5 is review-enforced today, which is exactly why this passed.

  • locality: the projection is computed where the Selection is written
  • hover returns to zero allocation (I5)

8 · The Selection prune ignores the ChangeSet in its hand

Strong Blocking

src/view/gantt-shell.ts:1082–1093, and the subscription at :647–652

this.#datasetChanges = subscribeToDatasetChanges(options.dataset, (changeSet) => {
  this.#layout.invalidateForChange(changeSet);   // uses it

});

Problem. Every commit — a cell edit, a drag, an undo — builds a Set of every live SegmentId in the Dataset and then filters the Selection against it. The ChangeSet one line above already names the Entries that changed and which of them lost segments.

12 · The row-order comparator returns NaN

Strong Blocking

src/view/gantt-shell.ts:1039

ids.sort((a, b) => (rank.get(a) ?? Infinity) - (rank.get(b) ?? Infinity));
// two Entries no planned row holds → Infinity - Infinity → NaN

Two selected Entries that the current plan does not hold — filtered out, or inside a collapsed subtree — compare to NaN. The doc comment above claims they "keep their place in Dataset order behind the rows that are showing", and that only holds because V8 treats a NaN comparator result as 0. That is engine behaviour, not a contract, and selectedEntryIds is the ordering every command, the gesture pipeline and the public getter read. Fix: rank an unplanned Entry as rank.size + its index in Dataset order, so the comment becomes true by construction.

20 · The e2e suite works around a Popup defect, and says so

Worth exploring

e2e/selection.spec.ts (pickableBarOf) · src/extensions/popup.ts · src/extensions/focus-trap.ts

The known, deferred defect — Popup.open() arms dismissOn: 'scroll' before activateFocusTrap(), and focusFirst() calls .focus() with no preventScroll — now has a test-side workaround: pickableBarOf centres the bar, and the comment ends "it does not fix it". Top recommendation

Give data/ the SegmentId → EntryId index — finding 6

The Selection changed unit and nine bodies across four layers each learned to walk Segments back to Entries. Six of them scan the whole Dataset. GanttShell absorbed six of them and grew a hundred lines doing it.

One index in the store that already owns the Segments collapses #groupSegmentsByOwner, #findSegmentOwner, #forgetSegmentsTheDatasetDropped and the scan inside selectedEntryIds. It gives finding 1 the uniqueness check it needs, finding 8 the cheap prune, finding 15 its lookup, and finding 7 the field it should have been reading all along. It is the one change that four other findings land on.

Sequence: findings 1–5 first, because they are correctness in data/ and each lands on its own. Then 6, then 7–9 on top of it. Then 10–12, which are surface and spec. 13–20 after.
