The whole branch, not the last commit. Net src/ change against main is comments only; the substance is the ADR, the rewritten docs, and the harness/theme-push first consumer. The strip is clean: no ThemeResolver, no theme-resolver-failed, no widened observer survives in src/.

Verdict

The ADR's core reasoning holds: the wrapping app already resolves a dark-mode signal, a push costs it one line, and the pull design bought an observer, a re-entrancy guard and a public error code. The strip removes all of that. But the branch carries resolver-era residue in three places (the toolbar's duplicate ThemeChoice, the ADR's overclaim about self-mutation, the stale resolver review), and the new harness page repeats a hand-tuned-token pattern AGENTS.md names by number. Nothing is High: no src behaviour ships wrong. Eight findings, all Medium or Low.

Findings

F1 · Medium

The harness toolbar still carries a resolver-era duplicate of Theme

harness/gantt-toolbar.ts:17 · :33 · :65 · :69 · :79 · :207

Problem: the strip made theme three literals again, so the public Theme is 'auto' | 'light' | 'dark'. The toolbar nevertheless keeps a private ThemeChoice with that exact shape and a comment rationalising it ("named again here so this file states its own contract"). On main the file imported Theme. This is the clearest thing the resolver left behind.

Fix: import Theme from freegantt again, delete ThemeChoice and its comment, and let the five signatures use the public name.

F2 · Medium

ADR 0029's consequences overclaim: the library's own write still wakes its own observer

docs/adr/0029-the-app-pushes-the-theme.md:79–82 · src/view/gantt-shell.ts:1104–1107 · :1117–1122 · :2048–2057

Problem: the ADR says "With no observer on attributes we do not own, there is no mutation of ours that can wake a read of ours." The first clause is true; the second is not. The library writes data-fg-theme in #applyTheme (gantt-shell.ts:2054–2056) and still observes data-fg-theme under the root (gantt-shell.ts:1117–1122). Its own later gantt.theme = … write re-enters the observer — the code comment at gantt-shell.ts:1104–1107 says exactly that. The re-entrancy class is gone because the observer callback no longer invokes a consumer function, not because no self-mutation wakes the watch. The accepted record should state that reason.

Fix: reword to "the observer now calls only resolveTheme and writes nothing, so a self-write settles after one no-op wake instead of re-entering a consumer callback."

F3 · Medium

A resolver-era review is committed on the branch, un-annotated

plans/reviews/2026-09-19-433-theme-resolver-branch-review.md:1 · :9–11 · :99–115

Problem: the file's verdict says "Two real problems ship: a failing ThemeResolver loops forever (F1), and the widened observer is unscoped (F2)" — about a design ADR 0029 overturned and the next commit deleted. Its pass-2 table is empty. A reader landing on the branch sees a live defect list for code that no longer exists, with no note that the design was overturned.

Fix: either delete the file, or add a one-line banner at the top: superseded by ADR 0029; F1–F2 describe the removed ThemeResolver and are closed by the strip, not by the fixes proposed.

F4 · Low

"three causes" was weakened to "any cause" for the resolver, and not restored

docs/05-consumer-api.md:261–262 · CONTEXT.md:540

Problem: main reads "for any of three causes"; the branch reads "for any cause". The edit existed to admit the resolver's wide observer; with the resolver gone there are again exactly three causes (theme write, OS flip, ancestor pin), and both sentences still list those three. CONTEXT.md:540 also says the observer is "narrowed to data-fg-theme alone", phrasing that only reads as a narrowing against the deleted wide watch.

Fix: restore "three causes" in both, and CONTEXT's main wording "watching data-fg-theme under the root node".

F5 · Medium

The first-consumer page repeats the hand-tuned pane width instead of gridWidth: 'fitColumns'

harness/theme-push.html:12–18 · harness/theme-push.ts:27–41

Problem: the page copies the old template's --fg-grid-pane-width: 220px and --fg-row-height: 32px, and passes no gridWidth. AGENTS.md names --fg-grid-pane-width hand-tuned to one column set as one of the three exact API gaps the harness exists to surface (#157); harness/main.ts:86 and harness/planner.ts:207 already pass gridWidth: 'fitColumns'. The new page is the library's model consumer, so it should not spread the pattern.

Fix: pass gridWidth: 'fitColumns' and drop --fg-grid-pane-width; drop --fg-row-height unless the page deliberately wants 32px (default is 36).

F6 · Low

The page's e2e seam uses a double cast instead of the harness's declare global pattern

harness/theme-push.ts:47–48 · e2e/theme-push.spec.ts:12–14 · cf. harness/zoom.ts:24–29, harness/hierarchy.ts:27–33

Problem: every sibling page declares its test seam with declare global { interface Window { … } }. This page instead writes (window as unknown as { __gantt: Gantt; __ganttPinned: Gantt }), which discards type checking and re-declares __gantt (already declared globally by other pages). The e2e then narrows the same global to { resolvedTheme }, which is probably why the cast exists: a proper declaration would collide.

Fix: add the standard declare global for __ganttPinned: Gantt, assign directly, and let the spec read window.__ganttPinned.resolvedTheme against the same type.

F7 · Low

The page asserts an app dark-mode signal that nothing on the page consumes

harness/theme-push.html:53–56 · harness/theme-push.ts:22 · :60

Problem: the intro calls the dark class on <html> "this page's own signal", but no rule on this page keys off .dark; harness-nav.css and harness-chrome.css read [data-theme] and prefers-color-scheme. So the demo toggles a class nobody can see, and only the two Gantts change. The ADR's whole premise is that the app has a real signal; the page should show it.

Fix: style the page chrome off the same class (or off data-theme set in the same handler), so a reader sees the app flip and the Gantts follow. Then the classList.remove('dark') reset at theme-push.ts:22 stops being a no-op.

F8 · Low

The ADR's survey of framework signals leaks into the consumer reference

docs/05-consumer-api.md:237–238 · docs/adr/0029-the-app-pushes-the-theme.md:16–18

Problem: docs/05 — the consumer API reference — names Tailwind, Filament, next-themes and Bootstrap 5.3. These are not banned Gantt vendor names, so no guard fires, but the repo's posture is that product evidence lives in the ADR and a spec states the decision. The mechanism ("a class on <html>, or data-bs-theme") needs no brand list; the ADR already carries it.

Fix: drop the parenthetical brands in docs/05, or point the reader at ADR 0029 for the survey.

F9 · Low

The ADR's "a function never becomes a config value" leans on a serialisation reason that does not apply

docs/adr/0029-the-app-pushes-the-theme.md:74–77

Problem: the paragraph cites CONTEXT.md's Aggregator rule — "a name serializes into a document and a function does not". A Gantt theme is runtime config; it is never written into a document. The real cost of the resolver was the observer and its re-entrancy, which the Consequences section already states. Borrowed authority weakens an otherwise sound argument.

Fix: cut the serialisation appeal, or say plainly that the same "a config value is data, not behaviour" preference is being applied by analogy.
