# #130 — WBS

**Reported:** 2026-09-05. **Status:** open, planned. **Position:** after S5 closes and merges, before S7.

Grilled with the maintainer on 2026-09-05. Every decision below is settled. No code is written yet.

## What it is

`wbs()` — a first-party Dataset plugin that gives every Entry a dotted position code: `1`, `1.1`,
`1.1.1`, then `2` for the next root. Glossary entry: `CONTEXT.md`, **WBS**.

The library works with the plugin removed. Nothing in `src/` keys off a WBS.

## Decisions

### W1 — the WBS is derived, never authored

A consumer never sends a WBS, never writes one, and never reads one back from a Document. The plugin
computes it. The number is fluid: moving an Entry renumbers it, and the `id` stays put.

Rejected: a frozen code, which fills a value once and renumbers only when a consumer asks. Rejected
too: one Field that accepts an authored value and derives the rest, which puts `1.2.1` and
`PROJ-ENG-01` in one column with no rule saying which a reader is looking at.

A frozen, consumer-authored code is a **separate, later** feature with a separate Field. It is the
only thing that needs the uniqueness rule the issue's comment asked for. This plugin's default cannot
collide, because position is unique.

### W2 — the WBS is not the Entry id, and cannot become one

`Entry.id` is identity and is not editable — `EntryEdit` omits `id` from `EntryInput` by construction.
A WBS changes on every reorder. An identity that changes is not an identity, and a renumber would
have to rewrite every `parentId`, every plugin-store row and every undo entry in one atomic pass.

A consumer who wants "no id system of my own" gets a generated id (`entryId()`) plus a WBS beside it.

### W3 — the number counts authored order, not displayed order

Authored order is the consumer's `entries` array, which is the store's insertion order and what
`toJSON` writes back (D-S2-12). Depth comes from `parentId`.

Sort, filter and collapse are per-Gantt view knobs (D-S4-28). They never reach `data/`. So:

- A Gantt sorted by `start` reads its WBS column out of sequence.
- A Gantt filtering half the tree reads its WBS column with gaps.
- Two Gantts on one Dataset always agree on every WBS.

All three are correct. A number that changed because someone filtered a view would not be a code
anyone could quote.

### W4 — ship against array order; drag-to-reorder is a separate issue

Row reorder by drag does not exist, and `plans/s4-hierarchy-and-rows/README.md:336` parks it until an
**authored order Field** exists (D-S4-31). That Field is a prerequisite for the issue's headline demo
("drag 1.3 to the top and it becomes 1.1"), and it is not a WBS feature.

The plugin ships now against array order and renumbers correctly on add, remove and reparent. Its
contract is "authored sibling order", which does not change when the order Field lands — WBS reads
the new order with no API change.

**The issue's demo sentence changes**: the visible proof is *reparenting renumbers the tree while the
ids stay put*, not *drag to the top*.

### W5 — every Entry is numbered

Every kind, every depth, no skip predicate, no per-kind opt-out. An Entry a Gantt's filter hides is
still numbered, because the number is the Dataset's and the filter is the Gantt's. A skip list would
make the answer depend on which Gantt is asking, which is W3 undone.

Depth is unbounded — as many levels as the tree has.

### W6 — the seam is one closure, called top-down

```ts
export interface WbsContext {
  entry: Entry;
  parentWbs?: string;   // undefined at a root
  index: number;        // 1-based position among siblings, authored order
  depth: number;        // 0 at a root
}
export type WbsCode = (ctx: WbsContext) => string;

const decimalWbs: WbsCode = ({ parentWbs, index }) =>
  parentWbs === undefined ? String(index) : `${parentWbs}.${index}`;
```

The default is those two lines, so the shipped behaviour and a custom one run the same path (I11).
The closure sees the entry, so `PROJ-ENG-01`, a kind prefix, or letters at one level are all
reachable.

Rejected: a formatter over the index path (`[1,2,1] => string`), which cannot read the entry.
Rejected: a whole-map generator (`tree => Map<EntryId, string>`), which makes every consumer
re-implement the tree walk the library already does.

### W7 — the factory takes `key`, `code` and `compare`, and nothing else

```ts
// data-side — only the plugin can declare these
new Dataset({ plugins: [wbs({ code, compare })] });

// presentation — already the consumer's, no plugin option needed
new Gantt({ dataset, gridColumns: [{ field: 'wbs', header: 'Code', width: 90, align: 'end' }] });
```

That is ADR 0005's line: a Field is what a value is, a Grid column is where a Gantt shows it.

- **`key`**, default `'wbs'`. A consumer who already declares a `wbs` Field cannot install the plugin
  at all otherwise — `FieldRegistry.register` throws `DuplicateFieldKeyError` on a key that exists
  (`src/data/fields/field-registry.ts:116`), and `DatasetOptions.fields` is seeded before plugins set
  up. One option turns a hard block into a rename.
- **`code`**, default `decimalWbs`.
- **`compare`**, default natural order — see W8.
- **No `formatValue`.** `code` already returns the display text; a formatter on top would be a second
  knob for one job. A consumer who wants `01.01` writes it in `code`.
- **No `field: Partial<Field>` escape.** It would invite overriding `key` and `source`, which would
  break the plugin from outside.

### W8 — the default comparator is natural order, and it is required

The shipped fallback comparator uses `Intl.Collator` (`src/view/grid-columns.ts:26`). It sorts
`['1.10','1.2','1.1']` to `1.1, 1.10, 1.2` — wrong. The plugin must declare its own `compare` or the
column is broken out of the box.

Natural order — split into digit and non-digit runs, compare digit runs numerically — gets
`1.2 < 1.10` right *and* `ENG-01 < ENG-02` right. So the default closure and most custom ones both
sort correctly with nothing passed.

Rejected: comparing the underlying index path. Exact for the default, meaningless the moment a caller
supplies `code`.

Where the comparator earns its keep: with `tree: true`, sorting siblings by `wbs` reproduces the
authored order, which is a no-op. On a **flat** row source (`tree: false`) it rebuilds outline order
in a flat list, and any custom `code` whose order differs from position needs it.

### W9 — installing declares the value; showing it stays the Gantt's call

`wbs()` is a Dataset plugin. It declares the Field with `column` defaults (a Field with no `column`
key cannot be a grid column at all — `FieldNotColumnableError`, `src/view/grid-columns.ts:44`). The
consumer names it: `gridColumns: ['wbs', 'name']`.

The plugin does **not** ship a Gantt-side half calling `registerGridColumn`. A Dataset does not know
how many Gantts are bound to it, and a column appearing in a chart nobody asked for crosses the layer
line.

### W10 — one folder for shipped plugins

`src/extensions/features/wbs.ts`, exported as `wbs` from the package root (the package has one export
path, `"."`). The root of `src/extensions/` is the machinery; `features/` is the plugins we ship.
Which kind a plugin is, is already visible in its signature and in where it installs
(`DatasetOptions.plugins` vs `GanttOptions.plugins`) — a second folder would repeat what the type
system says, and `extensions-public-only` matches `^src/extensions` as a whole anyway
(`.dependency-cruiser.cjs:99`). S7's `entryDependencies()` and `scheduling()` go here too.

## Two core prerequisites

Both are core gaps this plugin exposes. Both are worth fixing on their own merits, and neither is
about WBS. They land as their own issues, before the plugin.

### P1 — `FieldContext` has no way to reach a second Entry (#214)

`FieldSource`'s `compute` is `read(entry, ctx)`, and `FieldContext` carries `timeZone`,
`read(entry, key)` and `durationOf` (`src/model/field.ts`). `ctx.read` reads a field off an entry the
caller already holds. There is no way to reach the parent, a sibling, or the roots — `entry.parentId`
is a string, not an Entry. A per-entry context cannot express a position in a tree.

```ts
export interface EntryTree {
  roots(): readonly Entry[];                    // authored order
  childrenOf(id: EntryId): readonly Entry[];    // authored order
  parentOf(entry: Entry): Entry | undefined;
}

export interface FieldContext {
  readonly timeZone: string;
  readonly tree: EntryTree;                     // new, required
  read<K extends FieldKey>(entry: Entry, key: K): CoreFieldValue<K> | undefined;
  durationOf(entry: Entry): Duration;
}
```

**Required, not optional.** Optional would let a site pass nothing and render an empty WBS column with
no error — the silent failure P2 exists to close.

Four sites build a `FieldContext`, and all four can supply one:

| Site | Has |
|---|---|
| `src/data/dataset-state.ts:155` | the Store itself |
| `src/view/gantt-shell.ts:1613` | the Dataset; passes a `FieldLookup` only, by choice |
| `src/data/rollup.ts:112` | the effective entry map it already builds |
| `src/extensions/features/inline-editing.ts:99` | `PluginContext`; builds from public reads, and `entries.childrenOf` is public |

`ComputedFieldCache` (`src/data/computed-cache.ts`) clears on every `datasetRevision` bump, so one
walk numbers the whole tree per commit and every other read is a map hit.

Rejected: the plugin keeps its own map, rebuilt on every `change`, and the Field reads that. It needs
no core change, but it re-derives in a plugin the tree the library already holds, and it stores
derived data in a `PluginStore` meant for authored data — where it would then serialize. That is the
shape CLAUDE.md's stop rule says to report rather than build.

### P2 — a write to a compute-sourced Field is silently dropped (#213)

`src/data/fields/source-strategy.ts:126` is `write(edit) { return edit; }`. Probed against the shipped
computed core Field: `dataset.entries.update('a', { duration: … })` throws nothing, reports nothing,
and writes nothing.

So "the WBS cannot be changed" today means "ignored in silence" — a consumer syncing a WBS edit from
their backend sees no error and the value never lands. Fix it for **every** compute Field at once:
throw `ReadOnlyFieldError`. `duration` has the same hole now.

## Not in scope

- A frozen, consumer-authored WBS code, and the uniqueness rule that goes with it (W1). Revisit after
  a caller needs it.
- The authored order Field and drag-to-reorder (W4) — its own issue, D-S4-31.
- A WBS as the Entry id (W2). Closed, not deferred.

## Acceptance

- Every Entry in a tree fixture reads its dotted code through
  `dataset.entries.fieldValue(id, 'wbs')`; a four-level tree numbers to four levels.
- `update(id, { parentId })` renumbers the affected subtrees on commit, and every `id` is unchanged.
- No `wbs` key appears anywhere in `toJSON()`.
- `update(id, { wbs: '3.1' })` throws `ReadOnlyFieldError` (P2).
- A custom `code` closure produces `PROJ-ENG-01`-style codes from `entry` data.
- `sort: { field: 'wbs' }` on a flat row source orders `1.2` before `1.10`.
- A Dataset with no `wbs()` installed behaves byte for byte as it does today.
- **Visible:** the harness tree page gains a WBS column; reparenting a bar renumbers the tree live
  while the changeset log shows the ids unchanged.
