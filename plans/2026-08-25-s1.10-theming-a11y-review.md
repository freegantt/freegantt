## Summary

The spec is well-written, thorough, and internally consistent. It closes every finding from `fix-issue1-apis.md` cleanly. Most decisions are sound. Below are findings across three axes: **Spec correctness** (references, logic), **Architecture** (layering, simplification), and **Standards** (repo rules, naming).

## Hard findings

### H1 — ARIA role nesting: `.fg-row` is `role="row"` but lives under `gridLayer`, not the host

**§2 D-S1.10-5, table row 2 + row 1**

The host (inside the timeline pane) carries `role="grid"`. The `.fg-row` elements live in `gridLayer` (the grid pane). ARIA requires `role="row"` to be a *child* of `role="grid"` in the DOM tree. The current DOM structure is:

```
host (role="grid") ─ in timeline pane
├── grid pane
│   └── rowLayer
│       └── .fg-row (role="row")  ← NOT a descendant of host in the DOM
├── splitter
└── timeline pane
    ├── headerLayer
    ├── barLayer
    └── contentSizer
```

`.fg-row` is a sibling subtree, not a descendant. A screen reader following the ARIA tree sees `role="grid"` with no `role="row"` children.

**Fix options:**
1. Move `role="grid"` and `aria-rowcount` to `rowLayer` (the actual parent of rows). The host becomes a neutral container. Bars in the timeline pane get `role="presentation"` or no grid-related role.
2. Accept the DOM reality: rows get `role="listitem"` with `aria-setsize`/`aria-posinset` instead of the grid pattern. The full grid role (row/gridcell/rowheader) lands when S6's columns make the grid pane an actual tabular structure.
3. Move `.fg-row` rendering into the timeline pane alongside bars. Breaks the grid/timeline split.

**Recommended:** Option 2 for S1.10, with a clear note that the full ARIA grid pattern lands at S6 when column cells exist. The current spec's role table is aspirational for the DOM shape S6 will create, not implementable today.

### H2 — `render/dom/index.ts` line references are inaccurate

**§3.5 and §2 D-S1.10-6**

The spec lists "every `node.style.position/visibility/top/left` write in `mount`/`syncHeader`/`syncRows`/`syncBars` (`index.ts:48,71,108,131,161,164,171-176`)".

Missing from the list: **tick's `position: absolute`** (line 52), **band's `position: relative`** (line 72), **bar's `position: absolute`** (line 131). The count says "48,71,108,131" but 48 is actually the tick's `create` at line 49-53 (where `position = 'absolute'` is line 52), not a separate entry.

### H3 — `ensureBaseStyles` is document-level state but CLAUDE.md I2 bans module-level singletons

**§2 D-S1.10-8**

The spec's own defense is correct: "the DOCUMENT holds the state, not a module variable, so two Gantt instances in one document share one injected sheet without this being I2's kind of module-level singleton." But this defense needs to appear in the decision itself, not just in the function's doc comment. A reviewer unfamiliar with the plan will see `data-freegantt-styles` as state and flag it against I2. The decision should state explicitly: "I2 governs shared *mutable state* (configuration, subscriptions, caches); an idempotent one-time DOM write guarded by a DOM attribute marker is outside I2's scope because the second caller's call is a no-op — no shared mutable state exists."

## Judgement calls

### JC1 — `a11yLabel` is DOM vocabulary in a DOM-free layer

**§2 D-S1.10-5**

`FrameBar.a11yLabel` lives in `layout/` (DOM-free core). The spec's own defense: "layout/ is backend-neutral and ARIA is a DOM vocabulary — render/dom maps it to aria-label at sync time." This is architecturally sound — the same pattern as `kind` → `data-kind`. But the name `a11yLabel` still carries ARIA's vocabulary into the pure layer. An alternative is `displayLabel` or `assistiveText`, which are not DOM-specific. Since the spec explicitly cites the `kind`/`data-kind` precedent and names this a deliberate pattern, the choice is defensible — but should be recorded as a decision (not an assumption) so future contributors don't treat it as accidental.

### JC2 — `RowGeom` gains `index` but `BarGeom` doesn't carry it

**§2 D-S1.10-7, §3.5**

The spec says "RowGeom gains index (already on FrameRow, just not carried into BarGeom's row sibling type today)." But the proposed `BarGeom` type in §3.5 only adds `flags: BarFlags`, not `index`. The `aria-rowindex` for a bar would need to derive from its row's index. The spec says "from `FrameBar.a11yLabel`... carried the same way `label` already is" — but `label` is a string on `FrameBar` itself, while `index` lives on the row. Either:
- `FrameBar` should also carry `rowIndex` (derived from the row at `computeFrame` time), or
- `BarGeom` should include `index` and the `patch` reads it from there.

This is not specified clearly. The implementer will need to decide how `aria-rowindex` reaches the bar element.

### JC3 — `width: 100%` on `.fg-row` is structural but `height: 100%` on `.fg-rows` is dependent

**§2 D-S1.10-6, CSS rules**

The spec moves `node.style.width = '100%'` from row `create` (render/dom/index.ts:111) to `.fg-row { width: 100% }` in the stylesheet. Good — it's structural.

But `rowLayer.style.height = '100%'` (pane-layout.ts:88) is not in the CSS rules list. It depends on the parent's flex layout (`fg-rows-clip` has `flex: 1 1 auto`). This is a borderline case: the value is always `'100%'`, but the spec's rationale for inline styles is "per-instance geometry driven by live numbers." `'100%'` is not a live number. The spec should state explicitly why this one stays inline, or move it to the stylesheet.

### JC4 — The lint rule scope `src/render/**` + `src/view/**` has a gap

**§3.3**

The rule allows `transform`/`width`/`height` in `src/render/**` and `src/view/**`. But `src/interaction/` (future) may also need per-frame geometry writes. The spec doesn't state whether the rule's scope will grow. A note that "the scope is expected to widen as `interaction/` ships gesture previews" prevents surprise.

## Simplification opportunities

### S1 — Cut the "no renames" section's defensive prose

**§0 Q2, §2 D-S1.10-1**

The spec spends ~200 words defending why shipped class names aren't renamed to the issue comment's BEM scheme. This is valuable as a decision record but verbose as spec text. The decision could be one sentence: "Class names are the names already in code (§0 Q2); the BEM scheme never shipped and is rejected." The evidence (test churn, no behavior change) can live in the decision's `*Rejected:` block alone, not repeated across Q2 and D-S1.10-1.

### S2 — The TODO mixes implementation order with acceptance criteria

**§8 TODO, §8 Acceptance**

The acceptance checklist (U1–U7, [S1-A1]/[S1-A4]) duplicates user stories from §1. A cleaner structure:
- §8 TODO: implementation phases only (what to build, in what order)
- §6 Tests: what tests to write (already there)
- §1 User stories: what to accept (already there, with the acceptance checkboxes there too)

The acceptance checklist at the bottom of §8 is a third copy of the same content. Merge it into §1's user stories as tick-boxes, or into §6's test list as `// acceptance: U1` annotations.

### `formatDate` vs. "exactly one formatting helper"

`plans/01 §5` says "Exactly one formatting helper (`formatEndInclusive`) renders inclusive ends." The spec ships `formatDate` alongside it. This is not a contradiction — `formatDate` formats a start (already inclusive), while `formatEndInclusive` converts half-open `end` to inclusive display. Two helpers, one conversion. But the spec's phrasing in §2 D-S1.10-4 ("a second inclusive helper is exactly what `plans/01 §5`'s 'exactly one' forbids") could be read as implying `formatDate` is an inclusive helper. It isn't — it's a plain formatter. The decision should say: "Two helpers: `formatDate` for starts (no conversion), `formatEndInclusive` for ends (half-open → inclusive). The constraint is one conversion path, not one function."

## Consistency checks

### No contradictions found with locked decisions

- **D11** (a11y): The spec correctly implements D11's "solid accessibility built in as slices land" by shipping roles/labels with the rows/bars that create the surface, deferring only navigation to S4.
- **D6** (time model): `formatEndInclusive`/`formatDate` correctly go through zone-aware `time/` primitives.
- **D8** (split pane): The CSS rules preserve the grid/timeline split structure.
- **D12** (stack): No new runtime deps introduced; `ensureBaseStyles` is pure DOM manipulation, no framework.

### No contradictions found with invariants

- **I2** (no module-level singletons): `ensureBaseStyles` uses a DOM marker, not a module variable. Defense stated.
- **I9** (pixel identity): The CSS rules don't affect row positioning (transform stays inline).
- **I12** (time→px via TimeScale, scroll via ScrollModel): No changes to these paths.

### Minor inconsistency

`plans/01 §4` (line 303) documents `BarFlags` as `{ hasConflict?: boolean; inCycle?: boolean }`. The spec's D-S1.10-3 renames these to `conflict`/`cycle`. The "spec edits implied" section (§7) correctly lists this as a §4 edit. But the §4 code block in the spec still shows the old names. This is expected (the edit lands with the step), but the §7 list should explicitly say "§4 code block: `hasConflict`→`conflict`, `inCycle`→`cycle`" — which it does (line 292). ✅ Consistent.

## Actionable recommendations

1. **H1:** Revise the role table in §2 D-S1.10-5. Either (a) assign `role="grid"` to `rowLayer`, not the host, or (b) defer the full grid pattern to S6 and use `role="list"`/`role="listitem"` with `aria-setsize`/`aria-posinset` now. Option (b) is simpler and honest about the current DOM shape.
2. **H2:** Correct the line numbers in §3.5 to: tick `create` (49-53), band `create` (69-77), row `create` (105-113), bar `create` (127-132), headerLayer `mount` (159-161), barLayer `mount` (162-164), contentSizer `mount` (169-176).
3. **H3:** Add one sentence to D-S1.10-8's decision text: "I2 governs shared mutable state; an idempotent one-time DOM write guarded by a marker attribute is not mutable state."
4. **JC2:** Clarify how `aria-rowindex` reaches `.fg-bar`. Either add `rowIndex` to `FrameBar` (computed in `computeFrame`), or carry it through `BarGeom`.
5. **JC3:** Add `rowLayer.style.height = '100%'` to the "stays inline" list in D-S1.10-6 with rationale: "depends on parent flex layout, not a live number, but moving to CSS requires the parent's flex context which is already in the stylesheet — acceptable either way; keeping inline for clarity."
6. **S1:** Condense D-S1.10-1 to one paragraph + `*Rejected:` block.
7. **S2:** Move the acceptance checklist into §1's user stories as tick-boxes; remove the duplicate from §8.
