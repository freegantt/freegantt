# S5.7 — Grid chrome: cell renderers, column resize, column reorder

**Slice:** S5 · **Step:** 7 of 12 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-17, D-S5-18, D-S5-34 · **Closes:** S4 deferred rows "`cellRenderer`" and "Column resize and reorder"
**Prerequisite:** S5.4 · **Ends with:** a column edge drags to a new width, a header drags to a new position, and both fire one `gridColumnsChange`.

## 1. Decisions

### D-S5-17 — `cellRenderer` sits on the Gantt's column, never on the Field

S4 promised this (D-S4-14): `formatValue` is the Dataset's, returns text, and fills `FrameRow.cells`; a renderer is code the Gantt holds.

```ts
export interface GridColumn {
  field: FieldKey;
  header?: string;
  width?: number;
  flex?: number;
  align?: 'start' | 'end';
  /** S5.7 — per-column, more specific than `GanttOptions.cellRenderer` (D-S5-11). */
  cellRenderer?: CellRenderer;
  /** S5.8 — this column's cells open the inline editor. Default `false`. */
  editable?: boolean;
  /** Default `true`. A fixed column refuses the resize drag and the resize chord. */
  resizable?: boolean;
  /** Default `true`. A pinned column refuses the reorder drag and the move chord. */
  movable?: boolean;
}
```

`editable`, `resizable` and `movable` appear with the code that honours them, not before (I11) — `editable` lands in S5.8 and is listed here only because it shares the type.

The renderer receives the already-formatted `value`, so the common case (wrap the library's text in a span with a class) needs no formatting knowledge:

```ts
{ field: 'cost', cellRenderer: ({ value, entry }) =>
    ({ class: { over: isOver(entry) }, text: value }) }
```

`data/` still never holds a renderer. A column with a `cellRenderer` is a Gantt value; `toJSON` sees none of it, and a `Field` declaration is unchanged.

### D-S5-18 — One event pair for every column presentation change

```ts
export interface GridColumnsChange {
  from: readonly GridColumn[];
  to: readonly GridColumn[];
}
```

`beforeGridColumnsChange` is cancelable; `gridColumnsChange` follows a commit. Three things fire the pair, and they share one commit sequence in `GanttShell`:

1. a resize drag on a column edge,
2. a reorder drop of a header,
3. `gantt.gridColumns = […]`.

This is the `gridWidth` precedent exactly (S1.8): one commit sequence, one place it lives, and a veto restores the state the drag started from, so a refused drag leaves nothing behind. Two pairs (`beforeColumnResize`, `beforeColumnOrderChange`) would be two names for "this Gantt's columns changed", and a consumer persisting layout would have to subscribe to both and merge them.

Payload columns are **resolved** columns — what the Gantt actually shows, with the Field's own `column` defaults already merged (D-S4-12). A consumer keeps `to` in memory and passes it straight back as `gridColumns` within the same session — a same-process reuse, so a `cellRenderer` closure (S5.7's own addition to `GridColumn`) round-trips fine, nothing serializes it.

**Persisting across a reload needs the plain fields only (issue #137 F13).** `GridColumn.cellRenderer` is a function; `JSON.stringify(to)` drops it silently (or throws, under `JSON.stringify`'s stricter cousins), so "persist `to` as JSON, read it back next mount" is not the same claim as "keep `to` in memory." A consumer persisting layout across reloads writes the plain subset — `to.map(({ field, header, width, flex, align, editable, resizable, movable }) => ({ field, header, width, flex, align, editable, resizable, movable }))` — and re-supplies any `cellRenderer` at construction time, the same way it supplied it originally, since a function was never going to survive a storage round-trip regardless of this event's payload shape. README §5's example already does the narrower, correct thing (`to.map((c) => c.field)`); this decision states why that is the pattern rather than the exception.

Column state stays view state. A reorder never touches the Field registry and never reaches the Document (ADR 0005). Two Gantts on one Dataset have independent column layouts, exactly like selection and collapse.

**Gestures.** The resize grip is a `.fg-column-resizer` in the header cell, 6px wide, with `--fg-column-resizer-hit` for the pointer target. It reuses `interaction/pointer-gesture.ts` — the same controller drag and resize already use (I6: one transaction per gesture, at commit; here, one event pair at commit). A reorder drag moves the header cell with a drop indicator between columns. Both gestures live in `interaction/column-gestures.ts`, because `view/` does not own pointer sequences.

A width drag clamps to a per-column floor (`--fg-column-min-width`, fallback 40) the same way `minGridWidth` floors the pane splitter (#127). Dragging a column to zero is an accident, never an intent.

**Keyboard parity** (S5.11 checks it, this step ships it): on a focused header cell, `Alt+ArrowLeft` / `Alt+ArrowRight` move the column, and `Shift+ArrowLeft` / `Shift+ArrowRight` resize it by one step. Both go through the same commands the pointer gestures run (D-S5-26).

### D-S5-34 — A hidden column is declared, not deleted (#184, added after S5.10)

`gantt.gridColumns = […]` replaces the authored list whole. A consumer with a "hide this column" control therefore had to keep two lists, or read the list back, filter it, stash the removed entry and splice it in later. Both answers throw away the widths and the order the *user* set on the columns that stayed. The harness wrote the first one, which is how this was found.

`GridColumn` gains one key:

```ts
{ field: 'cost', header: 'Budget', hidden: true }
```

**Hidden means declared and not painted.** The column keeps its place in `gridColumns`, keeps its `width`, and keeps its position in the order, so showing it puts it back exactly where it was. It leaves the resolved columns, which is what takes it out of the grid, out of the pane width (`gridWidth: 'fitColumns'` follows it in), out of `ctx.view.resolvedColumns()`, and out of the resize and reorder gestures — one filter, in `resolveColumns`, so no caller downstream needs to know the key exists. The column is still resolved before it is dropped, so a misspelled field throws where the column is declared and not later when it is shown.

**Two verbs write that key.** The stored state is the long form; the shorthand is what an app author calls:

```ts
gantt.hideGridColumn('cost');
gantt.showGridColumn('cost');
gantt.hiddenGridColumns; // ['cost']
```

`showGridColumn` removes the key rather than writing `hidden: false`, so a bare `'name'` reads back as a bare `'name'` — the same care a resize already takes to rewrite only what it touched (#181). No `toggle*` verb: `toggleCollapse` names the state it toggles, and `toggleGridColumn` could not, since a column has `editable`, `resizable` and `movable` to toggle as well.

**No new event pair.** Hiding runs `ColumnChrome#commitDeclared`, the one commit sequence a resize drag, a reorder drop and a plain assignment already share, so `beforeGridColumnsChange` refuses it like any other column change. This is deliberately the opposite call from D-S5-33, which declined a pair on `registerGridColumn`: that registration changes nothing the consumer owns, so its `from` always equalled its `to`. Hiding changes what `gantt.gridColumns` answers.

**Provenance holds (D-S5-33).** `hidden` is a key on a declaration, so it travels with the declarer the same way `width` does. A hidden consumer column stays in `gantt.gridColumns` and in both halves of the payload, which is what makes the documented save round-trip restore it hidden. A hidden plugin column stays the plugin's: it is absent from the getter, from the payload and from `hiddenGridColumns`, and a consumer who hides one sees a payload reporting no change — the same truthful answer a resize of a plugin column already gives.
