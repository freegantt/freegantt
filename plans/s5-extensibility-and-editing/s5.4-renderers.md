# S5.4 — Renderer callbacks

**Slice:** S5 · **Step:** 4 of 12 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-10, D-S5-11, D-S5-12 · **Closes:** `plans/02` §4 level 3
**Prerequisite:** S5.1 · **Ends with:** `barRenderer` and `cellRenderer` paint consumer output through the existing reconciler, text-safe by default.

## 1. Decisions

### D-S5-10 — `ElementDescription` is the reconciler's vocabulary as plain data

```ts
// model/render.ts — types only
export interface ElementDescription {
  tag?: string;                                   // default 'div'
  class?: Readonly<Record<string, boolean>>;
  style?: Readonly<Record<string, string>>;
  attrs?: Readonly<Record<string, string>>;
  /** Text content. The only text channel. Escaped by construction — it is set as `textContent`. */
  text?: string;
  /** Raw HTML. Explicit opt-in, and never combined with `text` (I13). */
  html?: string;
  /** Keyed children. A child with no `key` is keyed by its index. */
  children?: readonly (ElementDescription & { key?: string })[];
}
```

The type is bounded by what `render/dom/sync-keyed.ts` already applies: attributes, class, style, text, keyed children. It carries no node, no event handler and no lifecycle hook. A renderer that needs one of those means the design is wrong — stop and discuss (CLAUDE.md, `plans/01` §8.1). Consumer interactivity goes through commands (S5.2) and events (`plans/02` §3), which is what those seams are for.

Nodes are recycled by virtualization, so a renderer must never return a live node (`plans/02` §4). Plain data is also what makes a renderer testable in `pure` mode with no DOM at all.

`html` sets `innerHTML` on that one element and skips its `children`. It is the explicit opt-in I13 names, and `render/dom` is the only place that reads it.

### D-S5-11 — One slot per point; consumer config wins; two plugins is an error

```ts
export type RendererPoint = 'bar' | 'cell' | 'header' | 'tooltip';
```

Four points, one slot each. Resolution order:

1. `GanttOptions.barRenderer` / `.cellRenderer` / `.headerRenderer` / `.tooltipRenderer` — the consumer's own, level 3 of the ladder.
2. A plugin's `ctx.view.registerRenderer(point, renderer)` — level 5.
3. The library default.

A consumer's explicit renderer is never silently replaced by a plugin it installed. Two plugins claiming one point throw `RendererAlreadyRegisteredError`, naming the point and both plugin ids — principle 6, diagnostics over a silent last-wins. A consumer that wants a plugin's renderer to win removes its own.

`cell` and `header` renderers receive the resolved column, so one function can branch on `column.field`. The per-column form (`GridColumn.cellRenderer`, S5.7) is more specific and wins over the Gantt-wide `cellRenderer` for that column alone.

```ts
export type BarRenderer = (ctx: { entry: Entry; item: FrameBar }) => ElementDescription | undefined;
export type CellRenderer = (ctx: { entry?: Entry; row: FrameRow; column: ResolvedColumn; value: string }) => ElementDescription | undefined;
```

`undefined` means "keep the library's own output for this one". That is what lets a per-kind map cover one kind and leave the rest alone, with no need for the caller to reproduce the default.

### D-S5-12 — A per-kind map resolves kind, then `'*'`, then the default

`plans/02` §4.1 already publishes the shape:

```ts
barRenderer: {
  milestone: ({ entry }) => diamond(entry),
  buffer:    ({ entry }) => hatched(entry),     // a consumer-defined kind
  '*':       ({ entry }) => defaultish(entry),
}
```

A function is the single-renderer form; a record is the per-kind form. Resolution reads the exact kind, then `'*'`, then the library default. The record form exists so the common case needs no branching, and so a consumer kind slots in by name (`plans/00` principle 9).

Only `bar` takes the per-kind form. A cell belongs to a column and a header to a band; neither has a kind to key on.

## 2. Files

| File | Job |
|---|---|
| `src/model/render.ts` | `ElementDescription`, `Renderer`, the four point types, `RendererByKind` |
| `src/view/renderer-registry.ts` | slot per point, config-over-plugin resolution, `RendererAlreadyRegisteredError` |
| `src/render/dom/element-description.ts` | apply one description to one node, inside the reconciler's scope |
| `src/render/dom/index.ts` | bars and cells call the resolved renderer; `undefined` keeps the current path |
| `src/api/gantt.ts` | the four renderer options and live properties |

`element-description.ts` is `render/dom`'s, not `view/`'s: applying attributes to a node is paint. The registry is `view/`'s, because resolving which renderer a Gantt uses is that Gantt's state.
