**Slice:** S5 · **Step:** 12 of 13 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-40, D-S5-41, D-S5-42 · **Closes:** issue #159
**Prerequisite:** S5.1, S5.8, S5.10 · **Ends with:** one `watchAllErrors` call in `harness/editing.ts`
that logs every refusal and every recovered fault, from both the Dataset and the Gantt, and toasts

**Amended during implementation.** This box read "toasts every refusal and every recovered fault".
The page already toasts its own words for the two refusals it causes on purpose — the mobilization
veto and the lock — and two acceptance tests read those words (`[S3-A8]`, `plugins.spec.ts`). A

## 1. Decisions

Recorded in [ADR 0009](../../docs/adr/0009-core-raises-an-error-report-the-consumer-retains-it.md). This step implements it.

### D-S5-40 — Core raises an Error report; the consumer retains it

`error` fires on the Dataset and on the Gantt, carrying an `ErrorReport`. **There is no `gantt.errors` array and no ring buffer.**

Two halves of one argument. Core must *raise*, because core is the only thing that can observe a refusal: `data/transaction.ts:183` throws `MutationCancelledError` after `emit('beforeChange')` returned false, and a plugin's own handler ran beside the vetoing one and never learns the outcome. `DatasetPluginContext.events` is `beforeChange`/`change` and nothing else, so a plugin can never be the recorder — it also cannot see the Rollup's `AggregatorFailedError`, a renderer throwing in `render/dom/index.ts:81`, or a disposer throwing.

Core must not *retain*, because retention is policy: the cap, the overflow rule, the dedupe, the ordering and what clears it are consumer decisions, and a buffer hanging off `Gantt` is permanent weight for a consumer who never reads it. Their version is three lines:

```ts
const seen: ErrorReport[] = [];
watchAllErrors([dataset, gantt], (report) => { seen.push(report); toast(report.message); });
```

The report:

```ts
interface ErrorReport {
  readonly at: Instant;                          // time/'s now() — I10
  readonly code: ErrorCode;                      // kebab-case, open at the tail
  readonly message: string;
  readonly severity: 'error' | 'warning' | 'info';
  readonly by: 'core' | 'consumer' | PluginId;   // who refused
  readonly entryId?: EntryId;
  readonly field?: FieldKey;
  readonly cause?: unknown;                      // the FreeGanttError, when one exists
}
```

It lives in `model/`, so it is reachable from both buses — `DatasetEventMap` is already `model/`'s
public event vocabulary. **Implementation deviation:** it is `model/error-report.ts`, not
`model/errors.ts`. `errors.ts` names `ChangeSet` (for `MutationCancelledError`), and `change-set.ts`
must now name `ErrorReport` (for `DatasetEventMap`), so one file for both closes a `no-circular`
cycle. The split also says out loud what `CONTEXT.md` stresses: `FreeGanttError` is the class you
**catch**, an `ErrorReport` is the record you **subscribe to**.

Flat fields plus `cause`, not a wrapped error: every report renders and serializes with no type test, and nothing is lost — `cause` carries `MutationCancelledError.changeSet`, `PluginSetupError.pluginId`, and the chain. Not every raise site has an error object (a silent gesture veto has none), which is why `code`/`message` are the required pair and `cause` is optional.

`by` is the field name because `origin` is taken (`ChangeOrigin`) and `CONTEXT.md` bars a bare `source` (Field source, Row source).

**Two type names the sketch above leaves implicit, and both shipped.** `by`'s union is named `ErrorReporter`, so a consumer can write the type of a filter over it. `ErrorReportInput` is `Omit<ErrorReport, 'at'>`, because a raise site names the fault and `time/` stamps the clock — that is what keeps every `now()` read inside `time/` (I10).

`ErrorCode` is `'mutation-cancelled' | … | (string & {})` — the shape `EntryKind` already uses. Autocomplete on the shipped codes, and a plugin can still mint its own, which `by: PluginId` requires.

**`CellEditorRefusal`'s keys go kebab-case** (`derivedValue` → `derived-value`) and become codes. It
touches `REFUSAL_TEXT`, the `data-reason` values, `e2e/editing.spec.ts` and `s5.8`'s own refusal
table. One refusal must not have two spellings, and kebab is the better value for a DOM attribute
anyway. **Implementation note:** `view/styles.ts` needed no selector change. Its one rule matches the
`[data-reason]` attribute and never a value, so nothing there spelled a reason.

### D-S5-41 — `severity` is `error`/`warning`/`info`, so a Refusal is not a Fault

`'info'` — a Refusal: the library said no on purpose and nothing is broken. `'warning'` — degraded but recovered. `'error'` — something broke and nothing caught it.

Not `'refusal' | 'fault'`: those are two different things, not two levels, so a field named `severity` would have covered two concepts with one generic word (CLAUDE.md, the #7 precedent).

This is what lets the event be named `error` without breaking `CONTEXT.md`'s standing rule that a Refusal is not an Error. The distinction moved from the event's name into the payload. The name buys familiarity — every consumer knows what `on('error')` gives them — and `severity` pays the honesty back.

**The seven existing `console.*` sites keep the severity they already chose.** Four are `console.error` and three are `console.warn`; no site is re-litigated.

| Site | Severity |
|---|---|
| `render/dom/index.ts:81` — a renderer threw, fell back to default output | `warning` |
| `extensions/install-dataset-plugins.ts:98` — a dataset plugin's disposer threw | `error` |
| `extensions/plugin-runtime.ts:155` | `warning` |
| `extensions/plugin-runtime.ts:169` — a plugin's disposer threw | `error` |
| `view/plugin-ports.ts:397` — a tooltip renderer threw, fell back to the default content | `warning` |
| `view/gantt-shell.ts:465` | `warning` |
| `data/serialization/index.ts:81` — a Document key dropped on read | `warning` |

Each site **always raises**. Its `console` call becomes a **fallback that fires only when nothing is subscribed to `error`** — Node's `EventEmitter` convention, where an unhandled `'error'` is treated as unhandled. A consumer who subscribes gets silence and full control; a consumer who does not keeps exactly the output they have today. No regression either way, and the consumer needs no config key and no build flag to choose.

**Not behind `isDevMode()`.** `data/dev-mode.ts` reads `import.meta.env.DEV`, which Vite replaces when **this repo** builds `dist/`, not when a consumer builds their app. It bakes to `false` and Rollup drops the branch: `render/dom/index.ts:81`'s message is already behind that guard and appears **zero** times in `dist/api/index.js`, while the two unguarded disposer `console.error`s survive. `isDevMode()` is a library-development flag — true only for our own harness, running from source — so guarding these seven sites with it would delete them from the shipped library entirely, in a consumer's dev and prod alike. That is a capability loss, not a quiet-in-production win.

**And not a build flag of any kind.** One `dist/` serves every consumer, and their production mode is invisible when we build it. The three mechanisms that could see it — `process.env.NODE_ENV` left unresolved for their bundler, dual builds behind `exports` conditions, or a runtime config key — each cost something (raw-ESM consumption, a doubled tree-shaking budget in S5.13, or permanent bundle weight), and the subscription check above already gives the consumer the off switch.

**Every refusal raises, silent gestures included.** `plans/02` §3's "a vetoed gesture is silent" stays true of the *UI* — nothing is drawn, nothing throws — and gains one sentence: it reports. The echo (a consumer's own `false` coming back to them) is one record per gesture, and `by` makes it filterable. `by` is the fact worth having when three plugins and a consumer handler all hold a veto.

### D-S5-42 — `watchAllErrors` gives one feed over two emitters

Reports originate in two places, and `plans/02` §3 keeps them there: a Dataset raises what a Dataset observes, a Gantt raises what a Gantt observes. A consumer wants one subscription.

```ts
const stop = watchAllErrors([dataset, gantt], (report) => {
  toast(report.message);
  if (report.severity !== 'info') sendToTelemetry(report);
});
```

An `api/` helper beside `attemptMutation`, and for the same reason: a common consumer job that needs boilerplate the library can write once. It de-duplicates by emitter identity, so `[dataset, gantt1, gantt2]` subscribes the shared Dataset once, and returns one disposer that unsubscribes all of them.

**Not** the Gantt forwarding the Dataset's reports. Two Gantts on one Dataset would deliver every Dataset report twice, reports raised during `new Dataset(...)` would be missed entirely, and the Gantt would claim authorship of what it did not observe.

**This step ships no presenter.** A generic toast is not Gantt domain knowledge, and shipping one means owning its stacking, timing, theming and announcement. `harness/editing.ts` demonstrates the wiring; promote it to `extensions/features/` only if that harness code turns out to be what every consumer copies verbatim. Shipping nothing also keeps S5.13's `sideEffects` array and tree-shaking budget clean by construction.

## 5. Found while implementing — not this step

- **A `before*` veto cannot say why.** Core raises `entry-move-cancelled` / `mutation-cancelled` with
  a message that names the event and nothing else, because the bus reports a `false`, not a reason.
  A page that already showed its own words then has to choose between its message and the report's.
  `harness/editing.ts` chose, and the Ends-with above records it. **Filed as issue #210**, which
  carries three candidate shapes and picks none yet.
- **`plugin-ports.ts`'s tooltip renderer is `warning`, not `error`.** Resolved after the merge. §1's
  table said `error`; the implementer flagged the conflict and built the table as written, which was
  correct. The evidence settles it: the site's own message says "falling back to the default
  content", so it recovered, and `CONTEXT.md`'s **Severity** entry names "a renderer that threw and
  fell back to the default output" as *the* example of `warning`. Two sites raising one code after
  the same recovery must agree. The table row was wrong, not the glossary.

  The `console.error` fallback stays `console.error`. `RaiseError` takes the site's own line so each
  site's output is byte-identical to what it printed before S5.12, and deriving the console method
  from `severity` is what that design refused.

- **`data/rollup.ts` raises nothing.** §2's file table lists it, §4 has no box for it, and it has no
  bus: it is a pure, `rollup-is-removable` leaf. Its `AggregatorFailedError` is thrown, so the caller
  already sees it. Left alone deliberately.
- **#204's list of six `isDevMode()` sites is really a list of two.** The handoff counts seven guard
  sites and hands one (`render/dom/index.ts`) to this step. Four of the other six *are* the guard
  around one of this step's own seven `console.*` calls, one line above it:
  `plugin-runtime.ts:103`/`155`, `serialization/index.ts:73`/`81`, `plugin-ports.ts:415`/`417`, and
  `gantt-shell.ts:473`/`474`. D-S5-41 says those seven are not behind `isDevMode()`, so this step took
  all four guards down with them. What is left for #204 is `data/build-commit-change-set.ts:66` and
  `data/transaction.ts:163`, both of which are library-development assertions, not consumer warnings.
- **The `data/dev-mode.ts` leaf widening is now unused for two layers.** `render/` and `extensions/`
  no longer import it: this step took the last call site out of each. `.dependency-cruiser.cjs` still
  lists `DEV_MODE_LEAF` on `render-boundary` and `extensions-public-only`. Narrowing a shared guard is
  not this step's call; it belongs with #204, which is the audit of the two sites that remain
  (`data/build-commit-change-set.ts`, `data/transaction.ts`).
- **`view/entry-gesture-context.ts` needed no change.** §2's file table lists it beside
  `gesture-pipeline.ts`, but the file is types only and holds no veto path.
