# S5.12 — Error reporting

**Slice:** S5 · **Step:** 12 of 13 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-35, D-S5-36, D-S5-37 · **Closes:** issue #159
**Prerequisite:** S5.1, S5.8, S5.10 · **Ends with:** one `watchAllErrors` call in `harness/editing.ts` that toasts every refusal and every recovered fault, from both the Dataset and the Gantt.

## 1. Decisions

Recorded in [ADR 0009](../../docs/adr/0009-core-raises-an-error-report-the-consumer-retains-it.md). This step implements it.

### D-S5-35 — Core raises an Error report; the consumer retains it

`error` fires on the Dataset and on the Gantt, carrying an `ErrorReport`. **There is no `gantt.errors` array and no ring buffer.**

Two halves of one argument. Core must *raise*, because core is the only thing that can observe a refusal: `data/transaction.ts:183` throws `MutationCancelledError` after `emit('beforeChange')` returned false, and a plugin's own handler ran beside the vetoing one and never learns the outcome. `DatasetPluginContext.events` is `beforeChange`/`change` and nothing else, so a plugin can never be the recorder — it also cannot see the Rollup's `AggregatorFailedError`, a renderer throwing in `render/dom/index.ts:81`, or a disposer throwing.

Core must not *retain*, because retention is policy: the cap, the overflow rule, the dedupe, the ordering and what clears it are consumer decisions, and a buffer hanging off `Gantt` is permanent weight for a consumer who never reads it. Their version is three lines:

```ts
const seen: ErrorReport[] = [];
watchAllErrors([dataset, gantt], (report) => { seen.push(report); toast(report.message); });
```

The report:

```ts
interface ErrorReport {
  readonly at: Instant;                          // time/'s now() — I10
  readonly code: ErrorCode;                      // kebab-case, open at the tail
  readonly message: string;
  readonly severity: 'error' | 'warning' | 'info';
  readonly by: 'core' | 'consumer' | PluginId;   // who refused
  readonly entryId?: EntryId;
  readonly field?: FieldKey;
  readonly cause?: unknown;                      // the FreeGanttError, when one exists
}
```

It lives in `model/errors.ts`, beside `FreeGanttError` — `model/`'s runtime carve-out already covers that file, `DatasetEventMap` is already `model/`'s public event vocabulary, and the type must be reachable from both buses.

Flat fields plus `cause`, not a wrapped error: every report renders and serializes with no type test, and nothing is lost — `cause` carries `MutationCancelledError.changeSet`, `PluginSetupError.pluginId`, and the chain. Not every raise site has an error object (a silent gesture veto has none), which is why `code`/`message` are the required pair and `cause` is optional.

`by` is the field name because `origin` is taken (`ChangeOrigin`) and `CONTEXT.md` bars a bare `source` (Field source, Row source).

`ErrorCode` is `'mutation-cancelled' | … | (string & {})` — the shape `EntryKind` already uses. Autocomplete on the shipped codes, and a plugin can still mint its own, which `by: PluginId` requires.

**`CellEditorRefusal`'s keys go kebab-case** (`derivedValue` → `derived-value`) and become codes. It touches `REFUSAL_TEXT`, the `data-reason` values, and `view/styles.ts`'s selectors. One refusal must not have two spellings, and kebab is the better value for a DOM attribute anyway.

### D-S5-36 — `severity` is `error`/`warning`/`info`, so a Refusal is not a Fault

`'info'` — a Refusal: the library said no on purpose and nothing is broken. `'warning'` — degraded but recovered. `'error'` — something broke and nothing caught it.

Not `'refusal' | 'fault'`: those are two different things, not two levels, so a field named `severity` would have covered two concepts with one generic word (CLAUDE.md, the #7 precedent).

This is what lets the event be named `error` without breaking `CONTEXT.md`'s standing rule that a Refusal is not an Error. The distinction moved from the event's name into the payload. The name buys familiarity — every consumer knows what `on('error')` gives them — and `severity` pays the honesty back.

**The seven existing `console.*` sites keep the severity they already chose.** Four are `console.error` and three are `console.warn`; no site is re-litigated.

| Site | Severity |
|---|---|
| `render/dom/index.ts:81` — a renderer threw, fell back to default output | `warning` |
| `extensions/install-dataset-plugins.ts:98` — a dataset plugin's disposer threw | `error` |
| `extensions/plugin-runtime.ts:155` | `warning` |
| `extensions/plugin-runtime.ts:169` — a plugin's disposer threw | `error` |
| `view/plugin-ports.ts:397` | `error` |
| `view/gantt-shell.ts:465` | `warning` |
| `data/serialization/index.ts:81` — a Document key dropped on read | `warning` |

Each site **always raises**, and keeps its `console` call **behind `isDevMode()`** (`data/dev-mode.ts`). In dev the console keeps a clickable stack, which no payload gives. In production the library goes quiet unless the consumer asked to hear. This is a deliberate behaviour change: a consumer who never subscribes loses a warning they see today.

**Every refusal raises, silent gestures included.** `plans/02` §3's "a vetoed gesture is silent" stays true of the *UI* — nothing is drawn, nothing throws — and gains one sentence: it reports. The echo (a consumer's own `false` coming back to them) is one record per gesture, and `by` makes it filterable. `by` is the fact worth having when three plugins and a consumer handler all hold a veto.

### D-S5-37 — `watchAllErrors` gives one feed over two emitters

Reports originate in two places, and `plans/02` §3 keeps them there: a Dataset raises what a Dataset observes, a Gantt raises what a Gantt observes. A consumer wants one subscription.

```ts
const stop = watchAllErrors([dataset, gantt], (report) => {
  toast(report.message);
  if (report.severity !== 'info') sendToTelemetry(report);
});
```

An `api/` helper beside `attemptMutation`, and for the same reason: a common consumer job that needs boilerplate the library can write once. It de-duplicates by emitter identity, so `[dataset, gantt1, gantt2]` subscribes the shared Dataset once, and returns one disposer that unsubscribes all of them.

**Not** the Gantt forwarding the Dataset's reports. Two Gantts on one Dataset would deliver every Dataset report twice, reports raised during `new Dataset(...)` would be missed entirely, and the Gantt would claim authorship of what it did not observe.

**This step ships no presenter.** A generic toast is not Gantt domain knowledge, and shipping one means owning its stacking, timing, theming and announcement. `harness/editing.ts` demonstrates the wiring; promote it to `extensions/features/` only if that harness code turns out to be what every consumer copies verbatim. Shipping nothing also keeps S5.13's `sideEffects` array and tree-shaking budget clean by construction.
