# S5.2 — Commands and keybindings

**Slice:** S5 · **Step:** 2 of 12 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-6, D-S5-7
**Prerequisite:** S5.1 · **Ends with:** one named command runs from a chord, from a menu item (S5.5), and from `gantt.commands.run(id)`.

## 1. Decisions

### D-S5-6 — One command registry; menus and chords both name a command

A command is a named, invokable action with a label and a condition.

**No `Command<TArgs>` generic (issue #137 G).** Every invocation path — a menu item, a chord, `gantt.commands.run(id)` — is argument-less; nothing in this slice calls a command with a payload. A generic that nothing instantiates non-trivially also erases at the registry boundary (`CommandRegistry.register` cannot know `TArgs` for a command it stores type-erased), which makes `run<TArgs>` type-unsound in practice — it would accept any `args` for any `id` with no way to check the pairing. Args return when a real caller needs them, as a new field on `Command`, not a generic reintroduced speculatively.

```ts
export interface Command {
  id: string;                                   // 'freegantt.collapseAll', 'demo.markLate'
  label: string;                                // menu text; also the a11y name
  /** Static availability. Absent means always available. */
  when?(ctx: CommandContext): boolean;
  run(ctx: CommandContext): void;
}

export interface CommandContext {
  gantt: Gantt;
  dataset: Dataset;
  /** The entry the invocation targeted: the right-clicked bar, the focused row, or none. */
  entry?: Entry;
  /**
   * What has focus when the invocation happened (issue #137 F6). S5.7's and S5.11's
   * chord scoping — "on a focused header cell", "on a selected bar", "on the splitter" —
   * has nothing else in `CommandContext` to read a `when` against. Filled by the keymap
   * resolver from view state; a menu or `run(id)` invocation with no meaningful target
   * for this kind leaves it `undefined`.
   */
  target?: { kind: 'row' | 'cell' | 'bar' | 'header' | 'splitter'; rowId?: EntryId; columnKey?: FieldKey };
}

export interface CommandRegistry {
  register(command: Command): void;
  run(id: string): void;                          // UnknownCommandError when nothing owns the id
  /** Commands whose `when` passes for this context, in registration order. */
  available(ctx: CommandContext): readonly Command[];
}
```

The registry is the a11y seam (D-S5-26). A pointer affordance and its command land in the same change, so the keyboard path is a binding over the same command rather than a second implementation of the same behaviour. This is also why the context menu (S5.5) has no item type of its own beyond an id and an optional separator.

Core registers its own commands during construction, before any plugin: `freegantt.collapseAll`, `freegantt.expandAll`, `freegantt.collapseRow`, `freegantt.expandRow`, `freegantt.zoomIn`, `freegantt.zoomOut`, `freegantt.panToToday`, `freegantt.selectAll`, `freegantt.clearSelection`, `freegantt.undo`, `freegantt.redo`. Every one already exists as a public method; the command is a named handle on it, never a second code path.

Commands are synchronous in S5. An async command needs a progress affordance and a cancel story, and no consumer has asked for one — README §10 records the deferral.

### D-S5-7 — Last registration gets first refusal; a decline falls through

```ts
export type KeyChord = string;         // 'ArrowRight', 'Mod+Z', 'Shift+F10', 'Alt+ArrowLeft'

export interface KeyBinding {
  chord: KeyChord;
  command: string;
  /** Extra condition beyond the command's own `when`. */
  when?(ctx: CommandContext): boolean;
  /** Fire even while the event's target is editable or mid-IME-composition. Default `false` (issue #137 F7). */
  captureInEditable?: boolean;
}
```

Resolution, on every key event: take the bindings for that chord, walk them **newest first**, and run the first one whose `when` and whose command's `when` both pass. A decline falls through to the next. Nothing matching means the event is untouched, so the browser keeps it.

Core registers first, so a plugin can override core — which is the whole reason a plugin exists. Among plugins, the later entry in `plugins` wins, and that order is the consumer's own array, read top to bottom. No priority numbers, no conflict error, and no arbitration table: the order is written at the install site, which is the same principle D-S5-23 applies to the extender.

`Mod` means `⌘` on Apple platforms and `Ctrl` elsewhere; the resolver is the only place that branches on it. Chord strings are parsed once at registration and compared as a normalized record, never re-parsed per event (I5's spirit: the key path allocates nothing per event).

**The editable-target rule (issue #137 F7).** Before resolving any binding, the resolver checks the key event's own target: an `<input>`, a `<textarea>`, an element with `contenteditable`, or an event mid-IME-composition (`event.isComposing`). For such a target, the resolver runs nothing and leaves the event alone — a plugin's bare-letter binding, or `Mod+Z` typed while the cell editor (S5.8) is open, must not fire while the user is typing. A binding opts back in with `captureInEditable?: boolean` on `KeyBinding` (default `false`) for the rare case that needs it (the editor's own Enter/Escape handling is not a `KeyBinding` at all — it is the editor's own key handler, S5.8 — so this default does not fight it).

A binding runs its command through the same `run(id)` a menu item uses, so a veto or a guard written once holds for both.

## 2. Files

| File | Job |
|---|---|
| `src/model/command.ts` | `Command`, `CommandContext`, `KeyBinding`, `KeyChord` — types only |
| `src/extensions/commands.ts` | the registry: register, run, available; `UnknownCommandError` |
| `src/extensions/keymap.ts` | chord parse, normalize, `Mod` resolution, newest-first resolution |
| `src/view/gantt-shell.ts` | registers the core commands; routes key events to the resolver before its own handling |
| `src/view/keyboard-navigation.ts` | its existing chords become bindings over core commands |
| `src/api/gantt.ts` | `Gantt.commands` (the registry, read-only property) |

`view/keyboard-navigation.ts` keeps the roving-focus mechanics. Only its action half moves to commands, so no behaviour changes in this step — the test file proves that by keeping its existing assertions green.

## 3. Tests

- `src/extensions/commands.test.ts` — `run` on an unknown id throws `UnknownCommandError`; `available` filters by `when`; a command's `run` gets the entry the invocation targeted
- `src/extensions/keymap.test.ts` — newest-first resolution; a declining `when` falls through to an older binding; `Mod` maps per platform; an unmatched chord leaves the event alone; a chord typed inside an `<input>`/`<textarea>`/`contenteditable` or mid-composition is ignored unless `captureInEditable` is set (issue #137 F7)
- `src/view/keyboard-navigation.test.ts` — existing assertions stay green with the actions behind commands
- `src/api/gantt.test.ts` — `gantt.commands.run('freegantt.collapseAll')` collapses; a plugin binding on `ArrowRight` wins over core only while its `when` passes
