# S5.2 — Commands and keybindings

**Slice:** S5 · **Step:** 2 of 12 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-6, D-S5-7
**Prerequisite:** S5.1 · **Ends with:** one named command runs from a chord, from a menu item (S5.5), and from `gantt.commands.run(id)`.

## 1. Decisions

### D-S5-6 — One command registry; menus and chords both name a command

A command is a named, invokable action with a label and a condition.

```ts
export interface Command<TArgs = void> {
  id: string;                                   // 'freegantt.collapseAll', 'demo.markLate'
  label: string;                                // menu text; also the a11y name
  /** Static availability. Absent means always available. */
  when?(ctx: CommandContext): boolean;
  run(ctx: CommandContext, args: TArgs): void;
}

export interface CommandContext {
  gantt: Gantt;
  dataset: Dataset;
  /** The entry the invocation targeted: the right-clicked bar, the focused row, or none. */
  entry?: Entry;
}

export interface CommandRegistry {
  register<TArgs>(command: Command<TArgs>): void;
  run<TArgs>(id: string, args?: TArgs): void;     // UnknownCommandError when nothing owns the id
  /** Commands whose `when` passes for this context, in registration order. */
  available(ctx: CommandContext): readonly Command<unknown>[];
}
```

The registry is the a11y seam (D-S5-26). A pointer affordance and its command land in the same change, so the keyboard path is a binding over the same command rather than a second implementation of the same behaviour. This is also why the context menu (S5.5) has no item type of its own beyond an id and an optional separator.

Core registers its own commands during construction, before any plugin: `freegantt.collapseAll`, `freegantt.expandAll`, `freegantt.collapseRow`, `freegantt.expandRow`, `freegantt.zoomIn`, `freegantt.zoomOut`, `freegantt.panToToday`, `freegantt.selectAll`, `freegantt.clearSelection`, `freegantt.undo`, `freegantt.redo`. Every one already exists as a public method; the command is a named handle on it, never a second code path.

Commands are synchronous in S5. An async command needs a progress affordance and a cancel story, and no consumer has asked for one — README §10 records the deferral.

### D-S5-7 — Last registration gets first refusal; a decline falls through

```ts
export type KeyChord = string;         // 'ArrowRight', 'Mod+Z', 'Shift+F10', 'Alt+ArrowLeft'

export interface KeyBinding {
  chord: KeyChord;
  command: string;
  /** Extra condition beyond the command's own `when`. */
  when?(ctx: CommandContext): boolean;
}
```

Resolution, on every key event: take the bindings for that chord, walk them **newest first**, and run the first one whose `when` and whose command's `when` both pass. A decline falls through to the next. Nothing matching means the event is untouched, so the browser keeps it.

Core registers first, so a plugin can override core — which is the whole reason a plugin exists. Among plugins, the later entry in `plugins` wins, and that order is the consumer's own array, read top to bottom. No priority numbers, no conflict error, and no arbitration table: the order is written at the install site, which is the same principle D-S5-23 applies to the extender.

`Mod` means `⌘` on Apple platforms and `Ctrl` elsewhere; the resolver is the only place that branches on it. Chord strings are parsed once at registration and compared as a normalized record, never re-parsed per event (I5's spirit: the key path allocates nothing per event).

A binding runs its command through the same `run(id)` a menu item uses, so a veto or a guard written once holds for both.

| File | Job |

| `src/model/command.ts` | `Command`, `CommandContext`, `KeyBinding`, `KeyChord` — types only |

`view/keyboard-navigation.ts` keeps the roving-focus mechanics. Only its action half moves to commands, so no behaviour changes in this step — the test file proves that by keeping its existing assertions green.
