# S5.8 — Inline editing

**Slice:** S5 · **Step:** 8 of 12 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-19, D-S5-20 · **Proves:** `[S5-A5]`
**Prerequisite:** S5.3, S5.7 · **Ends with:** a cost cell edits in place and commits one transaction, and a consumer replaces the whole editor through `beforeEntryEdit`.

## 1. Decisions

### D-S5-19 — The editor is a plugin, and `beforeEntryEdit` suppresses it

```ts
new Gantt({ container, dataset, plugins: [inlineEditing()] });
```

`plans/01` §10 already names editors as a dogfood case, and a read-only Gantt must not carry editor code (`[S5-A6]`). So the built-in editor is `inlineEditing()`, an ordinary plugin under the same import rule as the other two (D-S5-5).

**Opening.** A double-click, or `Enter` on a focused cell — the key S3 reserved for exactly this (D-S3-13). The cell's Field must be writable on that entry — one question, `canWrite(entry, field)`, since #256 (S5.7). `Interactions` gains `edit`, which S3 left off the type deliberately (`view/capability.ts`'s comment says "until S7/S5"; this is S5). One resolution hides the affordance and refuses the gesture (I14), the same as `move` and `resize`.

**Committing.** Enter or blur commits. Escape discards the edit and writes nothing (D-S5-47). One commit is one `dataset.entries.update(id, { [field]: value })` — one transaction, one changeset, one undo step (I6). Never per keystroke.

**The event pair.** `beforeEntryEdit` is cancelable and fires **before the editor opens**, not before the write. That is what makes "bring your own editor" work:

```ts
gantt.on('beforeEntryEdit', async ({ entry, field }) => {
  await myDialog.open(entry, field);
  return false;                       // suppress the built-in editor
});
```

`entryEdit` fires after the commit, carrying `{ from, to }`. A consumer that vetoes and then writes through `dataset.entries.update` gets the ordinary `change` event for the write — there is no second write channel.

```ts
export interface EntryFieldEdit {
  entry: Entry;
  field: FieldKey;
  from: unknown;
  to: unknown;
}
```

Named `EntryFieldEdit`, not `EntryEdit`: `EntryEdit` is already the write shape `update()` takes (`plans/02` §1, "one write shape"). One name, one concept.

A veto of the **write** is still `beforeChange` on the Dataset, unchanged. Two events, two questions: "may this editor open" and "may this changeset commit".

**Editing races a moving dataset (issue #137 F10).** Four cases, each with one stated answer:

- **The anchor entry disappears while the editor is open** (removed by another call, or the row virtualizes out of the frame). The editor closes without committing — there is nothing left to write to, and a value typed against a gone entry is not a value the consumer asked for.
- **`beforeChange` vetoes the commit** (a plugin's rule, unrelated to this editor, rejects the changeset). The editor does not close: it stays open, in the invalid state (`data-state~="invalid"`, the same one a failed `parseValue` uses), with focus still on the control. The user sees the same "this did not save" signal a parse failure gives, not a silent discard. Blur while invalid does not re-commit and does not pull focus back (D-S5-47): "focus is restored" scopes to the Enter path alone (#137 F5).
- **A blur commits while something else is also closing the popup** (a context-menu click on another cell, say, which both blurs the current editor and opens a menu). Blur-triggered commit runs first, synchronously, before the popup that caused the blur finishes opening — `Popup`'s own `dismissOn: ['blur']` (S5.3) already orders it this way for every popup, so the editor is not a special case. `extensions/features/inline-editing.test.ts` gets a named test for this ordering.
- **The entry is removed by an external call while a commit from this editor is already in flight** (the transaction opens against a store that no longer has the row). `dataset.entries.update` already throws `EntryNotFoundError` for an unknown id (`plans/02` §7); the editor catches that one case and closes without further error, since the user's own edit is now moot.

### D-S5-47 — the invalid Cell editor has a visible exit, and one command behind it

A refused commit keeps the editor open (#137 F5). Until now that state had one exit, Escape, and nothing said so. Focus returned to the control on every blur, so a pointer user was held in the cell with no way out but a key. Issue #160.

Three changes, one decision:

1. The invalid editor shows a **discard button** inside its own wrapper, after the control: `<button type="button" class="fg-cell-editor-discard" aria-label="Discard edit" title="Discard edit">×</button>`. It is in the focus trap's cycle, so Tab reaches it.
2. The button runs **`freegantt.discardCellEdit`** (label `Discard edit`, `when: () => editing.editor !== undefined`), an ordinary registration on the command registry (D-S5-6). That is the public way, and D-S5-26's rule — a pointer affordance and its command land together — is why there is no second implementation. No `Gantt` member is added: a read-only Gantt must carry no editor code (`[S5-A6]`, D-S5-19). `view/core-commands.ts` holds an inert placeholder registration (`when: () => false`) so a Gantt with no `inlineEditing()` still answers the id, and the plugin's own registration overrides it by D-S5-7 stacking.
3. **Blur while invalid stops re-committing.** `#onFocusOut` returns early when the editor is already invalid. It leaves the editor open and invalid, and it does not pull focus back. Re-attempting a value the Field just refused buys nothing and costs the user the cell.

Escape and the button take one road. Both call `CellEditorPorts.requestDiscard()`, which runs `ctx.commands.run('freegantt.discardCellEdit')`, and the registered command lands on `CellEditing.discard()`. Overriding the command therefore changes both, which is the point of routing an affordance through a command at all. #231 F2 closed the gap: Escape used to call `CellEditing.discard()` straight, so an override reached the button alone.

**The word is `discard`,** not revert and not cancel. `revert` names undo restoring a value already written in `data/`; `cancel` is the word `CONTEXT.md`'s **Veto** entry tells us to avoid. `CellEditorSession.revert()` and `CellEditing.revert()` are renamed `discard()`; the one port is `requestDiscard`.

**No ADR.** The domain-modeling skill's three tests need all three, and this fails the third: D-S5-19 and D-S5-26 already decide the shape, and this applies them. The `CONTEXT.md` **Discard** term carries the rest.

**One latent bug this surfaced.** `view/styles.ts` selected the refusal notice's look on `[data-reason]` alone — the attribute's mere presence. That held only while the notice was the single node wearing it. A refused commit's own editor now carries `data-reason` too, so the rule became `:not(:has(.fg-cell-editor-control))`, and a pre-existing test that went through the `refusal()` helper started failing. Neither was introduced here: a selector keyed on presence rather than on the thing it means can only fire once a second thing wears the attribute. #231 F1 closed it properly: the notice took its own class, `.fg-cell-notice`, and both `:not(:has(...))` sites went away.

### D-S5-20 — The `dateInput` seam, with no picker dependency

A date cell needs a date control. `plans/04` §1 budgets two runtime dependencies and a picker is not one of them, so the library ships the platform control and publishes a seam.

```ts
export interface DateInput {
  /** The control to mount in the cell. */
  readonly element: HTMLElement;
  /** Reads what the user entered, in the dataset's zone. `undefined` means "not a date". */
  read(): Instant | undefined;
  /** Called when the editor opens. */
  write(at: Instant): void;
  /** The editor calls this to learn when the user is done (Enter, or the control's own commit). */
  onCommit(handler: () => void): Disposer;
  destroy(): void;
}

export type DateInputFactory = (ctx: { zone: string; locale?: Intl.LocalesArgument }) => DateInput;

inlineEditing({ dateInput: myPickerFactory })
```

The default factory is `<input type="date">`, read through `time/`'s `toInstant` in the dataset zone and written back with `formatDate` — never with `Date` parsing, and never with an inline `end - 1` (the inclusive-display rule, `plans/01` §5). A date-only `end` reads and writes inclusively, through the one formatting helper, so what the user sees in the cell is what they see in the editor.

**A non-midnight instant refuses the default editor, it does not truncate it (issue #137 F11).** `<input type="date">` has no time-of-day control, so an entry whose stored instant is not midnight in the dataset zone (`2026-09-01T14:00Z`, say — a Field that carries a time component) cannot round-trip through it: opening it and pressing Enter with no change would silently rewrite the value to midnight, a data change the user never asked for. The default factory checks this on open — `time/`'s `toPlain` at the dataset zone, comparing against `startOfDay` — and when the instant is not midnight, the cell refuses to open the default editor at all, with the invalid state and a reason naming it (`data-state~="invalid"`, "this field carries a time of day; the default date editor cannot show it"). A consumer whose Field genuinely needs time-of-day editing passes its own `dateInput` factory (built on a `datetime-local` control, say) through `inlineEditing({ dateInput: … })` — this default only ever handles the date-only case it was built for.

Text and number cells need no seam: the editor mounts an `<input>` and parses with the Field type's own rules. **There is no default numeric parser (issue #137 F12).** A Field whose `formatValue` produces anything other than a plain string round-trip needs its own `parseValue` — `formatValue` is not invertible in general (a currency-formatted `"€1.234,56"` cannot be parsed back without knowing the format that produced it), so the library ships no guess at one. Without a `parseValue`, the Field's own `type` decides: `text` reads and writes the raw string; every other shipped type falls back to the invalid state on open, refusing to edit inline rather than silently parsing wrong — the cell stays read-only for that Field until the consumer supplies `parseValue`. (No shipped Field type is named `money`; a consumer type with currency formatting is exactly the case that needs its own `parseValue`.)

### Which refusals speak, and which stay silent (review SP1)

A double-click that opens no editor must not look the same in every case. The rule is one sentence:

> A cell that offers no editor refuses in silence. A cell that offers one, and cannot open it here, names the reason.

| The user double-clicks | The editor | Why |
|---|---|---|
| a cell whose entry resolves `edit: false` | silent | I14 hides the affordance from the same resolution that refuses the gesture. No affordance means nothing to explain. |
| a cell whose Field is not writable here (#256) | silent | Nothing offered the write, so the refusal is already visible. |
| a rolled-up parent's own rolled-up Field | names `derived-value` | The column does offer an editor. The value comes from the children. |
| a date Field with no stored date | names `no-date-value` | The default date control needs a date to seed. |
| a date Field whose instant carries a time of day (F11) | names `time-of-day` | The default `<input type="date">` cannot show it. |
| a Field with no `parseValue` and a non-`text` type (F12) | names `no-parse-value` | The library ships no guessed parse. |
| a second cell, while an open editor holds a refused value (review C2) | names `unsaved-value` | The first editor declines to close. The user fixes that value or presses Escape. |

The two silent rows are a decision, not an omission. A silent refusal answers "this cell is not editable". A named refusal answers "this cell is editable, but not by this editor". The two answers stay different on purpose.

**A refused *commit* speaks too (#234).** The seven rows above are open-time refusals, on a cell that
never opened. A commit that fails leaves the editor open instead, in `data-state="invalid"`, and it
names one of two reasons: `unreadable-value` when the control reads no value back from the text, and
`refused-write` when a handler vetoed the write. Both raise an Error report, `severity: "info"`, with
the reason key as the `code` — the same one-spelling rule the notice keys follow.

A vetoed cell commit therefore raises **two** reports, and that is deliberate. Core says a registered
handler refused this changeset (`mutation-cancelled`, `by: "consumer"`). This plugin says the editor
stayed open holding an unsaved value (`refused-write`, `by` its own id). They are different facts at
two layers, so the two messages never repeat each other: this plugin writes about editor state, and
never about why the write was refused.

**The mechanism.** A named refusal mounts a **refusal notice** over the cell. It uses the same row layer the editor uses (`ctx.view.rowLayer`, #158). The notice carries `class="fg-cell-notice"` and `data-reason="<key>"` (#231 F1: it held `class="fg-cell-editor"` and `data-state="invalid"` until an editor started carrying `data-reason` too). Its text is the reason. The same words are its `title`, because a cell is often narrower than the sentence. `inline-editing.ts`'s `REFUSAL_TEXT` holds every message, so the wording lives in one table and never at a call site.

The notice mounts no control and it takes no focus. It sets `pointer-events: none`, so the next double-click reaches the cell below it. Five things clear it: the next pointer press in this Gantt, Escape, a scroll, a Dataset change, and the next open.

The notice paints itself from published level-1 tokens (`--fg-warn`, `--fg-pane-bg`, `--fg-cell-padding-inline`), with a fallback for each. `styles.ts` selects it on its own class alone (#231 F1).

**A11y.** The notice carries `role="status"`. A screen reader does not announce a script-inserted `role="status"` node reliably. S5.11 owes the real announcement through its own polite live region — see [`s5.11-a11y-completion.md`](./s5.11-a11y-completion.md).

### Landed — implementation notes and open calls (2026-09-03)

The step file above did not pin every detail; these are the calls made while landing it, worth a
second look:

- **Date-field routing is `field.type === 'date'`.** Core `start` and `end` name that type, and the shipped type table seeds `date`. `inlineEditing.ts`'s `isDateField` matches the type name only — it does not special-case the two keys. A consumer Instant Field `{ key: 'permitExpiry', type: 'date' }` takes the date editor with no local `fieldTypes.date` bundle. A Field with no `type` does not. `writesSegmentEnvelope` still names `start`/`end` by key: that rule is the segment envelope door, not the date editor.
- **Two new `PluginContext` seams beyond what the step file named**: `ctx.interaction.canEdit(entry)`
  (the `edit` capability's resolution — no existing seam let a plugin ask any capability) and
  `ctx.interaction.proposeEntryEdit`/`announceEntryEdit` (a plugin raising an event pair it owns —
  every other `before*` pair in `GanttEventMap` is raised by core's own gesture pipeline, never by a
  plugin). Also `ctx.view.isColumnEditable(field)`, mirroring `resolveTooltipColumns`'s existing
  pattern. **#256 retired `isColumnEditable`.** A plugin asks `ctx.interaction.canWrite(entry, field)`
  now, which answers the cell rather than the column, and answers it for every writer at once.
- **The editor does not build on `createPopup`.** `Popup`'s `content` is a static `ElementDescription`
  rendered once by the reconciler, with no way to hand the caller a live, listener-attachable node —
  exactly what an editable `<input>` needs. It mounts directly through `ctx.view.rowLayer.present` instead
  (#158 — `Overlay.present` until then), positioned once at the cell's own rect with no flip/clamp (a
  cell editor always sits where the cell already is). The row layer carries it through a scroll,
  because the scroll that moves the rows moves it too.
- **`beforeEntryEdit` joined `AsyncCancelableEvent`.** The step file's own D-S5-19 code sample uses
  `async (…) => { await myDialog.open(...); return false }`, so the async-veto shape (D-S3-17) had to
  extend to this pair too — not spelled out explicitly in the TODO list, but required by the sample.
- **`beforeEntryEdit`'s `from`/`to` are both the pre-edit value.** It fires before the editor opens,
  before any candidate value exists — there is nothing else honest to put in `to` at that point.
- **A generic (non-date) field's seed text**: a Field with its own `parseValue` seeds the editor from
  the cell's already-rendered (formatted) text, since that is what `parseValue` is meant to invert; a
  plain `type: 'text'`/no-`type` Field seeds from the raw stored value directly.
- **Enter opens the selected entry's first `editable` column** (no per-cell keyboard focus exists yet
  — that is S5.11's roving-tabindex job, D-S5-25). A pragmatic simplification, not the final answer.
- **One open editor is one `CellEditorSession`** (the R1 fix slice). The class owns the mount, the
  position, the commit rules and its own teardown. `commit()` answers whether it closed, so the
  plugin reads that answer and no flag records it twice. A refused commit keeps its own editor, and
  `openFor` then opens no second one over it. `CellEditorPorts` is the class's seam — the idiom
  `view/column-chrome.ts` already sets — so a test drives a session with no mounted Gantt.
- **A `parseValue`'s `FieldContext`** is built for real from public reads (`entries.fieldValue` for
  `read`, `dataset.time.diffDays` for an approximate `durationOf`) — not a stub — since `extensions/`
  cannot reach `data/`'s own `createFieldContext`.
