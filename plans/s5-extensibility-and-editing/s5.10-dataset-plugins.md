**Slice:** S5 · **Step:** 10 of 12 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-23, D-S5-24, D-S5-30, D-S5-31 · **Closes:** issue #15, OQ8

## 1. Decisions

### D-S5-23 — `setExtender` takes a wrapper, so installing composes

This is `plans/s2-data-core/OPEN-QUESTIONS.md` OQ8, reading (b): the hook has **one occupant at a time**; a scheduling plugin is one candidate occupant with no special claim on it.

```ts
export type ExtenderWrapper = (next: EditExtender) => EditExtender;

// replace — ignore what was there
ctx.edits.setExtender(() => myExtender);

// tap in — run the current occupant, then adjust
ctx.edits.setExtender((next) => (request) => merge(next(request), myExtras(request)));
```

`data/` still holds **one** field and calls it at **one** site (D-S2-6). Nothing about the commit path changes: `DatasetDataOptions.editExtender` is already the composed result. What changes is only how a second plugin arrives.

What exclusivity was protecting survives intact: one extender means one call per transaction, one set of extra writes to check against the body's edits (I4), one deterministic answer, and no priority machinery in `data/`. Composition order is **not** the `plugins` array position — see D-S5-31 below: the host resolves setup order from `requires`, and that is also the order extenders wrap in. (Corrected per issue #137 F2: this paragraph previously claimed array order, which directly contradicted D-S5-31 stated a few decisions later in this same file.)

`EditExtenderConflictError` never gets written. There is no conflict to report when installing composes.

**Spec edits this decision carries** (do them in this step, not later): `plans/00` D4, `CLAUDE.md`'s Scheduling block, `plans/01` §7, `plans/03` §S3's extender note, and a superseding note on ADR 0002. The sentence becomes: *the hook has one occupant at a time; a scheduling plugin is one candidate occupant, with no special claim on it.*

The Rollup is untouched by any of this. It is step 5 of the commit sequence, not the hook (D-S2-22), so no install can switch off a core behaviour.

### D-S5-24 — `PluginStore` holds per-plugin per-entry data

ADR 0002 named the problem: per-plugin per-entry data must not live in `Entry.meta`, or a host and a plugin collide in one field.

```ts
export interface DatasetPluginContext {
  dataset: Dataset;
  events: DatasetEvents;                       // beforeChange / change
  fields: {                                    // S5.9, D-S5-21
    register(field: Field): void;
    registerType(name: FieldTypeName, type: FieldType): void;
    registerAggregator(name: AggregatorName, fn: Aggregator): void;
  };
  edits: { setExtender(wrap: ExtenderWrapper): void };
  /** This plugin's own reserved store, namespaced by plugin id. */
  store: { reserve<T extends object>(): PluginStore<T> };
  disposables: DisposableStore;
}

export interface PluginStore<T extends object> {
  get(id: EntryId): T | undefined;
  set(id: EntryId, value: T): void;
  remove(id: EntryId): void;
  readonly all: ReadonlyMap<EntryId, T>;
}
```

A `PluginStore` is a real store, not a side map:

- **When a write is legal (issue #137 F17):** a `store.set`/`remove` call during `setup` auto-wraps in its own transaction, the same rule `entries.add` already follows outside a `transaction()` body. A call during the extender wrapper joins the transaction already open for that commit, so its row lands in the same `ChangeSet` the entry edit does. A `store.set`/`remove` call at any other time (an event handler outside a transaction, for instance) auto-wraps the same way `setup` does — there is no third case.
- **A second `reserve()` by the same plugin (issue #137 F17)** returns the same store handle; it is not an error. Two plugins cannot collide, because `reserve()` is keyed by the calling plugin's own id.
- Its writes go through the open transaction and land in the same `ChangeSet`, so one undo step covers the entry edit and the plugin's own data (I7).
- **A store row is changeset content on its own.** `runTransaction` commits nothing when `buildCommitChangeSet` finds no rows, and `bumpDatasetRevision()` runs only inside `commitChangeSet` (`src/data/transaction.ts`). A transaction whose only write is a plugin-store row — pin an entry, flip a dependency's `active`, no entry field touched — must still build a changeset, or it silently no-ops: no `change` event, no undo record (breaking I7 for exactly the data this step adds), and no revision bump, so nothing repaints. The emptiness test widens with `StoreName`.
- **`datasetRevision` is therefore the invalidation signal for store data too.** A store write bumps it through the ordinary commit, and `FrameMemory` already keys on it — a reader outside `data/` needs no second revision. This is what S7's Gantt-side link emitter depends on (#136).
- `StoreName` widens from `'entries'` to `'entries' | \`plugin:${PluginId}\`` — the shape S2 reserved (`plans/03` §S2: "`StoreName` is `'entries'` only until the first plugin store exists").
- It serializes under `plugins: { [id]: … }` in the Document, at `schema: 3`. A Document read by an application that no longer installs that plugin keeps the data untouched and does not drop it — passenger data, the same posture undeclared `meta` keys already have.
- Removing an entry removes its plugin rows in the same changeset, exactly as descendants are removed today.

The harness lock plugin is the first occupant, so the mechanism ships with a user rather than as decoration (I11). S7's `Dependency` store is the second, and needs no core change to arrive.

### D-S5-30 — a `PluginStore` is readable by any plugin, writable by its owner only

The S5.0 grill on issue #111 (2026-09-02) found this gap while splitting S7's scheduling engine from its dependency data: the engine reads the edges, but `reserve()` alone gives every plugin a store nobody else can see. A private-only store makes that split, or any third-party engine reading a first-party store, unbuildable.

```ts
store: {
  reserve<T extends object>(): PluginStore<T>;
  /** Any other plugin's store, read-only. `undefined` if that plugin never reserved one. */
  read<T extends object>(pluginId: PluginId): PluginStoreView<T> | undefined;
};

export interface PluginStoreView<T extends object> {
  get(id: EntryId): T | undefined;
  readonly all: ReadonlyMap<EntryId, T>;
}
```

`PluginStoreView` drops `set`/`remove` — the type itself says who owns the writes, so a reviewer never has to check by hand which plugin an unfamiliar store call belongs to. `StoreName` widens once for this too: reads and writes both key off `plugin:${PluginId}`, so `read()` finds exactly the store `reserve()` made.

### D-S5-31 — `requires` orders setup; the `plugins` array's own order never matters

The same grill named the other half of the gap: once two plugins can compose (D-S5-23) and read each other's store (D-S5-30), which one sets up first is no longer bookkeeping — it decides whether a store exists yet when its reader looks for it. A caller who writes `plugins: [scheduling(), entryDependencies()]` should get the same result as the other order.

```ts
export interface DatasetPlugin {
  id: PluginId;
  /** Plugin ids that must also be installed. Does not imply an order in the array. */
  requires?: readonly PluginId[];
  setup(ctx: DatasetPluginContext): Disposer;
}
```

`dataset-plugin-host.ts` topologically sorts the installed set by `requires` before calling any `setup` — the array is an unordered set of what to install, not a sequence of when. A required id that is not present throws `MissingPluginError`, naming both ids, at construction. There is no `PluginOrderError`: once the host computes the order itself, there is no wrong order left for a caller to write.

**Considered and rejected: a plugin supplying its own default for what it requires**, so that installing `scheduling()` alone would silently bring in a default `entryDependencies()`. Rejected because a required plugin here is never a private implementation detail — Gap 1 above exists precisely because `entryDependencies()` is independently useful (arrows with no engine). Manufacturing one behind another plugin's factory reintroduces exactly what D-S5-23 already drew a line around: a plugin whose behaviour is on but that never appears in the caller's `plugins` array. `requires` stays a check, never a supplier — a missing prerequisite is a thrown error, not a quiet default. This is also what keeps an opt-in "install every first-party plugin" helper (S7, once `entryDependencies()` and `scheduling()` ship) honest: it can only ever be a named factory the caller calls, listing the same factories they could have typed by hand in either order — never a default the host reaches for on its own.

### The lock demo, deferred here from S3

`plans/03` §S3 deferred the lock-style extender demo to S5, because a harness page could not install one through the public API before this step. Now it can:

```ts
const dataset = new Dataset({ entries, plugins: [lockEntries(['t2'])] });
```

Drag `t1` and `t2` ghosts alongside it, because the extender wrote `t2`'s `start` too. Drop, and `beforeChange` refuses the write, so the whole transaction rolls back — one refusal, one undo-free result. S3 already proves the preview path in a `dom` test through the internal seam (S3 §0 P1); this makes it pokeable, which is what principle 7 asks of every slice.

**Refusal is `beforeChange`, not the extender (issue #137 F3).** `EditExtender` returns `EntryEdits` — there is no legal way for it to say "no", and it has no way to tell a preview call (S3.3's rAF loop, which needs `t2`'s cascade edits to draw the ghost) from the real commit call, since `EditRequest` carries only `{ entries, proposed }` in both. Making the extender throw would make the ghost preview throw too. So the lock plugin's extender wrapper only ever adds cascade edits, in every call, preview included; the refusal is a `ctx.events.on('beforeChange', ...)` handler, which fires exactly once, only at commit (S2.2's step 7), on the finished changeset — the extender's own cascade rows already merged in. Returning `false` there throws `MutationCancelledError` (D-S2-25), the ordinary veto path every gesture already uses: silent abort, no undo entry, no new error type needed.

`Dataset.plugins` is **read-only**, unlike `Gantt.plugins`. A Dataset plugin may declare Fields, and a Field must exist before the first Rollup (D-S5-4); adding one later would mean re-rolling the whole dataset under a Field the Document never had. A consumer that wants a different plugin set builds a Dataset with it. This asymmetry is deliberate and is stated in `plans/02` §2 with this reason.
