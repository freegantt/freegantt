### 0.3 Three questions, now answered — see D-S5-39 and the rewritten D-S5-26

**Q-A11Y-1 — does a bar gesture become a Command? No, and it does not need to.**
D-S5-26 said each keyboard path "runs the same command the pointer path runs". That held for two rows
only. For select, move, resize and edit, **the pointer path runs no command either** — it runs
`EntryGestureSession` through `view/gesture-pipeline.ts`. Making the claim literally true means
turning gestures into commands, which is open issue **#216** and much larger than this step.

**Answered: parity is one capability resolution and one focus scope, not one command.** I14 already
gives the no-drift guarantee, at the capability, which is where both paths already refuse. The focus
scope then gives the second half — what a chord means. D-S5-39 states the mechanism. #216 may later
turn gestures into commands; nothing in this step blocks it and nothing waits for it.

**Q-A11Y-2 — `Shift+Arrow` had three claimants. The standard resolves it.**
Extend-selection is `Shift+ArrowUp` / `Shift+ArrowDown`, not `Shift+Arrow` on the horizontal axis. In
the treegrid pattern, `Shift+Left`/`Shift+Right` on a focused **row** changes no selection at all. So
the horizontal chord stays free for the two shipped meanings, and the focus scope tells them apart:
on a header cell it resizes the column (S5.7), on a bar it resizes the bar's edge (S3.5). No claimant
moves, and nothing new collides.

**Q-A11Y-3 — a keyboard user cannot pick a Segment. Focus picks it.**
#211 landed after §1 was written. `spec-211-gesture-units.md` says a keyboard nudge "moves exactly
what a drag in the same state would move", and the pick is what decides between one Segment and the
whole Entry. Only a pointer could pick.

**Answered: focusing a bar picks it, exactly as clicking it does.** One focused bar node is one Item
is one Segment, and `pickedItemIdByEntryId` is already per-Entry. The whole-Entry case falls out for
free: focus a **grid row** instead of a bar, and there is no pick — which is the same distinction the
pointer already draws between a bar click and a grid-row click. No new concept, and the two panes
each keep meaning what they already meant.

One chord this leaves open, and it is now **[#218](https://github.com/Pawel-IT/FreeGantt/issues/218)**:
nothing steps the pick *along* a row, so a row's middle Segments stay out of reach. Related: **#215**
(a covered Segment cannot be picked by pointer either); the two are twins, and neither fixes the other.

### 0.4 Where the design comes from

The grid pane follows the published `treegrid` and `grid` authoring patterns key for key, and the
composite-widget focus rules that go with them: one tab stop per composite region, entry lands on the
last-focused element and otherwise the first, and a selection survives focus leaving the region — so
the timeline pane may act on a selection the grid pane made.

Three comparable products were read for the parts no standard covers. The one that publishes a full
map scopes every shortcut to the element that holds focus (whole chart, row, cell, header cell) and
lets the narrower binding win, which is the mechanism D-S5-39 adopts. It also puts scrolling on
`Alt+Arrow` and keeps the plain arrows for focus, which is the trade this step has to make too. None
of the three has Segments, so none of them answers §5's open chord.

Under CLAUDE.md those products are not named here, in any spec, doc or comment.

## 1. Decisions

### D-S5-25 — The grid pane carries the pattern; the timeline is a labelled region

Today the rows are `role="listitem"` and the bars `role="img"` (S1.10 shipped that, deliberately, before a keyboard controller existed). S5 completes it.

**Grid pane.** `role="treegrid"` when the row source is a tree, `role="grid"` otherwise. Rows are `role="row"` with `aria-level`, `aria-expanded`, `aria-posinset`, `aria-setsize` (three of the four already ship). Cells are `role="gridcell"` with `aria-colindex`. Column headers are `role="columnheader"` in a `role="row"` inside `role="rowgroup"`.

**Timeline pane.** `role="region"`, named by the Gantt's `a11yLabel`, holding the bars as focusable elements that keep their `role="img"` and their date-carrying `aria-label`. It is **not** a second grid.

The alternative — one `treegrid` spanning both panes via `aria-owns` — was considered and rejected. Rows virtualize: the owned node often does not exist, and `aria-owns` pointing at a missing id is undefined behaviour that differs per screen reader. Two coherent regions that share roving focus behave the same way for a user and are honest about what exists in the DOM.

**Roving tabindex.** One tab stop per pane. Inside a pane, arrows move focus and only the focused element carries `tabindex="0"`; every other carries `-1`. `Tab` moves between panes and out of the Gantt. Focus is a view concern and never reaches `data/` — the same rule collapse and selection already follow (D-S4-11).

Focus survives a frame rebuild: the shell restores focus by row id and column key after a sync, not by node identity, because nodes recycle (I8). A row that filtered away moves focus to its nearest surviving neighbour.

`--fg-focus-ring` joins the level-1 token table, with a visible default in both themes. Focus is never removed, only styled.

### D-S5-39 — Focus scope decides what a chord means

The old parity table gave one chord one meaning. Three chords then needed a second meaning, and the
table had no way to hold it. That is the wrong shape. A chord means what the **focused thing** says
it means, and the vocabulary for "focused thing" already exists:

```ts
export type TargetKind = 'row' | 'cell' | 'bar' | 'header' | 'splitter';   // model/command.ts
```

Five kinds, five scopes, and `CommandTarget.kind` is what a command's `when` already reads. The
keymap already resolves newest-first and checks both the binding's `when` and the command's
(`extensions/keymap.ts`, `resolve`). `gantt-shell.ts:1154`'s `#buildCommandContext` already fills
`kind: 'header'` from `columnChrome.focusedHeaderField` — **a focus fact, not a pointer fact**. S5.7
built the first scoped chord and did not name the pattern.

So this step adds no machinery. It widens that one function, so the roving focus fills all five
kinds instead of one, and every chord below reads `when: (ctx) => ctx.target?.kind === …`.

Two rules follow, and they are the whole design:

1. **A chord is scoped, and the narrower binding wins.** Registration order gives that for free —
   core registers first, so a later binding is checked first.
2. **Arrows navigate where the pattern says navigate, and act where the pane is for acting.** The
   grid pane is a `treegrid`, so its arrows move focus, without exception. The timeline pane is a
   region of focusable bars and explicitly *not* a grid (D-S5-25), so its arrows edit.

This is what replaces D-S5-26's "one command" claim (Q-A11Y-1). **Parity is one capability
resolution and one focus scope.** A capability that resolves false refuses the chord exactly as it
refuses the pointer, from that one resolution (I14).

### D-S5-26 — The chord map

**Between panes.** Two tab stops, one per pane. `Tab` and `Shift+Tab` move between them and out of
the Gantt. Entering a pane restores its last-focused element, and otherwise takes the first — the
pattern's stated rule for a grid. The container's own `tabindex="0"` (`view/pane-layout.ts:78`)
retires; it was the one honest tab stop before a keyboard controller existed, and now there are two.

**Grid pane** — `role="treegrid"` for a tree, `role="grid"` otherwise. The published pattern, key for
key. Everything here is scoped to `'row'` or `'cell'`.

| Chord | On a row | On a cell |
|---|---|---|
| `ArrowDown` / `ArrowUp` | next / previous row | next / previous row, same column |
| `ArrowRight` | expand; when expanded or a leaf, move to the first cell | next cell; no move at the last |
| `ArrowLeft` | collapse; when collapsed or a leaf, no move | previous cell; from the first cell, back to the row |
| `Home` / `End` | first / last row | first / last cell in the row |
| `Mod+Home` / `Mod+End` | first / last row | first / last row, same column |
| `PageDown` / `PageUp` | one viewport of rows | same |
| `Shift+ArrowDown` / `Shift+ArrowUp` | extend the Selection by a row | same |
| `Shift+Space` | select the focused row | select the row holding focus |
| `Mod+A` | select all (`freegantt.selectAll`, shipped) | same |
| `Escape` | clear the Selection (`freegantt.clearSelection`, shipped) | same |
| `Enter` | open the editor on the first editable cell | open the editor on **this** cell |
| `Shift+F10`, Menu | context menu at the focus | same |
| `*` / `Shift+8` | expand every row (shipped, undocumented until now) | same |
| `Delete` | delete the Selection's Segments (`freegantt.deleteSelection`, #212 fix-plan review, finding 12) | same |

Collapse and expand already sit on `ArrowLeft`/`ArrowRight` over `freegantt.collapseRow` /
`freegantt.expandRow` (S4.10). That is what the pattern asks for, so it stands unchanged.

**Timeline pane** — `role="region"`, focusable bars, scope `'bar'`. Not a grid, so arrows act.

| Chord | Action |
|---|---|
| `ArrowDown` / `ArrowUp` | focus the nearest bar one row down / up, skipping rows that draw none |
| `ArrowRight` / `ArrowLeft` | nudge the focused bar by one snap step (shipped, S3.5) |
| `Shift+ArrowRight` / `Shift+ArrowLeft` | resize the focused bar's `end` edge (shipped, S3.5) |
| `Alt+` either of the two above | the same, with snap suspended — fine placement (shipped, S3.5) |
| `Mod+ArrowRight` / `Mod+ArrowLeft` | step the Selection between the Segments of the focused row's Entry (`freegantt.selectNextSegment` / `selectPreviousSegment`, closes [#218](https://github.com/Pawel-IT/FreeGantt/issues/218)) |
| `Home` / `End` | focus the first / last bar of this row |
| `Space` | select the focused bar's Entry |
| `Shift+ArrowDown` / `Shift+ArrowUp` | extend the Selection by a row, as in the grid pane |
| `Shift+F10`, Menu | context menu at the focused bar |
| `Delete` | delete the Selection's Segments (`freegantt.deleteSelection`, #212 fix-plan review, finding 12) |

**Focusing a bar picks it** (Q-A11Y-3). The pick is what `spec-211-gesture-units.md` reads to decide
whether a nudge moves one Segment or the whole Entry, so the keyboard reaches both cases the same way
the pointer does: focus a bar to move that Segment, focus the grid row to move the Entry whole.

**`Mod+Arrow` is the one chord invented here, and [#218](https://github.com/Pawel-IT/FreeGantt/issues/218) shipped it.**
The arrows are spent — plain nudges, `Shift` resizes, `Alt` nudges finely — and a row that draws five
Segments still needs a way to reach the middle three. `Home`/`End` reach the outer two and no more.
`Mod+Arrow` is free in every scope, and it reads the way it reads everywhere else: *move, do not
act.* The alternative the pattern itself sanctions is `Tab` within a row, which is correct on paper
and wrong here — a packed row can draw forty items, and forty presses to leave a pane breaks the
two-tab-stop promise this same decision makes. Nothing surveyed offers a third answer, because
nothing surveyed has Segments.

**#218 closed this gap, so `[S5-A4]` carries no exception.** The keyboard reaches every bar of a row,
not only the first and the last. `plans/02` §4.1 states these bindings where a consumer reads them.

**One `Mod+Home`, two meanings, and that is the point.** In the grid pane it goes to the first row;
at the Gantt scope it pans to the dataset's start. Each pane's `Mod+Home` means the beginning of that
pane's own axis — rows in one, time in the other. That is D-S5-39 doing its job, not an accident.

**Header cell** — scope `'header'`, all shipped in S5.7:
`Shift+ArrowLeft`/`Shift+ArrowRight` resize the column, `Alt+ArrowLeft`/`Alt+ArrowRight` move it,
`ArrowLeft`/`ArrowRight` step between header cells, and `ArrowDown` drops into the rows.

**Splitter** — scope `'splitter'`, new this step. `ArrowLeft`/`ArrowRight` resize the grid pane.
S1.8 shipped the drag with no keyboard path, and parity means it gets one. It is a plain arrow, not
`Alt+Arrow`: nothing else is focusable there, so there is nothing to navigate away from.

**Whole Gantt** — the fallback scope, reached when the two panes do not claim the chord:

| Chord | Action |
|---|---|
| `Alt+ArrowLeft` / `Alt+ArrowRight` | pan the timeline horizontally |
| `Mod+Home` / `Mod+End` | pan to the dataset's start / end (`freegantt.panToStart` / `panToEnd`) |
| `Mod+=` / `Mod+-` | `freegantt.zoomIn` / `freegantt.zoomOut` — **new**, see §0.5 |
| `Mod+0` | `freegantt.panToToday` |
| `Mod+Z` / `Mod+Shift+Z` | undo / redo (shipped) |

**What this costs: eight default chords move.** `ArrowLeft`/`ArrowRight`/`ArrowUp`/`ArrowDown`,
`Home`, `End`, `PageUp` and `PageDown` stop panning the viewport and start moving focus, because the
grid pattern gives the plain arrows to focus and does not negotiate. The commands survive untouched
(`freegantt.panLeft` and its seven siblings); only the default bindings at
`view/gantt-shell.ts:1319-1327` change. Vertical panning then needs no chord at all — moving focus
scrolls the focused row into view, which is the reason the pattern prefers a roving `tabindex` over
the alternative. Horizontal panning still needs one, because the time axis holds nothing focusable,
and that is what `Alt+Arrow` is for.

**Screen-reader text.** A bar's `aria-label` names the entry and its dates through the same formatting helper the cells use — inclusive display, never a raw `end` (`plans/01` §5). A cell's accessible name is its column header plus its formatted value. The tooltip is never the only place information lives (D-S5-9): whatever a tooltip shows, the bar's label or description already says.

**Live announcements.** One polite live region per Gantt announces what a keyboard action did: "Framing moved to 12 September", "3 rows collapsed", "Budget column moved to position 3". It is written from the same commit sequences the events fire from, so nothing announces an action that did not commit.

**A refused cell edit announces nothing yet.** `inlineEditing()` mounts a refusal notice with `role="status"` when a cell offers an editor it cannot open (S5.8 §1, review SP1). A screen reader does not announce a script-inserted `role="status"` node reliably, so today the reason is visual and hover text only. This step owes that reason to the polite live region above, and the notice then keeps the visual half alone. **The feed to carry it now exists** — S5.12's `error` event already raises that refusal with the same `code` the cell's `data-reason` holds, so the region subscribes rather than gaining a second caller (§0.2).

### D-S5-27 — Axe runs on every harness page in CI

`@axe-core/playwright` is budgeted for this slice (`plans/04` §2). `e2e/a11y.spec.ts` walks every page in `harness/`, runs axe, and fails on any violation. New harness pages are covered by construction, because the spec enumerates the pages from the nav rather than by hand.

**Which list, exactly.** The nav's own `HARNESS_PAGES` array (`harness/harness-nav.ts`) is the list —
ten entries, one of them the docs index. It is not a glob over `harness/*.html`: `harness/diagram.html`
exists, sits in no nav, and is not a demo. A page the gallery does not link is a page nobody reaches,
so the nav is the honest source. S5.13 turns these same pages into the gallery, which keeps one list
serving both steps.

Axe cannot check keyboard parity, so the table above is tested separately in `view/keyboard-navigation.test.ts` — one assertion per row.
