# S5.9 — Plugin registrations and the consumer-defined kind

**Slice:** S5 · **Step:** 9 of 12 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-21, D-S5-22, D-S5-33, D-S5-35, D-S5-38 · **Proves:** `[S5-A3]` — the `plans/01` §2.5 open-set claim
**Prerequisite:** S5.1, S5.4, S5.6 · **Ends with:** a `'buffer'` kind that draws, aggregates, refuses resize and carries its own menu items, all from one plugin, with zero library edits.

## 1. Decisions

### D-S5-21 — A Field registers on the Dataset side; its column on the Gantt side

`plans/01` §10 put `registerField` on `PluginContext.data`. That is the wrong host. Fields are Dataset data: they are declared on the `Dataset`, they decide stored values, and the Rollup runs at construction, before any Gantt exists (ADR 0005, `plans/02` §4.2). A field registered by a view-side plugin would arrive after the first Rollup and after `fromJSON`.

So registration splits along the same line the two contracts already draw (D-S5-1):

```ts
// DatasetPluginContext (S5.10) — what a value IS
ctx.fields.register({ key: 'risk', type: 'score' });
ctx.fields.registerType('score', { rollUp: 'max', formatValue: asScore });
ctx.fields.registerAggregator('riskWeighted', fn);

// PluginContext (Gantt) — where this view SHOWS it
ctx.view.registerGridColumn({ field: 'risk', header: 'Risk', align: 'end' });
```

A plugin-registered Field is an ordinary Field: same registry, same rollup path, same changeset row, same `toJSON` (D-S4-15's data half). `UnknownFieldError` and `DuplicateFieldKeyError` apply unchanged. Registration is legal during `setup` only (D-S5-4), which for a `DatasetPlugin` means before entries are ingested — so the first Rollup already sees the Field.

`registerGridColumn` appends to the columns this Gantt paints, in registration order, after the consumer's own. A consumer that wants a different order sets `gridColumns` itself; the assignment wins, because config beats a plugin everywhere in this slice (D-S5-11). The plugin's column is never added to `gantt.gridColumns` — see D-S5-33.

### D-S5-33 — A declaration knows its declarer; a Document carries the consumer's only

*Landed on the #163 review branch, after S5.10 (issues #162 and #181).*

S5.9 let a plugin declare a grid column and S5.10 let one declare a Field. Neither path recorded
**who declared it**. Two consequences followed. A resize or a reorder wrote the whole painted list
back, so a plugin's column entered `gantt.gridColumns` and the `gridColumnsChange` payload, and the
documented save round-trip persisted it. And `toJSON` wrote every declared Field, so a plugin's Field
serialized as if the consumer had authored it.

Both faces take one rule.

**A registration records its declarer.** `ctx.view.registerGridColumn` stores the calling plugin's
id beside the column, the same way `registerRenderer` already takes one. `ctx.fields.register` does
the same for a Field. `PluginStore` set the precedent: it is named after its owner (D-S5-24), which
is what lets a reader tell one plugin's rows from another's later.

**The consumer's surface reports the consumer's declarations only.** `gantt.gridColumns` and both
halves of a `gridColumnsChange` payload carry the columns the consumer authored, before and after any
commit. `toJSON` writes the Fields the consumer declared. So the documented round-trip
(`gantt.on('gridColumnsChange', ({ to }) => save(to.map((c) => c.field)))`) saves what the consumer
wrote, and nothing else.

**Data outlives its plugin; a declaration does not.** This is where the two mechanisms differ, and
the difference is deliberate. A `PluginStore`'s rows are *data*: a Document keeps them under their
owner's id, and an application that no longer installs that plugin carries them through untouched
(D-S5-24). A Field or a column declaration is *code*: the plugin makes it again on its next install.
A Document that carried one would author a declaration with nothing behind it, and — worse — would
collide with the plugin's own `register` call on the next read, throwing `DuplicateFieldKeyError`.
Values are unaffected either way, because a plugin Field's values sit in `Entry.meta`, which
round-trips whether the Field is declared or not.

**No new event, and here is why.** #162 asked for the `before*`/`*` pair every mutating interaction
gets. Under this rule a registration mutates nothing the consumer owns, so there is nothing for a
consumer to veto or to observe: the pair would fire with `from` equal to `to`, always. The S5.9
review's actual complaint — "`gantt.gridColumns` can grow a field the consumer never assigned, with
no event that says a plugin column was adopted" — is answered by removing the adoption, not by
announcing it. A resize or a reorder of a plugin column still fires the ordinary pair, so a
`beforeGridColumnsChange` veto still reaches that gesture; its payload truthfully shows no change.

**Serialization is unchanged at `schema: 3`.** This narrows what a writer puts in `fields`; it adds
no key and changes no shape. A Document written before this rule still reads, and its stray rows
still decode as consumer Fields.

**Two things the rule fixed on the way.** Disposing a plugin no longer removes a column the
*consumer* authored for the same field — that column was never the plugin's to take. And a resize
now rewrites only the column it resized, so a bare `'name'` the consumer wrote stays a bare `'name'`.

**One gap it exposed.** `inline-editing.ts` walked `ctx.gantt.gridColumns` to find the first editable
column, which is the consumer's list and so never saw a plugin's column. `ctx.view.resolvedColumns()`
is the plugin-side answer to "what does this Gantt paint right now", and that feature reads it now.

### D-S5-38 — A plugin owns its own column's geometry (#189, added after S5.10)

D-S5-33 says a plugin's column declaration never reaches the consumer's surface or their Document. That is right, and it leaves a question it did not answer: a user drags the edge of a plugin's column, and **nobody** saves the width. It lives in `ColumnChrome`'s session state and is gone on reload.

**The answer is the same one the consumer already has, not a new mechanism.** The library reports column geometry and stores it for nobody. A consumer's own column width survives a reload only because the consumer saves `gantt.gridColumns` — the Document holds Entries and plugin data, never view state. So a plugin persisting its own column is the *symmetric* case, not a missing feature.

The path, through the public plugin surface alone:

```ts
setup(ctx) {
  ctx.view.registerGridColumn({ field: 'risk', ...(saved.width ? { width: saved.width } : {}) });
  ctx.events.on('gridColumnsChange', () => {
    const mine = ctx.view.resolvedColumns().find((column) => column.field === 'risk');
    if (mine?.width !== undefined) options.saveWidth(mine.width);   // this plugin's own option
  });
}
```

Two details make it work, and both are now written on `registerGridColumn`'s own doc, where a plugin author meets the requirement:

- **The event fires; the payload says nothing.** A resize of a plugin column runs the one commit sequence, so `gridColumnsChange` fires — that is what D-S5-33 already promised so a `beforeGridColumnsChange` veto still reaches the gesture. Its payload truthfully reports no change to the consumer's columns. So the plugin reads *its own column*, from `ctx.view.resolvedColumns()`, and never the payload.
- **`width` on the next registration restores it.** `registerGridColumn` takes a `GridColumnInput`, so the saved width goes straight back in.

**Rejected: a library-owned per-plugin geometry store.** Three reasons, in order of weight.

1. It would give a plugin's column a persistence path **the consumer's own columns do not have**. There is no view-state Document to put it in; inventing one is a far larger design than this issue, and it would have to serve both sides or neither.
2. `PluginStore` cannot hold it. A `PluginStore` is per-*Entry* data (`get(id: EntryId)`, D-S5-24) and belongs to a **Dataset** plugin. A column is registered by a **Gantt** plugin (D-S5-1, two contracts, two hosts), which has no store at all. The issue's own suggested route is closed: a Gantt plugin would have to ship a Dataset plugin as well, and then key a column width under a made-up entry id.
3. A plugin already has a place to put it — its own options, the channel every plugin uses to reach its host app (`lockEntries()` in the harness is the shipped example).

**What landed is a doc and a test.** The test is the round trip end to end: a plugin registers a column, a user drags its edge, the plugin hears the commit, reads its own width back, and a fresh Gantt gets it again on the next install. It fails if any link in that chain breaks, which is what makes the documented answer real rather than asserted.

### D-S5-22 — One kind, four seams, one plugin, zero core edits

`plans/00` principle 9 says a new kind of entry is configuration, never a core edit. Four seams make that true, and `[S5-A3]` is the proof:

| Question | Seam | Registered by |
|---|---|---|
| What shape does it draw? | `ctx.layout.registerItemProducer(kind, producer)` | Gantt plugin |
| How does it look? | `ctx.view.registerRenderer('bar', byKind)` or `barRenderer: { buffer: … }` | Gantt plugin or consumer config |
| What can you do to it? | `ctx.interaction.registerKindDefaults(kind, defaults)` | Gantt plugin |
| What actions does it offer? | `ctx.commands.register({ when: ({ entry }) => entry?.kind === 'buffer' })` | Gantt plugin |

```ts
export interface KindDefaults {
  move?: boolean;
  resize?: boolean;
  select?: boolean;
  edit?: boolean;
}
```

`registerKindDefaults` fills the same per-kind table `view/capability.ts` already resolves against (D-S3-9). Precedence is unchanged and stated once: the consumer's `interactions` wins, then the registered kind defaults, then the library's own table. A kind nobody registered still falls to the ordinary `'span'` row, which is why an unknown kind renders rather than throwing.

**`registerItemEmitter` becomes `registerItemProducer`.** S4 named the seam `ItemProducer` and the call `produceItemsForRow`; `plans/01` §10's prose still says emitter. One concept keeps one name (CLAUDE.md, #7). Spec edit, this step. S4 shipped the seam with three occupants and no way in from outside (D-S4-24); this step is that way in.

```ts
export type ItemProducer = (ctx: ItemProducerContext) => readonly FrameItem[];
```

The producer is pure and runs in `layout/`, registered from the DOM side — the same shape a decoration provider has (D-S5-15).

`Entry.kind` stays authored (`plans/01` §2.5). Registering a kind does not create entries of it and does not promote anything; `autoGroup` remains the only automated write to `kind` (D-S4-17).

### D-S5-35 — One gesture's rule is written by a verb, not by restating `interactions` (#195, added after S5.10)

`gantt.interactions` is the whole capability config. So `gantt.interactions = { resize: false }` drops every other rule the page holds, with no error and no event — the harness got away with writing exactly that only because it set nothing else. This is the shape D-S5-34 removed from `gridColumns`, on the one config where losing a key is a permission bug rather than a layout one.

**Two verbs write one gesture:**

```ts
gantt.setCapabilityRule('resize', false);                          // every other rule stands
gantt.setCapabilityRule('move', (entry) => entry.kind !== 'group'); // a predicate, like the config key
gantt.clearCapabilityRule('resize');                                // this Gantt states nothing here
```

**Both verbs assign a copy.** `setCapabilityRule` spreads the current value and writes one key; `clearCapabilityRule` spreads it and deletes one key. Neither one mutates the object the consumer assigned, so `plans/02` §2's "a config value is a value" holds unchanged, and the getter keeps answering with what this Gantt states.

**Clearing is not `true`.** The three states are a rule of `true`, a rule of `false`, and no rule at all — and only the third one lets the precedence below it answer. `setCapabilityRule('resize', true)` makes a rolled-up parent and a milestone resizable, which the per-kind table refuses on purpose (D-S3-9). This is why the pair is set/clear and not the show/hide pair D-S5-34 uses: `hidden` has two states, a capability rule has three.

**No merging setter.** `gantt.interactions = { resize: false }` merging into what is already there was considered and rejected. It would make assignment mean two things, it would contradict `plans/02` §2, and it would leave no way to remove a key — the exact state the harness needs when its "lock resize" box is unchecked.

The name comes from the glossary: **Capability** is whether a gesture is permitted on an Entry, and `CapabilityRule` is already the public type of every value in `Interactions`. The verb names the rule it writes, so `clearCapabilityRule('resize')` cannot be misread as "make resize impossible".

### Landed — implementation notes and open calls (2026-09-04)

- **D-S5-21's Field half is out of scope here.** `ctx.fields.register`/`registerType`/`registerAggregator`
  live on `DatasetPluginContext`, which S5.10 introduces — nothing to attach them to exists yet.
  `ctx.view.registerGridColumn` (the Gantt-side half) ships now; the two-line split D-S5-21 draws
  still holds, it just lands across two commits instead of one.
- **`ItemProducer` keeps `produce-items.ts`'s existing `(entry: Entry) => readonly Item[]` shape**,
  not the step file's own `(ctx: ItemProducerContext) => readonly FrameItem[]` sketch — S4 already
  shipped `Item`/`ItemProducer` with three occupants (`plans/s4-hierarchy-and-rows`, D-S4-24/D-S4-25);
  this step is the way in from outside, not a redesign of what a producer receives or returns.
  `ItemProducerRegistry` grew one method, `register(kind, producer): Disposer`, mirroring the
  registry's existing `extras` constructor argument rather than replacing it.
- **`ctx.layout.registerItemProducer` invalidates `FrameLayout`'s own per-row item cache.**
  `FrameMemory#packed` only forgets a row on a dataset change, row-count change, or metrics change —
  a producer swap is none of those, so the registration (and its disposal) both call
  `#layout.invalidateFrom(0)` before requesting a frame, the same invalidation a collapse change or a
  `gridColumns` commit already asks for. Missing this made the first draft of the S5-A3 test silently
  paint the old label.
- **`ctx.view.registerGridColumn` appends into `ColumnChrome`'s own `#pluginColumns`, resolved by a
  new `effectiveInput()`** (the committed columns plus every plugin column whose `field` they do not
  already name). The public `gridColumns` getter and a plain `gantt.gridColumns = […]` assignment stay
  scoped to the consumer's own authored list (D-S5-21: "the assignment wins"). A resize/reorder
  gesture reaches over `effectiveInput()`, so a plugin's own column is draggable. What that gesture
  commits keeps each column's declarer attached, so the plugin's column never joins the consumer's
  list — D-S5-33 revised this bullet, which originally let a commit bake one in.
- **`resolveCapabilities` grew a third, optional argument** — `registeredDefaultsFor` — resolved
  between the consumer's own `interactions` and the library table, never replacing either. Kind
  defaults live in one `Map<EntryKind, KindDefaults>` on `GanttShell`; `registerKindDefaults`
  re-resolves `#capabilities` and calls `#refreshAffordances()` immediately (capability changes paint
  through `InteractionState`, not the frame pipeline `registerItemProducer` above invalidates).
- **The per-kind bar renderer composes across plugins (review P2, 2026-09-04).** D-S5-22's second
  row said "one slot per point", after D-S5-11. That held U10 to one kind-defining plugin: the
  second one threw `RendererAlreadyRegisteredError`, although the two kinds never met. The `bar`
  point's per-kind map already carries a key, so `RendererRegistry` keys on it —
  `registerRenderer('bar', { buffer: … })` claims `bar:buffer`, and a second plugin claims
  `bar:risk` beside it. Two plugins that name the same kind still throw, and the error names the
  slot. `registerRenderer('bar', fn)` keeps the whole-point claim it always had: one function
  answers every kind, so it refuses, and is refused by, any per-kind claim. `cell`, `header` and
  `tooltip` are unchanged — they have no key to merge on, so one plugin claims each. D-S5-11's
  ladder is unchanged too: a consumer's own `barRenderer` still wins over every plugin slot, and a
  consumer map that misses the kind still falls to the library default, never to a plugin.
  `harness/plugins/risk-kind.ts` is the second kind-defining plugin, and it proves the pair.
- **A plugin's `setup` may return nothing (review P4).** `bufferKind()` closed with
  `return () => {};` because `setup` was typed `(ctx) => Disposer`. It owns nothing to dispose:
  `ctx.disposables` already retracts all four registrations.
- **`wholeEntryItem(entry)` is public (review P3).** `bufferKind()`'s item producer is
  `(entry) => [wholeEntryItem(entry)]` now, instead of an eight-line object literal that had to get
  `itemId(entry.id, 0)` right on its own.
- **No `plugin-host.ts` file.** The step file's own file table names one; the shipped architecture
  keeps every `PluginContext` seam built inline in `GanttShell`'s constructor (`view/gantt-shell.ts`),
  the same place `registerRenderer`/`registerDecoration`/`canEdit` already live — a second module
  would split one cohesive block of closures for no boundary this codebase draws elsewhere (S5.1
  through S5.8 all took the same shape; see `plans/00`'s note that slice-doc file tables illustrate
  rather than prescribe).
