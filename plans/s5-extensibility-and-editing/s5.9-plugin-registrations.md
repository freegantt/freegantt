# S5.9 — Plugin registrations and the consumer-defined kind

**Slice:** S5 · **Step:** 9 of 12 · **Spec:** [`README.md`](./README.md) · **Decisions:** D-S5-21, D-S5-22 · **Proves:** `[S5-A3]` — the `plans/01` §2.5 open-set claim
**Prerequisite:** S5.1, S5.4, S5.6 · **Ends with:** a `'buffer'` kind that draws, aggregates, refuses resize and carries its own menu items, all from one plugin, with zero library edits.

## 1. Decisions

### D-S5-21 — A Field registers on the Dataset side; its column on the Gantt side

`plans/01` §10 put `registerField` on `PluginContext.data`. That is the wrong host. Fields are Dataset data: they are declared on the `Dataset`, they decide stored values, and the Rollup runs at construction, before any Gantt exists (ADR 0005, `plans/02` §4.2). A field registered by a view-side plugin would arrive after the first Rollup and after `fromJSON`.

So registration splits along the same line the two contracts already draw (D-S5-1):

```ts
// DatasetPluginContext (S5.10) — what a value IS
ctx.fields.register({ key: 'risk', type: 'score' });
ctx.fields.registerType('score', { rollUp: 'max', formatValue: asScore });
ctx.fields.registerAggregator('riskWeighted', fn);

// PluginContext (Gantt) — where this view SHOWS it
ctx.view.registerGridColumn({ field: 'risk', header: 'Risk', align: 'end' });
```

A plugin-registered Field is an ordinary Field: same registry, same rollup path, same changeset row, same `toJSON` (D-S4-15's data half). `UnknownFieldError` and `DuplicateFieldKeyError` apply unchanged. Registration is legal during `setup` only (D-S5-4), which for a `DatasetPlugin` means before entries are ingested — so the first Rollup already sees the Field.

`registerGridColumn` appends to this Gantt's `gridColumns` in registration order, after the consumer's own. A consumer that wants a different order sets `gridColumns` itself; the assignment wins, because config beats a plugin everywhere in this slice (D-S5-11).

### D-S5-22 — One kind, four seams, one plugin, zero core edits

`plans/00` principle 9 says a new kind of entry is configuration, never a core edit. Four seams make that true, and `[S5-A3]` is the proof:

| Question | Seam | Registered by |
|---|---|---|
| What shape does it draw? | `ctx.layout.registerItemProducer(kind, producer)` | Gantt plugin |
| How does it look? | `ctx.view.registerRenderer('bar', byKind)` or `barRenderer: { buffer: … }` | Gantt plugin or consumer config |
| What can you do to it? | `ctx.interaction.registerKindDefaults(kind, defaults)` | Gantt plugin |
| What actions does it offer? | `ctx.commands.register({ when: ({ entry }) => entry?.kind === 'buffer' })` | Gantt plugin |

```ts
export interface KindDefaults {
  move?: boolean;
  resize?: boolean;
  select?: boolean;
  edit?: boolean;
}
```

`registerKindDefaults` fills the same per-kind table `view/capability.ts` already resolves against (D-S3-9). Precedence is unchanged and stated once: the consumer's `interactions` wins, then the registered kind defaults, then the library's own table. A kind nobody registered still falls to the ordinary `'span'` row, which is why an unknown kind renders rather than throwing.

**`registerItemEmitter` becomes `registerItemProducer`.** S4 named the seam `ItemProducer` and the call `produceItemsForRow`; `plans/01` §10's prose still says emitter. One concept keeps one name (CLAUDE.md, #7). Spec edit, this step. S4 shipped the seam with three occupants and no way in from outside (D-S4-24); this step is that way in.

```ts
export type ItemProducer = (ctx: ItemProducerContext) => readonly FrameItem[];
```

The producer is pure and runs in `layout/`, registered from the DOM side — the same shape a decoration provider has (D-S5-15).

`Entry.kind` stays authored (`plans/01` §2.5). Registering a kind does not create entries of it and does not promote anything; `autoGroup` remains the only automated write to `kind` (D-S4-17).

### Landed — implementation notes and open calls (2026-09-04)

- **D-S5-21's Field half is out of scope here.** `ctx.fields.register`/`registerType`/`registerAggregator`
  live on `DatasetPluginContext`, which S5.10 introduces — nothing to attach them to exists yet.
  `ctx.view.registerGridColumn` (the Gantt-side half) ships now; the two-line split D-S5-21 draws
  still holds, it just lands across two commits instead of one.
- **`ItemProducer` keeps `produce-items.ts`'s existing `(entry: Entry) => readonly Item[]` shape**,
  not the step file's own `(ctx: ItemProducerContext) => readonly FrameItem[]` sketch — S4 already
  shipped `Item`/`ItemProducer` with three occupants (`plans/s4-hierarchy-and-rows`, D-S4-24/D-S4-25);
  this step is the way in from outside, not a redesign of what a producer receives or returns.
  `ItemProducerRegistry` grew one method, `register(kind, producer): Disposer`, mirroring the
  registry's existing `extras` constructor argument rather than replacing it.
- **`ctx.layout.registerItemProducer` invalidates `FrameLayout`'s own per-row item cache.**
  `FrameMemory#packed` only forgets a row on a dataset change, row-count change, or metrics change —
  a producer swap is none of those, so the registration (and its disposal) both call
  `#layout.invalidateFrom(0)` before requesting a frame, the same invalidation a collapse change or a
  `gridColumns` commit already asks for. Missing this made the first draft of the S5-A3 test silently
  paint the old label.
- **`ctx.view.registerGridColumn` appends into `ColumnChrome`'s own `#pluginColumns`, resolved by a
  new `effectiveInput()`** (consumer's `gridColumnInput` plus every plugin column whose `field` it
  does not already name) — never written into `gridColumnInput` itself. The public `gridColumns`
  getter and a plain `gantt.gridColumns = […]` assignment stay scoped to the consumer's own authored
  list (D-S5-21: "the assignment wins"); a plugin column reaches that raw list only once a resize,
  reorder, or plain assignment commits over it, the same posture a `barRenderer`/`cellRenderer`
  override already takes. A resize/reorder gesture itself now reaches over `effectiveInput()`, not
  `gridColumnInput`, so a plugin's own column is still draggable.
- **`resolveCapabilities` grew a third, optional argument** — `registeredDefaultsFor` — resolved
  between the consumer's own `interactions` and the library table, never replacing either. Kind
  defaults live in one `Map<EntryKind, KindDefaults>` on `GanttShell`; `registerKindDefaults`
  re-resolves `#capabilities` and calls `#refreshAffordances()` immediately (capability changes paint
  through `InteractionState`, not the frame pipeline `registerItemProducer` above invalidates).
- **The per-kind bar renderer composes across plugins (review P2, 2026-09-04).** D-S5-22's second
  row said "one slot per point", after D-S5-11. That held U10 to one kind-defining plugin: the
  second one threw `RendererAlreadyRegisteredError`, although the two kinds never met. The `bar`
  point's per-kind map already carries a key, so `RendererRegistry` keys on it —
  `registerRenderer('bar', { buffer: … })` claims `bar:buffer`, and a second plugin claims
  `bar:risk` beside it. Two plugins that name the same kind still throw, and the error names the
  slot. `registerRenderer('bar', fn)` keeps the whole-point claim it always had: one function
  answers every kind, so it refuses, and is refused by, any per-kind claim. `cell`, `header` and
  `tooltip` are unchanged — they have no key to merge on, so one plugin claims each. D-S5-11's
  ladder is unchanged too: a consumer's own `barRenderer` still wins over every plugin slot, and a
  consumer map that misses the kind still falls to the library default, never to a plugin.
  `harness/plugins/risk-kind.ts` is the second kind-defining plugin, and it proves the pair.
- **A plugin's `setup` may return nothing (review P4).** `bufferKind()` closed with
  `return () => {};` because `setup` was typed `(ctx) => Disposer`. It owns nothing to dispose:
  `ctx.disposables` already retracts all four registrations.
- **`wholeEntryItem(entry)` is public (review P3).** `bufferKind()`'s item producer is
  `(entry) => [wholeEntryItem(entry)]` now, instead of an eight-line object literal that had to get
  `itemId(entry.id, 0)` right on its own.
- **No `plugin-host.ts` file.** The step file's own file table names one; the shipped architecture
  keeps every `PluginContext` seam built inline in `GanttShell`'s constructor (`view/gantt-shell.ts`),
  the same place `registerRenderer`/`registerDecoration`/`canEdit` already live — a second module
  would split one cohesive block of closures for no boundary this codebase draws elsewhere (S5.1
  through S5.8 all took the same shape; see `plans/00`'s note that slice-doc file tables illustrate
  rather than prescribe).
