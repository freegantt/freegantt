## 1. Decisions

### D-S5-28 — The tree-shaking budget is a probe plus a size limit

`[S5-A6]` says unused features are absent from a consumer bundle. Two checks, because either alone lies:

1. **A string probe.** Build a fixture entry that imports `Dataset` and `Gantt` and nothing else. Assert the output contains no marker string from `tooltips`, `contextMenu` or `inlineEditing`. Each built-in carries one distinctive literal for exactly this (its plugin `id`, which it already has).
2. **A size budget.** `size-limit` on two fixtures — core only, and core plus the three built-ins. The gap is the built-ins' real cost, and the core number is the one that must not creep.

The probe catches a feature pulled in by an accidental import. The budget catches slow growth that no probe can see. `plans/04` §2 already budgets `size-limit` for this slice.

D-S5-2's factory shape is what makes both checks pass. If a `features: { tooltips: true }` table had survived, the probe would fail on day one.

**`sideEffects` must be precise, not blanket-`false` (issue #137 F16).** `package.json` currently ships `"sideEffects": false` (`plans/04` §3, pre-S5). That is a bundler promise that importing any file causes no side effect — a promise `view/styles.ts`'s `ensureBaseStyles` already breaks (it injects a stylesheet on call) and a promise a factory-shaped plugin must keep, or `[S5-A6]`'s probe measures the wrong thing: a bundler is free to drop a "side-effect-free" module a consumer never called, which is what makes tree-shaking work at all, but only if the manifest tells it the truth. This step corrects `sideEffects` to an array naming exactly the files that inject something on import — `src/view/styles.ts` (the base stylesheet) — with everything else, including every `extensions/features/*` plugin factory, left side-effect-free. `tooltips()`, `contextMenu()` and `inlineEditing()` must stay pure factories (calling them may register things; importing the module must not) for this to hold — a lint or a code-review note here is not enough on its own, but the probe in point 1 above already catches a violation the moment an unused built-in's marker string leaks into the fixture build.

### D-S5-29 — The API reference renders the existing API report

`etc/freegantt.api.md` already exists and is already gated by `pnpm api-report` (I11). The docs seed renders that file rather than adding a documentation generator — a dev dependency for something the repo already produces is a cost with no gain.

The gallery is the harness. Each page gains a short explanatory block above the Gantt: what it demonstrates, the config that does it, and a link to the section of `plans/02` that governs it. The pages are the examples a consumer reads first, so `harness/main.ts` and its siblings stay under the same review rule they always were (CLAUDE.md) — code there that re-derives what the library computes is an API gap, and this step is the last chance to catch one before S6.

### D-S5-32 — The plugin guide is typechecked against the published types

S5 ships two plugin contracts, a registration gate and a disposal rule. None of that is
discoverable from `etc/freegantt.api.md`, which lists exports and states no lifecycle.
A plugin author needs prose. Prose about an API rots, so this one is verified, not just written.

`docs/06-plugin-authoring.md` carries the guide. Every code block in it is a fenced `ts` block.
`scripts/check-doc-examples.mjs` extracts each block and typechecks it against the **built**
package types, the way a third party resolves them — not against `src/`.

Two things fail the check, and both must:

1. An example that no longer compiles. The guide then names an API that moved.
2. An example that reaches a private path. `src/extensions/**` proves the dogfood rule for shipped
   code; this proves it for the documentation a third party actually copies.

This is the same posture as `guard-red-test` (`docs/04` §4): a guard with no failing fixture is
presumed broken, so the check ships with a fixture that fails on purpose.
