Problem: the D-S1.5-4 contract — bind always notifies the newcomer; every other notification fires iff the resolved value changed; batch coalesces re-entrantly and flushes in a finally — is implemented three times, kept aligned only by comments that cite each other.

Solution: one BindingRegistry module in layout/viewport/ parameterised by a resolve function and an equality function; the two models keep only their resolution logic, and Viewport's coalescer becomes a third caller of the same interface.

  • Locality: D-S1.5-4 tested once, fixed once
  • Leverage: one interface, three call sites today
  • S1.9 zoomTo batches ride the same interface
  • Resolution / recordAndCheckChange dual shapes deleted
  • ~120 duplicated lines removed
The 2026-08-23 review rejected a notify primitive when it had one consumer — one adapter, hypothetical seam. Three consumers exist now; the seam is real. Decide alongside: S2's data/ reactivity façade (alien-signals) — the registry should either consume that façade or be explicitly scoped to viewport models so two notification systems don't grow side by side.

2 · computeFrame's speed contract lives in a comment

Strong in-process

src/layout/frame.ts (LayoutInput.heights) · src/view/gantt-shell.ts (#heightsFor + 3 cache fields) · src/layout/row-height-index.ts

Before — caching sits on the wrong side of the seam

GanttShell (view/)

#heights · #heightsEntryCount · #heightsRowHeight · #heightsFor()

re-implements the cache the index needs to be O(log n)

computeFrame (layout/)

interface includes a 10-line doc comment: "build one index, reuse it across calls, call invalidateFrom yourself…"

After — the index never crosses the seam

GanttShell (view/)

frameLayout.frame({ entries, scale, preset, visible, overscan, rowHeight, revision })

FrameLayout (layout/)

owns the height index, its cache keys, and invalidation · calls computeFrame

computeFrame · PrefixSumHeightIndex (internal seam, still pure-testable)

Problem: LayoutInput.heights makes the caller responsible for building, keying, and invalidating the height index — implementation knowledge pushed across the seam as prose, and the shell dutifully carries four fields of bookkeeping for it.

Solution: a small stateful FrameLayout module in layout/ owns the index and its invalidation; computeFrame stays pure as an internal seam for tests; heights leaves the interface.

  • Interface shrinks; implementation absorbs the cache
  • Locality: S5's invalidateFrom lands in one module
  • Shell drops four fields and one method
  • Test surface unchanged — computeFrame still pure
The shell's own comment already concedes the shape: "variable per-row heights, S5, will need finer-grained invalidateFrom calls here instead of a full rebuild." Deepen before S5 lands that logic in view/, where layout/ tests can't reach it.

4 · GanttOptions is declared twice

Speculative in-process

src/api/gantt.ts · src/view/gantt-shell.ts

Before — three bands, two of them re-flattening

Gantt (api/)

…(options.scale ? { scale } : {}) …(options.scroll ? { scroll } : {})

GanttShell (view/)

same option type, same conditional spread, again

Viewport (layout/)

the object both bands were assembling

After — one assembly point

Gantt (api/)

public seam · builds the Viewport once from GanttOptions

GanttShell (view/)

{ host, dataset, viewport } — no re-declared options

Problem: GanttOptions and GanttShellOptions are the same shape with the same doc comments, and both constructors repeat the exactOptionalPropertyTypes conditional-spread dance to build what is ultimately one Viewport.

Solution: assemble the Viewport once (in Gantt or a small option-resolver) and hand the shell the object it actually wants; one options declaration survives.

  • One options doc, one spread
  • Shell's interface names what it consumes
Deliberately Speculative: the public Gantt / internal GanttShell split is a settled decision (#7), and S2–S6 grow GanttOptions (events, config, plugins) — the shapes may stop being identical on their own. Only worth doing if it falls out of other S1.8 shell work.

Naming, against the house rules

Verdict: strong. The glossary vocabulary (Entry, Dataset, Item, Row, Visible, Overscan, pane) is used consistently; greppable pairs hold; no vendor names; no "chart"-style double meanings found. Three names fail the read-the-call-site-aloud test:

NameRead aloudVerdict
GanttShell.#readMetrics(size) "read metrics of {width: 640…}" — but it doesn't read a measurement, it applies one: re-reads row height and pushes pane size into the viewport. Rename — e.g. applyPaneMeasurement. Same miss shape as #54.
ScrollModel.#recordAndCheckChange() the "And" names two jobs — record the state and compare it. Dissolves with candidate 1 (the registry owns the comparison).
LayoutInput.heights "compute frame with … heights" — a bare plural for a RowHeightIndex; "heights" could be an array of numbers. Dissolves with candidate 2 (the field leaves the interface).

Noted, not proposed

  • DEFAULT_OVERSCAN is defined in both layout/frame.ts and layout/viewport/viewport.ts — one default, two homes; folds into candidate 1 or 2 for free.
  • ScrollModel.state returns the live internal #position object — readonly guards compile time only; a caller mutating state.position.x writes model state without a notification. Freeze or copy before S4 hands state to host code.
  • Viewport.bind is single-subscriber but reads like the multi-binding models it fans into; a second bind silently replaces #onChange. State the contract (assert or doc) — today only GanttShell calls it.
  • Fit with S2/S3 checked: data/ and scheduling/ are still empty seams, no scheduling vocabulary has leaked into core, and the shell's capture-entries-by-reference is the documented S2 design (#33). Nothing shipped blocks the resolve-hook shape.
