## 1. API

### 1.1 `EntryEdit` and the three mutators

```ts
/** What a consumer may change. Input-shaped, so dates stay loose the way `EntryInput`'s are
 *  (plans/02 §2.1): the store reads them through time/'s `toInstant`/`toEndInstant` in the
 *  dataset's zone, exactly as construction does. `id` is not editable — an id is identity. */
export type EntryEdit<TMeta = unknown> = Partial<Omit<EntryInput<TMeta>, 'id'>>;

export interface EntryStore extends EntryStoreView {
  add(input: EntryInput): Entry;
  update(id: EntryId | string, edit: EntryEdit): Entry;
  remove(id: EntryId | string): void;
}
```

Read the call sites aloud, per CLAUDE.md:

```ts
dataset.entries.add({ id: 't9', name: 'Roofing', start: '2026-10-01', end: '2026-10-15' });
dataset.entries.update('t2', { name: 'Framing — north wing' });
dataset.entries.remove('t9');
```

"the dataset's entries — add this one", "the dataset's entries — update t2", "the dataset's entries —
remove t9". All three true, and all three are what `plans/02` §2 already publishes.

Each returns the entry as the store holds it — branded id, resolved instants — not the input. Inside
an open transaction that value comes from the write set (D-S2-21), which is what makes a
read-then-write helper correct; outside one, the auto-wrapped transaction has already committed by the
time it returns.

`id` accepts a plain `string` as well as an `EntryId`: a consumer holding an id from their own
database should not have to call `entryId()` to pass it, and `plans/02` §2.1's whole point is that
ids are loose on the way in and strict behind the boundary.

### 1.2 Auto-wrap (D-S2-8)

A mutator called with no transaction open wraps itself in one. Called with one open, it joins it.
One code path, decided by whether `DatasetData` has an open transaction — not by an option the
caller passes.

### 1.3 Validation (D-S2-10)

Validated **before** anything is written, so a rejected mutation leaves the store untouched:

| Condition | Error |
|---|---|
| `add` with an id already in the store | `DuplicateEntryIdError` (`duplicate-entry-id`) |
| `update`/`remove` of an unknown id | `EntryNotFoundError` (`entry-not-found`) |
| `parentId` naming an entry the store has no entry for | `EntryNotFoundError` |
| `parentId` making a cycle, self-parenting included | `ParentCycleError` (`parent-cycle`) |
| a date field naming no instant | `InvalidInstantError` — thrown by `time/input.ts`, unchanged |
| an edit naming a key that is not a field | `UnknownFieldError` (`unknown-field`) — in S2 the legal set is the core fields; S5's registry widens the set, not the check (D-S2-26) |
| a `beforeChange` handler refusing the committed changeset | `MutationCancelledError` (`mutation-cancelled`) — thrown at commit, not at the mutator call (D-S2-25) |

`EntryNotFoundError` gains an `operation` argument so its message names the call the consumer made
(`entries.update: no entry with id "t9"`). `reveal`'s existing call passes `'reveal'` and its message
is unchanged in substance. The `code` does not move, so nothing a consumer catches on changes.

Inside a transaction, validation runs at the mutator call, not at commit: a consumer's stack trace
should point at the line that made the bad edit, not at the closing brace.

`MutationCancelledError` is the one refusal that cannot work that way: a veto judges the changeset,
which does not exist until commit (S2.2 step 6). So an auto-wrapped mutator throws it from its own
call — the transaction opened and closed there — and an explicit `transaction()` throws it from the
closing call, with the refused changeset on the error for a handler that needs to say which edit lost.

Validation reads the **write set**, not the committed store (D-S2-21). Two cases turn on it, and both
are tests in §2: `add('t9')` twice in one body throws `DuplicateEntryIdError` on the second call, and
`remove('t9'); add('t9')` in one body throws nothing.

### 1.4 Cascading remove (D-S2-10)

`remove(id)` removes the entry **and every descendant**, in the same changeset. The alternatives —
rejecting the removal, or re-parenting the children — are recorded as rejected in the README: one
makes the consumer walk the tree and get it wrong, the other is a silent edit nobody asked for.

`byParent` is what the walk reads, so the cost is proportional to the subtree, not to the dataset.

### 1.5 Derived-span kinds and the rollup (D-S2-10, D-S2-22)

`DatasetOptions.derivedSpanKinds?: readonly EntryKind[]` names the kinds whose span follows their
children. Default `['group']`; `plans/01` §2.5 says the kind set is open, so a consumer's `'phase'`
opts in here. It is data the store reads, never a `kind === 'group'` literal — the check lives in a
seam, which is what §2.5 requires.

`EntryInput.start` and `EntryInput.end` become optional. An input of a deriving kind may omit both:
the store writes a zero-length span at the dataset's **Reference date**, so the stored model always has
both fields and no layer downstream handles absence. An input of a **non**-deriving kind that omits
either field is an `InvalidInstantError` — the field is required and `undefined` names no instant.

```ts
// data/span-rollup.ts
export function rollUpDerivedSpans(
  entries: readonly Entry[],
  proposed: ReadonlyMap<EntryId, EntryEdit>,
  kinds: ReadonlySet<EntryKind>,
): readonly FieldPatch[];
```

It is **not** a resolver and it does not occupy the hook. Grouping is core, so the rollup is core: it is
step 5 of S2.2's commit sequence, it runs on every transaction whether or not anything occupies the
hook, and nothing installable can displace it (D-S2-22). `#resolveProposal` keeps `identityResolver` as
its default, which is what D4 says an unoccupied hook is. This step fills the call site S2.2 left as a
no-op.

Rules the function obeys:

- **Bottom-up**, so nested groups compose in one pass. `parentId` cycles are rejected by §1.3 before
  the rollup runs, so it needs no cycle guard.
- **Never overwrites a field the body proposed** in the same transaction, and **does** overwrite one the
  resolver proposed — between two policies, the derived one is the stronger claim on a derived-kind span
  (D-S2-22). Always overwrites a stored value, so `update('p1', { start: X })` wins for that transaction
  and the next child move rolls it away.
- A **childless** deriving-kind entry keeps its Reference-date zero-length span.
- Its patch rows land in the **same changeset** as the edit that caused them, so one undo removes both.
  That is I7 demonstrated by a shipped feature rather than a test fixture.

**S3's engine never reaches this function, and does not need to** — the answer that closed OQ7
(D-S2-22). The engine moves children; the rollup catches the parents up in the same transaction, the
same changeset, one undo step, because it runs after the hook on every commit. So `scheduling-boundary`
stays exactly as ADR 0002 cut it, there is no import edge to widen, and `plans/03` §S3's "parent/`group`
rollup as a second pass" is deleted from the engine's job rather than re-homed.

**The rollup is a leaf (D-S2-23).** `data/transaction.ts` names it once, at step 5; nothing else in
`src/**` may import it, and `span-rollup-is-removable` says so. Delete the file and groups keep their
authored span — the same result a consumer asks for with `derivedSpanKinds: []`, which is why removing
it degrades the library rather than breaking it. That is the same removability the history and the document format get, at the smallest
scale in the slice, which makes this the cheapest step to establish the rule in.

## 2. Tests

`src/data/entry-store.mutation.test.ts`, pure:

- `add` returns the stored `Entry`; a second `add` with the same id throws and the store still holds
  one; the changeset carries one `added` row.
- `update` records one `updated` row per changed field, with `from` and `to`; an update that changes
  nothing commits nothing.
- Loose dates on `update` resolve through the dataset zone the way construction's do — the same
  `'2026-09-08'` reads to the same instant on both paths.
- `remove` of a parent removes the whole subtree in one changeset, deepest-first order irrelevant to
  the result.
- `parentId` cycle rejection: `a → b → a`, and `a → a`; the store is unchanged after the throw.
- Auto-wrap: three standalone mutators produce three changesets; the same three inside one
  transaction produce one.
- A derived-span kind with no dates gets a zero-length span at the reference date; a `'span'` kind
  with no dates throws.
- **Read-your-own-writes validation (§1.3):** `add('t9')` twice in one body throws on the second;
  `remove('t9'); add('t9')` in one body throws nothing and commits one net change.
- **Rollup (§1.5):** moving a child moves its parent, in one changeset, and one undo restores both;
  a two-level tree rolls up in one pass; a group whose span the same transaction proposed keeps the
  proposed value; a childless group keeps the reference-date span; with `derivedSpanKinds: []`
  nothing rolls up at all.
- A validation failure inside a transaction body leaves the store as the body found it — no partial
  commit — and the transaction commits nothing.
- **Removability (D-S2-23):** the same fixture constructed with `identityResolver` injected rolls up
  nothing and behaves identically in every other respect — the build-without-the-rollup, exercised
  rather than described.
