# S2.2 — Transactions, changesets, and the extension hook

**Slice:** S2 · **Step:** 2 of 7 · **Spec:** [`README.md`](./README.md) §2 D-S2-6, D-S2-7, D-S2-8, D-S2-9, D-S2-11, D-S2-21, D-S2-24, D-S2-25
**Baseline:** S2.1 merged and green · **Ends with:** one transaction → the extension hook → the rollup step → one changeset → `beforeChange` → one `change` event.
**Unblocked:** [`OPEN-QUESTIONS.md`](./OPEN-QUESTIONS.md) **OQ1** closed — the hook is `EditRequest → EntryEdits` via an `EditExtender`; `diagnostics` is deferred to S3. Revised 2026-08-27: no `FieldPatch`/`EditAdjustment` wrapper — see §2.2.

This step builds the commit path. Nothing public can reach it yet — the store's mutators require a
token only `data/transaction.ts` mints, and the public mutation API is S2.3 — so the whole step is
tested through `data/`'s internal seam. That is deliberate: the commit path is the one piece of S2
that every later slice runs through, and it is worth reviewing on its own, with no API surface
argument mixed into the diff.

## 2. API

### 2.1 `data/change-set.ts` (D-S2-7)

```ts
export type StoreName = 'entries';                    // S3 adds `plugin:${string}/${string}`
export type ChangeOrigin = 'user' | 'undo' | 'redo';   // 'engine' and 'load' arrive with their producers (D-S2-11)
/** Open by construction (D-S2-26, ADR 0005). Core keys are named for autocomplete and for the
 *  comparator table's exhaustiveness check; a key S5's field registry declares is equally legal and
 *  is validated at runtime, not by the type. Closing this union would make `FieldUpdated` and the
 *  undo record — both public — impossible to open without a breaking change. */
export type CoreFieldKey = keyof Omit<Entry, 'id'>;
export type FieldKey = CoreFieldKey | (string & {});

export interface EntityAdded   { store: 'entries'; entity: Entry }
export interface EntityRemoved { store: 'entries'; entity: Entry }
export interface FieldUpdated  { store: 'entries'; id: EntryId; field: FieldKey; from: unknown; to: unknown }

export interface ChangeSet {
  id: ChangeSetId;
  origin: ChangeOrigin;
  added: readonly EntityAdded[];
  removed: readonly EntityRemoved[];
  updated: readonly FieldUpdated[];
}
```

`ChangeSetId` and `changeSetId()` join `model/ids.ts` — `docs/02` §3.7's `model-is-types-only`
allowlist already names `changeSetId`, so the rule that lands in S2.7 needs no edit to accept it.
The counter that feeds it lives on `DatasetData`, never at module level (I2).

A field whose `from` equals its `to` is not recorded, and "equals" is per field — the table in
README D-S2-7 is the contract: `===` for the primitives and for `start`/`end` (both `Instant`, so
this is number equality, not date arithmetic, and the mutator has already read the loose input through
`time/` before comparing); element-wise on `segments`; reference-only on `meta`.

An `add` followed by a `remove` of the same id inside one transaction cancels and records neither —
the changeset describes the transaction's net effect, which is what makes undo exact and what makes a
sync adapter idempotent.

### 2.2 `data/edit-extension.ts` (D-S2-6)

```ts
export type EntryEdits = ReadonlyMap<EntryId, EntryEdit>;

export interface EditRequest {
  entries: ReadonlyMap<EntryId, Entry>;   // current store snapshot, before this transaction's edits
  proposed: EntryEdits;                   // what the caller asked to change
}
export type EditExtender = (request: EditRequest) => EntryEdits;   // extra writes only; empty map = no cascade

/** No cascade, ever — the baseline the tests contrast the default against. */
export const identityExtender: EditExtender;
```

**Revised (2026-08-27), at the user's explicit direction: a plain, usable API now over matching a
spec that hasn't been written yet.** `FieldPatch`/`EditAdjustment` are retired — `FieldPatch` was
`FieldUpdated` (§2.1) with `store` removed, and existed only to give an extender something to return. A
extender now returns `EntryEdits`: the same shape a caller already writes to
`dataset.entries.update()`. One vocabulary for an edit, whoever writes it. `entries` is a `Map`
(`EntryStore` already keeps `#byId` as one, S2.1), so `entries.get(id)` replaces a linear scan.

`diagnostics` is still not part of this shape in S2 (OQ1 closed on deferring it to S3). This revision
also drops the earlier "structurally identical to `ScheduleResult`" guarantee — that guarantee
protected a type that doesn't exist yet, for a slice with no design. S3 decides its own return shape
when it's actually designed.

`data/change-set.ts` gains `diffEdit(entries, id, edit): readonly FieldUpdated[]`, applying D-S2-7's
per-field equality table. The commit path calls it once per id in `proposed` and once per id in the
extender's returned `EntryEdits` — one function computes every `FieldUpdated` in the transaction,
whichever side proposed it.

The **default** extender is `identityExtender`, in S2 and after it — an unoccupied hook is the identity
function (D4). The span rollup does **not** occupy it: it is core, so it is its own commit step after the
hook (D-S2-22), landing in S2.3 with the mutators that can create children. The commit path never
branches on which extender is installed.

`DatasetDataOptions` gains `editExtender?: EditExtender`, **internal only** — `data/` is
unreachable through the `exports` map. `DatasetData` reads it once at construction into one field and
calls it at exactly one site. There is no `if (plugin)` in the commit path because there is nothing
to branch on.

### 2.3 `data/transaction.ts`

```ts
/** Only this file constructs one. Store mutators take it, so a mutation outside a transaction does
 *  not typecheck — the belt to docs/02 §3.6's braces. */
export type TxToken = { readonly __brand: 'TxToken' };

export function runTransaction<T>(data: DatasetData, body: () => T, origin: ChangeOrigin): T;
```

It returns the body's own return value, never a changeset (D-S2-8). `on('change')` is the only delta
channel, so there is no second one to keep in step.

The commit sequence, once per outermost transaction:

1. Run `body()`. Mutators record `{ before, after }` per touched field into the open transaction's
   **write set** and write nothing to the store yet.
2. Build `proposed` from the body's direct edits, diff each against `entries` via `diffEdit` to get
   its `FieldUpdated[]`.
3. Call the extension hook **once**. With the identity extender this returns an empty `EntryEdits` map.
4. Diff the extender's returned edits the same way and merge into the same pending set. An extender
   edit may not touch an `(id, field)` the body already proposed — the dev-mode assert I4 names; in S2
   nothing produces such an edit, and the assert is what catches the first one that does.
5. **Roll up derived spans, always** — a core step, not an occupant of the hook (D-S2-22). It reads the
   pending set (the body's edits and the extender's edits alike) and appends its own `FieldUpdated`
   rows directly (it already has both the old and the computed value in hand, so it skips `diffEdit`).
   It yields to a field the **body** proposed and wins over one the **extender** proposed. A dataset
   with no deriving kinds gets nothing appended. S2.3 lands the function; until then this is a no-op
   call site, which is what keeps the sequence one shape from the first step to the last.
6. Fold the pending set into one `ChangeSet`. If it is empty, stop: no store write and no event —
   so no history entry and no frame either, because both follow the event (D-S2-24). The body's own
   return value still comes back (D-S2-8).
7. Emit `beforeChange` with it. If any handler returned `false`, discard the write set and stop —
   nothing is written, the revision signal does not bump, and `change` never fires, so no history
   entry and no frame follow (D-S2-25). `runTransaction` throws `MutationCancelledError`.
8. Apply to the stores, bump the revision signal once.
9. Emit `change` with it — and stop.

**Step 9 is the end of the commit path (D-S2-24).** It does not push onto the history and it does not
call the view: both are *subscribers* to the event it just emitted, and this file imports neither.
That is what makes `history-is-removable` provable in S2.5 rather than merely asserted.

**The write set is readable (D-S2-21).** `get`, `has`, `size` and `childrenOf` consult it before the
committed indexes, and the validation S2.3 adds runs against the same overlay — so a read-then-write
helper is correct inside a transaction, which is the case D-S2-8 exists to allow. `all` stays
committed-only; that asymmetry is stated in its doc comment. Discarding the write set is the whole of
rollback, which is why a mid-body validation failure needs no rollback engine.

The pattern is the standard write set with read-your-own-writes (Yjs's `doc.transact`, TanStack DB's
optimistic mutations, Immer/Mutative drafts). Name it that in the file header so the next reader does
not read it as invented.

Nesting: `DatasetData` holds one open transaction. A nested `transaction()` call runs its body against
the open one and returns that body's value without committing (D-S2-8). Only the outermost runs
steps 2–7.

Re-entrancy: while steps 7 and 9 are fanning out, a flag is set. A mutator called during either
throws `MutationDuringNotificationError` before writing anything (D-S2-9, D-S2-25).

**Why the veto sits at 7 and not earlier.** After the extension hook and the rollup, so a handler judges the changeset
that would actually commit, cascades included; before the store write, so a veto is an early return
rather than an undo of work already done. A handler may refuse the changeset; it may not edit one —
the changeset is frozen in dev mode, and extending a change is the extender's job, which has one owner
(D-S2-25).

### 2.4 `DatasetData` — the public-facing half

```ts
transaction<T>(body: () => T): T;
on<K extends keyof DatasetEventMap>(name: K, handler: (payload: DatasetEventMap[K]) => void): void;
off<K extends keyof DatasetEventMap>(name: K, handler: (payload: DatasetEventMap[K]) => void): void;
```

`DatasetEventMap` is `{ beforeChange: { changeSet: ChangeSet }; change: { changeSet: ChangeSet } }` —
two events, both fire, same payload (D-S2-5, D-S2-25). `on`'s handler type returns `void | false`,
which `EventBus` already carries; `false` is honoured for `beforeChange` and ignored for `change`, the
way `GanttEventMap`'s pair already works. `api/dataset.ts` delegates all three.

`transaction()` takes no origin option in S2. `'user'` is the default and the only value a public
caller can produce; `interaction/` gets the option in S4 when it has a gesture to tag (§9).

## 3. Tests

`src/data/transaction.test.ts`, all pure:

- N mutations inside one transaction produce exactly one changeset and one `change` event.
- The changeset's `updated` rows carry `from` **and** `to` for every touched field.
- A field set back to its original value inside the transaction is absent from the changeset.
- An `add` + `remove` of the same id inside one transaction records neither.
- An empty transaction emits nothing, writes nothing, and pushes no history entry.
- `transaction()` returns the body's own value, in the outermost and the nested case alike.
- A nested `transaction()` joins the outer one: one changeset, one event.
- **Read-your-own-writes (D-S2-21):** inside one body, `get` after `add` returns the added entry;
  `size` counts it; `childrenOf` includes it; `all` does not, until commit.
- **Rollback:** a body that throws after two successful mutations leaves the store exactly as it was,
  and emits nothing.
- A mutation from inside a `change` handler throws `MutationDuringNotificationError` and leaves the
  store as the handler found it.
- **The hook is generic (D-S2-6):** with an injected extender that patches a second entry, the patch
  lands in the same changeset and the store shows both edits. With `identityExtender`, the same
  transaction produces the user's edit alone. `data/` has no scheduling-specific code path either way.
- The extension hook is called exactly once per transaction, whatever the body's size.
- **Veto (D-S2-25):** a `beforeChange` handler returning `false` leaves the store exactly as it was,
  emits no `change`, does not bump the revision signal, and makes `runTransaction` throw
  `MutationCancelledError` carrying the refused changeset.
- A `beforeChange` handler that returns nothing does not veto; with two handlers, one `false` is
  enough and the other still runs.
- `beforeChange` fires **after** the extension hook: with the injected patching extender, the payload
  the handler sees carries the extender's fields as well as the body's.
- An empty transaction emits neither `beforeChange` nor `change` — step 6 stops first.
- A mutation from inside a `beforeChange` handler throws `MutationDuringNotificationError`.
- **One channel (D-S2-24):** a handler registered through the public `on('change')` sees every commit
  this file makes, and it is the only way anything is told. There is no second notification to assert,
  which is the point — the test that would catch a private path is the dependency-cruiser rule, and it
  lands with the pieces it protects (S2.4, S2.5).
