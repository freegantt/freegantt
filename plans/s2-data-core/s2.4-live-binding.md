# S2.4 — Live binding: changesets drive the view

**Slice:** S2 · **Step:** 4 of 7 · **Spec:** [`README.md`](./README.md) §2 D-S2-15, D-S2-16, D-S2-17, D-S2-20 · **Closes:** #33
**Baseline:** S2.3 merged and green · **Ends with:** an edit in the console moves a bar on screen.

This is the step the slice is ordered around. Everything before it is invisible; from here on the
harness demonstrates the data core rather than describing it.

Two things land together because neither is honest without the other: the subscription that turns a
committed changeset into a render, and the frame scheduler that stops N mutations in one tick from
becoming N frames.

## 1. The subscription (D-S2-20)

```ts
// GanttShell constructor, after the viewport is bound
this.#datasetSubscription = dataset.on('change', () => {
  this.#viewportHandle.setEntries(dataset.entries.snapshot());
  this.#frames.request();
});
```

`ViewportHandle.setEntries(entries)` joins `setPaneSize(size)` and `setContentSize(size)` and behaves
identically — it writes the binding field and fans out inside `#notifications.batch(…)`:

```ts
setEntries: (entries) => {
  this.#notifications.batch(() => scaleHandle.setEntries(entries));
},
```

`ScaleBinding.entries` stops being a construction-time snapshot and becomes a field a bound Gantt
pushes to, which is what `paneWidth` already is. `TimeScaleModel`'s `BoundValue` then re-resolves
`fitDataset` on its own, through the equality check it already has (D-S1.5-4) — so an edit that does
not change the dataset's span does not churn the scale.

**Why this is not the `setEntries()` #33 warns against:** that warning is against a *public*
`gantt.setEntries()`, a second reactivity mechanism beside the changeset (#1's R4). This is the
changeset mechanism's own fan-out, on an internal binding handle, driven by exactly one subscription.
`GanttShellOptions` gains no entries key and `Gantt` gains no setter. If a later step finds itself
wanting one, the finding is against this subscription, not a reason to add a second path.

`destroy()` unsubscribes. A destroyed Gantt still subscribed to a shared Dataset is a leak, and S7's
mount/destroy audit is far too late to find it.

## 2. The frame scheduler (D-S2-15)

```ts
// src/view/frame-scheduler.ts — the only file allowed to call requestAnimationFrame (B10)
export class FrameScheduler {
  constructor(render: () => void);
  /** Coalesced: at most one render per animation frame, however many times this is called. */
  request(): void;
  /** Synchronous. Construction calls it; so do the tests that assert DOM right after a change. */
  flush(): void;
  /** Cancels a pending frame. `GanttShell.destroy()` calls it. */
  cancel(): void;
}
```

Every render request in `view/` goes through it: the dataset subscription, the viewport's `onChange`,
and the pane-size attachment. `GanttShell.render()` stays public and synchronous — it is what the
scheduler calls, and a caller that genuinely wants a frame now still has it.

**Not a second batcher.** `BatchedNotifier` coalesces one synchronous fan-out (one `setPaneSize`
touching two sub-models). `FrameScheduler` coalesces one animation frame (independent signals in one
tick). Different scopes; neither subsumes the other. Say so in the file header so the next reader
does not have to re-derive it.

### 2.1 Migration

Measured at baseline: 45 dom tests — `view/gantt-shell.test.ts` (19), `api/gantt.test.ts` (15),
`render/dom/index.test.ts` (11) — of which ~14 call sites set a property and then assert DOM. Each
gains one `flush()`.

Do this as its own commit inside the step, with no behaviour change of its own: the assertions do not
move, only the point at which the frame is known to have run. A test whose *assertion* has to change
is a finding against the scheduler, not a test to adjust.

`e2e/` needs no change: Playwright's own waiting already spans an animation frame, and
`e2e/scroll-sync.spec.ts` already awaits one explicitly.

## 3. Incremental invalidation, made falsifiable (D-S2-16)

`FrameLayout` gains an internal `heightIndexRevision` counter, bumped whenever `#heightsFor` builds a
new index. `[S2-A3]` reads it. The rule it makes checkable:

> A changeset containing only `updated` rows never rebuilds the row-height index. A changeset
> containing `added` or `removed` rows does.

That is what `#heightsFor`'s `(rowCount, rowHeight)` cache key already gives; the counter is what
turns it from a property of the current implementation into an asserted one.

## 4. `[S2-A3]` — one changeset, one layout pass, one frame

`src/view/gantt-shell.test.ts`, dom project. Over a 500-entry dataset, inside one transaction, update
one field on every entry. Assert, in one test titled with `[S2-A3]`:

- exactly one `change` event
- exactly one `computeFrame` call (spied through the `FrameLayout` the shell owns)
- exactly one `backend.sync` call (the null backend counts them)
- `heightIndexRevision` unchanged

Four counts, one transaction. Each of the four can fail independently, which is what makes the box
worth ticking.

## 5. The playground (D-S2-17)

`harness/data.html` + `harness/data.ts`, registered as the fifth input in `vite.config.ts`.

This step ships the mutation half: add / rename / move ±1 day / remove buttons, and a changeset log
panel that prints one row per `updated` field as `store · id · field · from → to`, plus one row per
`added`/`removed` entity. Undo/redo buttons arrive in S2.5, export/import in S2.6 — the page grows
with the slice rather than landing half-wired.

The log is built **from the changeset**, never by re-reading the dataset. A re-read cannot produce
`from`, which is exactly what `[S2-A4]` asserts in S2.7.

**Harness review (CLAUDE.md's standing rule).** Re-read `harness/main.ts` and the new `data.ts`
against it: no restated library defaults, no hand-built stand-ins for something the library computes,
public API only. `data.ts` is the first harness page that mutates, so it is the first honest test of
whether the mutation API is pleasant to call. Anything awkward there is an API gap to record against
this slice, not something to tidy in the harness.
