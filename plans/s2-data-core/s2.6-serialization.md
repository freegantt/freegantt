# S2.6 — Serialization and `apply`

**Slice:** S2 · **Step:** 6 of 7 · **Spec:** [`README.md`](./README.md) §2 D-S2-11, D-S2-12
**Baseline:** S2.5 merged and green · **Ends with:** export/import in the playground, `[S2-A2]`, and `[S2-A1]`.
**Blocked on:** [`OPEN-QUESTIONS.md`](./OPEN-QUESTIONS.md) **OQ3** — whether `apply` ships in S2 at all. §2 and its tests are the half that OQ3 removes; §1 and §3 stand either way.

Two halves of D7, and they are deliberately in one step: `toJSON`/`fromJSON` is the whole-document
contract, `apply(changeSet)` is the incremental one, and `plans/02` §6 calls them "inverse-ish
operations designed so a future sync adapter … is an extension, not a core change." Reviewing them
apart is how the two drift.

## 1. `toJSON()` / `fromJSON()` (D-S2-12)

### 1.1 The document

```ts
export interface DatasetDocument {
  schema: 1;
  timeZone: string;
  dateOnlyEnd: DateOnlyEndRule;
  derivedSpanKinds: readonly EntryKind[];
  entries: readonly EntryDocument[];
}
```

```json
{
  "schema": 1,
  "timeZone": "America/Chicago",
  "dateOnlyEnd": "inclusive",
  "derivedSpanKinds": ["group"],
  "entries": [
    { "id": "t1", "name": "Groundwork", "start": "2026-09-01T05:00:00.000Z", "end": "2026-09-11T05:00:00.000Z" }
  ]
}
```

The JSON shape is public API, semver-governed (`plans/02` §6), so it is one of the things the
`api-report` gate (S2.7) starts holding.

### 1.2 The four rules that make it byte-stable

1. Fixed key order — the writer declares keys in order and never iterates `Object.keys` over an
   entity. A store entity's key order is an implementation detail; a document's is a contract.
2. Optional keys omitted when absent, never written as `null`. `exactOptionalPropertyTypes` already
   makes "absent" and "explicitly undefined" different things in the model; the document keeps that.
3. Entries in the store's insertion order (D-S2-3), which is stable across updates.
4. Instants as `Z`-suffixed ISO. `fromJSON` then reads them as absolute, so the dataset zone never
   re-enters the reading and `dateOnlyEnd` has nothing to apply to.

Brands are stripped at the boundary and never appear in JSON — they exist only in TS types.

`meta` round-trips opaquely: the value is carried by reference into the document and back out, never
walked field by field. A consumer's `meta` key order is theirs, and re-serializing it would be the
library editing data it does not understand.

### 1.3 Reading and versions

```ts
static fromJSON<TMeta>(doc: DatasetDocument): Dataset<TMeta>;
```

`schema: 1` is the only version this build writes. The reader is a `readers: Record<number, Reader>`
map with one entry; an unknown `schema` throws `UnsupportedSchemaError` (`unsupported-schema`) naming
the version it found and the versions it reads. `plans/02` §6's "migrates older schemas forward" has
no older schema to migrate yet — the seam is the map, so the second entry is an addition rather than
a rewrite. Recorded so nobody builds a migration framework for a set of size one.

**Keys the reader does not know are dropped**, and `plans/02` §6's *"never silently drops fields"* is
corrected to *"never silently drops fields of a schema it reads"*. Preserving unknown keys verbatim
would force them through undo/redo too, which opens `EntryField` to arbitrary strings and undoes
D-S2-7's typed union. The rule a consumer needs is one sentence: **anything of yours goes in `meta`
and survives byte for byte; anything at top level belongs to the schema.**

`fromJSON` constructs a fresh `Dataset` with an empty history. A document is a state, not a session —
and `apply` says the same thing incrementally by pushing no history entry (§2).

Because it constructs a `Dataset` like any other, the **span rollup runs on read** (D-S2-22). A
document whose stored group span disagrees with its children is corrected in that one pass, so
`[S2-A2]` holds from the first `toJSON` onward. The correction raises a dev-mode `console.warn` naming
the entry: silently rewriting authored data with no feedback is the thing that makes a consumer
distrust the format.

### 1.4 `no-derived-in-json` (B9)

`src/data/serialization/**` may not import `layout/` or `view/`, and may not name `Row`, `Item` or
`GeometryFrame`. The rule lands in S2.7 with the rest; the directory it governs is created here, and
the point of the rule is that `rowCount` and a cached span are the two things a future author will be
tempted to cache into the document (principle 1: derived data is never persisted).

## 2. `apply(changeSet)` (D-S2-11)

```ts
export type RejectionReason = 'unknown-id' | 'duplicate-id' | 'stale-from' | 'invalid-value' | 'parent-cycle';
export interface Rejection { store: StoreName; id: string; field?: EntryField; reason: RejectionReason }
export interface ApplyReport { applied: number; rejected: readonly Rejection[] }

apply(changeSet: ChangeSet): ApplyReport;
```

- It **never throws mid-way**. A sync adapter — D7's designed-for consumer — cannot recover from a
  throw, because it has no way to learn which rows landed first.
- It runs as one transaction and emits **one** changeset of its own, tagged `origin: 'load'`, built
  from what actually applied. It pushes **nothing** onto the history: history is this session's edits,
  and a Ctrl+Z that reverts a remote change — then posts that revert back — is how a sync loop eats a
  collaborator's work (D-S2-11).
- The changeset handed in is a **request**; the changeset that comes out of `on('change')` is what
  **happened**. Conflating the two is how a sync loop echoes itself forever, so the two are never the
  same object and never share an id.
- `'stale-from'`: an `updated` row whose `from` does not match the current value is rejected, not
  applied. That is optimistic-concurrency detection for free, and it is the reason `from` is in the
  contract at all rather than only `to`. Matching is D-S2-7's per-field rule, and **`meta` is exempt**:
  an incoming `from` for `meta` was parsed from JSON and can never be reference-equal, so a staleness
  check on it would reject every remote `meta` write. A sync adapter gets last-write-wins on `meta`
  and concurrency detection on every other field — stated in the contract, not discovered.

## 3. `[S2-A2]` and `[S2-A1]`

**`[S2-A2]`** — `src/data/serialization/serialization.test.ts`, pure:

```ts
const doc = dataset.toJSON();
const round = Dataset.fromJSON(doc).toJSON();
expect(JSON.stringify(round)).toBe(JSON.stringify(doc));
```

String equality, not `toEqual`. The box says byte-stable, and a deep-equal assertion passes over a
document whose keys have been reordered — which is the exact regression rule 1 exists to prevent.

Covered: every optional field present; every optional field absent; `meta` holding nested objects and
arrays, with its own key order preserved; a non-UTC `timeZone`; `dateOnlyEnd: 'exclusive'`; a
non-default `derivedSpanKinds`; a dataset whose entries were added and removed after construction, so
insertion order is not simply the constructor's order; a document carrying an unknown top-level key
and an unknown entry key, asserted to be dropped deliberately; and a document whose stored group span
disagrees with its children, asserted to be corrected once and stable from the second write on.

**`[S2-A1]`** — `src/data/history.property.test.ts`, moved here from S2.5 per that step's §3.1,
because `toJSON()` is its comparison. Both resolver runs, as specified there.

## 4. Playground

`harness/data.ts` gains an export/import pair: a textarea, an **Export** button writing
`JSON.stringify(dataset.toJSON(), null, 2)` into it, and an **Import** button reading it back through
`Dataset.fromJSON` and rebinding the Gantt. Import replaces the dataset, so it also demonstrates that
a `Gantt` survives one — and if it does not, that is a finding against `destroy()`/rebinding, recorded
against this slice.
