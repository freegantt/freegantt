# S2.5 — Undo and redo

**Slice:** S2 · **Step:** 5 of 7 · **Spec:** [`README.md`](./README.md) §2 D-S2-13, D-S2-14, D-S2-23, D-S2-24, D-S2-25
**Baseline:** S2.4 merged and green · **Ends with:** undo and redo in the playground, and `[S2-A1]`.

The transaction is already the atomic unit and the changeset already records `from` and `to` per
field. Undo is therefore a small step: a stack, a cursor, and an inverse. Its acceptance test is not
small, and it is the one that carries I7 forward into S3.

It is also the step where the slice's removability claim is first paid for in full (D-S2-23): this is
the largest of the four leaves, and the one whose absence a consumer would most plausibly want.

## 1. API

```ts
// api/dataset.ts, delegating to data/history.ts
undo(): void;      // no return value — what it did arrives on `change`, like every other commit
redo(): void;
get canUndo(): boolean;
get canRedo(): boolean;

// DatasetOptions
history?: { capacity?: number };   // default 100 (D-S2-13)
```

`new Dataset({ entries, timeZone: 'UTC', history: { capacity: 200 } })` — "a dataset with a history
capacity of 200". `undo` is the verb the consumer calls; `history` is the thing that has a capacity.

`undo()` returns nothing, for D-S2-8's reason applied to D-S2-24: `on('change')` is the single delta
channel, and a `ChangeSet | undefined` return would be a second one that also overloads `undefined`
across "nothing to undo" — which `canUndo` already answers — and "there was nothing in it". A caller
that needs to know what an undo did reads the event, like the harness's log panel does. §9 of the
README records the named member it would come back as if a caller ever cannot.

## 2. Behaviour (D-S2-14, D-S2-24)

### 2.1 The history is a subscriber, not a step in the commit path

`data/history.ts` subscribes to `change` at `Dataset` construction and records what it hears. The
commit path does not know it exists: `data/transaction.ts` imports nothing from this file, and
`history-is-removable` (D-S2-23) allows exactly one importer, `data/dataset-data.ts`, which constructs
it. **Delete `history.ts` and one construction line and the commit path is unchanged, byte for byte.**

```ts
// data/history.ts — the whole coupling to the rest of data/
#onChange = ({ changeSet }: DatasetEventMap['change']): void => {
  if (changeSet.origin === 'user') this.#record(changeSet);
};
// constructor: dataset.on('change', this.#onChange)   ·   dispose(): dataset.off('change', this.#onChange)
```

Three consequences worth stating rather than discovering:

- **The origin filter names what it records**, not what it ignores, so `'undo'` and `'redo'` are
  skipped today (D-S2-14) and `'load'` will be skipped the day `apply` brings it (D-S2-11) with no
  edit here.
- **Order is insertion order** (`EventBus` iterates a `Set`), and the history subscribes at `Dataset`
  construction — before any `Gantt` exists. So `canUndo` is already true for every later handler,
  which is what the harness's undo button reads on the very event that enabled it. A consumer handler
  that throws cannot cost anyone an undo entry, because the entry was recorded first.
- **A consumer could write this file.** It uses `on('change')` and `transaction()` and nothing else.
  That is the test D-S2-24 sets, and this is the piece it matters most for: someone who wants
  branching history, or history scoped to their own document, is not forced to fork the library.

Undo itself runs back through the ordinary path — `runTransaction(data, …, 'undo')` — so an undo is a
commit like any other and the view updates through the one channel.

### 2.2 The rules

- A committed changeset is recorded with the cursor at the top. `undo()` applies the changeset at the
  cursor **inverted** — `to`→`from` per field, `added`↔`removed` — with `origin: 'undo'`, and steps
  the cursor down. `redo()` re-applies it as recorded with `origin: 'redo'` and steps back up.
- Neither re-runs the extension hook. `plans/01` §6: redo replays the recorded changeset, so an engine
  whose behaviour changed between library versions cannot rewrite history.
- Undo and redo do **not** record new entries — the origin filter is what makes that true, rather than
  a flag the commit path sets. They move the cursor.
- **The cursor moves on the `change` the undo commit emits, never on the `undo()` call** (D-S2-25).
  `beforeChange` fires for every origin, so a consumer's rule can refuse an undo the same way it
  refuses an edit; a refused undo throws `MutationCancelledError` and must leave the stack exactly
  where it was. Moving the cursor first and rolling it back on failure is two places that have to
  agree — hanging it off the event is one.
- A new edit while the cursor is below the top clears everything above it.
- At capacity the oldest entry drops. `canUndo` goes false at the bottom of the stack, not at the
  bottom of the session.
- An undo emits `change` like any other commit, so the view (S2.4) updates through the one path.

Because a changeset records the extension hook's patch alongside the user's edit (S2.2 step 4), undo
reverts both in one step. That is I7, and it is complete for the identity extender now and for a real
engine the day S3 installs one — no new machinery.

## 3. `[S2-A1]` — the property test

`src/data/history.property.test.ts`, pure, `fast-check` (its first use; `plans/04` §2 budgets it here).

```
for a random sequence of 1..50 mutations over a seeded dataset:
  before = JSON.stringify(dataset.toJSON())      // S2.6 lands toJSON; see §3.1
  apply the sequence
  undo until !canUndo
  after  = JSON.stringify(dataset.toJSON())
  assert after === before
```

Generators cover `add`, `update` (each editable field), `remove` (including a parent with a subtree),
and transactions wrapping 1..10 of the above. Shrinking gives a minimal failing sequence, which is
the whole reason this is a property test rather than a handful of examples.

**Run three times**, with the same generators — the heading said "twice" before the third case existed:

1. with `identityExtender` and no deriving kinds — the user's edits alone;
2. with the **span rollup step** and a fixture containing groups (D-S2-22) — a cascade S2 actually
   ships, and one no install can switch off;
3. with an injected extender that cascades an unrelated entry — so the engine half of I7 is proven
   before an engine exists. When S3 installs the real one, this test does not change; only what fills the
   extender slot does.

### 3.1 Ordering note

`[S2-A1]` compares `toJSON()` strings, and `toJSON()` lands in S2.6. Two options, and the second wins:

- Land `[S2-A1]` here against a deep-equal of `entries.all`, then tighten it in S2.6. Rejected: the
  box says byte-identical `toJSON()`, and a check that is tightened later is a check nobody re-reads.
- **Land the history here and `[S2-A1]` in S2.6**, immediately after `toJSON()`. The step's own tests
  (§4) are example-based and complete; the property test joins them one step later, in the step that
  gives it its comparison. The S2.6 TODO carries the box.

## 4. Tests (this step)

`src/data/history.test.ts`, pure:

- undo after one `update` restores the field; `canUndo` false afterwards on a fresh dataset.
- undo of a transaction with fifty edits restores all fifty in one call, and emits one `change`.
- undo of a cascading transaction restores the user's field **and** the patched one — the corruption
  class D-S2-14 closes. Run it twice: once against the **span rollup step** (D-S2-22), which is a real
  cascade S2 ships from the commit path itself, and once against an injected extender that patches an
  unrelated entry — so the history is proven agnostic to *both* sources of a cascade, not just one.
- redo re-applies; a new edit after an undo clears the redo stack and `canRedo` goes false.
- capacity: with `capacity: 3`, four transactions leave three undoable; the oldest is gone.
- undo/redo emit `change` with `origin: 'undo'`/`'redo'`, and push nothing onto the stack.
- undo of a cascading remove restores the whole subtree.
- **A refused undo (D-S2-25):** with a `beforeChange` handler returning `false`, `undo()` throws
  `MutationCancelledError`, the store is unchanged, and `canUndo`/`canRedo` read exactly as they did
  before the call — the entry is still on the stack and a second `undo()` with the handler removed
  applies it.
- **Removability (D-S2-23):** a `DatasetData` constructed with no history records nothing and commits
  identically — the same changesets, in the same order, from the same transactions. This is the test
  that would fail if the commit path ever grew a direct push.
- **Subscriber order (§2.1):** a handler registered by the consumer *after* construction reads
  `canUndo === true` inside the very `change` that enabled it.

## 5. Playground

`harness/data.ts` gains undo and redo buttons, `disabled` bound to `canUndo`/`canRedo`. The changeset
log shows the undo's own changeset, tagged with its origin — a reader can then watch a cascade go
away in one row, which is the thing the design exists to guarantee.
