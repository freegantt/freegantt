## Verdict

The two central rulings are still right:

1. The Field key is the whole address. Delete `FieldSource`.
2. A derived value never persists. Refuse the write. Omit the key from the Document.

The call sites for ingest, merge, and `fieldValue` are cleaner than today. What is not ready is
the write shape, the plugin home, and the working files disagreeing about rules they treat as
settled.

The key-is-the-address ruling and the derived-value-never-persists ruling do not fight each other.
The surrounding sentences do.

**Do not start group A** until plan B1 is settled with sample code, and until the README, the ADR,
and this file say the same thing.

## 3. Every consumer call

### 3.1 Construct

```ts
interface TaskData {
  owner?: string;
  cost?: number;
  phase?: number;
}
const dataset = new Dataset<TaskData>({
  timeZone: 'UTC',
  entries: [
    { id: 'p1', kind: 'group', name: 'Site' },
    { id: 't1', parentId: 'p1', name: 'Survey',
      start: '2026-01-05', end: '2026-01-09',
      data: { owner: 'Jo', cost: 400, phase: 2 } },
  ],
  fields: [
    { key: 'owner', column: { header: 'Own' } },
    { key: 'cost', type: 'money', rollUp: 'sum', editable: true },
    { key: 'ref', compute: (entry) => rowNumber(entry.id) },
  ],
});
```

Reads well. One generic. `phase` needs no Field. `compute` reads as English. Dates may be absent
on the group. Two generics that never meet was a real defect (`harness/planner.ts:31`).

**Smell:** `Dataset<TaskData>` types `entry.data`, not `fieldValue`, not `compute`, and not a
plugin Field. Three value kinds, one generic, and the generic only covers the bag. That is honest
only if plugin values do not live in `data` (plan B1).

**API 1.1 — the widening type is unstated.** `harness/main.ts:85` casts a Dataset through
`unknown` today. Either `Dataset<A>` is assignable to `Dataset` and the cast goes, or it is not
and the ADR records that the cast survives. Do not assert either from the type diagram —
`EntryStore`'s members are methods, so they compare bivariantly. Probe with a throwaway test,
read the answer, delete the probe.

**API 1.2 — the plugin surface carries the generic too.** `src/api/dataset.ts` publishes
`DatasetPlugin<TMeta, TFields>`, `DatasetPluginContext<TMeta, TFields>` and
`Dataset.fromJSON<TMeta, TFields>`. Group A's list does not name them. They are public.

### 3.2 Read a stored consumer value

```ts
dataset.entries.get('t1')?.data.owner     // 'Jo', typed as string | undefined
dataset.entries.fieldValue('t1', 'owner') // 'Jo', Field-aware
```

Two doors for one value. That is the same split a data grid uses: `row.data.cost` vs
`getValue('cost')`. Keep both. Teach them as:

- `entry.data.x` — the stored bag, typed by `TData`
- `fieldValue(id, key)` — any Field key, including `start`, `duration`, and `compute`

**Smell:** after this ADR, the typed door is the bag, and the Field-aware door stays weakly typed.
A renderer that wants types reaches into `data` and skips `compute`. #267 stays open for that
reason. Say so at this call site, not only in the issues table.

**API 6.2 — `TValue` on the compute arm promises a type that nothing reads.** `FieldRegistry`,
`DatasetOptions.fields` and `FieldLookup` all hold bare `Field`. `fieldValue(id, 'ref')` answers
`unknown`. Extend Field's “declaration-site aid” comment to say so. Keep #267 pointed at it.

**F3(c):** `fieldValue('t1', 'ownr')` returns `undefined` instead of `UnknownFieldError`. Forced
once undeclared keys emit ChangeSet rows. Acceptable if the plan says **read by key never throws;
declare by key still does.**

**API 3.1 — a `data` key that shadows a core key is unreachable.** `entry.data.start` stores
fine. `fieldValue(id, 'start')` answers `entry.start`. The consumer's value is then invisible.
State the rule: a `data` key that names a core key is a mistake. Raise the same ingest warning
the ADR already gives an unknown top-level key.

### 3.3 Write — the call that ships

Today (`plans/02:459`):

```ts
dataset.entries.update('t1', { start: '2026-10-05', cost: 12_000 });
```

After:

```ts
dataset.entries.update('t1', {
  start: '2026-10-05',
  data: { cost: 12_000 },
});
```

This is the worst call-site regression in the redesign. `plans/02` already shipped the flat write
as the common case. The ADR rejects “flat keys on the edit alone” because ingest, store, and
Document would then disagree. That argument is about shape consistency, not about the sentence
the app author reads.

`update('t1', { start, cost })` reads “change start and cost”.
`update('t1', { start, data: { cost } })` reads “change start and a data bag”.

The merge rule is right. The nesting is the cost of the namespace. Say that cost in the ADR as a
trade, not as “the edit carries the Entry's own shape” — that sentence hides the loss of the
shorthand `plans/02` named as a principle.

A smaller surface that keeps both rules:

```ts
// expert: the bag
update('t1', { data: { cost: 12_000, owner: 'Sam' } })
// common: one Field, still one write shape if core folds it
update('t1', { cost: 12_000 })
```

The ADR already rejected this. Re-open it only if you accept two write spellings for one store.
If you keep the nested-only write, `plans/02` must drop “common case is a shorthand” for Field
writes, in the same sweep as group F.

### 3.4 Merge and remove

```ts
dataset.entries.update('t1', { data: { owner: 'Sam' } });
// cost and phase stay
dataset.entries.update('t1', { data: { owner: undefined } });
// owner gone; changeset { field: 'owner', from: 'Jo', to: undefined }
```

Right. Today `update({ meta: { owner: 'Sam' } })` replaces and drops `progress`. Merge at one
door is the whole fix. `undefined` as remove matches the current write path and HTTP PATCH /
Immer-style patches.

`DataEdit` is the correct type under `exactOptionalPropertyTypes`. App authors never write the
name unless they factor a helper. Export it from `api/` (API 5.1). Give it a `plans/02` row.

Must land as omission, not intersection (F1 / API 4):

```ts
type EntryEdit<TData> =
  Partial<Omit<EntryInput<TData>, 'id' | 'data'>> & { data?: DataEdit<TData> };
```

The ADR's prose form of this does not compile. Write the type.

**API C1 — an undeclared `data` key still emits no ChangeSet row.** Open 1 is settled as *yes,
an undeclared key may travel in a `data` patch*. Putting keys into `proposedKeys` is necessary
and **not sufficient**. `diffEdit` (`src/data/change-set.ts:75-81`) iterates `registry.all` when
`proposedKeys` is set, so a key in the set and not in the registry is never visited.
`toStoredEdit` stamps `proposedKeys` on every public write (`src/data/entry-reader.ts:517`).
`ctx.read` answers `undefined` for an unregistered key (`src/data/fields/field-access.ts:87`).
Group B needs both: iterate the proposed keys and the registry; and give an undeclared key a
read path to `entry.data[key]`. Without them, the settled ruling ships as a silent write.

### 3.5 Derived write — four doors, one question

```ts
dataset.entries.update('p1', { data: { cost: 999 } });
// DerivedFieldNotWritableError
dataset.entries.add({
  id: 'p2', kind: 'group', name: 'East',
  start: '2026-01-01', end: '2026-02-01',
  data: { cost: 500 },
});
// dates and cost dropped; one warning
const json = dataset.toJSON();
// p1 has no start, end, or cost
```

The behaviour is right. The README's reason is still the old one. F5 is the better rule:

> Name a Field (a patch) and the library answers. Hand it a record and the library keeps what is yours.

That is PATCH vs PUT. `update()` is a patch. `add()`, `new Dataset({ entries })`, and `fromJSON`
are records. Imports from other tools date the parents; a throw at `add()` would reject ordinary
files. Fold F5 into the ADR and delete the bulk-versus-single sentence.

API 9.1 asked `add()` to throw because it adds one Entry. **F5 reversed that, and the reversal
stands.** `start` and `end` roll up (`core-fields.ts:74,85`), so dates on a group are a derived
value. `fixtures/hierarchy-dataset.ts:14-20` authors `plain-parent` with dates, and that Entry
becomes a rolling-up parent the moment the harness reparents a child onto it (F9).

I14 is: gestures and affordances share one resolver, and every **write** asks one `canWrite`
(`plans/01` I14). The ADR then lists four doors and three answers: refuse (`update`), drop
(`add` / `fromDocument`), omit (`toJSON`). Count the doors. Do not claim I14 for omit (CON S3).

**Missing door: autoGroup promotion (F9).** The harness's plain-parent authors dates, then
becomes a group when it gains a child. Nobody aimed at a derived Field, and the dates change
owner in that commit. List it as a door.

**Fifth door: an `EditExtender` cascade (API 8.1, F4).** The ADR puts the refusal at
`EntryStore.update()` so a cascade is not bound by it. `src/data/rollup.ts:196` calls
`editProposesField(body.get(parentId), field)` — `body`, never `merged`. Extender edits live in
`merged`. So a cascade's parent write commits, enters the ChangeSet, enters undo, and the same
pass overwrites it in the same commit. Filter at the hook boundary, drop, warn once. Do not let
a plugin win the pass: `toJSON` would omit the value anyway, so a “win” is a lie until the next
save. The filter also makes D-S2-22's *precedence clause* unreachable; it does not retire D-S2-22
(CON B3).

### 3.6 Dateless rows

```ts
dataset.entries.add({ id: 'later', name: 'Unscheduled' });
// no bar, grid row exists, start/end absent, no Segments
dataset.entries.update('later', {
  start: '2026-03-01',
  end: '2026-03-05',
});
// mints one Segment
dataset.entries.update('t1', { start: undefined, end: undefined });
// un-date — only if F6 lands
```

Right product. A row now, dates later is ordinary. Deleting the `referenceDate` fill is overdue.
The fill lives under **D-S2-10**, not D-S5-46 (CON B5). D-S5-46 keeps zero-length spans because
`[start, end)` makes an empty interval legal. It never mentions `referenceDate`.

Fold F6 as a biconditional: **an Entry has dates if and only if it holds at least one Segment.**
`start` and `end` are always the envelope. Then:

- `add({ start, end })` mints one Segment, as today.
- `add({ segments })` with no dates derives the envelope.
- `add({})` stores no dates and no Segments.
- `update(id, { start: undefined, end: undefined })` is the un-date verb, and it clears the
  Segments in the same write.

Two refusals stay: one date without the other, and `segments: []` on its own
(`EmptySegmentsError`). Add `start` and `end` to `isOptionalEntryKey`
(`field-access.ts:26`). `src/data/serialization/index.ts:45` and
`src/data/entry-reader.ts:127` both branch on `length === 1` today; each gains a `length === 0`
arm.

**F7 / API 12.2 — `durationOf` cannot answer, and it is public.**
`FieldContext.durationOf(entry): Duration` (`src/model/field.ts:189`) computes
`diffMs(entry.end, entry.start)`. The return type becomes `Duration | undefined`. That is
plugin-author surface. Group D does not list it. `weightedMeanByDuration` skips a dateless child
rather than weighting it.

The recorded hole stays: default `gridColumns` is `['name']`, so a dateless row has no UI path
to gain dates. Dating from the timeline is a later gesture. Fine, if the README keeps it as a
hole.

### 3.7 Computed Field

```ts
{ key: 'ref', compute: (entry) => rowNumber(entry.id) }
dataset.entries.fieldValue('t1', 'ref')  // number at runtime, unknown in the type
dataset.entries.get('t1')?.data.ref      // undefined — compute has no home
```

`compute` is the right word. `get` is already taken. Deleting `FieldSource` is the strongest
part of this ADR.

Plan B2 is still open and it is observable. On a group row, either `ref` shows a row number
(`compute` runs) or the cell is blank. **Run `compute` on every row.** The union closes storage,
not reading. A compute that reads `entry.data.cost` on a group sees the rolled-up value that the
Rollup put in the store. That is a stored read, not a second rollup. Point #214 at “cannot ask
if I am a parent”. Do not hold group C for plan B2.

**API 6.1 / CON S1 — the error has two names.** The ADR writes `ComputedFieldCannotStoreError`
at its Field union and `ComputedFieldCannotBeWrittenError` in its consequences. Keep the second.

**API 6.3 — `{ key: 'data' }` type-checks.** `FieldKey` is `CoreFieldKey | (string & {})`, so
only the registry refuses the reserved key, and only at runtime. Acceptable. Write it down so
nobody “fixes” `FieldKey` and flattens the brand.

### 3.8 Live config

```ts
dataset.rollUpKinds = ['group', 'phase'];
```

The ADR makes this the only destructive setter in the library and clears undo history. No
popular grid does that with a property assign. Changing an aggregate on a data grid does not
delete source rows. A SQL `NOT NULL` change is a migration, not a setter. The plan does not
schedule this work (CON S6).

Take F8. Scan, refuse, name the entries:

```ts
// RollUpKindsWouldDropValuesError:
// 'phase' rolls up 'cost'. 3 entries hold an authored 'cost' ('p-1', 'p-2', 'p-7').
// Clear those values, then set the kinds.
```

The consumer then deletes in their own transaction. Undo stays theirs. After a legal flip, run
the Rollup once so the screen matches. This deletes the ADR's new transaction and history wipe.
Smaller surface.

Flipping a kind out of the set keeps the last derived answer as authored. That matches D-S4-6
and is honest.

`DatasetState.setRollUpKinds` (`dataset-state.ts:289-293`) swaps two references and does nothing
else today. The ADR's “the flip is a transaction” and “a destructive reconfiguration clears the
history” are both new work it gives itself.

### 3.9 Core editable override, gone

```ts
// today
{ key: 'start', editable: false }
// after
interactions: { edit: (entry, field) => (field === 'start' ? false : undefined) }
```

Fair trade if #256 also gates `entries.update()`. Today `interactions.edit` gates the editor and
the drags only. After the deletion, `update('t1', { start })` still writes. Two doors, two
answers, I14 fails. The ADR already flags this. It is not optional.
`CORE_FIELD_OVERRIDABLE_KEYS` deletion has no group (CON S6).

### 3.10 Document

```ts
const doc = dataset.toJSON();
const restored = Dataset.fromJSON<TaskData>(doc);
```

A group in `doc` has no `start`, `end`, or rolled-up `cost`. Reload re-derives.
`toJSON` → `fromJSON` → `toJSON` is stable. Byte-identical to the input is not.

This is a product decision, not a storage trick. A Document becomes a save format with a recipe,
not an interchange file with numbers. Typical project-plan files persist parent dates even when
children drive them, so a third-party reader can open the file without the Aggregators. The ADR
accepts that cost. Keep it as a decision in `plans/02`, not only in the ADR.

The public class publishes `toJSON` / `fromJSON` (`src/api/dataset.ts:312,326`) and calls
`toDocument` inside. Pin one sentence in both files.

Schema: do not reuse 1–5 at release. A stale local `schema: 3` and a future released
`schema: 3` are then the same number. Release as `6`, or add `preRelease: true`.

**#270 is cache invalidation.** The live store still holds the derived value. A declining
Aggregator leaves a stale parent. The Document omission makes the reload correct and the live
store wrong until #270 lands. Fix #270 before or with group C, or the first save/load after a
child disappears will disagree with the screen. F9's last sentence is a behaviour change:
today a childless rolling-up parent keeps the last value (`rollup.ts:184` skips it).

### 3.11 Plugin author

```ts
setup(ctx) {
  ctx.fields.register({
    key: 'progress',
    type: 'percent',
    rollUp: 'weightedMeanByDuration',
  });
}
const extender: EditExtender = (request) => {
  const next = request.proposed.get(id);
  // where is progress?
  return new Map([[parentId, { data: { progress: 0.4 } }]]);
};
```

Plan B1 is the API. Three homes, three sentences:

| Option | App author | Plugin author | Honest generic? |
|---|---|---|---|
| A — share `data` | `entry.data.progress` after install | `fieldValue(id, 'progress')` as `unknown` | No. `Dataset<TaskData>` omits `progress` |
| B — `entry.pluginData` | never sees it | third bag on the Entry | Yes for `data`; a fourth Document key |
| C — existing `PluginStore` | `fieldValue` still, if the registry points at the store | `ctx.store.reserve<ProgressRow>()` already ships | Yes |

`src/data/plugin-store.ts` already states the reason it exists: per-plugin per-entry data must
not live on the consumer bag, or an application and a plugin collide. Option A re-opens that
collision under a new name.

Verified (API C4): `PluginStores` at `plugin-store.ts:42`, `reserve<T>()` / `read<T>()` at
`:62,74`, and `PluginStore` / `PluginStoreView` are already public from
`src/api/dataset-plugin.ts:29`. Option C adds no store and no Document key. Its real cost: with
two homes for Field values, `fieldValue(id, 'progress')` must resolve **which** home.
`FieldRegistry.#declaringPlugin` already records it (`field-registry.ts:99`). Write the read
path for both callers, not just the write path.

Option C is the VS Code / Redux-slice pattern: each plugin owns a slice. Option A is the
shared-metadata bag pattern (one dictionary, last writer wins at the key). The registry already
refuses a duplicate declaration. It does not refuse a value the consumer wrote before the plugin
existed (plan B3 / #192).

Settle plan B1 with these two call sites written under A and under C, then pick. Group A cannot
type `Entry.data` until that pick exists. If the pick is A, the ADR must say `Dataset<TData>` is
“the consumer's keys; plugin keys are extra and untyped” — that is a lie generic unless you
write it as `TData & Record<string, unknown>` and give up the check.

**This review recommends C** for Field identity that a plugin owns (`progress` as scheduling),
and keep A only for values the app declares. A plugin-declared Field is plugin data. The store
for that already exists. The cost is `fieldValue` learning the declaring plugin. That is one
indirection, not a new Document key. Option C would also close plan B3 at no extra cost.

## 4. Wrong cites and missing work

## 5. Proposed smaller surface (F1–F9)

These are proposals from the 8 September draft. They are not decisions. Fold each accepted fix
into the ADR or the README. Each one was checked against: **does this leave the API simpler than
it found it?**

| Added | Removed |
|---|---|
| `DerivedFieldNotWritableError` | `UnknownFieldError` from `entries.fieldValue()` |
| `RollUpKindsWouldDropValuesError` | the *“a destructive reconfiguration clears the history”* rule |
| `DataEdit` (the ADR's own) | two type names the first draft proposed, then dropped (`EntryDataSlot` and a second input type) |

### F1 — `EntryEdit` restates `data` by omitting it

Lands in: the ADR, beside `DataEdit`. Group A. See §3.4.

### F2 — the stored record is `Readonly<Partial<TData>>`

Lands in: the ADR's *“The internal `Entry` describes its own object”* consequence. Group A.

`EntryInput.data?: TData`, `Entry.data: Readonly<TData>` and an ingest fill of `{}` cannot all
be true. `Dataset<{ owner: string }>` then reads `entry.data.owner` as `string` while it holds
`undefined`.

```ts
export interface Entry<TData = Record<string, unknown>> {
  data: Readonly<Partial<TData>>;
}
```

A conditional slot type (`EntryDataSlot`, API 2.1) would keep a required key required. Both were
drafted and dropped: they add two public names and a second shape at two doors. `Partial`
charges that consumer one narrow. The slot type stays additive if a consumer ever proves the
need. **Pick F2 or accept a required-key lie in writing.** Do not leave `Readonly<TData>` plus
fill `{}`.

### F3 — one address rule, at every read door

Lands in: group B, as three list items. Settled Open 1 says an undeclared key may travel in a
`data` patch. Three edits make that true, and they stand or fall together.

**a. Build the proposed set from inside the namespace.** `toEditReading` seeds it from the
edit's top-level keys (`entry-reader.ts:483`), and the only top-level key now is `data`:

```ts
const proposed = new Set<string>(Object.keys(edit).filter((key) => key !== 'data'));
for (const key of Object.keys(edit.data ?? {})) proposed.add(key);
```

**b. Give `diffEdit` a second pass.** Keep the registry walk for row order, then drain the rest:

```ts
for (const key of authored) {
  if (registry.get(key)) continue;
  emit(key, current.data[key], next.data[key]);
}
```

**c. Read by key never throws.** After (b) a ChangeSet carries rows naming undeclared keys. So
`entries.fieldValue` and `ctx.read` answer `entry.data[key]` for an undeclared key, and
`undefined` for a key nothing holds.

The rule: **read by key never throws; declare by key still does.** `gridColumns`, `rollUp` and
the editors keep their errors.

One open loss, not fixed here: `fieldValue(id, 'ownr')` answers `undefined` where it throws
today. If that reads as too loose once the code lands, the answer is a dev-time warning, never a
second key space.

### F4 — the plugin cascade drops, at the hook boundary

Lands in: group C's door table, as a fifth row. Filter where the hook's writes are read —
`DatasetState.extraEditsReadingFor` → `toStoredEdits` — and report once at
`severity: 'warning'`. Widening `editProposesField` from `body` to `merged` does not work:
group C omits the key from the Document, so a cascade that wins the pass writes a value that
disappears on the next save. `start` and `end` roll up, so this also drops a cascade's date
write on a rolling-up parent. That is already the rule for a person: `canWrite` closes both
edges of a group today.

### F5 — a patch that names a derived Field throws; a record that carries one drops

Lands in: the ADR's *“`update()` refuses; `add()` drops”* section — the behaviour stands, the
reason changes.

| Door | Answer | Why |
|---|---|---|
| `entries.update()` | `DerivedFieldNotWritableError` | a patch names the Field |
| `entries.add()`, `new Dataset({ entries })`, `fromDocument` | drop, report once | a record carries every key of an Entry's shape |
| the extension hook | drop, report once | a throw there breaks a user gesture the plugin has nothing to do with |

This reverses API 9.1. Keep the ADR's *“one report per operation, not per value”* rule.

### F6 — dates and Segments, as one biconditional

Lands in: group D, as its first list item. See §3.6.

### F7 — `durationOf` answers `undefined`

Lands in: group D's list. Plugin-author surface.

```ts
durationOf(entry: Entry): Duration | undefined;
```

`fieldValue` and `ctx.read` already answer `| undefined`, so `CoreFieldValues` needs no change.
Two call sites do: `weightedMeanByDuration` (`aggregators.ts:14`) and `inline-editing.ts:113`.

### F8 — `rollUpKinds` refuses a flip that would drop values

Lands in: the ADR's *“Changing `rollUpKinds` drops the values”* consequence, which shrinks.
See §3.8. Flipping a kind **out** stays legal and loses nothing: the last derived answer
becomes authored. After a legal flip, run the Rollup in one transaction.

### F9 — autoGroup promotion is a door

Lands in: group C, as a new list item and an acceptance check. See §3.5.
`fixtures/hierarchy-dataset.ts:14-20` is the live example. State the consequence:

> Promotion is the third way an Entry becomes a rolling-up kind, beside `kind` at ingest and a
> `rollUpKinds` flip. Its dates become derived at that commit, and the Rollup recomputes them
> from the new child. A parent that later loses its last child keeps no dates and draws no bar.

## 6. State handling vs other frameworks

Vendor Gantt product names do not appear here. The comparisons are client stores, documents,
and data grids.

### Derived state must not be stored — this ADR matches the default

| System | Rule |
|---|---|
| React | Do not put computed values in state. Compute during render. |
| Redux | Selectors derive; the store holds sources. |
| Vue | `computed` never writes back into data. |
| Data grid | `valueGetter` / aggregations live in the row model, not in the row's source object. |
| Spreadsheet file | The file holds the formula. A cached number is optional and can go stale. |
| This ADR | Rollup writes the live store so the grid can read it. `toJSON` omits it. Reload recomputes. |

That is the right default for a library that owns the Aggregators. The live store still holds
the derived value (React would not). That is a cache, and #270 is cache invalidation. Typical
project-plan files do the opposite: they persist parent dates so a foreign reader can open the
file. FreeGantt is choosing “recipe, not numbers”. Teach that at `toJSON()`, because it
surprises every user who inspects the file.

### Merge vs replace — this ADR matches PATCH, not replace-the-bag

| System | Update of a bag |
|---|---|
| HTTP | PATCH merges; PUT replaces. |
| React class `setState` | Shallow merge. |
| React `useState` | Replace. |
| Immer | Patch one key. |
| Data grid cell edit | Patch one field. |
| Today's `meta` | Replace. This is the bug. |
| After | Merge `data`. `undefined` removes one key. |

Correct. F5's patch-vs-record split is the same distinction as PATCH vs PUT. Keep that
vocabulary in the ADR.

### Namespaced storage — this ADR matches a reserved-vs-attributes split, not a flat row

| System | Reserved vs consumer |
|---|---|
| JSON:API | `{ id, type, attributes: { … } }` |
| GraphQL input | Nested input vs `id` |
| HTML | reserved attrs vs `data-*` |
| This ADR | core keys on the Entry, everything else in `data` |

A namespace is the right answer to “a later core key must not steal `entry.colour`”. The
rejected flat-Entry draft was the “extra columns on the row” model. That model fails the
Document reader (unknown top-level key) and fails a later core-key promotion. Good rejection.

The remaining smell is the word `data`: it already names the core layer `data/`. The call
`entry.data.owner` is fine. The spec sentence “`data/` merges `data`” is not. Keep the call
site. In specs, write `data/` for the layer and `entry.data` for the bag. Never the bare word.
`values` collides with `RollUpContext.values`. Do not rename the call.

### Plugin state — option A fights the industry default

| System | Plugin-owned per-row values |
|---|---|
| VS Code | Extension memento, not the editor's document model |
| Redux | `combineReducers` — one slice per owner |
| Data grid | row data vs context vs column-def state |
| Shared meta bags in CMS tools | Collisions, last writer wins |

FreeGantt already built the slice (`PluginStores`) because ADR 0002 forbade parking plugin data
on the consumer bag. ADR 0011 then parks plugin Field values on that bag anyway, and calls it
“today's behaviour”. Today's behaviour is the thing ADR 0002 was written to stop, one level up.
Plan B1 is not a polish question.

### Destructive config — take F8; the ADR's version is an outlier

No mainstream client store clears undo because a grouping or aggregate setting changed. They
either refuse, or they keep source rows and recompute. F8 is refuse-then-user-deletes. That is
the only version that does not invent a new kind of setter.

### Optional dates — matches “unscheduled task”, not “always a span”

SQL NULL, calendar events without a time, and unscheduled tasks in project-plan UIs all exist.
Filling a clock reading at construction was the lie. The blast radius is large (duration,
Segments, sort, `fitDataset`). F6's biconditional is how you keep that blast to one rule.
