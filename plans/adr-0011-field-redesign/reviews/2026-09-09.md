# Review — ADR 0011 field redesign — what is left

**Status 2026-09-09, end of day.** The merged review that stood here has been worked through. Every
finding that was a document defect is fixed in
[`../README.md`](../README.md) or in
[`docs/adr/0011-…`](../../../docs/adr/0011-consumer-values-live-in-data-and-a-derived-value-never-persists.md),
and is gone from this file. What stays is **seven decisions that are yours** and **five questions**.

The review's findings were audited against HEAD before any of them were acted on — every code cite
opened, three throwaway probes run (`tsc` twice, `vitest` once, all deleted). The audit found four
things the review got wrong. Those are in §3, because one of them would have shipped a broken type.

Nothing here argues against the two central rulings. **The Field key is the whole address** and
**a derived value never persists** should both land. What is not ready is the plugin home, the
cascade, and the `rollUpKinds` setter.

## 1. Decisions — yours

Each one changes something a reader can observe. Each has a recommendation, and none of them is
taken. They now live in the plan and the ADR under the ids below, so this file can be deleted
without losing them.

### D1 — Where does a plugin's own Field value live? (plan **Blocking B1**)

**Gates group A.** `Dataset<TData>` is a lie generic the moment a plugin installs, because the
plugin's key is not in `TData`.

| | App author | Plugin author | Honest generic? |
|---|---|---|---|
| **A — share `data`** (HEAD) | `entry.data.progress` after install | `fieldValue(id, 'progress')` as `unknown` | No |
| **B — `entry.pluginData`** | never sees it | a third bag on the Entry | Yes, at a fourth Document key |
| **C — the plugin's own store** | `fieldValue`, if the registry routes | `ctx.store.reserve<T>()`, already ships | Yes |

➡️ **Recommend C.** `PluginStores` already ships and D-S5-24 exists precisely because ADR 0002
ruled that per-plugin per-entry data must not sit on the consumer's bag. A is that collision under
a new name. C also closes B3 for free. **Its cost is real and unbudgeted:** `fieldValue` must route
to the declaring plugin, the read path has to be written for both callers, and C has no work group
in the plan.

You asked, in the grill, for sample code for both callers under each option before anyone picks.
That has not been written yet, and I have not written it — it is the one thing that settles this.

### D2 — What does a `compute` Field show on a rolling-up parent? (plan **Blocking B2**)

➡️ **Recommend: run `compute` on every row, and drop this from Blocking.** The union closes
storage, not reading. A `compute` Field reading `entry.data.cost` on a group sees what the Rollup
already put in the store — a stored read, not a second rollup. Blanking `ref` on every group row
reads as a bug. It changes what a cell shows, not what the store holds, so it does not gate group C.

You held this on 2026-09-08 pending a clarification of what the Field is for. Still yours.

### D3 — What does a plugin cascade's write to a derived cell do? (ADR **Open 5**)

**This is new, and it undercuts a promise the grill accepted.** The guard sits on
`EntryStore.update()`, so a cascade is exempt from the throw — that placement is deliberate and it
is what keeps the plugin-author story free of a predicate. But **exempt from the throw is not "the
write survives"**. Verified at HEAD:

- `rollup.ts:196` yields to `body.get(parentId)`, and `build-commit-change-set.ts:301` binds `body`
  to the transaction body **alone**. An extender's edits reach only `merged`.
- So a cascade's parent write commits, enters the ChangeSet, enters undo — and the same pass
  overwrites it. `foldChangeSet` does no per-field dedupe, so **both rows land in one undo step**.
- The grill's own sample code depends on this: `cascade.set(phase.id, { start: moved.start })` on a
  pinned phase. That line compiles and does not do what it says.

➡️ **Recommend: drop the cascade's derived write at the hook boundary, and report once at
`severity: 'warning'`.** `toJSON` omits the value in any case, so a cascade that "won" the pass
would still lose at the next save — letting it stand publishes a value with a lifetime of one
transaction. Widening `editProposesField` from `body` to `merged` is the tempting fix and it is the
wrong one for the same reason.

**The alternative is honest too:** let it stand, and say in writing that a plugin may put a value in
a derived cell that lives until the next pass and never reaches the file. Pick one. Either way this
is a fifth door and the ADR now carries a row for it.

**Answer before group C**, which deletes the `body`/`merged` split.

### D4 — Does a `rollUpKinds` flip refuse, or destroy? (ADR **Open 6**)

The ADR as written makes `rollUpKinds` the only destructive setter in the library and **clears undo
history**. `DatasetState.setRollUpKinds:289-293` swaps two references today and does nothing else,
so both the transaction and the history wipe are work the ADR gives itself.

➡️ **Recommend: refuse instead.** Scan, throw `RollUpKindsWouldDropValuesError` naming the Fields
and up to three Entry ids, let the consumer clear those values in their own transaction. Undo stays
theirs. This deletes the ADR's new transaction *and* the history wipe — a smaller surface, not a
bigger one. No mainstream client store deletes history because a grouping setting changed.

Flipping a kind **out** is not in question: the last derived answer stays, now authored (D-S4-6).

### D5 — Does `plans/02`'s "common case is a shorthand" survive?

`plans/02:459` ships `update('t1', { start, cost })`. This ADR ships
`update('t1', { start, data: { cost } })`. One sentence names two Fields; the other names one Field
and a container. The merge rule is right and the nesting is the price of the namespace — but the
principle `plans/02` states as a principle does not survive it for Field writes.

➡️ **Recommend: accept the loss and rewrite the principle in group F.** Do not re-open the flat
edit unless you will accept two write spellings for one store. The ADR now states the cost as a
trade instead of calling the nesting a feature. **This edits a locked spec** — see Q4.

### D6 — The schema restart (ADR **Open 3**, open half)

You decided `5` now, `1` at release, and that decision stands. The half nobody answered: after the
restart, a pre-release `schema: 3` and a future released `schema: 3` are the same number in two
different shapes.

➡️ **Recommend: no change to the numbering.** Nothing reads schemas 1–4, and the collision needs a
released reader that has already reached version 3. Add one rule to the release gate instead: a
released reader refuses a file it did not write. Cheap, and it retires the hazard permanently. (A
draft fix proposed releasing as `6` or adding `preRelease: true`; both spend a public number to
solve a problem that only exists before the library is public.)

### D7 — What does an S7 plugin do with a `progress` value it did not write? (plan **Blocking B3**)

➡️ **Downstream of D1.** Option C closes it at no cost. Answer D1 first, then see whether this is
still a question.

## 2. Questions

**Q1 — `EditOf<T>`: is that the name?** The `EntryEdit` type the review published does not compile
against the un-date verb (see §3.1), and the fix is one shared mapped type behind both edit shapes:

```ts
/** An edit of `T`: every key optional, an already-optional key removable by an explicit
 *  `undefined`. Not exported — `DataEdit` and `EntryEdit` are the names a consumer reads. */
type EditOf<T> = { [K in keyof T]?: {} extends Pick<T, K> ? T[K] | undefined : T[K] };
```

Call site: *"a data edit is an edit of `TData`"*, *"an entry edit is an edit of an entry input
without `id` and `data`, plus a data edit."* Both read true. `*Of` matches the house convention
(`DatasetPluginOf`), though there it means *bound to a Dataset type* rather than *of this shape*.
It is deliberately **not exported**, so it is not app-author surface. I put it in both documents
because the type has to exist for either edit shape to be right — but the name is a call you may
want to make yourself.

**Q2 — what does the `duration` column show on a dateless row?** Optional dates make
`FieldContext.durationOf` answer `Duration | undefined`, and `core-fields.ts:118` is the shipped
`duration` core Field's `compute` arm. So a **public column** starts answering `undefined`. Nothing
in the ADR, the plan or the review says what that cell renders — blank, an em dash, or something
else. It is small and it is consumer-visible. The original review missed this call site entirely.

**Q3 — where does the `mergeColumn` fix land?** It is live on `main` and independent of the ADR.
I fixed it and added the four test rows on this branch, because the plan says *fix first*.
`verify:full PASS — all 16 checks green, test:e2e included`. It sits in **its own commit**, ahead of
the document work, so it cherry-picks to `main` as one change if you would rather it went that way.
No issue tracks it — searched every open and closed title and body; #142 and #249, which its code
comment cites, are both closed.

**Q4 — may group F edit the locked specs?** The sweep has to change `plans/00`–`02` (§2.6's Source
sentence, `:738`'s `meta` rule, `:749`'s error rows, the shorthand principle) and `CLAUDE.md` and
`CONTEXT.md`. `protect-spec.sh` asks for permission rather than blocking. I have edited **only**
this folder and the ADR so far, and touched no locked spec. Confirm before group F runs.

**Q5 — delete this file?** Every open item above now lives in the plan (Blocking B1–B3, Open 5–7)
or the ADR (Open 3, 5, 6). This file is a summary of them and nothing else. Once you have read it,
it can go — that is what its own header asked for.

## 3. What the audit corrected in the review itself

Recorded because a review's account of the code is a claim, and four of these claims were wrong.

1. **The published `EntryEdit` type was broken, and it broke its own companion.**
   `Partial<Omit<EntryInput<TData>, 'id' | 'data'>>` refuses
   `update(id, { start: undefined, end: undefined })` under `exactOptionalPropertyTypes` (`TS2379`,
   probed) — the *identical* trap the ADR documents for `DataEdit` one paragraph earlier. The review
   published the broken type in one section and the call it refuses in another. Fixed with `EditOf`
   (Q1); probed that `{ start: undefined }` compiles and `{ name: undefined }` still does not.
2. **`durationOf`'s blast radius was understated.** The review named two call sites and one of them
   (`inline-editing.ts:113`) is a *provider*, not a caller. It missed `core-fields.ts:118` — the
   public `duration` Field — plus `field-access.ts:92`, the API report, and four test stubs. That
   miss is Q2.
3. **The proposed fourth `mergeColumn` test row is not a defect case.** Probed against the real
   registry: it passes today. It takes the `sizing = own` branch, which is never the broken one. The
   row is still worth having, for a different reason — it guards against a *wrong fix*, a per-key
   fallback that would leak the bundle's `width` into a `flex`-declaring Field. The plan now says
   that.
4. **The Gate grep count was stale** (631/120 measured before the review file itself existed; 648
   across 121 files at HEAD), and two line cites were off by a few lines (`harness/main.ts:89`, not
   `:85`; the `proposedKeys` stamp is in `toEditReading`, not `toStoredEdit`).

Everything else the review claimed about the code, the locked specs and the two documents checked
out at HEAD — including all three wrong-cite findings (D-S2-22, D-S4-2, D-S5-46), which were right,
and one of which the audit found **understated**: the `referenceDate` fill is written under
D-S2-10 **and** D-S2-22, not D-S2-10 alone.
