- **`pnpm verify:full` is the gate, and its last line is the answer.** Every caller runs this one command: you, `.githooks/pre-push`, and CI. `pnpm verify` is the browser-free chain inside it, so `e2e/**` is invisible to `verify` alone. `verify:full` runs `verify` and then the browser check, and prints one verdict line: `verify:full PASS — …` or `verify:full FAILED at check N of M: …`. Report that line, never `EXIT: $?` — a run with no verdict line is unproven, not green. Capture it with a redirect: `pnpm verify:full > /tmp/v.log 2>&1; tail -3 /tmp/v.log`. A pipe (`| tail -4`) makes `$?` read `tail`, which prints `EXIT: 0` over a failure.
- **Never poll CI by hand. `pnpm pr-wait <n>` is the one command, and its last line is the answer.** It watches the CI workflow run for the pull request's head commit (`gh run watch`), ignores skipped draft-time jobs, and prints `pr-wait PASS — …` or `pr-wait FAILED — …`. A draft runs nothing. A `workflow_dispatch` run proves the gate and cannot close a `pr-wait` — push a commit so `synchronize` fires. Report the verdict line, never an exit code.
- **A ready pull request with no run at all means it conflicts. Check `mergeable` first.** `gh pr view <n> --json mergeable,mergeStateStatus` — a `CONFLICTING`/`DIRTY` pull request gets **no `pull_request` workflow run whatsoever**. GitHub builds a test merge commit to run the gate against, a conflict means there is none to build, and no event recovers it: `opened`, `ready_for_review`, `reopened` and `synchronize` all fire nothing. The symptoms name the wrong cause — `pnpm pr-wait` says "no live pull_request gate run", `gh pr checks <n>` says "no checks reported", and `gh run list` shows nothing on the head sha, so it reads as a broken trigger. **Merge `main` into the branch and push. That is the fix.** Do not push commits to chase the trigger, and do not `git commit --allow-empty`: neither can help, and the empty commit stays in the branch forever. Two checks keep you off the wrong trail: `gh run list --limit 5` unfiltered shows other branches running fine in the same minutes, and `gh api repos/{owner}/{repo}/actions/permissions` shows Actions enabled. A squash-merged pull request is the usual way a branch gets here — the branch keeps the commits whose content `main` already has, so the next pull request off it conflicts.
- **`verify`/`lint`/`typecheck` output truncation.** `pnpm verify 2>&1 | tail -100`-style commands get re-run many times (seen 17x, 13x, 25x in one session) chasing truncated output, at ~25,000 tokens/session. Use the `verify:full` redirect-and-verdict pattern above; for `lint`/`typecheck`, redirect to a log file once and `grep -n "FAIL\|error"` it instead of re-running with a longer `tail`.
